# Proposed spec amendments 65 (SPEC-0032, SPEC-0021; REQ-039)

Date: 2026-10-25 (from `date -u`). Approved specs change only through a proposal like this one (principle 6). Applied by ADR-0127. The paths: `docs/specs/0032-github-events-label-each-pr-people-approve-specs-a-red-branch-stops-work.md` and `docs/specs/0021-when-a-fix-list-verdict-s-only-item-is-the-final-commit-and.md`. The number 65 was reserved for this build on #179 by the conductor. It closes the two gaps the conductor recorded on #179 while reviewing the build of SPEC-0032 rule 5.

1. **SPEC-0032 rule 5, every flip of a spec needs a person.** A pull request whose diff sets a spec's status line to `Approved`, whether through a `Final:` line or an ordinary commit, or by adding the spec as `Approved`, fails `check_specs.py` unless a comment or a review body by an account in `spec_approvers` has the first line `Approve: <sha> SPEC-<n>` for that spec. The check reads the saved comments and reviews of the pull request (`--comments FILE [--reviews FILE]`) and git only; without `--comments` (a local run) it prints one line saying so and does not check the approval. The message names the spec and rule 5 and never a handle or a sha.
2. **SPEC-0032 rule 5, an approval is for one text.** The approval counts only while the spec file at the head equals the spec file at `<sha>` apart from its `- Status:` line; a `<sha>` that is not a commit of the repository counts for nothing. A later change to the text of the spec needs a new `Approve:` line.
3. **SPEC-0021 rule 4.** The clearance check of a covered fix list keeps its text; the check of the two additions above is made by `check_specs.py`, which the governance workflow runs on every pull request, so that a flip made without a `Final:` line is reached.
