# Proposed spec amendments 73 (SPEC-0007, SPEC-0010, SPEC-0032; REQ-039)

Date: 2026-10-25 (from `date -u`). Approved specs change only through a proposal like this one (principle 6). Applied by ADR-0137. The paths: `docs/specs/0007-metrics.md`, `docs/specs/0010-proof-checks.md`, `docs/specs/0032-github-events-label-each-pr-people-approve-specs-a-red-branch-stops-work.md`. The number 73 is the one the conductor reserved for brief #216.

1. **SPEC-0010 rules 16 and 17, proof runs where it can change a result.** The `proof` workflow no longer runs on an edited description (`edited` leaves its types), a superseded run is cancelled (a group per pull request), and for a status-only final commit the job reports success without running the suite: the head is one commit after its parent, that commit changes only `- Status:` lines, `proof` passed on the parent (one `GET` of its check runs, `checks: read`), and the current tip of the default branch is already in the parent (`git merge-base` of the parent with the tip is the tip), so that nothing of main is untested, as the parent's run tested the parent merged with main as it was (`scripts/agk/status_only.py`); any doubt runs the suite in full. The job reports one `outcome: skipped` step then.
2. **SPEC-0007 rule 13, governance on an edited description.** On `edited` only the steps that read the pull request body run (the base of the merge ref, the body file, the comments, the states of the pull requests, `check_specs`, `check_pr_mode`, the open briefs and the body shape); the job and its name stay, so the required check still reports. A superseded run of a pull request is cancelled and a push to the default branch never is; a run for an edited description has a group of its own, so that it cannot cancel the full run of the same commit. `governance` always runs in full on a commit. The run is named `governance edited` for an edited description and `governance full` otherwise (`run-name`), and the first step of the partial run reads the latest completed full run of the head with one `GET` of the workflow runs (`actions: read`) and fails the job unless that run succeeded (`scripts/agk/full_run.py`): an unreadable or missing run fails too, so a partial run that is green on the body steps cannot replace a failed full run as the required check.
3. **SPEC-0032 rule 1, the router on comments.** A comment starts a job only when its first line starts with `Verdict:`, `Approve:`, `Approval:` or `Correction:` (a job-level `if`); other comments (reports, questions, takes, notes) change no state and start none. The other triggers are unchanged.
