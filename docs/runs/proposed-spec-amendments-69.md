# Proposed spec amendments 69 (SPEC-0028; REQ-035)

Date: 2026-10-25 (from `date -u`). Approved specs change only through a proposal like this one (principle 6). Applied by ADR-0133. The path: `docs/specs/0028-in-flow-mode-a-kit-build-pull-request-does-not-bump-the-vers.md`. The number 69 and ADR-0133 were reserved for this build on #212 by the conductor, on the maintainers' word of 2026-10-26, after a tag was made by hand on a commit that was not a release.

1. **SPEC-0028 rule 4, only the merge commit of a release is tagged.** The maintainers tag the merge commit of a release pull request and no other commit. The guide says so.
2. **SPEC-0028 rule 5, a check on every pushed tag.** A workflow, `agk-tag.yml` (this repository's own; not installed in a project, because its script is kit-only), runs on the push of a tag `v*` and checks out the tagged commit with its full history. `scripts/agk/check_tag.py` (kit-only, like `check_release.py`) fails the job when the tag is not of the form `vN.N.N`, when `agk.toml`, `kit/manifest.json` and `.claude-plugin/plugin.json` do not all state the tag's version, when `CHANGELOG.md` has no section for the tag, when a fragment is left under `changelog.d/`, or when `kit/hashes.json` does not match the kit files (`kit_hashes.problems` against the first parent). On a failure the job opens or updates the one issue `The tag <tag> is not a release`, labelled `agk-release` (created when missing): a plain issue for a person, not a brief, because only a person can fix a tag, with no `Priority:`, `Advances:` or `Touches:`; it says the commit, the check that failed with its output, and the fix (delete the tag and its release, and tag the merge commit of the release pull request). The workflow deletes nothing, moves no tag, makes no release and no commit; its only write is that issue.
