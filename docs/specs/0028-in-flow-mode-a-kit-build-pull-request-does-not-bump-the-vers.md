# SPEC-0028: In flow mode a kit build pull request does not bump the version, and one release pull request bumps it for all of them

- Status: Approved
- Owner: reviewer group (a team from config/reviewers.yaml)
- Requirements: REQ-035, REQ-038

Status is `Draft` or `Approved`. An Approved spec is owned by its reviewer group; agents propose patches.
Written by the intake of one sentence (SPEC-0012): "In flow mode a kit build pull request does not bump the version, and one release pull request bumps it for all of them, so independent kit builds can run in parallel." It is step 0b of the conductor plan (issue #160) and follows SPEC-0025 rule 8, whose release model was left to this intake. It is about how this repository releases the kit: it changes nothing a project installs or runs, and in strict mode nothing changes at all. Evidence: every kit build pull request bumps `agk.toml`, `kit/manifest.json` and the plugin and regenerates `kit/hashes.json`, so two parallel kit builds always collide on the same lines.
The maintainers gave 4 answers before it was written, in the brief of issue #160 and not as interview questions: (1) in flow mode a build pull request leaves the three versions as they are, adds one line under an Unreleased heading of a new `CHANGELOG.md` naming its pull request and its one-line change, and refreshes `kit/hashes.json` for the files it changed, and the kit-version checks accept that; (2) a release pull request, opened by a session on the maintainers' word, moves the Unreleased lines under the new version and bumps the three versions together and nothing else, a check fails a release pull request that changes any other file, and the maintainers merge and tag it; (3) in strict mode nothing changes, a build pull request bumps as today; (4) `check_numbers`, `renumber` and the union logs apply as built, and a collision in `kit/hashes.json` between two parallel builds is resolved by regenerating it after the rebase with one command.

## Rules

1. **The changelog.** `CHANGELOG.md` at the root of this repository (a new kit file; not installed in a project) has the heading `# Changelog`, then `## Unreleased`, then one `## <version> (<YYYY-MM-DD>)` heading for each release, newest first. A line is `- #<n> <one-line change>`: the number of the pull request and what it changes, in one line. `kit/templates/changelog.md` holds the shape.
2. **A build pull request in flow mode.** In flow mode (`pr_mode = "flow"` in `agk.toml`) a pull request that changes a file the installer writes (the files `kit/manifest.json` lists) leaves `version` in `agk.toml`, `kit_version` in `kit/manifest.json` and `version` in `.claude-plugin/plugin.json` as they are, adds exactly one changelog fragment `changelog.d/<slug>.md` (rule 11) in place of a line under `## Unreleased` of `CHANGELOG.md`, and does not edit `CHANGELOG.md` or `kit/hashes.json` (rule 16). The check of the bump rule (`kit_hashes.py`) accepts a change to an installed path without a bump when the pull request adds exactly one well-formed fragment against the base; it fails, naming the rule and the path class, a build that edits `CHANGELOG.md` or `kit/hashes.json`, or that changes a file the installer writes without adding exactly one fragment (rule 12). The row of the current version in the table is not compared between releases, because the release regenerates it (rule 4); the rows of earlier versions are never touched.
3. **Strict mode.** In strict mode (the default) the bump rule, the checks of the versions and `kit/hashes.json` are exactly what they are before this spec: a build pull request bumps the three versions, and no changelog line is required.
4. **The release pull request.** In flow mode a pull request that raises `version` in `agk.toml` is a release pull request. It is opened by a session on the maintainers' word, and it changes only these five files: `CHANGELOG.md`, `agk.toml`, `kit/manifest.json`, `.claude-plugin/plugin.json` and `kit/hashes.json`, and deletes the fragments under `changelog.d/`. It moves every line under `## Unreleased` under a new heading `## <new version> (<date>)`, unchanged and in order, then writes there the line of each fragment as `- #<n> <one-line change>` in the order of the pull request numbers and deletes the fragments (rule 13), leaves `## Unreleased` empty, regenerates `kit/hashes.json` with `python3 scripts/agk/kit_hashes.py --write`, and raises the three versions to the same new number, which is greater than the old one. The maintainers merge it and tag it; no check merges or tags.
5. **The release check.** A new check, `scripts/agk/check_release.py` (kit-only, never installed; a step of the governance workflow of this repository), reads git and the files of the work tree only. In strict mode and when no version is raised it prints `ok release` and checks nothing. For a release pull request it fails, naming the rule and the path class and never a value, when a changed file is outside the five of rule 4 and the deleted fragments under `changelog.d/`, when the three versions differ or do not rise, when the Unreleased lines were not moved unchanged, when `## Unreleased` is not empty afterwards, or, for the fragments (rule 14), when a fragment is left, added or edited, when a fragment line is not under the new heading with its `#<n>` and in order, or when the pull request number of a fragment cannot be read.
6. **Collisions.** `check_numbers.py`, `intake.py renumber` and the `merge=union` logs apply as built (SPEC-0025). A build edits neither `CHANGELOG.md` nor `kit/hashes.json` (rule 2), so two parallel builds do not collide on them: each adds a fragment of its own (rule 11). The command `python3 scripts/agk/kit_hashes.py --write` belongs to the release pull request (rule 4).
7. **The rules of the sessions.** The build changes `CLAUDE.md` rule 2 and `constitution/principles.md` rule 3 (protected files, named by the build's ADR) to say: one open pull request per session; several sessions may have one each; a pull request never stacks on another's unmerged change; dependence is declared with `Depends-on`. The ruling of the verdict on step 0a puts this change in the build of this spec.
8. **The guide.** A section on developing the kit (in `docs/guides/reference.md`) tells a kit developer, in flow mode, to add the changelog line, how a release pull request is made and checked, and the one command that resolves a `kit/hashes.json` collision.
9. **How it changes.** SPEC-0008 (the bump rule and the table) and SPEC-0025 (rule 8: the release model) are Approved: the build changes them by `docs/runs/proposed-spec-amendments-N.md`, applied by its ADR. The build is a kit change of this repository only, measured first and split at about 600 changed lines of code and tests: the changelog and its template, the bump-rule change, the release check and its workflow step, the two protected files, the guide section, an ADR that names the protected classes it touches, tests first. Whether it bumps itself: it is the first change under this rule and it still bumps, as the last build that does (it is built while this repository's own builds are serial).
10. **The tests.** Fixtures in `tmp_path`, with git: a flow-mode change to an installed file with and without a changelog line, and in strict mode; a release pull request that is right, one with a sixth file, one with versions that differ or do not rise, one that changes an Unreleased line while moving it, and one that leaves Unreleased non-empty; the regeneration after a collision; the text of `CLAUDE.md`, the principles and the guide section. No network and no model.

### The changelog fragments (from SPEC-0031)

These were SPEC-0031 rules 1 to 8, in their text unchanged; SPEC-0031 keeps its number and points here, its rule N being rule N + 10 (brief #386, amendment 108, ADR-0245). Inside them a bare "rule N" names rule N + 10 of this section, and "SPEC-0028 rule N" names rule N above.

11. **The fragment.** In flow mode a build pull request adds one file `changelog.d/<slug>.md`, where `<slug>` is the pull request number or the branch slug (`[a-z0-9-]+`). The file holds exactly one line, `- <one-line change>`, and a newline; it carries no pull request number.
12. **The build.** In flow mode a pull request that changes a file the installer writes adds exactly one fragment and does not edit `CHANGELOG.md`. A pull request needs a fragment exactly when SPEC-0028 rule 2 requires a changelog line (the trigger of SPEC-0028 rule 2); one that does not meet that trigger may add a fragment and is not failed for it. The flow-mode check (the check of the bump rule of SPEC-0028 rule 2) fails, naming the rule and the path class and never a value, when `CHANGELOG.md` is edited, when no fragment is added, when more than one is added, or when a fragment does not have the form of rule 1. The line under `## Unreleased` that SPEC-0028 rule 2 requires is replaced by the fragment.
13. **The release script.** A script in `scripts/agk/` (kit-only) run by the release pull request moves the line of every file under `changelog.d/` under the new heading `## <version> (<date>)` of `CHANGELOG.md`, in the order of the pull request numbers, each written as `- #<n> <one-line change>`, deletes the fragments, and writes no other file. The script reads `<n>` from the pull request that added the fragment: the merge or squash commit that added the file (`git log --diff-filter=A`), whose subject carries `(#<n>)`. A fragment whose pull request number cannot be read stops the script. `## Unreleased` stays and is empty.
14. **The release check.** `check_release.py` (SPEC-0028 rule 5) adds `changelog.d/` to the files a release pull request may change, accepts the deletion of a fragment and nothing else there, and fails, naming the rule and the path class, when a fragment is left, when a fragment line is not under the new heading with its `#<n>` and in order, when the pull request number of a fragment cannot be read, or when a fragment is added or edited.
15. **Strict mode.** In strict mode nothing changes: no fragment is required and `CHANGELOG.md` is as before.
16. **`kit/hashes.json`.** Before the build, its ADR records a measurement of whether the release can regenerate `kit/hashes.json` from the files of the release. If it can, a build pull request in flow mode does not edit the file and the check of rule 2 fails one that does; the release regenerates it and `check_release.py` accepts that. If it cannot, the ADR records why and the builds refresh the file as SPEC-0028 rule 2 says.
17. **How it changes.** SPEC-0028 (rules 2, 4, 5 and 6) is Approved: the build changes it by `docs/runs/proposed-spec-amendments-N.md`, applied by its ADR, which names each protected class it touches. The build is its own pull request from the default branch after this intake, tests first.
18. **The tests.** Fixtures in `tmp_path`, with git: a build with one fragment and one with none, two, a malformed line, or an edit of `CHANGELOG.md`, and a change to a file outside the trigger with and without a fragment; strict mode; two builds merged one after the other with no conflict on `CHANGELOG.md`; a release that gathers the fragments in pull request order, one that leaves a fragment, one that changes a line while moving it, one whose fragment has no readable pull request number, and one that touches a sixth file; the regeneration of `kit/hashes.json` if the measurement says it can be. No network and no model.

## Tests

- Rule 2: a flow-mode change to an installed file with an Unreleased line and refreshed hashes passes the checks; REQ-035 AC1.
- Rule 2: the same change without the line fails naming the rule and the path class; REQ-035 AC2.
- Rule 3: in strict mode the bump is required and no line is; REQ-035 AC3.
- Rules 4 and 5: a release pull request that moves the lines and raises the three versions passes; REQ-035 AC4.
- Rule 5: a sixth changed file, versions that differ or do not rise, a changed or unmoved line, or a non-empty Unreleased fails; REQ-035 AC5.
- Rule 6: after two builds collide in the hashes table, the regenerated table is accepted; REQ-035 AC6.
- Rule 7: `CLAUDE.md` and the principles hold the new text; REQ-035 AC7.
- Rule 8: the guide section names the changelog line, the release pull request and the one command; REQ-035 AC8.
- Rules 11 to 18: the tests of SPEC-0031 `## Tests` (REQ-038 AC1 to AC7), its rule N read as rule N + 10. Under the amended rule 2 the "Unreleased line and refreshed hashes" of the first two lines above are the one fragment of rule 11, with `kit/hashes.json` left as it is.
