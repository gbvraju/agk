# SPEC-0025: A team can run independent pull requests in parallel without colliding

- Status: Approved
- Owner: reviewer group (a team from config/reviewers.yaml)
- Requirements: REQ-032

Status is `Draft` or `Approved`. An Approved spec is owned by its reviewer group; agents propose patches.
Written by the intake of one sentence (SPEC-0012): "A team can run independent pull requests in parallel without colliding on numbers or logs, a pull request that needs another one's unmerged change says so and cannot merge before it, and each repository chooses a strict or a flow mode for how many pull requests a person may have open." It is the first phase of the brief for teams (issue #133), generic and project-agnostic: it holds for every project the kit is installed in and names no project and no reader. The working rule "one open pull request at a time" guarded against undeclared stacking, a pull request built on another's unmerged change; phase 1 makes independent work collide-free, makes dependence explicit and lets each repository choose its mode. It changes how many pull requests may be open, never what a pull request must prove: tests first, proof, review, a listed author's verdict and a person's merge are the same in every mode. This intake takes the pre-L2 path (SPEC-0012): it merges with the spec `Draft` and the ADR `Proposed`, and the next pull request is the approval alone, the two status lines and nothing else, cleared by the maintainers before part (a) starts.
The maintainers gave seven answers before it was written, in the issue and not as an interview: (1) duplicate numbers are a governance failure and `intake.py renumber` moves a pull request's own numbers, no number being edited by hand; (2) the append-only logs are marked `merge=union` in the shipped `.gitattributes`, with GitHub's behaviour verified at the build; (3) with two or more listed verdict authors a verdict by the pull request's own author does not count; (4) a body may declare `Depends-on: #n` and a check fails while a named pull request is not merged; (5) `pr_mode` in `agk.toml` is `strict` (the default) or `flow`; (6) this repository switches to `flow` by a separate pull request after parts 1 to 5 are released; (7) release pull requests for this repository in flow mode have their own intake after part 6.

## Rules

1. **Duplicate numbers fail.** A governance check (`check_numbers.py`, installed) fails when two requirements in `docs/requirements.md`, two specs in `docs/specs/` or two ADRs in `docs/adr/` carry the same number in the checked-out tree. In CI that tree is the pull request's merge commit, so a collision with the default branch shows there. The message names the rule and the duplicated id and never a title. It reads files only. The first pull request to merge keeps its numbers.
2. **Renumbering is a command, never a hand edit.** `python3 scripts/agk/intake.py renumber <id>` takes an id of the pull request's own requirement (`REQ-nnn`), spec or ADR, moves the pull request's own requirement, spec and ADR to the next free numbers on the default branch (read from `origin/<default branch>` as `ids` does), renames the files, rewrites the ids inside the pull request's own files and every reference the pull request adds, and changes nothing that is on the default branch. It prints what it moved. A second run changes nothing. It refuses when the work tree is dirty or when an id is not the pull request's own.
3. **The append-only logs merge as a union.** The shipped `.gitattributes` template marks `docs/runs/decisions-log.md`, `docs/runs/residuals.md` and the catch logs (`docs/runs/architect-catches-*.md`) `merge=union`, so two pull requests that each append a line merge without a conflict. It does not mark `docs/requirements.md`, whose status lines change in place. At the build the behaviour of GitHub's merge conflict check is measured; if it does not honour `merge=union`, the build raises a question with the measured behaviour and two options (keep union for local rebases only, or one file per log entry with a generated index) and builds neither until it is ruled.
4. **No self-clearance.** When two or more verdict authors are listed (SPEC-0021 rule 5), a verdict by the pull request's own author does not count: it clears nothing, covers nothing and is not a review round, for the metrics, the facts and `check_final_clearance.py`. The workflow passes the pull request's author login to the checks; the metrics read it from the pull request record. With one listed author nothing changes.
5. **Declared dependence.** A pull request body may carry lines `Depends-on: #n`. A governance check fails while any named pull request is not merged, naming the rule and the number. The workflow fetches the state of each named pull request with a read-only GET into a file (as it fetches the comments); the check reads that file, and without it prints `skipped (no states file)` and passes.
6. **The mode.** `agk.toml` gains `pr_mode = "strict" | "flow"`, default `strict`. In strict mode a person has one open pull request at a time: a check fails on a pull request whose author has an older open pull request (the lowest number wins), and a `Depends-on` line fails the check. In flow mode any number of pull requests may be open and `Depends-on` is allowed. The workflow fetches the author's open pull requests with a read-only GET into a file; the check reads it, and without it prints `skipped (no open pull requests file)` and passes. `agk.toml` is protected, so a change of mode needs an ADR in the same pull request. `doctor` reports the mode, and the getting-started guide says that new projects start strict and switch by ADR once the team knows the method.
7. **The workflow reads and writes files only.** The workflow keeps the permissions `contents`, `pull-requests` and `issues`, each `read`. Every new fetch is a step with `gh api --method GET` that writes a file in the runner's temporary directory; a check reads files and git, and makes no network call.
8. **This repository.** Parts 1 to 5 are built for every project. After they are released a separate pull request switches this repository to `flow` by an ADR; until then this repository stays strict, with the maintainers' docs-only exception of 2026-10-24. The release model in answer 7 (kit build pull requests do not bump the version in flow mode; one release pull request bumps `agk.toml`, `kit/manifest.json` and the plugin together and moves an Unreleased changelog section) is a later intake of this repository only and is not built here.
9. **Not built.** A cap on the number of open pull requests in flow mode (the report's "changes waiting for a review", with their age, shows the queue), a server or a database, any network call in a check.
10. **How it is built.** The build is a kit change in three parts, each with a bump, an ADR that names the protected classes, the hashes, and its tests first: (a) the duplicate-number check and `intake.py renumber` (rules 1 and 2); (b) the `.gitattributes` lines, after the verification of rule 3; (c) the author rule, `Depends-on` and `pr_mode` with their workflow fetches (rules 4 to 7). The Approved specs this touches are changed by `docs/runs/proposed-spec-amendments-N.md`, applied by the part's ADR: SPEC-0021 rule 5 (the author), SPEC-0007 (the review rounds), SPEC-0012 (`renumber`), SPEC-0002 and SPEC-0001 (the `.gitattributes` and `agk.toml` templates), SPEC-0003 or the doctor spec (the mode). Each part is measured first and split at about 600 changed lines of code and tests; part (c) is the likeliest to need a split.
11. **The tests.** Fixtures in `tmp_path`: trees with and without duplicate numbers; `renumber` on a pull request branch behind a merge on the default branch, twice; the `.gitattributes` template; verdicts by the pull request's author with one and with two listed authors; bodies with `Depends-on` lines with and without the states file in each mode; the open pull requests file for an author with an older pull request; the mode in `agk.toml` and `doctor`; the workflow for its permissions, its GET-only fetches and the absence of any write. No network and no model.

## Tests

- Rule 1: a tree with two requirements, two specs or two ADRs of the same number fails with the rule and the id; unique numbers pass; REQ-032 AC1.
- Rule 2: `renumber` moves the pull request's own numbers, renames the files, rewrites the ids and the references it added, leaves the default branch's files alone, and is idempotent; REQ-032 AC2.
- Rule 3: the template marks the append-only logs and not the requirements file; REQ-032 AC3.
- Rule 4: with two listed authors the pull request author's verdict clears nothing, covers nothing and is no round; with one it does; REQ-032 AC4.
- Rule 5: the check fails while a named pull request is not merged and skips without the file; REQ-032 AC5.
- Rule 6: strict fails on an older open pull request and on `Depends-on`, skips without the file, and the default is strict; REQ-032 AC6.
- Rule 6: flow passes both, and `doctor` reports the mode; REQ-032 AC7.
- Rule 7: the workflow's permissions are three `read`, its new fetches are GET-only steps that write files, and the checks import no network module; REQ-032 AC8.

## Proof

REQ-032 AC1 and AC2: *two pull requests can be developed in parallel and the second to merge renumbers itself by a command.* Rules 1 and 2. REQ-032 AC3: *appended log lines do not collide.* Rule 3. REQ-032 AC4: *a person cannot clear their own pull request when others are listed.* Rule 4. REQ-032 AC5 to AC7: *dependence is declared and enforced, and the mode is the repository's choice.* Rules 5 and 6. REQ-032 AC8: *the workflow still only reads.* Rule 7. The first pull request built under flow mode in this repository, with the number of maintainer actions it took, is recorded by the maintainers in `docs/runs/method-weight-2.md`.
