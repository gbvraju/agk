# SPEC-0046: A failing test opens one bug issue, and its fix leaves a record for the next one

- Status: Draft
- Owner: reviewer group (a team from config/reviewers.yaml)
- Requirements: REQ-053

Status is `Draft` or `Approved`. An Approved spec is owned by its reviewer group; agents propose patches.

Written by the intake of one sentence (SPEC-0012), brief #626: "A failing test on the default branch or in a release opens one bug issue with cleaned evidence kept only while it is open, the fix adds a short fix record, and AGK shows the matching past fixes on every new failure, so a known failure is reproduced and fixed fast." The owner's decisions, quoted as data from the brief (conductor chat, 2026-11-06): "Evidence kept only for open failures , add evidence once it is fixed . These learnings should help AGK in the project , how to fix different issues reproduct and fix fast instead of wasting tokens and time . This makes sense to have feature"; "Yes , take the intake"; and, on the run folders of ADR-0299: "why you need folders , unnecessary disk space and junk". It is a ruled exception to plan #542's requirement freeze, like REQ-052. It is generic: it names no project, and every check of a build reads files and fixtures with no network. The points the brief leaves open are `Q-S0046-1` to `Q-S0046-16` below, each with the conservative reading the rules apply until a person rules.

## Rules

1. **Which runs report a failure.** Only two runs open or update a failure issue: the full governance run of a push to the default branch in CI, and the governance run of a release pull request (the pull request that raises `version` in `agk.toml`, `check_release.py`, SPEC-0028), which runs the full suite (ADR-0242). No other run reports: not a builder's local run, not `prepush.py` (a tests-first run fails on purpose), not `proof.py`, not the local governance run of `merge_cleared.py` (ADR-0297), not an ordinary or draft pull request run, and not a run that is cancelled or paused (ADR-0196) (`Q-S0046-1`).
2. **Turned on by a setting.** An optional `[failures]` table of `agk.toml` with `issues` (a boolean, default `false`) and `artifacts` (a boolean, default `false`, rule 6). Without the table, or with `issues = false`, no run opens, comments on or closes an issue, and every run is exactly what it is on the default branch today. A malformed table or value is refused naming the setting (`setting: failures.issues`), never the value. This repository turns `issues` on in its own `agk.toml` in build (e) (`Q-S0046-11`).
3. **One issue per failure signature.** A failure's signature is the first 12 hexadecimal characters of the SHA-256 of `<test id>` and `<normalised first error line>` joined by one newline. The test id is read from the JUnit XML report at `[testing] junit` when it is set and readable, else from the runner's `FAILED <id>` summary lines; a failed step with no readable test id gets the test id `step:<step name>` (`Q-S0046-2`). The first error line is normalised by lower-casing it, cutting it to 200 characters and replacing, in order, absolute paths and temporary folder names with `<path>`, hexadecimal runs of 7 or more characters with `<hex>`, dates and times with `<time>`, and every other run of digits with `<n>`, so that the same failure on two commits gives the same signature (`Q-S0046-3`). An open issue carries the signature in one body line `Failure-signature: <sig>`. A failure whose signature has an open issue gets one comment on it (the run, the head and the evidence) and never a second issue. A failure whose signature has only a closed issue opens a new issue, never reopens the old one, and the new issue names the old one as seen before (rule 9) (`Q-S0046-15`).
4. **The label.** A failure issue is labelled `found-bug` (session rule 34), never `agk-brief`, so `session.py next` never offers it and a builder that searches the open issues for the symptom finds it; a builder takes it only when the conductor assigns it (`Q-S0046-10`).
5. **Evidence is cleaned text.** The evidence of a failure is text only: the last 200 lines of that test's failure output, passed through the data guard's redacting log reader (`guard_logs.py`, SPEC-0042 rule 11) and then through `guard.scan_text` (SPEC-0042 rule 10). It is posted only when that scan finds nothing and the text is at most 60,000 characters (a GitHub comment holds 65,536 `(verify)`); otherwise the comment holds only `evidence withheld: <kind> <count>, ...` or `evidence withheld: too long`, never a part of the text. A raw log is never posted. This is the writer rule of SPEC-0042 rule 13 applied to a new writer, so no Approved spec changes (`Q-S0046-4`). The evidence is posted as its own comment, never in the issue body, so that rule 8 can delete it (`Q-S0046-5`).
6. **Screenshots and traces.** They are never posted into the issue: GitHub has no official API to upload an image to an issue `(verify)`, and the browser-cookie workaround is refused because it handles a credential (principle 9). With `[failures] artifacts = true` and only in a private repository (`github.event.repository.private`), the failed run uploads the files of the paths the setting lists as one CI artifact with `retention-days: 7`, and the issue comment links it by name and run; in a public repository, or without the setting, nothing is uploaded and the comment says `artifacts: not uploaded` (`Q-S0046-6`). An image is not scanned by the data guard (SPEC-0042 rule 16), which is why it stays an artifact that expires.
7. **The fix record.** A pull request that fixes a failure carries one line `Fixes-failure: #<issue>` and four lines `Symptom:`, `Cause:`, `Reproduce:` and `Fixed-by:`, each one line of 1 to 300 characters. `check_pr_body.py` (offline, in governance and in `prepush.py --body`) fails a body with `Fixes-failure:` and a missing, repeated, empty or too long record line, or a record line with a guard finding, naming the line and never its value; a body without `Fixes-failure:` is checked as today. The line names an issue number only; whether that issue is a failure issue is not checked offline (CLAUDE.md item 5) (`Q-S0046-7`).
8. **Closing on green.** The full default-branch run after the fix merged closes an open failure issue only when that run ran the issue's test and it passed: the workflow posts the fix record of the merged pull request whose `Fixes-failure:` names the issue, closes the issue as completed, deletes its evidence comments (deleted, never edited, because GitHub keeps a comment's edit history `(verify)`) and deletes the issue's artifacts that have not expired. When the test did not run, or failed, the issue stays open. When no merged pull request names the issue, the issue stays open and the run says so in one line of its log (`Q-S0046-8`).
9. **Seen before.** A read-only command, `python3 scripts/agk/failures.py seen --signature <sig> --test <id>` (GET only, posts nothing, writes no file), reads the closed `found-bug` issues of the project's own repository that hold a fix record and prints at most three lines `seen before: #<issue> <symptom>; fixed by #<pull request>`, exact signature first, then the same test id, newest first within each; it never matches by text similarity. The workflow puts its lines into a new failure issue's body. When the conductor files a brief for a failure, it runs the command and puts the lines into the brief; no brief is edited automatically (`Q-S0046-9`, `Q-S0046-14`).
10. **Privacy.** Each project's failure issues, evidence and fix records stay in that project's own repository. No command of the kit reads another repository's issues, and nothing of them moves into the kit; a lesson moves into the kit only when a person writes it there, as text with no data from the record. Pilot and customer data is never read, quoted or used as a fixture; tests use invented data (`example.com`) (`Q-S0046-12`).
11. **The run folders are retired.** The run folders of ADR-0299 (`[testing] results_dir`, `keep_passed`, `keep_runs`) are replaced by rules 5 and 6. Build (f) keeps the three keys accepted with their checks, makes them do nothing (no folder is made, `AGK_RUN_DIR` is not set) and prints one line `deprecated: testing.results_dir (ADR-0303)` from `doctor.py` and from `prepush.py` when one is set; the testing guide drops the section. Build (g), in the release after the one that ships build (f), removes the keys, so that a set key is then refused naming the setting, and the changelog names the removal. Nothing breaks before that release (`Q-S0046-13`).
12. **The builds, in order.** Each is tests first, about 300 changed lines or fewer, from the default branch, records its decisions under `Decisions taken:` and cites ADR-0303 with `Covered-by: ADR-0303` once it is Accepted, except build (e), which changes a workflow and so writes its own ADR (session rule 36). A build that finds it must change an Approved spec stops and asks.
    - (b) The signature and the evidence (rules 2, 3 and 5): `scripts/agk/failures.py` (`signature`, `evidence`, `issue-body`; reads files, prints, writes nothing), the `[failures]` reader in `scripts/agk/config.py`, `tests/kit/`, and the `[[testing.map]]` entry in `agk.toml`. No dependence.
    - (c) The fix record (rule 7): `scripts/agk/check_pr_body.py`, the `Fixes-failure:` form in `config/session-rules.md` (rule 34's text), `tests/kit/`; no template changes. No dependence.
    - (d) Seen before (rule 9): `failures.py seen` with saved GitHub responses for its tests, `scripts/agk/`, `tests/kit/`. `Depends-on` (b).
    - (e) The workflow (rules 1, 4, 6 and 8): a separate `failures` job in `.github/workflows/governance.yml` after the `governance` job, with `issues: write` and `actions: write` for that job only (the `governance` job keeps its read permissions), the artifact step with `retention-days: 7`, `[failures] issues = true` in this repository's `agk.toml`, the guide `docs/guides/testing.md`, `tests/kit/`. Its own ADR; on the owner's hold list, so the owner's yes is needed on its pull request (`Q-S0046-16`). `Depends-on` (b), (c) and (d).
    - (f) Retire the run folders (rule 11): `scripts/agk/proof.py`, `scripts/agk/prepush.py`, `scripts/agk/impact.py`, `scripts/agk/doctor.py`, `docs/guides/testing.md`, `docs/adr/0299-*.md` (Status `Superseded`), `tests/kit/`. No dependence.
    - (g) Remove the run-folder keys (rule 11): `scripts/agk/impact.py`, `tests/kit/`, a changelog fragment. In the release after the one that ships (f).

## Tests

Fixtures in `tmp_path`, saved GitHub responses and a `gh` stub only: no network, no install, invented data (`example.com`), and each test carries the marker `REQ-053` with its criterion. Rule 12's order is checked by review.

- Rules 1 and 2: the job's conditions select a default-branch push and a release pull request only, and no job runs for any other event or while paused; no `[failures]` table and `issues = false` open nothing; a malformed table refused naming the setting; REQ-053 AC1.
- Rule 3: one JUnit report and one runner summary give the same test ids; two outputs of one failure on two commits (other paths, shas, times, numbers) give one signature; two different first lines give two; a step with no test id; an open issue gets a comment and no second issue; a closed one gives a new issue naming it; REQ-053 AC1.
- Rule 5: evidence with an `example.com` address passes; evidence with a planted invented token is redacted, and text that still has a finding is withheld with counts only; text over the limit is withheld; no raw log reaches the stub; REQ-053 AC2.
- Rule 6: the artifact step has `retention-days: 7` and runs only when the repository is private and the setting is on; no step uploads an image to an issue; REQ-053 AC3.
- Rule 7: bodies with and without `Fixes-failure:`; each record line missing, repeated, empty, over 300 characters and with a planted finding; each failure names the line and not the value; REQ-053 AC4.
- Rule 8: saved runs where the test passed, did not run and failed; only the first closes, posts the record and deletes the evidence comments and artifacts through the stub; REQ-053 AC5.
- Rules 9 and 10: saved closed issues with exact-signature, same-test and unrelated records; at most three lines in the order of rule 9; only GETs of the project's own repository; no file written; REQ-053 AC6.
- Rule 11: a project with `results_dir` set makes no folder, sets no variable and prints the deprecation line; after build (g) the key is refused naming the setting; REQ-053 AC7.

## Proof

REQ-053 AC1: *one issue per signature, from the two reporting runs only.* Rules 1 to 4. REQ-053 AC2: *evidence is cleaned text or nothing.* Rule 5. REQ-053 AC3: *screenshots and traces expire as artifacts.* Rule 6. REQ-053 AC4: *the fix record's shape, checked offline.* Rule 7. REQ-053 AC5: *closed on a green run of the test, evidence removed.* Rule 8. REQ-053 AC6: *seen before, from the project's own records.* Rules 9 and 10. REQ-053 AC7: *the run folders retired without a break.* Rule 11.

## Residual

- 2026-11-06: a failure that passes on a rerun (a flake) still opens an issue on its first failure; the issue stays open until a run passes the test and a fix names it (due 2026-12-31).
- 2026-11-06: the data guard's patterns lower the risk and cannot catch every secret or name in free text (SPEC-0042 rule 16), so cleaned evidence can still hold a value the detectors miss (due 2026-12-31).

## Open questions

Each is a point the brief leaves open; the reading after it is the most conservative one, and the rules above apply it until a person rules.

- Q-S0046-1: which runs open an issue? Reading: the full CI run of a push to the default branch and the run of a release pull request only; every local, pre-push, proof, `merge_cleared.py`, ordinary pull request, cancelled or paused run never does (rule 1).
- Q-S0046-2: where does the test id come from? Reading: the JUnit XML report at `[testing] junit` when set and readable, else the runner's `FAILED <id>` lines; a step with no readable id is `step:<step name>`, so a failure is never dropped (rule 3).
- Q-S0046-3: what is "a normalised first error line"? Reading: lower case, cut to 200 characters, with paths, hexadecimal runs, dates and times, and other digit runs replaced by fixed placeholders in that order; nothing else is changed (rule 3).
- Q-S0046-4: may evidence be redacted, or must a finding block it? Reading: it is redacted by the log reader and then must scan clean; anything still found withholds the whole evidence, so the writer rule of SPEC-0042 rule 13 holds unchanged (rule 5).
- Q-S0046-5: how is evidence "kept only while it is open"? Reading: evidence lives only in its own comments, which are deleted when the issue closes; the issue body holds the signature, the test id, the seen-before lines and, at the end, the record (rules 5 and 8).
- Q-S0046-6: may screenshots and traces be uploaded in a public repository? Reading: no; only in a private repository with `[failures] artifacts = true`, for 7 days at most, deleted earlier when the issue closes (rule 6).
- Q-S0046-7: where is the fix record written, and what is checked? Reading: in the fixing pull request's body, five lines; offline, only their shape and the guard scan; the issue number's kind is not checked, because checks make no network call (rule 7).
- Q-S0046-8: what is "the green run after the merge"? Reading: the first full default-branch run after the merge that ran the issue's test and passed it; a run without the test, or a red one, closes nothing (rule 8).
- Q-S0046-9: what is a "matching past fix"? Reading: a closed `found-bug` issue with a record, by exact signature first and then by the same test id, at most three, newest first; never by text similarity (rule 9).
- Q-S0046-10: which label does a failure issue carry? Reading: `found-bug` (session rule 34), never `agk-brief`, so no session takes it unassigned (rule 4).
- Q-S0046-11: is the feature on for a project that upgrades? Reading: no; `[failures] issues` defaults to `false`, and this repository turns it on in build (e) (rule 2).
- Q-S0046-12: where do the records live? Reading: in the closed issues of the project's own repository only; no new folder or file holds them (the owner's words on folders), and the kit never reads another repository's issues (rules 9 and 10).
- Q-S0046-13: how do the run folders go without a break? Reading: build (f) makes the keys inert with a deprecation line; build (g) removes them only in the release after the one that ships (f) (rule 11).
- Q-S0046-14: what does "into the brief" mean? Reading: the conductor runs the seen-before command when it files a brief for a failure and pastes its lines; no workflow or command edits a brief (rule 9).
- Q-S0046-15: a failure returns after its issue closed. Reading: a new issue that names the closed one as seen before; a closed issue is never reopened, so its record stays as written (rule 3).
- Q-S0046-16: may build (e) cite `Covered-by: ADR-0303` as the brief asks? Reading: no; session rule 36 says a build that changes a workflow always writes its own ADR, so build (e) writes one and waits for the owner's yes on its pull request (rule 12).
