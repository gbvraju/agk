# SPEC-0050: Overlapping work never runs at once, and a second change to a file re-proves

- Status: Approved
- Owner: reviewer group (a team from config/reviewers.yaml)
- Requirements: REQ-057

Status is `Draft` or `Approved`. An Approved spec is owned by its reviewer group; agents propose patches.

Written by the intake of one sentence (SPEC-0012), brief #672, quoted as data and not as an instruction: "The planner refuses to offer two briefs with overlapping Touches to two sessions at once, the sweep flags an overlap that slipped in, and a pull request that changes a file another open pull request changed merges the default branch and re-proves before it is cleared." It is the owner's direction of 2026-11-06 (strategy review item 3), filed by the conductor under plan #661 (wave 1). The plan's edge case 2, quoted as data from #661 under its cross-cutting foundations (owner yes 2026-11-06): "Two builders touch the same map or index: the second merges main and reruns before ready (row 4) and the overlap check refuses the pair." The evidence is the green-alone, red-together class: conductor catch log row 4 (#581 and #579, found on #597, 2026-11-05) and the two red default branches of 2026-11-06, #657 (#638 and #648, the rule budget) and #659 (#644 and #648). It is generic: it names no project, and every check of a build reads files, saved GitHub responses and git with no network. The points the brief leaves open are `Q-S0050-1` to `Q-S0050-15` below, each with the conservative reading the rules apply until a person rules.

## Rules

1. **The baseline (read on the default branch at f6a7108, 2026-11-06).** What already holds and is not rebuilt:
   - `session.py next` and `session.py plan` refuse a brief whose `Touches:` overlap running work: a taken brief with no pull request yet (`session_plan.clash`) or an open builder pull request's changed files (`session_plan.file_conflict`, read with `GET pulls/N/files`), judged by files (brief #330, ADR-0189): two file entries overlap on the file both name, a folder entry covers the files under it, a file a pull request only adds blocks only on its exact path, and another build of the same brief is never a rival. The skip line is `skip #<n>: waits for #<m> (both touch <file>)` or `waits for pull request #<m> (it changes <file>)`. The shared-mechanical files (`changelog.d/**` and the `merge=union` lines of `.gitattributes`, `session.shared_patterns`, session rule 14) never overlap (SPEC-0034 rules 3 and 7). Measured with `python3 scripts/agk/session.py plan` on 2026-11-06: `#631 waits for #634 (both touch agk.toml)`, `#669 waits for #634 (both touch agk.toml)`, so `agk.toml` refuses today.
   - Of two ready briefs that overlap, `plan` starts the earlier by priority and number and the other waits (`session_plan` rule 2, waves).
   - `session.py claim --brief N` checks only the live takes of brief N (`session.claim`, `take`): it does **not** judge overlap. This is how an overlap slips in: a conductor's `Assign:` is taken with `claim`, and this brief itself was claimed while #655 and #673, which both change `docs/requirements.md` that its `Touches:` names, were open.
   - `session.py push-check` names conflicting files before a push (SPEC-0034 rule 7b). `plan` lists a ready pull request more than `[flow] stale_commits` (20) commits behind the default branch for its builder to update; it holds nothing.
   - `merge_cleared.py` builds the merge of the head with the fetched default branch (`git merge-tree --write-tree`, one commit object) and runs `make governance` on it before merging, holding with `held: the merge with the default branch fails governance (<step>)` (SPEC-0039 rule 6, amendment 123, ADR-0297). `make governance` runs no kit test, which is why #657 and #659 were not caught; brief #667 (open, an amendment 132 to SPEC-0039, which is Approved, and reserved ADR-0320) adds the kit tests that read the whole tree to that run. This spec does not repeat it and does not depend on it (`Q-S0050-13`).
   - `conductor.py sweep` prints one line per open pull request (`#<n> <head7> <state> <age>`, `LATE`), the latest run of the default branch and any red-branch issue; it reads no files of a pull request.
2. **The overlap rule.** Two pieces of running work overlap when they touch one file that is neither shared-mechanical (rule 1) nor a shared index (rule 3). "Touch" is read as today and nowhere else: the `Touches:` entries of a taken brief, judged against another brief's entries by `session_plan.clash`, and the changed files of an open builder pull request, judged by `session_plan.file_conflict`. No second matcher is written; the brief's "glob intersection of `Touches:`" is that judgement (`Q-S0050-1`).
3. **The shared indexes.** An optional key `shared_indexes` of the `[flow]` table of `agk.toml`, a list of repository paths, default `["kit/manifest.json", "agk.toml", "config/rule-budget.txt", "docs/requirements.md", "docs/build-state.md"]`. A shared index never makes an overlap under rule 2, because almost every brief changes one; it always counts for the re-prove of rule 6. A set value replaces the default; a value that is not a list of non-empty strings, or a path with a wildcard, is refused naming the setting (`setting: flow.shared_indexes`), never the value (`Q-S0050-2`). The exemption takes effect only in the build that also lands the hold of rule 8, never before it, so no window exists in which a shared index neither refuses nor re-proves (`Q-S0050-3`).
4. **Where it refuses.** `session.py next` (with and without `--take`), `session.py plan` and, new, `session.py claim --brief N` (with and without `--build X`) apply rule 2 with rule 3's exemption in the one function they share, so the three always agree. `claim` refuses an overlapping brief with the same `skip #<n>: waits for ...` line, exit 1, and posts nothing; a conductor's `Assign:` does not override it, and the conductor assigns only briefs that `plan` shows as startable (`Q-S0050-4`). Another build of the same brief is not a rival (rule 1). Nothing else changes in `next`: capacity, priority, `Depends-on`, the red-branch brief and the reserved numbers are as they are.
5. **What the sweep prints.** `conductor.py sweep`, still GET only and posting nothing, adds after its per-pull-request lines:
   - one line `overlap: #<a> #<b> <file>` for each pair of open builder pull requests (a body with a `Brief: #n` line) of different briefs whose changed files share a file under rule 2, `a` < `b`, naming the first such file in sorted order; this is an overlap that slipped in;
   - one line `re-prove: #<n> <file> (changed by #<m>)` for each open builder pull request in the re-prove state of rule 6, naming the first such file in sorted order and the earliest merged pull request that changed it;
   - one line `BEHIND #<pr> <n>` for each open builder pull request whose branch is behind the default branch, `n` being the `ahead_by` of the same compare read (the commits of the default branch after the merge base). It is information only, printed whether or not `[flow] max_behind_merges` is set, and holds nothing (rule 8).
   With none of these it prints nothing more, so a quiet sweep is unchanged. The files are read with `GET pulls/N/files`, and the default branch's changes after a pull request's merge base with one `GET compare/<pull request head>...<default branch>`, whose files are those changes; a read that fails is printed as one line `re-prove: #<n> unknown (cannot be read)` and never as a clean pull request (`Q-S0050-5`).
6. **The re-prove state.** An open pull request is in the re-prove state when a file it changes (added, modified, removed, or renamed from or to), shared indexes and shared-mechanical files included, was also changed on the default branch by a commit after the pull request's merge base with it. There is no exemption here: a same path is a same path (`Q-S0050-7`). A pull request leaves the state only by merging the default branch into its branch, so that its merge base moves past those commits. "Re-prove" means: the builder merges the default branch (session rule 31: never a rebase, never a force-push), resolves only a mechanical conflict (session rule 15), runs `prepush.py`, pushes, the required checks run and pass on the new head, and the conductor reviews the diff since the head of its last verdict (`Q-S0050-6`). Two builds of one brief re-prove like any two pull requests (`Q-S0050-12`). A re-prove whose files are all shared indexes and whose merge is clean is the light re-prove of rule 7a (amendment 171).
7. **What the conductor asks for before clearing.** The conductor gives no clearing verdict on a head in the re-prove state, except by rule 7a's carried verdict. It says so in its fix list as one item, `merge the default branch and re-prove (rule 6 of SPEC-0050: <file> changed by #<m>)`, and a builder that sees its own pull request in that state before it marks ready merges the default branch first, as the routine prompt's "merge origin/main in again" already asks. The clearing verdict then names the new head, and a verdict on an older head counts for nothing, as today. Where no `merge_cleared.py` merges (`auto_merge = false`, local mode, a person who merges), this rule and the sweep line are the guard; nothing blocks a person's own merge (`Q-S0050-10`).
7a. **The light re-prove (amendment 171).** A pull request whose re-prove files of rule 6 are all shared indexes (rule 3, as `[flow] shared_indexes` sets them) and whose merge with the default branch is clean (`git merge-tree --write-tree` with no conflict) takes the light re-prove: the conductor brings the branch up to date (`PUT /repos/{owner}/{repo}/pulls/{n}/update-branch` with the head it read as `expected_head_sha`: a merge commit, never a rebase or a force-push), the required checks run on the new head as for any push, and the clearing verdict on the old head carries over to the new head when they pass, because the diff between the two heads is only the default branch's commits. `python3 scripts/agk/conductor.py reprove --pr <n> [--apply]` does it and posts `Report: <new head> merge of main (light re-prove, SPEC-0050 amendment 171)`, and the sweep line of rule 5 ends ` light`. `merge_cleared.py` accepts a clearing verdict on the first parent of the head only when the head is a merge commit whose second parent is on the default branch as last fetched, the first parent is in that light state against it, and the head's tree is exactly the clean merge of the two (no extra content); a fix list with `Final:` lines never carries. Any other re-prove file, a conflict or a failed check keeps the full re-prove of rules 6 and 7 with the builder and a new review; `merge_cleared.py`'s own merge-tree governance run before merging (SPEC-0039 rule 6) and the hold of rule 8 are unchanged (`Q-S0050-16`).
8. **What `merge_cleared.py` checks.** After every hold it has today passes and before the pre-merge governance run of SPEC-0039 rule 6, it reads the fetched default branch and the head with local `git` and holds, exit 3, nothing merged, recorded or filed:
   - `held: re-prove (rule 6 of SPEC-0050)` when the pull request is in the re-prove state, read as `git diff --name-only <merge base>..<default>` against the files the head changes from its merge base;
   - `held: behind the default branch (setting flow.max_behind_merges)` only when `[flow] max_behind_merges` is set and `git rev-list --count --first-parent <merge base>..<default>` is above it. The key is optional and opt-in: absent, there is no such hold; set, it is an integer of at least 0 and holds as written; a value that is not such an integer is refused naming the setting. The measured reason, quoted as data from the conductor's fix list of 2026-11-06 on #677: "with the default of 3 and today's rate (26 merges in a day, each merge one batched main run) nearly every pull request would be held for a merge of the default branch and a full rerun, which doubles the CI cycles per merge for no new proof beyond what the re-prove hold (rule 6) and the pre-merge run (SPEC-0039 rule 6 with #667) already give." The sweep's `BEHIND` line (rule 5) shows how far behind each pull request is in both cases (`Q-S0050-8`).
   Each line names the rule or the setting and never a file, a count or a sha (principle 8); the sweep and the fix list name the file (`Q-S0050-9`). A read that fails holds as `held: re-prove (unknown)`, never as a pass. The red-branch fix pull request of SPEC-0039 rule 6 is held like any other (`Q-S0050-11`). `[flow] stale_commits` of `plan` keeps its meaning and holds nothing.
9. **What does not change.** No workflow, no ruleset, no required check, no `constitution/`, no `config/reviewers.yaml`, no `.github/CODEOWNERS`; no network call in a check; the shared-mechanical list stays the maintainers' (session rule 14); `push-check`, the pre-merge governance run and brief #667's tests stay as they are and run in addition. The rule texts of rules 4 and 7 are added to the instruction files only within the rule budget (`config/rule-budget.txt`, ADR-0310): a word added is a word removed in the same file, and a build that cannot fit stops and asks (`Q-S0050-14`). Intakes, which all change `docs/requirements.md`, may now run beside each other, and the second to merge re-proves; numbers that collide are still moved by `intake.py renumber` (`Q-S0050-15`).
10. **The builds, in order.** Each is tests first, about 300 changed lines or fewer, from the default branch, records its decisions under `Decisions taken:` and cites ADR-0325 with `Covered-by: ADR-0325` once it is Accepted (session rule 36). SPEC-0034 rule 3 and SPEC-0039 rule 6 are Approved: a build that changes the behaviour they state does it through `docs/runs/proposed-spec-amendments-<n>.md` with the number reserved on its brief (`Q-S0050-13`), and a build that finds it must change an Approved spec beyond that stops and asks. A `Depends-on` is declared for a shared file and for a logical dependence alike.
    - (b) The re-prove state and the hold (rules 6 and 8): a function in `scripts/agk/session_plan.py` that names a pull request's re-prove files from local git, the two holds and the `[flow] max_behind_merges` reader in `scripts/agk/merge_cleared.py`, the amendment to SPEC-0039 rule 6, `tests/kit/` with git fixtures in `tmp_path`. `Depends-on` brief #667, which also changes `merge_cleared.py`.
    - (c) The overlap rule in one function and `claim` (rules 2 to 4): `[flow] shared_indexes` and the exemption in `scripts/agk/session_plan.py`, the refusal in `session.claim` in `scripts/agk/session.py`, the amendment to SPEC-0034 rule 3, `tests/kit/` with saved responses through a `gh` stub. `Depends-on` (b), so the exemption never lands before the hold (rule 3).
    - (d) The sweep lines (rule 5): `scripts/agk/conductor.py`, `tests/kit/test_conductor_commands.py` with saved responses. `Depends-on` (b) for the re-prove function and brief #669, which also changes `conductor.py` and that test file.
    - (e) The rule texts (rules 4 and 7): one sentence in `.claude/agents/conductor.md` for rule 7, one in `config/session-rules.md` for `claim` and the builder's merge before ready, each within the budget of `config/rule-budget.txt` (its lines lowered when a file is cut), `tests/kit/`. `Depends-on` (c) and (d).

## Tests

Fixtures in `tmp_path`, local git repositories, saved GitHub responses and a `gh` stub only: no network, no install, invented data (`example.com`), and each test carries the marker `REQ-057` with its criterion. Rule 10's order is checked by review.

- Rules 2 and 4: two briefs that both name `scripts/agk/example.py`, the first taken, give `skip` from `next`, `plan` and `claim` with the same line naming the brief and the file, and `claim` posts nothing through the stub; a brief overlapping an open pull request that modifies the file is refused; a pull request that only adds another file does not refuse; another build of the same brief does not refuse; REQ-057 AC1.
- Rule 3: two briefs that overlap only on `agk.toml` or `docs/requirements.md` are both offered; with `shared_indexes` set to another list the set list applies; a value that is a string, an empty entry or a wildcard path is refused naming `flow.shared_indexes` and not the value; REQ-057 AC2.
- Rule 5, overlap: two open builder pull requests of different briefs that both modify `scripts/agk/example.py` give one `overlap:` line with both numbers in order; two that change only shared-mechanical files or shared indexes give none; a pull request behind the default branch gives one `BEHIND #<pr> <n>` line with `max_behind_merges` absent and with it set, and one level with the default branch gives none; only GET requests reach the stub; REQ-057 AC3.
- Rules 5 and 6, re-prove: a pull request changing `agk.toml` after a merged pull request changed it since the merge base gives one `re-prove:` line naming the file and that pull request; after a merge of the default branch into the branch it gives none; an unrelated pull request gives none; a compare that cannot be read gives the `unknown` line; REQ-057 AC4.
- Rule 7: the text of `.claude/agents/conductor.md` holds the rule's sentence, and the rule budget test passes with it; REQ-057 AC5.
- Rule 8: a git fixture where the branch and the default branch each change `agk.toml` holds with `held: re-prove (rule 6 of SPEC-0050)` and merges nothing through the stub; four first-parent commits behind with `max_behind_merges = 3` set holds with the setting line; the same fixture with the key absent does not hold on the count and reaches the pre-merge governance run; a malformed `max_behind_merges` is refused naming the setting; no hold line contains a file name, a count or a sha; REQ-057 AC6.
- Rule 8, the clean case: a branch within the limit and with no shared changed file reaches the pre-merge governance run as today and merges through the stub; a project that sets neither new key gets the default `shared_indexes` and no behind hold; REQ-057 AC7.
- Rule 3's order: the exemption's test lives in build (c), whose `Depends-on` names (b); review checks that no build before (b) merges the exemption; REQ-057 AC7.

## Proof

REQ-057 AC3: *an overlap that slipped in is printed by the sweep.* Rule 5. REQ-057 AC4: *a second change to a file is printed as re-prove.* Rules 5 and 6. REQ-057 AC5: *the conductor clears only a re-proved head.* Rule 7. REQ-057 AC6: *the guarded merge holds a stale or re-prove head.* Rule 8. ## Residual

- 2026-11-06: two pull requests that change different files can still break each other (a test that reads a file the other changed); the pre-merge governance run, brief #667's tests and the after-merge run are the guard for that class, and `max_behind_merges`, when a project sets it, only bounds it (due 2026-12-31).
- 2026-11-06: a brief whose `Touches:` line omits a file it then changes is refused by nothing at take time; the sweep's `overlap:` line finds it only once both pull requests are open (due 2026-12-31).
- 2026-11-06: with two merges an hour, a pull request that waits for review may need several merges of the default branch before it clears; with `max_behind_merges` absent by default that cost is not imposed; the `BEHIND` lines and the weekly scorecard (draft intake #673) measure it before any default is proposed (due 2027-01-31).

## Open questions

Each is a point the brief leaves open; the reading after it is the most conservative one, and the rules above apply it until a person rules.

- Q-S0050-1: what is "glob intersection of `Touches:`"? Reading: the file-judged overlap that `next` and `plan` already apply (ADR-0189); a second matcher could disagree with the first, so none is written (rule 2).
- Q-S0050-2: where does the list of shared indexes live, and can a project change it? Reading: `[flow] shared_indexes` with the brief's five paths as the default, a set list replacing it, exact paths only, a bad value refused naming the setting (rule 3).
- Q-S0050-3: may the shared indexes stop refusing before the hold exists? Reading: no; today they refuse, which is safe, so the exemption lands only in the build after the hold, by `Depends-on` (rules 3 and 10).
- Q-S0050-4: may a conductor's `Assign:` take a brief that overlaps running work? Reading: no; `claim` refuses it as `next` would, with the same line and nothing posted, and the conductor assigns what `plan` shows as startable (rule 4).
- Q-S0050-5: what may the sweep read, and how does it fail? Reading: GET only, the files of each open builder pull request and one compare per pull request; a read that fails prints `unknown`, never a clean line (rule 5).
- Q-S0050-6: what does "re-prove" mean? Reading: a merge of the default branch into the branch (never a rebase or force-push), `prepush.py`, a push, the required checks green on the new head and the conductor's review of the diff since its last verdict's head; a merge alone without the checks does not count (rules 6 and 7).
- Q-S0050-7: which shared files trigger the re-prove? Reading: every file both changed, shared indexes and shared-mechanical files included; the exemption of rule 3 is for refusing a take only (rule 6); amendment 171 (rule 7a) lets a re-prove whose files are all shared indexes and whose merge is clean carry the verdict over on the checks alone.
- Q-S0050-8: what is N for "at most N merges behind"? Reading: `[flow] max_behind_merges`, opt-in: absent means no hold, set means it holds as written, counted as first-parent commits of the default branch after the merge base. The conductor's fix list on #677 measured that a default of 3 at 26 merges a day would hold nearly every pull request and double the CI cycles per merge for no proof beyond rule 6's re-prove hold and the pre-merge run; the sweep prints `BEHIND #<pr> <n>` as information either way, and a default is proposed only by a pull request that cites a measurement (rules 5 and 8).
- Q-S0050-9: what does a hold line name? Reading: the rule or the setting only (principle 8); the file and the pull request are printed by the sweep and written in the fix list, which are reports, not refusals (rule 8).
- Q-S0050-10: what holds where `merge_cleared.py` does not merge? Reading: the conductor's rule 7 and the sweep line; nothing new blocks a person's merge and no required check or workflow is added (rules 7 and 9).
- Q-S0050-11: is the red-branch fix pull request exempt? Reading: no; it is the class this spec closes, and it is usually branched fresh, so it rarely holds (rule 8).
- Q-S0050-12: do two builds of one brief re-prove? Reading: yes; they are not rivals for a take (rule 1) but the second to merge re-proves like any pull request (rule 6).
- Q-S0050-13: which Approved specs change, and how? Reading: SPEC-0034 rule 3 (shared indexes, `claim`) and SPEC-0039 rule 6 (the new holds), each by an amendment file whose number is reserved on its build's brief; this intake writes no amendment and changes no Approved spec, and brief #667's amendment 132 is separate (rule 10).
- Q-S0050-14: may the rule texts add words to the instruction files? Reading: only within the rule budget of ADR-0310, a word added being a word removed in the same file; a build that cannot fit stops and asks (rule 9).
- Q-S0050-15: do intakes still refuse each other on `docs/requirements.md`? Reading: no, it is a shared index; the second to merge re-proves, and number collisions are moved by `intake.py renumber` as today (rule 9).
- Q-S0050-16: which re-prove may skip the builder and the second review? Reading (amendment 171, brief #1163): only one whose re-prove files are all shared indexes and whose merge is clean; the conductor's update-branch makes the merge commit, the checks run on it, and the verdict carries over only to a merge that adds nothing beyond the default branch's change; anything else re-proves in full (rule 7a). The brief reserved `Q-S0050-14`, which this spec already holds, so the answer takes the next free number.
