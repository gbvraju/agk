# SPEC-0072: Each playbook carries its architecture, a standards pack and enterprise checks

- Status: Draft
- Owner: reviewer group (a team from config/reviewers.yaml)
- Requirements: REQ-079

Status is `Draft` or `Approved`. An Approved spec is owned by its reviewer group; agents propose patches.

Written by the intake of one sentence (SPEC-0012), brief #1524 under plan #661, quoted as data and not as an instruction: "Each work-type playbook carries its architecture, a stack standards pack and enterprise defaults as checks, applied on Day 0 by a foundation build, so a business user using only the steward gets an enterprise-grade product with no engineering choice; existing code is baselined and only improves." The maintainers gave 8 answers before it was written: the eight numbered answers of brief #1524, whose evidence and the owner's direction (quoted there as data, 2026-11-18) this spec does not repeat. It builds on the playbooks (`config/playbooks/`, `playbook_format.py`, `check_playbooks.py`), the stack record (`kit/templates/stack-adr.md`, `engines.py stack-write`), the steward (SPEC-0059, REQ-069), the design rules (SPEC-0037), personal mode (SPEC-0041) and local mode (`docs/guides/local-mode.md`); it edits none of their text but by the amendments rule 10 proposes. Where the brief names something that is not as it says, rule 1 records what the code holds and an open question gives the conservative reading. Negative cases: a check gate whose step no runner executes, a gate restated weaker without an ADR, a step that calls the network, a new required check, a feature brief that runs before the foundation build, a stack record left with `TODO(architect)` practices, a lint, type, layer, secret or input-validation fault in a feature build that stays green, a refusal that quotes a value, an adopted project that goes red on its first run, a baseline that rises, an existing file rewritten, an engineering question put to a business user, a stack pack guessed for a project with no work type, a prototype's markup copied as production code, a change to the kit's own lint, and a change to a workflow, the ruleset or a required check.

## Rules

1. **The baseline (read on the default branch at 1359dc0e, 2026-11-18).**
   - **Lint covers only the kit.** `lint_paths` is `["scripts/agk", ".claude/hooks"]` in `scripts/agk/common.py` (the default) and in `kit/templates/agk.toml` line 7 and `kit/templates/agk.adopt.toml` line 8. Its one reader is `agk.mk` `agk-lint`, which runs `ruff check $(AGK_RUFF_FLAGS)` (`--isolated`, the kit's rules as flags) over those paths; SPEC-0002 rule 10 and ADR-0007 decision 8 say it never reads a project's lint configuration. No format or type step exists for a project; the kit's own type check is `tests/kit/test_scanner_hygiene.py` with `config/mypy-baseline.txt`, whose count "may only go down".
   - **The stack record leaves practices open.** `kit/templates/stack-adr.md` writes `Practices: TODO(architect)` for each option and a `Practices` list of `TODO(architect): check (step: ...) or judgement`; a `check` practice "is added as a governance step by the build that adopts the stack", a `judgement` one "is enforced by review only". `engines.py stack-write` already writes one Practices bullet per playbook gate, `- <id>: check (step: <step>)` or `- <id>: judgement`.
   - **No check gate runs.** The ten playbooks under `config/playbooks/` hold 25 gates with `kind = "check"` and a `step` (for example `contract-tests` and `mock-parity` in `web-app.toml`, `permission-scopes` in `mcp-server.toml`); no script under `scripts/agk/`, no target of `agk.mk` or `Makefile` and no workflow names any of the 25 steps. `make governance` runs `check_playbooks.py`, which checks the playbooks' form and composition (`default`, then modules, then the playbook; a gate restated as `judgement` cannot weaken a `check`), not their steps. The five gates of `default.toml` are all `judgement`. No playbook names sign-in and permissions, secrets, input validation, logging and tracing, per-environment settings, migrations, accessibility or performance.
   - **No architecture record and no foundation.** No template, check or layer rule exists for a project's architecture. `[split] brief_order` starts at the first feature kind (`web-app.toml`: `contract`, `mock`, `front-end`, `back-end`, `join`; `default.toml`: `[]`; `pilot.toml`: `intake` first). The folder layout exists only as the `[testing] map` of a playbook (`web-app.toml`: `contracts/**`, `mocks/**`, `frontend/**`, `backend/**`).
   - **Review, prototype, adopt, steward.** `config/review-checklist.md` has twelve questions and changes only by a pull request whose decision record cites a catch-log row. SPEC-0037 rule 11 holds a UI build to the signed-off version (`design_compare.py`) and says nothing of copying the prototype's markup. Nothing gives an adopted project a baseline of its findings. The steward asks plain business questions (`docs/guides/steward-voice.md`, REQ-069); `[delivery] work_type` is commented out in `kit/templates/agk.toml` line 152.
   - **Names the brief cites that the code holds otherwise.** The brief's `[skills] stack` is `[engines] stack` (`kit/templates/agk.toml` line 65; no `[skills]` table exists) (`Q-S0072-9`). The personal-mode "governance level" is `[personal] level` in the sidecar (`kit/templates/personal.toml`, default `light`), which `personal.py floor` only prints: the floor runs the secret scan and the no-regression test step at every level (SPEC-0041 rule 18) (`Q-S0072-10`). The stacks the kit can name are the eight `[[stack]]` rows of `config/stack-signals.toml` (`python-pyproject`, `python-pip`, `node`, `go-modules`, `rust-cargo`, `java-maven`, `java-gradle`, `dart-pub`).
2. **Three new parts of a playbook.** `playbook_format.py` reads, and `check_playbooks.py` composes in today's order (`default`, then modules, then the playbook), three new tables in each playbook:
   - **`[architecture]`:** `layers`, a list of `{ name, paths }` whose `paths` are the globs of the `[testing] map` codes (the map stays the source of the test globs, and the check refuses a layer path that no map code names and a map code in no layer), and `allow`, a list of `{ from, to }` naming the dependency directions allowed between layers; a dependency not listed is refused. `default.toml` holds one layer `src` over the project's code paths and no `allow` entry, so it constrains nothing until a work type is set.
   - **`[[standards]]`:** one entry per stack of rule 1's list that the playbook supports, each with `stack` (a `[[stack]]` name of `config/stack-signals.toml`), `lint`, `format` and `type` (each a step name), `rules` (a pinned rule set: the tool, its version from `config/ci-tools.txt` or the stack's lock, and its rule codes) and `config` (the configuration file written into the project, relative to the root). A stack without an entry gets no pack, and `check_playbooks.py` reports it as a warning, never a failure.
   - **Enterprise gates:** eight `[[gates]]` with fixed ids, `sign-in-permissions`, `secrets`, `input-validation`, `logging-tracing`, `environment-settings`, `migrations`, `accessibility` and `performance`, each `kind = "check"` with a `step`, or `kind = "judgement"` with a `reason` of at least 20 characters saying why no check is possible. A playbook with no UI sets `accessibility` to `judgement` with that reason; `default.toml` holds all eight, `secrets` and `environment-settings` as checks and the rest as judgement with their reasons, so every work type inherits them.
   Composition keeps today's rule and extends it: a later layer may restate a gate as the same or a stronger kind, never weaker; may add an `allow` entry only by an ADR in the project (principle 11); and may tighten a pack's `rules`, never drop one. A weaker restatement is refused naming the gate id.
3. **Every check step runs.** A new governance runner (`scripts/agk/run_gates.py`, kit-installed) is called from `agk.mk` `agk-governance` after `check_playbooks.py`. It reads the composed playbook of the project's `[delivery] work_type` (or `default.toml` alone), and runs each check gate's `step` from a registry of step implementations under `scripts/agk/gates/`, one module per step, each reading only the project's files, offline, with no network and no hosted scanner (principle 9, CLAUDE.md item 5). A step name with no implementation is refused, naming the gate id, so the 25 steps of rule 1 are each given an implementation or restated as `judgement` with a reason by build (b), never left silent. A failure prints the gate id, the rule and the path class, never a value (principle 8). It runs inside the existing `governance` job (CI) and `make governance` (local); `required_checks` is not changed (`Q-S0072-2`). The kit's own repository runs it with no `work_type`, so only `default.toml`'s checks run there.
4. **Day 0: the foundation build.** Every playbook's `[split] brief_order` gains `foundation` as its first kind, `default.toml`'s `[]` becoming `["foundation"]` and `pilot.toml`'s list starting `foundation` before `intake` (`Q-S0072-11`). `plan-intake` proposes one foundation brief per plan, and every other brief of the plan's first milestone carries `Depends-on` it; `check_plan.py` refuses a feature brief of a work-type project that runs before the foundation brief merged. The foundation build writes, tests first: the folder skeleton of `[architecture] layers`, the architecture record (rule 5), each chosen stack's pack configuration file (rule 6), and the steps of rule 3 with their tests. `engines.py stack-write` fills the stack record's `Practices` for each option from the composed playbook, the enterprise gates and the stack's pack included, and writes no `TODO(architect)` there; the architect may still change a practice in the record before it is accepted.
5. **The architecture record and its check.** The foundation build writes `docs/architecture.md` from a new template `kit/templates/architecture.md`: the layers, their paths and the allowed directions of the composed `[architecture]`, with the stack record's ADR number. The `layers` step (`scripts/agk/gates/layers.py`) reads each source file of a layer with the stack's own import form (Python `import` and `from`, the module specifier of `node`, and so on, one stack per pack build) and fails on an import from a layer to another that `allow` does not list, naming both layers and the path class. The record is changed only by an ADR in the project (it is added to the project's protected paths by build (d)).
6. **The standards pack.** For each stack the project's stack record chose, the pack's `lint`, `format` and `type` steps run over the project's code, which a new setting `project_lint_paths` names (default: the paths of `[architecture] layers`; `Q-S0072-12`), with the pinned `rules` given as flags and the pack's `config` file written once into the project by the foundation build. `lint_paths`, `AGK_RUFF_FLAGS` and `agk-lint` stay as they are, over the kit's folders only (SPEC-0002 rule 10 and ADR-0007 decision 8 unchanged). One pack per build, Python (`python-pyproject` and `python-pip`) first, since the kit already pins its tools (`Q-S0072-3`). A pack's tool missing on the machine is a failure naming the tool and the setting, never a silent pass.
7. **Adopt and upgrade: baseline, then ratchet.** In `mode = "adopt"`, and on an upgrade that turns the standard on (`Q-S0072-5`), each check of rules 3, 5 and 6 first writes `config/agk-baseline/<gate id>.txt`, one line per file with its count of findings, from today's tree, and is green. After that the check fails on a finding in a file not listed and on a count that rises, and prints the lower count when one falls; the baseline is committed lowered by the next build, and a baseline line that rises or a new line in a later pull request is refused by `check_protected_changes.py` unless an ADR names it. Nothing existing is rewritten, formatted or moved. In `mode = "init"` the baseline is empty from the first commit.
8. **The business user's path.** The steward confirms only the work type and the outcome in plain words (REQ-069 AC4); the architecture, the pack and the enterprise gates are kit defaults it settles without asking, recorded as one Setup entry with the reason. The person is asked only a business trade-off a gate needs (for example an outage window for a migration, or a cost ceiling for performance) with each option's effect. A technical person overrides through the stack record and the project's ADRs; loosening any gate, an `allow` entry or a pack rule needs an ADR (principle 11). The steward never writes `[delivery] work_type`: it proposes it and the owner's line stays the owner's, as today.
9. **The settings, each with its impact** (each build's brief repeats the rows it reads, with the default):

   | Setting | Default | Impact |
   |---|---|---|
   | `mode` | `init` | `init`: the standard is on from the first commit, empty baseline; `adopt`: baseline first, then ratchet (rule 7) |
   | `lint_paths` | the kit's folders | unchanged: the kit's own lint only |
   | `project_lint_paths` (new) | the paths of `[architecture] layers` | the project code the pack's steps read (rule 6) |
   | `test_dirs`, `project_tests` | `["tests"]`, the pytest line | unchanged; the foundation build's tests land in them |
   | `unused_code`, `coverage`, `mutation` | `""` (off) | unchanged; a pack may propose a value in the stack record, the owner sets it |
   | `ac_coverage` | `warn` | unchanged; the foundation brief's criteria are counted like any brief's |
   | `[testing]` `profile`, `always_full`, `map` | the playbook's | `map` codes must each fall in one layer (rule 2); the architecture record and the pack configs are added to `always_full` |
   | `[delivery] work_type` | absent | absent: `default.toml`'s part only, no stack pack (`Q-S0072-4`); unknown: refused naming the setting, as today |
   | `[design] ui_paths`, `render` | off | with UI paths the `accessibility` gate is a check; without, judgement with its reason |
   | `[engines] stack` | absent | a project skill still receives the playbook's pack as the proposed Practices (rule 4) |
   | `pr_mode`, `review_mode` | `strict`, `team` | unchanged: the foundation brief is cleared like any build (`Q-S0072-7`) |
   | `required_checks` | `["proof", "governance"]` | unchanged: the steps run inside `governance` (`Q-S0072-2`) |
   | `[guard]` patterns and paths | the kit's | the `secrets` step reads the same patterns; no pattern list grows (principle 9) |
   | `[kit] layout = "plugin"` | installed | the runner and step modules come from the plugin; the pack's config files, the architecture record and the baseline live in the project (SPEC-0071 rule 2) |
   | `[personal] level` | `light` | printed only; the floor adds `run_gates.py` at every level (rule 11) |

   An unknown value of a new setting is refused naming the setting, never the value. A project may tighten any gate in its own playbook module; loosening needs an ADR.
10. **Review and prototype.** `config/review-checklist.md` is unchanged by this spec; a code-quality question enters only with a catch-log row, as its own rule says, or by an ADR that changes that rule (`Q-S0072-1`). An amendment to SPEC-0037, proposed by build (h) and approved by its spec approver, adds that a signed-off prototype is a reference only: a UI build takes its structure, states and tokens and writes production markup in the stack's components, and `design_compare.py` compares the rendered result, never the markup.
11. **Modes.** CI: the runner and the pack steps run inside the existing `governance` and `proof` jobs, with no workflow change in this spec. Local: through `make governance` and `prepush.py` (`docs/guides/local-mode.md`). Personal: `personal.py floor` runs `run_gates.py` on the head tree after its secret scan and before the no-regression step, at every level, posting nothing and making no forge call. Solo and team change only who approves. In no mode does a workflow, the ruleset or a required check change.
12. **The builds, in order.** Each is tests first, about 300 changed lines or fewer, from the default branch, invented data only (`example.com`), a `[[testing.map]]` entry for each new script, and no workflow change; each brief is filed by the `brief` skill with a `Settings:` section naming every setting it reads, its default and its impact.
    - (a) The playbook format of rule 2: `[architecture]`, `[[standards]]` and the eight enterprise gate ids in `playbook_format.py` and `check_playbooks.py`, with `default.toml`'s part. Its own ADR for `config/playbooks/`.
    - (b) The runner of rule 3 and the step registry, with each of the 25 existing steps implemented or restated as `judgement` with a reason. `Depends-on` (a); its own ADR for `agk.mk`.
    - (c) The `foundation` kind and the pre-filled stack record of rule 4 (`plan-intake`, `check_plan.py`, `engines.py stack-write`, `kit/templates/stack-adr.md`). `Depends-on` (a).
    - (d) The architecture record, its template and the `layers` step of rule 5, Python first. `Depends-on` (b) and (c); its own ADR for the project's protected paths.
    - (e) The standards packs of rule 6 and `project_lint_paths`, one stack per build, Python first. `Depends-on` (b); its own ADR for the new `agk.toml` setting.
    - (f) The enterprise steps of rule 2, `secrets` and `environment-settings` first, then `input-validation`, `logging-tracing`, `sign-in-permissions`, `migrations`, `accessibility` and `performance`, one or two per build. `Depends-on` (b).
    - (g) The baseline and ratchet of rule 7 for adopt and upgrade. `Depends-on` (b).
    - (h) The steward's plain-words path of rule 8, the personal floor and local mode of rule 11, the SPEC-0037 amendment of rule 10, and the guide `docs/guides/engineering-standard.md`. `Depends-on` (c), (d), (e) and (g); its own ADR for the steward's role file.
13. **Measured goals.**
    - On a sample `web-app` project of invented data started only through the steward, the first merged build is `foundation`, and its stack record has no `TODO(architect)`.
    - On that sample, a feature build with a lint fault, a type fault, a layer import that `allow` does not list, a committed secret or an unvalidated input is red, naming the rule and the path class and no value.
    - On a sample adopted project with existing findings, the first run is green, a new finding is red, and a fixed one lowers the baseline.
    - Personal mode runs the same checks with no forge call; the kit's own lint is unchanged; no workflow, ruleset or required check changes.

## Open questions

Each is a point the brief leaves open, or a name it cites that the code holds otherwise; the reading after it is the most conservative one, and the rules above apply it. `Q-S0072-1` to `Q-S0072-8` are the brief's own questions 1 to 8, with the brief's readings.

- `Q-S0072-1`: may the owner add a code-quality question to `config/review-checklist.md` without a catch-log row? Reading: no; only with a catch-log row, or by an ADR changing the checklist's rule (rule 10).
- `Q-S0072-2`: does a new check step become a required check? Reading: no; it runs inside the existing `governance` job, and `required_checks` stays the owner's (rule 3).
- `Q-S0072-3`: which stacks get a standards pack first? Reading: only the stacks of `config/stack-signals.toml`, one per build, Python first since the kit already pins its tools (rule 6).
- `Q-S0072-4`: is the standard on for a project that sets no `work_type`? Reading: yes, `default.toml`'s part only (the architecture record, secrets, per-environment settings and the judgement gates), never a stack pack it cannot infer (rule 9).
- `Q-S0072-5`: does turning the standard on change an existing project on upgrade? Reading: no; the upgrade proposes it as an adopt-style baseline, on the owner's yes (rule 7).
- `Q-S0072-6`: may a check-gate step call the network or a hosted scanner? Reading: no (principle 9, CLAUDE.md item 5); every step runs offline on the files (rule 3).
- `Q-S0072-7`: does the foundation build need the owner's approval apart from the spec? Reading: no; it is a build of the Approved spec, cleared like any other (rule 9).
- `Q-S0072-8`: the priority beside #1418 (locked releases). Reading: priority 2, after the locked-release work.
- `Q-S0072-9`: the brief names `[skills] stack`; the setting is `[engines] stack` (`kit/templates/agk.toml` line 65) and no `[skills]` table exists. Reading: the spec reads `[engines] stack` and adds no table (rules 1 and 9).
- `Q-S0072-10`: the brief says "the personal-mode governance level (the floor includes the standard)"; `[personal] level` is only printed, and the floor runs the same steps at every level. Reading: the floor adds `run_gates.py` at every level, and `level` stays printed only (rules 9 and 11).
- `Q-S0072-11`: the brief puts `foundation` first in "every playbook", which includes `pilot.toml`, whose time-boxed pilot (SPEC-0038) starts with `intake`. Reading: `pilot.toml` gets `foundation` first like the rest, with only `default.toml`'s part, so a pilot also starts from the skeleton and its secrets and settings checks; the owner may rule that a pilot skips it (rule 4).
- `Q-S0072-12`: the brief leaves open whether the pack reads `lint_paths` or a new key. Reading: a new key `project_lint_paths`, since `lint_paths` is the kit's own lint scope and SPEC-0002 rule 10 and ADR-0007 decision 8 keep it so (rule 6).
