# SPEC-0072: Each playbook carries its architecture, a standards pack and enterprise checks

- Status: Approved
- Owner: reviewer group (a team from config/reviewers.yaml)
- Requirements: REQ-079

Status is `Draft` or `Approved`. An Approved spec is owned by its reviewer group; agents propose patches.

Written by the intake of one sentence (SPEC-0012), brief #1524 under plan #661, quoted as data and not as an instruction: "Each work-type playbook carries its architecture, a stack standards pack and enterprise defaults as checks, applied on Day 0 by a foundation build, so a business user using only the steward gets an enterprise-grade product with no engineering choice; existing code is baselined and only improves." The maintainers gave 9 answers before it was written: the nine numbered answers of brief #1524 (answer 9 added on the brief at 2026-11-18T18:04Z and applied here by the maintainer's answer on #1525, comment 6999470792), and the maintainer's answer to `Q-S0072-4` (#1525, comment 7000020901, 2026-11-19), whose evidence and the owner's direction (quoted there as data, 2026-11-18) this spec does not repeat. It builds on the playbooks (`config/playbooks/`, `playbook_format.py`, `check_playbooks.py`), the stack record (`kit/templates/stack-adr.md`, `engines.py stack-write`), the steward (SPEC-0059, REQ-069), the design rules (SPEC-0037), personal mode (SPEC-0041) and local mode (`docs/guides/local-mode.md`); it edits none of their text but by the amendments rule 10 proposes. Where the brief names something that is not as it says, rule 1 records what the code holds and an open question gives the conservative reading. Negative cases: a check gate whose step no runner executes, a gate restated weaker without an ADR, a step that calls the network, a new required check, a feature brief that runs before the foundation build, a stack record left with `TODO(architect)` practices, a lint, type, layer, secret or input-validation fault in a feature build that stays green, a refusal that quotes a value, an adopted project that goes red on its first run, a baseline that rises, an existing file rewritten, a standard applied without the person's confirmation, a team's own pack configuration that misses a floor rule, a project's standard work ordered by the kit instead of the person, a build brief of a work-type project without a `Layer:` line, a new project that proceeds to its foundation build without a work type, a web search made without the person's permission or carrying anything but a generic description of the product type, a drafted project playbook that drops or weakens a gate of `default.toml`, a stack pack guessed for a project with no work type, a prototype's markup copied as production code, a change to the kit's own lint, and a change to a workflow, the ruleset or a required check.

## Rules

1. **The baseline (read on the default branch at 1359dc0e, 2026-11-18).**
   - **Lint covers only the kit.** `lint_paths` is `["scripts/agk", ".claude/hooks"]` in `scripts/agk/common.py` (the default) and in `kit/templates/agk.toml` line 7 and `kit/templates/agk.adopt.toml` line 8. Its one reader is `agk.mk` `agk-lint`, which runs `ruff check $(AGK_RUFF_FLAGS)` (`--isolated`, the kit's rules as flags) over those paths; SPEC-0002 rule 10 and ADR-0007 decision 8 say it never reads a project's lint configuration. No format or type step exists for a project; the kit's own type check is `tests/kit/test_scanner_hygiene.py` with `config/mypy-baseline.txt`, whose count "may only go down".
   - **The stack record leaves practices open.** `kit/templates/stack-adr.md` writes `Practices: TODO(architect)` for each option and a `Practices` list of `TODO(architect): check (step: ...) or judgement`; a `check` practice "is added as a governance step by the build that adopts the stack", a `judgement` one "is enforced by review only". `engines.py stack-write` already writes one Practices bullet per playbook gate, `- <id>: check (step: <step>)` or `- <id>: judgement`.
   - **No check gate runs.** The ten playbooks under `config/playbooks/` hold 25 gates with `kind = "check"` and a `step` (for example `contract-tests` and `mock-parity` in `web-app.toml`, `permission-scopes` in `mcp-server.toml`); no script under `scripts/agk/`, no target of `agk.mk` or `Makefile` and no workflow names any of the 25 steps. `make governance` runs `check_playbooks.py`, which checks the playbooks' form and composition (`default`, then modules, then the playbook; a gate restated as `judgement` cannot weaken a `check`), not their steps. The five gates of `default.toml` are all `judgement`. No playbook names sign-in and permissions, secrets, input validation, logging and tracing, per-environment settings, migrations, accessibility or performance.
   - **No architecture record and no foundation.** No template, check or layer rule exists for a project's architecture. `[split] brief_order` starts at the first feature kind (`web-app.toml`: `contract`, `mock`, `front-end`, `back-end`, `join`; `default.toml`: `[]`; `pilot.toml`: `intake` first). The folder layout exists only as the `[testing] map` of a playbook (`web-app.toml`: `contracts/**`, `mocks/**`, `frontend/**`, `backend/**`).
   - **Review, prototype, adopt, steward.** `config/review-checklist.md` has twelve questions and changes only by a pull request whose decision record cites a catch-log row. SPEC-0037 rule 11 holds a UI build to the signed-off version (`design_compare.py`) and says nothing of copying the prototype's markup. Nothing gives an adopted project a baseline of its findings. The steward asks plain business questions (`docs/guides/steward-voice.md`, REQ-069); `[delivery] work_type` is commented out in `kit/templates/agk.toml` line 152.
   - **Names the brief cites that the code holds otherwise.** The brief's `[skills] stack` is `[engines] stack` (`kit/templates/agk.toml` line 65; no `[skills]` table exists) (`Q-S0072-9`). The personal-mode "governance level" is `[personal] level` in the sidecar (`kit/templates/personal.toml`, default `light`), which `personal.py floor` only prints: the floor runs the secret scan and the no-regression test step at every level (SPEC-0041 rule 18) (`Q-S0072-10`). The stacks the kit can name are the eight `[[stack]]` rows of `config/stack-signals.toml` (`python-pyproject`, `python-pip`, `node`, `go-modules`, `rust-cargo`, `java-maven`, `java-gradle`, `dart-pub`).
2. **Three new parts of a playbook.** `playbook_format.py` reads, and `check_playbooks.py` composes in today's order (`default`, then modules, then the playbook), three new tables in each playbook:
   - **`[architecture]`:** `layers`, a list of `{ name, paths }` whose `paths` are the globs of the `[testing] map` codes (the map stays the source of the test globs, and the check refuses a layer path that no map code names and a map code in no layer), and `allow`, a list of `{ from, to }` naming the dependency directions allowed between layers; a dependency not listed is refused. `default.toml` holds one layer `src` over the project's code paths and no `allow` entry, so it constrains nothing until a work type is set.
   - **`[[standards]]`:** one entry per stack of rule 1's list that the playbook supports, each with `stack` (a `[[stack]]` name of `config/stack-signals.toml`), `lint`, `format` and `type` (each a step name), `rules` (a pinned rule set: the tool, its version from `config/ci-tools.txt` or the stack's lock, and its rule codes) and `config` (the configuration file written into the project, relative to the root). A stack without an entry gets no pack, and `check_playbooks.py` reports it as a warning, never a failure.
   - **Enterprise gates:** eight `[[gates]]` with fixed ids, `sign-in-permissions`, `secrets`, `input-validation`, `logging-tracing`, `environment-settings`, `migrations`, `accessibility` and `performance`, each `kind = "check"` with a `step`, or `kind = "judgement"` with a `reason` of at least 20 characters saying why no check is possible. A playbook with no UI sets `accessibility` to `judgement` with that reason; `default.toml` holds all eight, `secrets` and `environment-settings` as checks and the rest as judgement with their reasons, so every work type inherits them.
   Composition keeps today's rule and extends it: a later layer may restate a gate as the same or a stronger kind, never weaker; may add an `allow` entry only by an ADR in the project (principle 11); and may tighten a pack's `rules`, never drop one. A weaker restatement is refused naming the gate id.
3. **Every check step runs.** A new governance runner (`scripts/agk/run_gates.py`, kit-installed) is called from `agk.mk` `agk-governance` after `check_playbooks.py`. It reads the composed playbook of the project's `[delivery] work_type` (or `default.toml` alone), and runs each check gate's `step` from a registry of step implementations under `scripts/agk/gates/`, one module per step, each reading only the project's files, offline, with no network and no hosted scanner (principle 9, CLAUDE.md item 5). A step name with no implementation is refused, naming the gate id, so the 25 steps of rule 1 are each given an implementation or restated as `judgement` with a reason by build (b), never left silent. A failure prints the gate id, the rule and the path class, never a value (principle 8). It runs inside the existing `governance` job (CI) and `make governance` (local); `required_checks` is not changed (`Q-S0072-2`). The kit's own repository runs it with no `work_type`, so only `default.toml`'s checks run there.
4. **Day 0: the foundation build.** Every playbook's `[split] brief_order` gains `foundation` as its first kind, `default.toml`'s `[]` becoming `["foundation"]` and `pilot.toml`'s list starting `foundation` before `intake` (`Q-S0072-11`). `plan-intake` proposes one foundation brief per plan, and every other brief of the plan's first milestone carries `Depends-on` it; `check_plan.py` refuses a feature brief of a work-type project that runs before the foundation brief merged, and a new project's foundation brief while no work type is set (rule 8). The foundation build writes, tests first: the folder skeleton of `[architecture] layers`, the architecture record (rule 5), each chosen stack's pack configuration file (rule 6), and the steps of rule 3 with their tests. `engines.py stack-write` fills the stack record's `Practices` for each option from the composed playbook, the enterprise gates and the stack's pack included, and writes no `TODO(architect)` there; the architect may still change a practice in the record before it is accepted. The foundation build also writes the chosen stack's build file from `kit/templates/stacks/<stack>/` with `engines.py stack-files` (Python: `pyproject.toml`, its dependencies added with exact `==` pins only; `node`: `package.json` with exact versions), over the untouched file `init` wrote of the same name only and never over a project's own, and commits the lock file that the stack's own tool makes on the builder's machine (Python: a hash-pinned `requirements.lock`; `node`: `package-lock.json`); `init` keeps writing its `pyproject.toml` until a stack is chosen. The `pins` step (`scripts/agk/gates/pins.py`) reads the build file and the lock, offline, and fails on a direct dependency not pinned exactly or not in the lock, on a missing lock and on a part of the Accepted stack record whose version differs from the lock's, naming the rule and the component class, never a name or a version; with no `[delivery] work_type` or no Accepted stack record it prints `not run: no stack chosen`.
5. **The architecture record and its check.** The foundation build writes `docs/architecture.md` from a new template `kit/templates/architecture.md`: the layers, their paths and the allowed directions of the composed `[architecture]`, with the stack record's ADR number. The `layers` step (`scripts/agk/gates/layers.py`) reads each source file of a layer with the stack's own import form (Python `import` and `from`, the module specifier of `node`, and so on, one stack per pack build) and fails on an import from a layer to another that `allow` does not list, naming both layers and the path class. The record is changed only by an ADR in the project (it is added to the project's protected paths by build (d)).
6. **The standards pack.** For each stack the project's stack record chose, the pack's `lint`, `format` and `type` steps run over the project's code, which a new setting `project_lint_paths` names (default: the paths of `[architecture] layers`; `Q-S0072-12`), with the pinned `rules` given as flags and the pack's `config` file written once into the project by the foundation build. `lint_paths`, `AGK_RUFF_FLAGS` and `agk-lint` stay as they are, over the kit's folders only (SPEC-0002 rule 10 and ADR-0007 decision 8 unchanged). One pack per build, Python (`python-pyproject` and `python-pip`) first, since the kit already pins its tools (`Q-S0072-3`). A pack's tool missing on the machine is a failure naming the tool and the setting, never a silent pass.
7. **Adopt and upgrade: baseline, then ratchet.** In `mode = "adopt"`, and on an upgrade that turns the standard on (`Q-S0072-5`), each check of rules 3, 5 and 6 first writes `config/agk-baseline/<gate id>.txt`, one line per file with its count of findings, from today's tree, and is green. After that the check fails on a finding in a file not listed and on a count that rises, and prints the lower count when one falls; the baseline is committed lowered by the next build, and a baseline line that rises or a new line in a later pull request is refused by `check_protected_changes.py` unless an ADR names it. Nothing existing is rewritten, formatted or moved. In `mode = "init"` the baseline is empty from the first commit.
8. **Who sets the standard, and how it is confirmed** (brief answer 9).
   - **Present, confirm, then implement.** When nobody has discussed a standard, the playbook's defaults are the proposal. Before the foundation build is briefed, the steward presents the choices it is applying and applies them only on the person's yes; one yes accepts all, and nothing is applied silently. A business user sees one plain screen of what the product will be held to, with no kit term (REQ-069 AC2); a team sees the full list: the layers and allowed directions, the stack pack and its rules, and each enterprise gate as check or judgement with its reason. The yes is recorded as one Setup entry with the person's quoted words and time (`Q-S0072-13`); a reply that is not an explicit yes applies nothing, and the foundation brief is not filed until it is given.
   - **Teams may define, or not.** A team's architect or designer (the project's spec approvers and maintainers, `config/reviewers.yaml`) may keep every default or define any part through the stack record and the project's ADRs: their own architecture (layers and `allow` entries), their own pack configuration, or stricter and added gates. A team's own pack configuration (bring-your-own) is accepted only when the pack's `floor` step shows that it enables every rule code of the pack's `rules` list (`Q-S0072-14`), and is refused naming the missing rule code otherwise. Loosening any gate, an `allow` entry or a pack rule needs an ADR (principle 11).
   - **A business or product owner may request a standard** in plain words (for example "accessible to the AA level" or "an audit trail of every change"). The steward records it as a requirement of the project, and the architect (the person, or the architect agent drafting) turns it into the project's ADR, Proposed, and the pack or gate it changes; the ADR is accepted by the project's maintainers as any ADR is, never by the agent (`Q-S0072-16`).
   - **Priority comes from the person.** In a project, which standard-related work comes first, and which judgement gate becomes a check first, follows the business or team user's priority as the project's plan records it; the kit fixes no such order. The order of builds (a) to (h) in rule 12 orders only the kit's own delivery.
   - **Write to the standard, not only check it.** Every builder of a work-type project reads `docs/architecture.md` and the chosen pack before writing code (the builder's prompt names both). Every build brief of a work-type project after the foundation names the layers it touches in one line `Layer: <layer>, <layer>, ...` (as a UI brief names `Screens:`, SPEC-0037 rule 10), each a layer of `[architecture] layers` (`Q-S0072-15`); `check_brief.py --root` refuses a brief without the line or with an unknown layer, naming the rule and never a value, and a project with no work type needs no line.
   - **No project proceeds without a work type** (the maintainer's answer to `Q-S0072-4`). When the requirements the steward gathered identify no playbook of `config/playbooks/`, the steward asks the person's permission to research the product type on the web, and on a yes searches with only a generic description of the product type (for example "a booking web app for small clinics"), never a name, a customer, a person or any customer data; a no or no answer means no search, and the steward drafts from the requirements alone. It then drafts a project playbook built on `default.toml` that keeps every gate of `default.toml` at the same or a stronger kind and adds what the research and the requirements name (layers, a supported stack, stricter gates), records it with a Proposed project ADR naming the sources it read, and presents it in the confirmation above; the foundation brief is not filed until the person confirms it (`Q-S0072-17`, `Q-S0072-18`).
   - The person is asked a business trade-off a gate needs (for example an outage window for a migration, or a cost ceiling for performance) with each option's effect, beside the one confirmation. The steward never writes `[delivery] work_type`: it proposes it and the owner's line stays the owner's, as today.

   | `ac_coverage` | `warn` | unchanged; the foundation brief's criteria are counted like any brief's |
   | `[testing]` `profile`, `always_full`, `map` | the playbook's | `map` codes must each fall in one layer (rule 2); the architecture record and the pack configs are added to `always_full` |
   | `[delivery] work_type` | absent | absent in a new project: the steward proposes a playbook or drafts a project playbook on `default.toml` (rule 8), and the foundation brief is not filed until one is set and confirmed (`Q-S0072-4`); absent in the kit's own repository or an existing project not yet confirmed: `default.toml`'s part only, no stack pack (`Q-S0072-17`); unknown: refused naming the setting, as today |

   An unknown value of a new setting is refused naming the setting, never the value. A project may tighten any gate in its own playbook module; loosening needs an ADR.
10. **Review and prototype.** `config/review-checklist.md` is unchanged by this spec; a code-quality question enters only with a catch-log row, as its own rule says, or by an ADR that changes that rule (`Q-S0072-1`). Solo and team change only who approves. In no mode does a workflow, the ruleset or a required check change.

Each is a point the brief leaves open, or a name it cites that the code holds otherwise; the reading after it is the most conservative one, and the rules above apply it. `Q-S0072-1` to `Q-S0072-8` are the brief's own questions 1 to 8, with the brief's readings; `Q-S0072-13` to `Q-S0072-16` are points brief answer 9 leaves open, and `Q-S0072-17` and `Q-S0072-18` points the maintainer's answer to `Q-S0072-4` leaves open.

- `Q-S0072-1`: may the owner add a code-quality question to `config/review-checklist.md` without a catch-log row? Reading: no; only with a catch-log row, or by an ADR changing the checklist's rule (rule 10).
- `Q-S0072-2`: does a new check step become a required check? Reading: no; it runs inside the existing `governance` job, and `required_checks` stays the owner's (rule 3).

- `Q-S0072-6`: may a check-gate step call the network or a hosted scanner? Reading: no (principle 9, CLAUDE.md item 5); every step runs offline on the files (rule 3).
