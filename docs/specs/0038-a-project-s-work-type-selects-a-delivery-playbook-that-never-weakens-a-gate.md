# SPEC-0038: A project's work type selects a delivery playbook that makes delivery faster and never weakens a gate

- Status: Draft
- Owner: reviewer group (a team from config/reviewers.yaml)
- Requirements: REQ-045

Status is `Draft` or `Approved`. An Approved spec is owned by its reviewer group; agents propose patches.
Written by the intake of one sentence (SPEC-0012): "A project declares its work type and the kit applies that type's delivery playbook, so each kind of work (web, mobile, cloud migration, RAG, MCP, multi-agent, voice) is built along its fastest proven path while every governance gate stays as it is." It is generic and project-agnostic: it names no project, no vendor, no framework and no hosting service, and it needs only files and a shell; every check reads files with no network. The plan is issue #499 and the brief is issue #500. The maintainers gave 5 answers before it was written: the five numbered answers of brief #500 (the requirement and its six criteria, this spec and its proposed gates per work type, ADR-0251 and one row of `docs/runs/decisions-log.md` for the owner's direction, the open points as questions, and documents only), under the brief's principles: a playbook is data, not code; it can make delivery faster and never removes or weakens a gate, only adds gates of its work type; the owner chooses the work type and a session never does; every speed claim is `measured` with its record or `expected`; checks run with no network and refusals name the rule and the file, never a value. The points the brief leaves open are `Q-S0038-1` to `Q-S0038-12` below, each with the conservative reading that the rules apply until a person rules. Today the kit runs one flow for every project (vision, spec, design, stack ADR, briefs, builders, verdicts), and the only place the kind of work shows up is the stack ADR of `/agk:stack`; in the pilot's Phase 2 a hand-designed strategy (contract-first front end and back end with mocks, a per-module `[testing]` map, milestone pull requests, lock slots, joins ordered by demo value) cut the critical path, and nothing in the kit chose it. Negative cases: a playbook with a missing or unknown section, an unknown work type, a speed claim with neither basis, a `measured` claim whose record file is missing, a gate removed, skipped or relaxed, a `fast` testing profile, `pr_tests = "selected"` or a governance setting named as a setting (a backticked token or `<setting> =`) all fail, while the same word in plain English passes naming the rule and the file; an unknown `work_type` fails naming the setting; with no declaration nothing changes; no session ever writes the declaration, and a lane never lets two overlapping briefs run together.

## Rules

1. **A playbook is data.** A playbook is one TOML file per work type, `config/playbooks/<work type>.toml`, read with the standard library's `tomllib` (`Q-S0038-5`, `Q-S0038-6`). It holds no code, no command to run, no URL, no project name, no vendor or framework name and only invented data (addresses at `example.com`). The work types are a fixed list, `web-app`, `mobile`, `cloud-migration`, `rag-app`, `mcp-server`, `multi-agent` and `voice-agent`, and the file's name and its `work_type` key are the same one of them. The kit ships each playbook verbatim (listed in `verbatim` of `kit/manifest.json`), so a project gets every shipped playbook unchanged by an install or an upgrade, and the installer's hashes hold it unchanged; a project adds gates of its own as practices of its stack ADR (rule 6), never by editing a playbook.
2. **The format.** A playbook has `format = 1`, `work_type`, `title` (one plain line) and exactly these sections, each required, and no other key: `[[phases]]` (`name`, `order`, an integer from 1, and `after`, the names of the phases it follows), `[split]` (`brief_order`, the kinds of brief in the order they are filed, and `depends_on`, a list of `[later, earlier]` kind pairs), `[[lanes]]` (`name`, `kinds`, the brief kinds that run in that lane), `[testing]` (`profile`, `always_full`, a list of path globs, and `map`, a list of `{ code, tests }` suggestions), `heavy_steps` (the names of the steps that run under the heavy-step lock), `[[gates]]` (`id`, `kind` = `check` or `judgement`, `text`, `step` for a check, the governance step the adopting build adds, and `owner_only`, `true` for an action only the owner takes), `evidence` (the items a verdict cites), `[milestones]` (`shape`, one of `per-brief`, `per-phase` or `per-batch`, and `batch_by`, a plain line), and `[[claims]]` (`text`, `basis` = `measured` or `expected`, and, for `measured`, `record`, a repository path of a run record). `check_playbooks.py` (rule 4) fails a file with a missing section or key, an unknown one, a value of the wrong type, a `work_type` outside the list of rule 1 or not the file's name, a phase whose `after` names an unknown phase or makes a cycle, a lane or split kind not in `brief_order`, a gate without `kind`, or a check gate without `step`, naming the rule and the file and never the value.
3. **Speed claims.** Every claim of a playbook is `measured` or `expected`. A `measured` claim names in `record` a file under `docs/runs/` of the repository that holds it, and `check_playbooks.py` fails a `measured` claim whose record file is not there, or a claim with neither basis, naming the rule and the file (`Q-S0038-3`). The check reads only that the file exists, never what it says: whether the record supports the claim is the review of the pull request that adds it. Nothing in the kit presents an `expected` claim as proven: a reader that prints a claim prints its basis with it.
4. **A playbook only adds gates.** A playbook can change the order of work, its lanes, the tests it suggests, the batching and the milestone shape, and it can add gates of its work type; it never removes, skips or relaxes a gate. `check_playbooks.py` fails a playbook, naming the rule and the file, that: has any key outside the format of rule 2 (so no key can name a governance step to skip); sets `[testing] profile = "fast"` (an unmapped file only listed, not run) or a `pr_tests` key; names as a setting, in any of its values, a setting of `agk.toml` that governs a gate (`required_checks`, `ac_coverage`, `review_mode`, `pr_mode`, `agent_apps`, `paused`, `execution`, `pr_tests`), or a principle or a session rule to set aside, where a setting counts as named only in a backticked token (`` `pr_tests` ``) or in the form `<setting> =` or `<setting>:`, so that the same word in plain English ("test execution under the lock", "a paused pipeline") is never refused; or marks as `owner_only = false` a gate whose text names signing, an apply of infrastructure, a release or a secret. A gate's `owner_only = true` means a session never takes that action: it prepares the evidence and stops (session rule 2). The step is added to `agk-governance` in `agk.mk`, after `check_design.py`, and it checks the declaration of rule 5 as well.
5. **The declaration.** A project declares its work type with one line in the `[delivery]` table of `agk.toml`: `work_type = "<work type>"`, one value from the list of rule 1 that names a playbook present under `config/playbooks/` (`Q-S0038-1`). `agk.toml` is a protected path, so the line lands only with an ADR in the same pull request, and that ADR is the owner's choice. A session may propose a work type, in the stack ADR's context or in a `Question:`, and never writes, changes or removes the line itself (`CLAUDE.md item 1`). `check_playbooks.py` and `doctor.py` fail an unknown value, or one whose playbook is missing, naming the setting `work_type` and never its value. With no `[delivery]` table, or no `work_type` in it, no command reads a playbook and every command prints and writes exactly what it prints and writes today; `doctor.py` prints one line `work type: none (no playbook)`. A change of the line follows `Q-S0038-2`.
6. **Where `/agk:stack` reads the playbook.** With a declared work type, `engines.py stack-write` writes into the stack ADR's skeleton one **Practices** bullet for each gate of the playbook, `- <id>: check (step: <step>)` or `- <id>: judgement`, marked `(playbook <work type>)`, beside the practices the options name, and writes the playbook's `[testing]` profile, `always_full` and `map` suggestions into the parenthesis of the `test selection` practice for each option. They are proposals: the architect chooses as today, and the `[testing]` table of `agk.toml` changes only by the existing step after **Chosen** (`skills/stack/SKILL.md`), never by a reader of the playbook. A project adds a gate of its own as one more practice bullet there, never by editing the playbook. Without a declaration the skeleton is the same as today.
7. **Where `/agk:brief` reads the playbook (the split and the milestone shape).** With a declared work type, `playbook.py split` prints, for the owner and the session filling briefs, the proposed brief kinds in `brief_order`, each later kind with the `Depends-on:` line its `depends_on` pairs give, and the milestone shape (`per-brief`: one pull request per brief, as today; `per-phase` and `per-batch`: the briefs of a phase or a batch are numbered as one milestone in their titles). It prints and writes no file; `skills/brief/SKILL.md` tells the session to show it before filling a brief, and the maintainers still decide each brief's content. A milestone shape never puts two items in one pull request (CLAUDE.md item 2): a milestone groups pull requests, it never merges them.
8. **Where `session.py plan` reads the playbook (the lanes).** With a declared work type, the plan names, for each ready brief, its lane: the lane whose `kinds` hold the brief's `Kind:` line, or `lane: none` for a brief without one (`Q-S0038-8`). The lane only labels and orders the ready briefs (within the same priority, the earlier phase first); waves, capacity, the merge queue and the safe merge set are decided as SPEC-0034 rule 15 decides them, so a lane never lets two briefs whose files overlap run together. The plan prints the playbook's `heavy_steps` once, as the steps a builder runs under `lock.py run --name heavy` (session rule 30); it changes neither `lock_slots` nor any lock setting. Without a declaration the plan prints exactly what it prints today.
9. **The evidence a verdict cites.** With a declared work type, the conductor's role file (`.claude/agents/conductor.md`) says that a clearing verdict on a pull request of that project names, in one `Playbook evidence:` line, each `evidence` item of the playbook that applies to the brief, with where it was read, or `not applicable: <reason>`; and that a missing judgement gate is a fix item, never a clearing verdict. `check_pr_body.py`, `proof.py` and the CI proof job do not change: the conductor reads the line (`Q-S0038-10`).
10. **The gates proposed per work type.** Each gate below is marked `check` (a governance step can verify it from committed files with no network) or `judgement` (recorded, and read by the conductor and the owner), the way `/agk:stack` marks practices (`Q-S0038-4`). A gate that needs a browser, a device, a cloud account, a model or a network to decide is `judgement` with its evidence file as the check.
    - **web-app:** contract tests, `check` (the `[testing]` map names a test glob for every contract path); a mock parity check, `check` (the mock names exactly the operations of the contract file); an e2e smoke run per merge batch, `judgement` (its run record is evidence); accessibility, `judgement` (with SPEC-0037's checks where a prototype exists).
    - **mobile:** a device and simulator matrix, `check` (the matrix file lists the playbook's minimum entries) with its results `judgement`; offline states, `check` (each screen of the inventory lists an `offline` state); store signing, `judgement` and `owner_only`.
    - **cloud-migration:** inventory, then wave plan, then cut-over, `check` (each cut-over brief depends on its wave plan brief, which depends on the inventory brief); a rollback rehearsal as evidence, `judgement`; plan diffs as evidence, `judgement` (a committed plan output with no secret, session rule 2); any apply, `judgement` and `owner_only`.
    - **rag-app:** a versioned evaluation set, `check` (the set's file has a version line and invented data only); a quality bar for retrieval and for answers, `check` that both bars are declared as numbers and `judgement` that the recorded run meets them; prompt and model version pinning, `check` (the pin file names exact versions and no floating alias); a privacy review of the corpus, `judgement`.
    - **mcp-server:** tool schema contract tests, `check` (the `[testing]` map names a test glob for every schema file); permission scopes, `check` (every tool declares its scopes and none is a wildcard); a prompt-injection test set, `check` (the set exists and the map names its tests).
    - **multi-agent:** role and handoff contracts, `check` (a contract file for each role and handoff, with tests mapped); trace-based evaluation, `judgement`; cost and latency budgets, `check` that they are declared as numbers and `judgement` that a recorded run meets them.
    - **voice-agent:** a latency budget, `check` that it is declared and `judgement` that a recorded run meets it; an ASR/TTS evaluation set, `check` (the set exists with a version line); barge-in and fallback scenarios, `check` (each scenario is listed and the map names its tests).
11. **The first two playbooks.** `config/playbooks/web-app.toml` comes from the pilot's Phase 2 strategy: phases `contract`, then `mocks`, then `front-end` and `back-end` in two parallel lanes, then `joins` ordered by demo value; `[testing]` profile `balanced` with a per-module `map` suggestion and `always_full` for the contract folder; the e2e smoke run as a heavy step; milestone shape `per-batch`, batched by demo value; and the web-app gates of rule 10. Its speed claims are `expected` until the Phase 2 record is a file under `docs/runs/` of this repository, then `measured` with that path (`Q-S0038-3`). The pilot's data is private, so such a record is anonymised: it holds only timings, counts and the strategy's shape, and no project name, no organisation, no people, no screen or feature names and no data from the pilot, and it uses invented names only (`example.com`); the review of the pull request that adds it checks this. `config/playbooks/rag-app.toml` has phases `corpus` (with the privacy review), `evaluation set`, `retrieval`, `answers` and `joins`; the evaluation set before any retrieval or answer brief; the evaluation run as a heavy step; the rag-app gates of rule 10; and only `expected` claims, since no run has measured it. Both use invented data only.
12. **The builds, in order.** After this intake, the conductor splits #499 into these builds, each of about 600 changed lines of code and tests or fewer, each from the default branch with its own ADR naming the protected classes it changes and citing ADR-0251, and one fragment under `changelog.d/` where it changes a file the installer writes (SPEC-0031). A `Depends-on` is declared for a shared file and for a logical dependence alike; builds with neither run in parallel.
    - (a) **The format and its check** (rules 1 to 4): `scripts/agk/playbook.py` (new, installed: reading and checking a playbook), `scripts/agk/check_playbooks.py` (new, installed), `agk.mk` (one line in `agk-governance`), `kit/manifest.json`, `tests/kit/test_check_playbooks.py`. No dependence.
    - (b) **The declaration** (rule 5): `scripts/agk/playbook.py` (reading `[delivery]`), `scripts/agk/check_playbooks.py`, `scripts/agk/doctor.py`, `kit/templates/agk.toml` (the commented `[delivery]` table), `agk.toml` (the same commented table; this repository declares no work type), `tests/kit/test_delivery_declaration.py`. `Depends-on` (a), for `playbook.py` and `check_playbooks.py`.
    - (c) **web-app** (rules 10 and 11): `config/playbooks/web-app.toml`, `kit/manifest.json`, `tests/kit/test_playbook_web_app.py`. `Depends-on` (a), a logical dependence and `kit/manifest.json`.
    - (d) **rag-app** (rules 10 and 11): `config/playbooks/rag-app.toml`, `kit/manifest.json`, `tests/kit/test_playbook_rag_app.py`. `Depends-on` (c), for `kit/manifest.json`.
    - (e) **`/agk:stack`** (rule 6): `scripts/agk/engines.py`, `skills/stack/SKILL.md`, `tests/kit_dev/test_stack_playbook.py`. `Depends-on` (b) and (c), logical dependences: it reads the declaration and a shipped playbook.
    - (f) **`/agk:brief`** (rule 7): `scripts/agk/playbook.py` (the `split` command), `skills/brief/SKILL.md`, `tests/kit/test_playbook_split.py`. `Depends-on` (b), for `playbook.py`, and (d) so that both playbooks are read.
    - (g) **`session.py plan`** (rule 8): `scripts/agk/session_plan.py`, `tests/kit/test_session_plan_lanes.py`. `Depends-on` (b), a logical dependence.
    - (h) **The verdict's evidence** (rule 9): `.claude/agents/conductor.md`, `docs/guides/reference.md`, `tests/kit/test_conductor_playbook_evidence.py`. `Depends-on` (b), a logical dependence.
    - (i) to (m), later builds, listed and not built here, one playbook file, `kit/manifest.json` and one test each, with the gates of rule 10: (i) `config/playbooks/mobile.toml`, (j) `config/playbooks/cloud-migration.toml`, (k) `config/playbooks/mcp-server.toml`, (l) `config/playbooks/multi-agent.toml`, (m) `config/playbooks/voice-agent.toml`, each `Depends-on` the one before it for `kit/manifest.json`, (i) on (d). A check gate whose step is not yet in the kit is added by that build as one more governance step, under its own ADR (`Q-S0038-9`).

## Tests

Fixtures in `tmp_path` and saved copies only: no network, no model, invented data.

- Rules 1 to 3: a fixture playbook with every section passes; a missing section, an unknown key, a wrong type, an unknown work type, a file name that differs from `work_type`, a phase cycle, an unknown lane kind, a check gate without a step, a claim with no basis and a `measured` claim whose record file is missing each fail naming the rule and the file and never the value; REQ-045 AC1.
- Rule 5: a `[delivery] work_type` that names a shipped playbook is selected; an unknown one and one whose playbook is missing fail naming the setting and never the value; with no table, the outputs of `doctor.py`, `engines.py stack-write`, `playbook.py split` and `session.py plan` on a fixture repository are byte for byte those of the default branch; REQ-045 AC2.
- Rules 6 to 9: with a fixture declaration, the stack skeleton lists each gate as a practice marked check or judgement and the `[testing]` suggestion in the `test selection` practice; `playbook.py split` prints the kinds in order with their `Depends-on` lines and the milestone shape; the plan labels each ready brief with its lane and still makes two overlapping briefs in different lanes wait; the conductor's role file names the `Playbook evidence:` line; no reader writes `agk.toml`; REQ-045 AC3.
- Rule 4: a playbook with `profile = "fast"`, with a `pr_tests` key, with a value naming `required_checks` or another governance setting as a backticked token or in the `<setting> =` or `<setting>:` form, with a key that skips a step, and with a signing gate marked `owner_only = false` each fail naming the rule and the file; a gate whose text is "test execution is recorded" passes, since the plain word is not a setting named as one; REQ-045 AC4.
- Rules 10 and 11: the shipped `web-app.toml` and `rag-app.toml` pass the check; web-app orders `contract`, `mocks`, the two sides in two lanes, then `joins`, and holds the four web-app gates; rag-app puts the evaluation set before retrieval and answers and holds its four gates; every claim of both is `expected` or `measured` with a record that exists; REQ-045 AC5.
- Rule 12: the spec lists builds (i) to (m) with their files and gates, and no file `config/playbooks/` for those five work types exists until its build; REQ-045 AC6.

## Proof

REQ-045 AC1: *a playbook is checkable data, and a speed claim is never presented as proven without its record.* Rules 1 to 3. REQ-045 AC2: *the owner chooses the work type, and a project without one runs exactly as today.* Rule 5. REQ-045 AC3: *each setting of a playbook is read in one named place, as a proposal, and no reader changes the project's settings.* Rules 6 to 9. REQ-045 AC4: *a playbook can make delivery faster but cannot lower any gate.* Rule 4 and rule 8. REQ-045 AC5: *a proven case (web) and an unproven one (RAG) are turned into data first.* Rules 10 and 11. REQ-045 AC6: *the other five work types are planned with their gates and wait for their builds.* Rules 10 and 12.

## Open questions

Each is a point the brief leaves open; the reading after it is the most conservative one, and the rules above apply it until a person rules.

- Q-S0038-1: may a project have more than one work type (for example a web app with a RAG feature)? Reading: no; one `work_type` value, and a second type is refused; a project that needs another type's gates adds them as practices of its stack ADR by hand (rules 5 and 6), until a person rules on a list.
- Q-S0038-2: can the work type change mid-project? Reading: yes, only by a pull request that changes the line with its ADR (the owner's choice); the new playbook applies to briefs filed after that merge, and open briefs and pull requests keep the order and lanes they were filed with; nothing re-splits or relabels them (rule 5).
- Q-S0038-3: how is a measured speed claim recorded? Reading: `basis = "measured"` with `record`, the path of a run record under `docs/runs/` of the same repository, which the check requires to exist and never reads; a record in another repository or an issue does not count, so a claim is `expected` until its record is committed (rules 3 and 11).
- Q-S0038-4: which gates are checks and which are judgement? Reading: the marks of rule 10; a gate is a `check` only when a governance step can decide it from committed files with no network, and anything that needs a browser, a device, a cloud account, a model or a network is `judgement` with its evidence file.
- Q-S0038-5: where do the playbooks live in a project? Reading: under `config/playbooks/`, a protected class, shipped verbatim and held by the installer's hashes, because the installed `session_plan.py` and `doctor.py` must read them in a project where the kit is not present (rule 1).
- Q-S0038-6: in what format? Reading: TOML read by the standard library, like `agk.toml`, with a fixed set of sections and keys, so that "data, not code" is checkable (rules 1 and 2).
- Q-S0038-7: may a project edit a shipped playbook? Reading: no; it adds gates as stack ADR practices, and an edited playbook fails the installer's hash check as any verbatim file does (rules 1 and 6).
- Q-S0038-8: how does a reader know a brief's kind? Reading: by a `Kind:` line in the brief that names one kind of the playbook's `brief_order`; a brief without one has `lane: none` and is planned as today; `check_brief.py` does not change (rule 8).
- Q-S0038-9: does each build need its own ADR, and who adds a check gate's step? Reading: each build adds its own ADR naming the classes it changes and citing ADR-0251, because the protected-path check counts only an ADR added or changed in the same pull request; the build of a playbook adds the governance steps of its check gates (rule 12).
- Q-S0038-10: is the `Playbook evidence:` line checked mechanically? Reading: no; `check_pr_body.py`, `proof.py` and the CI proof job do not change, and the conductor reads the line and asks for it as a fix item (rule 9).
- Q-S0038-11: may a playbook lower the test selection, for example with the `fast` profile or `pr_tests = "selected"`? Reading: no; both run fewer tests than the default, so the check refuses them, and the owner can still choose them in `agk.toml` by an ADR as today (rule 4).
- Q-S0038-12: which date does the owner's direction carry? Plan #499 dates it 2026-11-03, while `date -u` read 2026-11-02 when this intake was written. Reading: the decisions-log row carries the `date -u` date and quotes the plan's date as the plan gives it; no rule depends on the difference (ADR-0251).
