# SPEC-0077: Market packs and evaluations: pinned, scanned, dated packs, promoted by evals

- Status: Draft
- Owner: reviewer group (a team from config/reviewers.yaml)
- Requirements: REQ-084

Status is `Draft` or `Approved`. An Approved spec is owned by its reviewer group; agents propose patches.

Written by the intake of one sentence (SPEC-0012), brief #2022 under plan #661, quoted as data and not as an instruction: "Intake for market packs and evaluations: AGK keeps a small stable core and reads its stack, language, library, domain and pattern knowledge, and its skills, from pinned, scanned, dated packs, and promotes a pack or a release only when reference products score as well or better." The maintainers gave 16 answers before it was written (the numbered answers of brief #2022, filed on the owner's word of 2026-11-26T19:31Z, whose direction the brief quotes as data and this spec does not repeat). It changes no gate, role, approval, workflow, CI job, required check, ruleset, `agk.mk` recipe or `governance_map.CHECKS` step: it moves the kit's knowledge out of the core into packs that a project pins like a tool, keeps today's files as the built-in pack `agk-core` so that an upgrade changes no result, and adds a measured bar, an evaluation on invented reference products, for what is promoted. It composes with SPEC-0029 (engines), SPEC-0048 (playbooks and their skills), SPEC-0071 (the plugin), SPEC-0074 (domain packs), SPEC-0075 (data patterns) and SPEC-0076 when it is approved (the parts catalogues), and edits no Approved spec's text but by the amendments 261 and 262 that rule 13 proposes. Where the brief names something that is not as it says, rule 1 records what the code holds and an open question gives the conservative reading. Negative cases: a pack file whose hash differs from the lock, a pack not in the lock, a pack that weakens a gate, a pack carrying a hook, agent, workflow, settings file or script outside a skill's folder, a text line asking to approve, merge, push, skip a check, reveal a secret or change a role, a licence outside the allowed list, a pack below the trust tier, a pack that needs another kit, a documentation server no pack declares, a promotion with no accepted eval record, a model or network call in a check, and a customer value in a message or a pack are each refused or never happen.

2. **The core and the knowledge** (`Q-S0077-1`). The **core** stays in the kit and changes only by release: the constitution, the session and core rules, the roles and their guards, the gates' runner and interfaces (`scripts/agk/gates/`, `run_gates.py`), the evidence and review protocol, the templates' shapes, and the readers and their checks. The **knowledge** moves to packs, in nine kinds, each named by one word: `playbooks`, `domains`, `standards`, `stack-defaults`, `stack-signals`, `domain-signals`, `data-patterns` (SPEC-0075), `parts` (SPEC-0076 when approved) and `skills` (a `SKILL.md` that an `[engines]` key or a playbook's `skills` names). The kit keeps today's files where they are as its **built-in pack** `agk-core`: no file moves in this spec's first slice, and with no `[packs]` table every reader gives today's result.

3. **The pack format.** A pack is a folder, or a plugin of the kit's marketplace, holding one `agk-pack.toml` (`format = 1`) with: `id` (`^[a-z][a-z0-9-]*$`, never `agk-core` but for the built-in pack), `version` (an exact version, no range), `publisher`, `tier` (`official` for a vendor's own, `curated` for one the kit's maintainers reviewed, `community`), `licence` (an SPDX id), `source` (a public URL), `kit` (the kit versions it fits), `as_of` and `reviewed` (each `YYYY-MM-DD`, `reviewed` with who reviewed it, a role or a team name, never a person's address), `kinds` (a list of rule 2's words), `files` (each path relative to the pack with its SHA-256), `permissions` (rule 6) and `evals` (the path of rule 9's record that measured it, optional). Every knowledge item carries `source` with an access date, or `basis = "expected"`, as domain packs and derived playbooks already do. A new script `scripts/agk/check_packs.py` (standard library and `common.py` only, no network, no model), called by `check_playbooks.py` so that it runs inside the existing governance step `playbooks`, fails a missing or unknown key, a value of the wrong type (a `bool` is never a number), a kind outside rule 2, a file that is not listed or whose hash differs, a file under no kind's folder, an item with neither `source` and date nor `basis`, and a line that `guard.scan_text` flags, each naming the rule, the pack id and the key, never a value.

4. **Pinned like a tool.** A project lists its packs in `[packs] use = [{ id = "...", version = "...", sha256 = "..." }]`, where `sha256` is the hash of the pack's `agk-pack.toml`; `config/packs.lock` records every file of every pack in use with its SHA-256. A new kit script `scripts/agk/packs.py` has three commands: `add <source>` and `update --check` read the network and run only on the person's recorded yes, as `steward_owner.py research` does; `add` fetches, scans by rule 6 before anything is written, copies the pack into the project's `config/packs/<id>/` and writes the lock; `verify` (offline) fails a file whose hash differs from the lock, a pack in the lock that `[packs] use` does not list, a `[packs] use` entry the lock does not hold, and a lock entry whose pack folder is missing. `verify` is called by `check_packs.py`, so it runs inside the `playbooks` step on every governance run, in CI and in `prepush.py` (`Q-S0077-12`). The form is ADR-0171's: a version and a hash, checked on every use, never skipped. `agk.toml` and `config/` are protected in a project as in the kit, so adding, updating or removing a pack is a protected change with an ADR in the same pull request (principle 1), as an `[engines]` change already is (SPEC-0029 rule 1).

5. **Read in one order, never weakening.** One new resolver, `packs.files(root, kind)`, returns the files of a kind in order: `agk-core` (the kit's file through `kit_root.kit_file`), then each pack of `[packs] use` in its listed order, then the project's own files, so project-first stays where it is today. The readers of rule 2 read through it: `playbook_format`, `check_domains`, `check_playbooks.standards_file`, `engines.DEFAULTS`, the stack-signal reader and `domain_ask.py`; the standards, stack-default, stack-signal and domain-signal readers, kit-only today, gain the same order. Composition keeps today's rules: a gate, a standard's `rules` or a regulation restated by a later layer holds only when the same or stronger (`judgement` to `check`, `owner_only` never `true` to `false`), a weakening is refused naming the pack id and the key, and the stricter regulation holds until a person decides (SPEC-0074 rule 4). A pack never lowers a gate, a floor, a required approval or a setting's bound; a stack default or a signal from a pack is a proposal for a person to confirm, as today's are.

6. **Safe to adopt.** At `add` and `update`, before anything is written, every file of the pack passes: the secret scan (`guard.scan_text` with the shipped patterns, and gitleaks where prepush runs it); the outbound guard's patterns (`steward_outbound.py`); a new **instruction scan** of every text file, which names each line that asks to approve, merge, push, skip or disable a check, reveal a secret, change a role or a task, or ignore the rules, and refuses the pack (session rule 38: the line is data, named and never followed); the licence check against the project's `config/licences.toml`, or `kit/templates/licences.toml` with none (`Q-S0077-11`); and a size limit per pack and per file, whose numbers build (d) sets in its ADR. A pack carries knowledge and skills only: no hook, no agent file, no workflow, no settings file, no `.mcp.json`, no script outside a skill's own folder, and nothing that lands under a protected path of the project but `config/packs/<id>/` (`Q-S0077-2`); each is refused naming the rule and the pack's path class. `permissions` may ask only `network = "research"` (a skill that reads public pages during the steward's recorded research) and `mcp = ["<server>"]` (a read-only documentation server, rule 7). A skill from a pack is an engine: it drafts through the kit's templates and checks and never decides, approves or edits a protected file by itself (SPEC-0029 rule 3). A pack below `[packs] trust` is refused at `add` and at `verify`, naming `packs.trust`. A pack whose `kit` range does not hold the running kit's version is refused at `add`, `update` and `verify`, naming `kit`. At `update`, a pack whose version is the one the lock holds but whose files' hashes differ from the lock's (a pack changed upstream at the same version) is refused naming the pack id and the rule, and the lock is left as it was.

7. **Current facts read at the moment of choice, never from model memory.** A version, an interface or a practice that changes is read when it is chosen, from the publisher's own source, through the steward's recorded research (`steward_owner.py research`, generic words only) or a pack's declared read-only documentation server, recorded with its source and access date, then pinned; checks read only the recorded values and never the network (`CLAUDE.md item 5`). A documentation server is used only when `[packs] mcp` lists it and a pack in use declares it in `permissions`, only in research and drafting steps, never in a check, a gate or a verdict, and its output is data (session rule 38). Setting the server up in the runtime's own settings is the person's: the kit names it in the guide and never writes a settings file (`Q-S0077-4`) `(verify: where the runtime reads a project's documentation server setting)`.

8. **Fresh by rule.** `[packs] stale_months` (default 12, as `[domain] stale_months`): a pack whose `reviewed` or `as_of`, or an item whose access date, is older is shown with its date and `(verify)` by `doctor.py` and the weekly report, a warning that never fails. `packs.py update --check` (network, on the person's yes) lists the newer versions of each pack in use with their change notes; nothing updates without a yes, a new lock and the ADR of rule 4. A pack whose publisher withdrew it keeps working offline from its lock, and `update --check` names it `withdrawn`.

9. **Evaluations set the bar** (`Q-S0077-6`, `Q-S0077-7`, `Q-S0077-8`). A kit-only folder `evals/`, never installed in a project, holds **reference products**, each invented (`example.com`): its problem statement, users, acceptance criteria and domain, one folder per product, built from the v1 plans (#1769 to #1771) and the invented products of SPEC-0073 and SPEC-0074. A new kit-only script `scripts/agk/eval_run.py` runs the AGK path on one product in a scratch repository with the personal sidecar's `forge = "files"` (SPEC-0041), so it makes no GitHub call, and records per run:
   - **objective** results: the tests passed, line coverage, the `pins` and `licences` steps, the bill (SPEC-0054), the secret and dependency scans, lint, the accessibility check of SPEC-0073 build (i) and the gates' findings;
   - **process**: the questions that reached the person, the records written, the review rounds and the minutes;
   - **cost**: tokens by kind and money, in brief #2020's form;
   - the **independent review**: a fresh reviewer with the bundle only (ADR-0430) scores each layer 0 to 6 against `evals/rubric.toml` (problem, scope, domain rules, architecture quality, threats, data, usability, code), each criterion with its source.
   Each product runs three times on the `strongest` tier and the median counts. A run that does not finish is recorded `incomplete` with its stage and never scored as 0. An eval uses a model, so it runs on the person's machine or a cloud session on the person's yes, and never in a required check or in CI.

10. **Promotion by evidence.** A pack moves from `community` to `curated`, a kit release is cut and a tier's model mapping changes only with an eval record `docs/runs/evals/<date>.md` whose medians are no worse than the last accepted record's beyond `tolerance` (a key of `evals/rubric.toml`, `Q-S0077-13`) and which states the cost per accepted feature; a regression names the product, the layer and the score. The owner accepts a record with one plain yes (in team mode, a `spec_approvers` login's own words); the steward never accepts one (principle 2). `scorecard.py` gains one line with the last accepted record's medians. SPEC-0048 rule 24's promotion of a derived playbook keeps its evidence path unchanged; this rule reads it only through the kit release that ships the promoted playbook, which, as every release, needs a record once rule 9 exists.

11. **Roles later.** A pack may name `roles` (for example `architect`, `domain-expert`, `designer`) for its skills; until brief #1381's roles exist, every pack skill runs in today's roles and the key is printed by `doctor.py` and read by nothing else. The domain expert's confirmations (SPEC-0074 build (h)) and the per-role paths plug in without a change to this spec.

12. **Settings.** One optional `[packs]` table, read by `config.packs_settings` in `steward_settings`' form (a `bool` is never a number), added to `config.TABLE_KEYS`, printed by `doctor.py` and removed by `uninstall.py` through `KIT_SETTINGS`, each with a test. A refusal is `the [packs] table is refused (setting: packs.<key>)`, exit 1, never the value. With no table only `agk-core` is read, so an upgrade changes nothing.

    | Setting | Values | Default | Impact |
    | --- | --- | --- | --- |
    | `use` | a list of `{ id, version, sha256 }` | `[]` | the packs read after `agk-core`, in order (rule 5); a malformed entry, a repeated id or `agk-core` is refused naming `packs.use` |
    | `trust` | `official`, `curated`, `community` | `curated` | the lowest tier allowed; a pack below it is refused at `add` and `verify`; another value is refused naming `packs.trust`; `community` is set by the ADR any `agk.toml` change carries (`Q-S0077-3`) |
    | `stale_months` | a whole number from 1 to 60 | 12 | the age past which a pack or item is shown with `(verify)` and warned, never failed (rule 8); otherwise refused naming `packs.stale_months` |
    | `mcp` | a list of server names | `[]` | the documentation servers a pack may use in research (rule 7); a name that no pack in use declares is refused naming `packs.mcp` |

    An unknown key is refused naming it; a `[packs]` key placed in another table is reported by `misplaced_settings` and never read. Read beside it:
    - `[engines]` (SPEC-0029 rule 1): a value may also be `<pack id>:<skill>` for a skill of a pack in use, verified by the lock; `doctor.py` reports it `present`, `absent` or `missing` as today, never `plugin-unreadable` (amendment 261). A prefix that names no pack in use stays `cannot-check plugin-unreadable` as today.
    - A playbook's `skills` key (SPEC-0048 rule 12): unchanged, unprefixed names; a pack's skill counts as present when the pack is in use and its skill folder is in the lock (`Q-S0077-10`).
    - `[domain] packs` (SPEC-0074 rule 12): a name may also be a domain pack carried by a pack in use (amendment 262, item 2).
    - `[delivery] work_type` and `[models]`: read as today, through the resolver.
    - `review_mode`: `solo`, the one person's yes adds a pack and accepts an eval record; `team`, a `spec_approvers` login's own words.
    - `execution`: every check is file-only in either value.
    - `[personal]` (`forge = "files"`): packs are pinned in the sidecar and evals use the same form, nothing posted.
    - The kit's own repository: `agk-core` only, no `[packs] use`; it evaluates every release (rule 10).

13. **The amendments** (principle 6, `Q-S0077-9`). The Approved specs change only by two proposals written with this intake under `docs/runs/`, each applied word for word by the build named in it on the owner's `Maintainer answer: amendment <n> approved`, which no session posts: amendment 261 (SPEC-0029 rules 1 and 2, an engine value from a pinned pack and its doctor line, by build (e)) and amendment 262 (SPEC-0074 rules 3 and 12, the seed domain packs as their own curated pack and a `[domain] packs` name from a pack in use, by build (j), after (b) and (h)).

14. **The builds**, each tests first, about 300 changed lines or fewer, from the default branch, with its own ADR naming its path classes, invented data only (`example.com`), a `[[testing.map]]` entry per new script, no workflow change and at most 6 code paths in `Touches:`:
    - (a) `agk-pack.toml` and `check_packs.py` in the `playbooks` step, the `[packs]` table and its reader, `doctor.py` and `uninstall.py`, and `agk-core` as the built-in pack.
    - (b) `packs.files(root, kind)` and the readers of rule 5. Depends on (a).
    - (c) `packs.py add|verify|update --check`, `config/packs.lock` and `verify` inside the `playbooks` step. Depends on (a).
    - (d) The instruction scan and the adoption checks of rule 6. Depends on (c).
    - (e) `[engines]` values from packs and the doctor lines, amendment 261. Depends on (c).
    - (f) `[packs] mcp` and the research path of rule 7. Depends on (d).
    - (g) `evals/` with two reference products (a booking web app and a payments API), `evals/rubric.toml` and `eval_run.py` over the personal sidecar. Depends on brief #2020.
    - (h) The eval record, the promotion rule and the scorecard line (rule 10). Depends on (g).
    - (i) The stale warning and `update --check` (rule 8). Depends on (c).
    - (j) The seed domain packs and the stack catalogues as their own curated packs, amendment 262. Depends on (b) and (h).
    Builds (a) to (e) are the first slice: a project can adopt a pinned, scanned outside pack and skill safely; (g) and (h) give the bar.

15. **Measured goals.** On the two reference products of build (g): a curated pack that replaces a built-in stack catalogue gives medians no worse than `agk-core`'s; a pack with one instruction-shaped line is refused at `add`; a changed file hash fails governance; a pack that weakens a gate is refused; an `[engines]` skill from a pack in use reads `present`; each eval run states its cost per accepted feature; three runs of one product differ by at most `tolerance`. No check uses the network or a model.

16. **The class stays closed.** Knowledge enters a project only through a pinned, scanned pack or the project's own files, and only an eval record the person accepted promotes a pack, a release or a tier's mapping.

## Tests

- Rules 3, 4 and 6: each malformed `agk-pack.toml` (a missing or unknown key, a `bool` for a number, a kind outside rule 2, an unlisted file, a wrong hash, an item with no source), a changed file against the lock, a pack missing from the lock or from `[packs] use`, a hook, agent, workflow, settings file or stray script in a pack, a licence outside the list, an oversized file and an instruction-shaped line are each refused naming the rule, the pack id and the key, never a value (REQ-084 AC1, REQ-084 AC3).
- Rule 5: on saved trees, `agk-core` then two packs then the project's file compose in order; a later pack's stronger gate replaces a weaker; a weakening is refused naming the pack and the key; two packs with different regulations on one attribute keep the stricter with both sources; with no `[packs]` table every reader's result equals today's (REQ-084 AC2).
- Rule 6: a pack whose `kit` range does not hold the running kit's version is refused naming `kit` at `add`, `update` and `verify`; at `update`, a pack at the locked version whose file hashes changed upstream is refused naming the pack id and the rule, and the lock is unchanged (REQ-084 AC3).
- Rule 4: `packs.py verify` runs inside the `playbooks` step with the network blocked; `add` and `update --check` refuse without the recorded yes and open no socket in a test (REQ-084 AC3).
- Rules 7 and 12: a documentation server not listed in `[packs] mcp`, or listed and declared by no pack, is refused naming `packs.mcp`; no check or gate reads a server (REQ-084 AC4).
- Rule 12: each row of the settings table, set, absent, unknown or of the wrong type, gives the stated impact; an `[engines]` value `<pack id>:<skill>` of a pack in use reads `present`, `absent` or `missing`, and of no pack in use `plugin-unreadable` (REQ-084 AC5).
- Rule 8: a pack or item older than `stale_months` warns with its date and `(verify)` and never fails; a withdrawn pack verifies offline (REQ-084 AC6).
- Rules 9 and 10: on a saved run tree, the record holds the objective, process, cost and review parts; an `incomplete` run is never 0; the median of three runs is used; a record worse beyond `tolerance` names the product, the layer and the score and blocks promotion; a record with no person's yes promotes nothing (REQ-084 AC7).
- Rules 12 and 16: solo and team acceptance; personal mode posts nothing; the same checks run in a CI-mode governance run, `make -f agk.mk agk-governance` and `prepush.py`, with no workflow, ruleset, required check or governance step list change (REQ-084 AC8).

- github: `check_packs.py` and `packs.py verify` run inside the existing `governance` job's `playbooks` step, with no workflow, ruleset, required-check or label change.
- local: the same checks run in `prepush.py` and `make -f agk.mk agk-governance`, with no recipe change.
- personal: packs are pinned in the sidecar, and evals run over the sidecar's files with nothing posted.
- stacks: each stack's knowledge arrives as a pack, and the core has no stack of its own beyond `agk-core`.

## Open questions

- `Q-S0077-1` (the owner's): its own spec, or amendments to SPEC-0029, SPEC-0048 and SPEC-0074? Reading: its own spec, composing with each (rule 2).
- `Q-S0077-2`: may a pack carry scripts, for example a stack's own check, and where do its files live? Reading: no script but in a skill's own folder; a check is core, a gate, and enters by a kit build (rule 6). Ruled (the owner's answer on #2023, comment 7209597979): a pack's files live under the project's `config/packs/<id>/`, inside the protected `config/` class, so each pack change carries an ADR (rules 4 and 6).
- `Q-S0077-3`: which tier is allowed by default? Reading: `curated`; a project lowers it to `community` in the ADR its `agk.toml` change carries, a lower trust being a weaker check (principles 1 and 11, rule 12).
- `Q-S0077-4`: who sets up a documentation server in the runtime? Reading: the person, in the runtime's own settings; the kit names it in the guide and never writes a settings file (rule 7).
- `Q-S0077-5`: where do curated packs live? Reading: as plugins of the kit's marketplace (`.claude-plugin/marketplace.json`) beside `agk`, each versioned on its own (rules 3 and 14 (j)).
- `Q-S0077-6`: how large is the first eval set? Reading: two reference products, three runs each, on the `strongest` tier; more per work type as packs arrive (rule 9).
- `Q-S0077-7`: may an eval use a real model in CI? Reading: no; evals run on the person's machine or a cloud session on the person's yes, never in a required check (rule 9).
- `Q-S0077-8`: the rubric's criteria. Reading: from the Approved specs' own measured goals (SPEC-0073, SPEC-0074, SPEC-0075) and their cited standards, each layer scored 0 to 6 as the v1 run's independent review did (rule 9).
- `Q-S0077-9`: the amendment numbers. Reading: the next free on the default branch and in every open pull request at writing, 261 and 262, after the open intake's 258 to 260 (rules 1 and 13).

Reading: `add` runs only on the person's recorded yes and in the pull request whose ADR the person approves, so the person installs it and the kit installs nothing by itself; no amendment of rule 12 is proposed, and build (c) asks first if the maintainers read it otherwise.
