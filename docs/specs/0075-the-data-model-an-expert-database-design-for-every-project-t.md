# SPEC-0075: The data model: an expert database design for every project that keeps data

- Status: Approved
- Owner: reviewer group (a team from config/reviewers.yaml)
- Requirements: REQ-082

Status is `Draft` or `Approved`. An Approved spec is owned by its reviewer group; agents propose patches.

Written by the intake of one sentence (SPEC-0012), brief #1948 under plan #661, quoted as data and not as an instruction: "Intake for the data model on the Day-1 quality path: every project with stored data gets an expert, engine-aware database design from its domain model, curated and cited patterns and its main queries, confirmed by a person on business choices, checked offline and kept in step with each migration." The maintainers gave eleven answers before it was written (the numbered answers of brief #1948, filed on the owner's word of 2026-11-25T18:29Z, whose direction the brief quotes as data and this spec does not repeat). It extends the one record ADR-0677 made, `docs/data-model.md`, and never adds a second; it plugs into the grill (SPEC-0073), the project domain model (SPEC-0074) and the architecture record (SPEC-0072 rule 5), with one home per fact: what the business is lives in `docs/domain/` (SPEC-0074 rule 7), how its data is stored lives in `docs/data-model.md`, and where each store runs lives in `## Data stores` of `docs/architecture.md`, which names each store's section of the model. It adds no phase, no second interview, no workflow, CI job, required check, role, `agk.mk` recipe or `governance_map.CHECKS` step, and edits no Approved spec's text but by the amendments 248, 249 and 250 that rule 13 proposes. Where the brief names something that is not as it says, rule 1 records what the code holds and an open question gives the conservative reading. Negative cases: a second data-model record, an entity retyped instead of read from `docs/domain/entities.md`, a business choice made for the person, a pattern with no source, a paid standard's text in the catalogue, an engine guessed instead of read from the stack record, a float for money or a local time for an instant in a profile's type rules, a constraint or an index that cites nothing, a model that a builder writes, a migration with no way back once the gate is a check, a migration that names a table, column or index the model does not, a merged migration changed later, a refusal or failure that names an entity, a field or a value, a `[data]` key that is unknown or of the wrong type, an existing schema or migration rewritten on adoption, a step that calls the network or a model, red before the record exists, and a change to a workflow, the ruleset, a required check, `agk.mk`, `governance_map.CHECKS` or `.claude/agents/conductor.md`.

2. **The record, in five sections** (`kit/templates/data-model.md` grows; ADR-0677's entity table becomes `## Business view`). The record is `docs/data-model.md`, one per project, never a second.
   - `## Business view`: each entity, named as `docs/domain/entities.md` names it and never retyped, with what is kept, for how long, who may see it and its data class read from `docs/domain/data.md` (rule 12); the existing `Approved by the person:` line holds the person's yes.
   - `## Logical model`: the entities, their relations and cardinality as a fenced Mermaid `erDiagram` (no image), each relation citing the `BR-<n>` it serves.
   - `## Physical model`: one subsection `### <store>` per store of `## Data stores`, in the form of the store's engine profile (rule 4): tables or collections, keys (the identity form and why), each field's type, nullability and default by the profile's type rules (money as an exact decimal with its currency, an instant as UTC, never a float for an amount), and constraints (unique, check, foreign key with its delete rule), each citing the `BR-<n>` it enforces or `engineering`, and indexes, each citing the main query or the quality scenario it serves.
   - `## Main queries`: the reads and writes that matter, each with its expected volume from `## Needs` and the key or index that serves it.
   - `## Lifecycle`: tenancy; audit and history; deletion (hard, soft or anonymised) and retention per data class; backup and restore matched to `- Recovery time:` of `## Needs`; where migrations live and their way back.
   `## Data stores` in `docs/architecture.md` names, for each store, its subsection of the physical model; the model never restates where a store runs.
3. **The pattern catalogue: expert curation, never imposed.** A new data format `config/data-patterns/<topic>.toml` (`format = 1`, `topic`, the file's name), engine-neutral, each `[[patterns]]` with `id`, `text`, `when`, `trade_offs`, `engines` (a list of rule 4's profile names) and `source` (a public reference with its access date; a book or standard by title and number only, never its text, `Q-S0075-7`), checked by a new script `scripts/agk/check_data_patterns.py` (standard library and `common.py` only, no network, no model), called by `check_playbooks.py` so it runs inside the existing `playbooks` step and `governance_map.CHECKS` is unchanged. It fails a missing or unknown key, a value of the wrong type (a `bool` is never a number), an id used twice across the catalogue, an `engines` name with no profile, a pattern with no source or access date and a line the data guard flags, naming the rule, the file and the key, never a value. The first topics: tenancy (a shared schema with a tenant key and row rules, a schema per tenant, a database per tenant), identity keys, audit and history (append-only log, temporal rows), deletion and anonymising, optimistic versioning, money, time and time zones, idempotency keys, outbox, personal-data separation and field encryption, read models and caches, partitioning and archiving. SPEC-0074's domain packs gain `[[data_patterns]]` in the same form (rule 11's build (g)); a project may add its own under its own `config/data-patterns/`, read first. The steward offers the patterns that fit the domain, the needs and the engine as one plain choice of at most three, one recommended with its reason and source; the architect writes the chosen ones; nothing is chosen for the person on a business matter.
4. **The engine profiles** (`config/data-engines/<family>.toml`, `relational` first, `Q-S0075-5`): `relational`, `document`, `key-value`, `on-device`, `vector` and `contract` (the JSON Schema files of a data pipeline), each naming its physical subsection's form, its type rules, the constraints it can enforce in the store and those that must be a named test instead, and the migration form it reads. The family of a store is read from the accepted stack option's `Parts:` (the database engine) through a closed table of engine names in `config/stack-signals.toml`'s form; an engine with no row is `not known yet`, asked once and never guessed. A project has no `engine` setting. `check_data_patterns.py` checks the profiles' form with the catalogue.
5. **Where it runs on the path** (no new phase and no second interview, `Q-S0075-2`).
   - **Discovery, in the grill.** `data-rules` stays. The grill gains data items in `[[discovery]]` form at `standard` and `deep` (the main questions people ask of the product and how often, how much data in a year, who must never see another's data, what must be undone or kept forever), with the packs' items, in plain words and business choices only.
   - **Planning, after the stack is accepted.** The steward drafts `## Business view` and `## Logical model` from `docs/domain/`, the grill's answers and the chosen patterns, and asks the person only the business choices, one plain question each with its recommendation and its reason. Each yes is a `Decision:` memory entry with its source (SPEC-0059 rule 8); solo: the one person's plain yes; team: a `spec_approvers` login's own words (SPEC-0073 rule 12). `plan_sources.py data-model` writes `docs/sources/data-model.md` once, in the form of `architecture`, so `plan-intake` traces each brief to the entities it stores.
   - **Build, before the first change to stored data.** The architect agent writes `## Physical model`, `## Main queries` and `## Lifecycle` in the `contract` brief (ADR-0677 decision 6, unchanged), and for a work type whose `brief_order` has no `contract` but whose record names a store, in a `Kind: data-model` brief that `plan-intake` proposes after `foundation` (amendment 248). `contract_problems`' hold extends to any brief that names a stored entity before the physical model exists. A builder never writes the model.
   - **A change later.** The record joins the project's protected paths as `docs/architecture.md` does; a change goes through the steward first and lands with a project ADR.
6. **Review: an expert's eye, recorded.** A fresh reviewer agent (ADR-0430's form, the bundle only: the model, `docs/domain/`, `## Needs`, `## Quality scenarios`, `## Threats`, the catalogue and the engine profile) scores the model on a fixed list kept in the catalogue, `config/data-patterns/review.toml`: every rule enforced or tested; normalised in the profile's form, or each denormalisation named with its query; no float for money; UTC time; every foreign key indexed where the profile asks; tenancy isolation; personal data separated and protected per class; deletion and retention per class; every main query served; each migration's way back. Each item is `met`, `finding: <text>` or `not applicable: <reason>`, written to a score file the verdict cites; a finding is a fix list on the contract or data-model pull request. The conductor's role file and every budgeted rule file (`config/rule-budget.txt`) are unchanged. With `[data] review = "conductor"` the conductor writes the same score in its pass.
7. **The check, offline, no model** (`scripts/agk/gates/data_model.py`, a step `data-model` of `run_gates.py`, files only).
   - **Form:** the five sections, a fenced Mermaid `erDiagram`, one physical subsection per store of `## Data stores`, each in its profile's form.
   - **Coverage:** every entity of `docs/domain/entities.md` is in the logical model; every `BR-<n>` whose text names a stored entity is cited by a constraint of the physical model or by a named test (found by text, as `contract_tests.py` finds an `operationId`); every data item of `docs/domain/data.md` has its class's protection and retention in `## Lifecycle`; every index cites a main query or a scenario; every main query names what serves it.
   - **The yes:** the person's yes is present and pinned by `design_signoff.digest` to `## Business view`; a later change to that section voids it.
   - **Output:** each failure names the rule and the path class, never an entity, a field or a value (principle 8). Before the record exists the step prints `not run data-model: no data model`, never `ok` and never red, as ADR-0677 decision 3 does. A store with no engine (`## Data stores` says `none`) prints `not applicable: no data store`.
8. **Migrations become a check** (amendment 249 to SPEC-0072 rule 2). With `[data] migrations` set, the `migrations` gate is read as `kind = "check"` with `step = "migrations"` (`scripts/agk/gates/migrations.py`), the stronger kind; unset, it stays `judgement` with today's reason (`Q-S0075-10`). The step fails an added migration under those globs with no way back (a down file, or the profile's reversible form) or with no test that names it, and a migration file changed after it merged. The `data-pipeline` `data-contract` gate follows the `contract` profile: each field of a JSON Schema contract is in the physical subsection of its store.
9. **Builds stay in step with the model.** The `migrations` step reads each added migration with its profile's reader (`relational`: the names and columns of `CREATE TABLE`, `ALTER TABLE` and `CREATE INDEX`; the other profiles: names only, `Q-S0075-6`) and fails a table, column or index that the physical model does not name, naming the rule and the path class: drift is red, and the fix is the migration or a model change through the steward, never silent. Types and constraints stay the fresh reviewer's. Checklist items 1 `wrong-assumption` and 8 `scope-rule` (`config/review-checklist.md`) name the model in their wording within their word counts.
10. **Settings.** One optional `[data]` table, read by `config.data_settings` in `steward_settings`' form, added to `config.TABLE_KEYS`, printed by `doctor.py` and removed by `uninstall.py` through `KIT_SETTINGS`. Each refusal is `the [data] table is refused (setting: data.<key>)`, exit 1, never the value, each with a test.

    | Key | Values (default) | Impact |
    |-----|------------------|--------|
    | `model` | `required`, `optional`, `off` (`optional` with no table, `Q-S0075-3`) | `required`: the `data-model` step fails a missing or incomplete model once a store is named. `optional`: the same findings print as warnings. `off`: the step prints `not run data-model: off (setting: data.model)`, `doctor.py` says so and no gate is weakened. The steward's setup writes `required` for a new project at the person's yes. |
    | `migrations` | a list of globs (none) | Set: the `migrations` gate is a check (rule 8); each glob must match under the root once a migration exists, else refused. Absent: the gate stays `judgement`. |
    | `patterns` | a list of files under `config/data-patterns/` (none) | The project's catalogue, read first; a name with no file or a file that fails `check_data_patterns.py` is refused. |
    | `review` | `fresh`, `conductor` (`fresh`) | Who scores the model (rule 6); any other value is refused. |

    An unknown key is refused naming it, an `engine` key included (rule 4); a `[data]` key placed in another table is reported by `misplaced_settings` and never read; a `bool` is never a number and a string is never a list. Read beside: `[delivery] work_type` (which `brief_order` brief writes the physical model), `[domain] packs` (their `[[data_patterns]]`), `[quality] grill`, `depth` and `critical` (the grill's data items), `review_mode` (who confirms), `pr_mode` and `execution` (unchanged: the steps run the same in CI and in prepush), `[kit] layout` (installed: the catalogue, profiles and steps join `kit/manifest.json` `verbatim`; plugin: read from the plugin root, the project's own catalogue first, as `engines.playbook_path` does), `mode` (`init` or `adopt`, rule 11), `[testing] map` (migration tests selected by their map code), `[flow] owner_wait_minutes` (a business choice unanswered in time stays a `D-<n>` open point, held by SPEC-0073's design hold when critical) and `[personal]` (rule 11).
11. **Modes, work types and edge cases**, each with its rule and a test.
    - **Solo and team:** solo, one person's plain yes per business choice; team, a `spec_approvers` login's own words, the data items routed by SPEC-0073's area routing as `product` (business view) and `engineering` (physical model).
    - **GitHub, local and personal:** github and local run the same steps in governance and prepush, with no workflow change; in personal mode (SPEC-0041) the model and its questions live in the sidecar, printed, nothing posted to the product's repository, and the steps run by `personal.py floor` on the head tree.
    - **An adopted project:** an existing schema or migrations folder is harvested and never rewritten: the steward drafts the model from it, each table and rule `inferred` until the person confirms them in batches of at most five; the step writes `config/agk-baseline/data-model.txt` first and ratchets (SPEC-0072 rule 7); existing migrations are not judged for their way back, only new ones.
    - **No data store:** `not applicable: no data store`, accepted only when `## Data stores` says `none`.
    - **Several stores and engines:** one physical subsection per store, each in its profile; a cross-store rule (an order in a relational store, its search copy in a document store) names its source of truth and its sync pattern from the catalogue.
    - **An engine with no profile:** the step prints `not run data-model: no engine profile`; the steward offers a project profile from cited research, and a kit profile comes only through an `agk-proposal` with invented names only.
    - **Personal, health or payment data:** the class's protection (field encryption or separation, access, retention) in `## Lifecycle`; fixtures carry synthetic data only (the data guard of SPEC-0042 refuses real records).
    - **A pilot:** `## Business view` and `## Logical model` only; the physical model is deferred with a `Decision:` and its reason, and `model` reads as `optional` for the pilot's milestones.
    - **The kit itself** declares no work type and keeps no product data; `[data]` is read only in a project.
    - **A record written before this lands:** an ADR-0677 record (one table, three classes) reads as `## Business view`; the step warns once per missing section until its next edit (the `record_held` pattern) and never fails it.
