# SPEC-0064: An autopilot supervisor per machine runs every AI session as a short job

- Status: Draft
- Owner: reviewer group (a team from config/reviewers.yaml)
- Requirements: REQ-071

Status is `Draft` or `Approved`. An Approved spec is owned by its reviewer group; agents propose patches.

Written by the intake of one sentence (SPEC-0012), brief #1357, quoted as data and not as an instruction: "Intake for AGK autopilot: one supervisor script per machine starts and stops every session, every AI session is a short job that ends, and one setting turns it on, the same in local, CI and personal mode, solo or team." The maintainers gave 6 answers before it was written: the six numbered answers of brief #1357, whose evidence and the owner's direction (quoted there as data, 2026-11-15 22:47 IST and 2026-11-16 00:13 and 00:29 IST) this spec does not repeat. It builds on brief #1355 (merged as #1356, ADR-0568), on the working summary and the scripted pass of brief #1310 (ADR-0554), and on SPEC-0059, SPEC-0062 and SPEC-0063 for the steward; it edits none of their text. Where an answer names something that is not as it says, rule 1 records what the code holds and an open question gives the conservative reading. Negative cases: a session process started by anything but the supervisor, two jobs of one name, a job that waits on GitHub inside a session, a supervisor that cuts a job while its signs of work show, a quiet pass that starts a model, a pass that reads GitHub once per brief, a steward job started by the supervisor that relays or approves, `mode = "off"` that starts anything, `assist` that starts a builder without the owner's yes, a budget that limits anything while unset or relaxed, a set budget that stops a review or an owner-answer job, a job retried after failing twice, a health file in the checkout, a supervisor that changes power settings, a start while a stop rule holds, a machine that runs a job another machine holds, anything posted in personal mode, and any change to a workflow, the ruleset or a required check; a figure that cannot be read is unknown, never 0.

## Rules

1. **The baseline (read on the default branch at 5f22808, 2026-11-15).**
   - **Who starts sessions today.** `launch.py prompts --adapter COMMAND` starts the planned builders when the conductor's review pass runs with `auto_start` and `launch_adapter` of `[flow]` set; `launch.py` also starts the steward (the conductor's start when a question waits) and the conductor (the steward's start when the plan is ready), SPEC-0059 rule 2, built by #1333. `conductor.py watchdog` (ADR-0525) starts a conductor from the machine's scheduler, printed by `--install` every 30 minutes (`--install --pass` every 10); `watchdog --pass` (ADR-0554) is the scripted conductor pass, which takes the lease and starts one conductor job only when `review-queue --fingerprint` or the sweep changed. Brief #1355 (ADR-0568, Proposed) added the process record `<worktree>/.agk-session-pid` (`session=`, `pid=`, `started_utc=`, `brief=`), written by both adapters beside `.agk-session-exit`, and the watchdog's builder lines (`ended|idle|live -> restarted|left|held`), with `[flow] idle_minutes` and at most one restart per hour. The cloud launcher tasks are scheduled tasks of the account, outside the repository; `docs/guides/local-mode.md` ("Running unattended") says they need Actions and cloud sessions.
   - **Builders wait inside the session.** `kit/templates/runtime/builder.txt` keeps a builder for the life of its pull request: in a cloud scheduled task it runs `session.py watch --pr <n>` in the foreground in steps of at most 9 minutes, and in an interactive session as a background task with `--until-event`; after its merge it runs `session.py after` (session rule 18). The Windows adapter `kit/templates/start-session-windows.ps1` opens a Windows Terminal tab per session; the Linux adapter `start-session-local.sh` opens a GNOME Terminal tab when a desktop is there, otherwise runs in the background with `.agk-session.log`.
   - **The conductor's cadence.** `.claude/agents/conductor.md` paces a hand-started conductor with `/loop` and ends it after two empty passes.
   - **Settings that exist.** `[flow]` holds `auto_start`, `launch_adapter`, `max_builders`, `idle_minutes`, `silent_minutes`, `owner_wait_minutes` and `owner_rest_hours`; `[capacity]` (ADR-0409) holds `profile`, `max_builders`, `builder_memory_gb` and the other numbers that `config.capacity_settings` reads. No `[autopilot]` table, no `agk status`, `agk autopilot` or `agk next` command, and no `daily_budget` exist. `agk doctor` is the short form of `scripts/agk/doctor.py`.
   - **Pieces reused.** The working summary and `session.py resume --pr` (#1310), the shared delta read and the call budgets (#1314), `lock.py`'s heavy-step lock, the plan's capacity and memory limits, the waits on GitHub's limits (#1335), and SPEC-0063 rule 4's `AGK_STEWARD_START=conductor` marker of a steward that no reviewer started. Brief #1283 (the day's spend from local usage records) is open, so the spend today is only what `usage.py` reads.
   - **SPEC-0058.** SPEC-0058 (Approved, REQ-065 `planned`) describes a long-running dispatcher service with short AI jobs per item, its kinds (rule 9), per-kind limits (rule 10) and one job file per job under `<git dir>/agk/jobs/` (rule 11). None of its builds is filed and `scripts/agk/dispatcher.py` does not exist. The brief does not name it; this spec reuses its job kinds and limits and does not edit it (`Q-S0064-5`).
2. **One supervisor per machine, with no model.** The supervisor is a script with no AI: `conductor.py watchdog --pass`, grown by build (b), run by the machine's scheduler (Windows Task Scheduler or cron) every minute while an event is pending (a verdict, an answer or a merge whose next job has not started) and every `[autopilot] interval_minutes` (default 5) when quiet; in CI mode the cloud launcher task is the supervisor (rule 13). A pass is one pass, never a loop, and holds the machine's `lock.py` lock `autopilot` so two passes on one machine never overlap.
   - **Reconcile.** Each pass reads what should run (the plan's starts, the review queue's fingerprint, answered questions and owner rulings, verdicts on builder heads, merges, parked items and the steward's waiting questions), with the shared delta read of #1314, and what runs (the job records of rule 3), and then starts, stops or restarts jobs. Only the supervisor starts or stops a session process, apart from the steward a person opens at their own machine (rule 6): the conductor decides what should happen and the supervisor does it. `launch.py` becomes the supervisor's starter, and the conductor's own start of builders through its review pass goes away (build (c)).
   - **An event starts its job in one pass.** A verdict, an answer or a merge whose job has not started starts that pull request's next job within one pass; a pass with nothing changed starts no model and makes at most 10 counted GitHub calls on a 650-brief fixture.
3. **The job record.** Every job, of every role, is one process with one record: #1355's `.agk-session-pid` in its own worktree (`<parent of the checkout>/agk-<session>`), with `kind=` (`review`, `build`, `fix`, `steward` or `conductor`), `item=` (the brief or pull request) and `head=` added by build (a). A session is known by its record, never by its name alone; a second job of a name with a live record is never started. A job's log file is `<worktree>/.agk-session.log`, kept out of git as the record is.
4. **Every AI session is a short job that ends.** The jobs are a conductor review pass; a builder job from its take to tests green and ready for review, then one job per fix list, per merge-of-main or conflict need and per red check (`Q-S0064-1`); and a steward answer pass. A job runs headless in its own worktree `(verify: the runtime's headless flags, one version read)`, posts its result (`Report:`, `Verdict:` or `Question:`), refreshes the working summary and exits. No session waits on GitHub: the waits belong to the supervisor, which starts the next job of a pull request on its event and resumes it from the summary, the newest verdict and the diff (#1310). A long step (a heavy test run under `lock.py`) stays inside one job and is never cut by the supervisor while #1355's signs of work show; SPEC-0058 rule 10's per-kind wall-clock limits stay the outer bound once built.
   - **The working summary carries the reasoning** (`Q-S0064-1`, ruled with conditions). Because a fix list is a new job, the summary that `session.py summary --pr N --file FILE` posts (#1310) has fixed sections: the decisions and why, the alternatives rejected, the risks, how to run its tests, and where it is stuck. A summary with one of them missing is refused, naming the section, and a job ends only after its summary is accepted. The sections fit within `[flow] summary_lines`.
   - **Measured, and reversible.** The fix-list rounds per pull request (the `Verdict: fix list` comments before a clearing verdict) are measured over the merged pull requests before build (c) and again after it. When the rounds rise, one session may continue across a fix list instead of a new job; the figure and the choice are recorded in build (c)'s follow-up.
5. **No tabs to manage.** Jobs run in the background with the log file of rule 3. With `[autopilot] show_jobs = true` a job also shows in a terminal tab that closes when it ends; the default is `false`. One command, `agk status` (an installed script of build (a), `scripts/agk/autopilot.py status`), lists the running jobs (what each does, since when, its last event), the queue, what waits on the owner, the held jobs and why the supervisor is quiet; it reads the records and makes at most the calls of one pass, and posts nothing.
6. **The steward is the only interactive session.** In solo mode it is the person's front door (SPEC-0062); in team mode one per reviewer machine, first come first served (SPEC-0063). When a question waits and no steward is open, the supervisor starts a short steward job with `AGK_STEWARD_START=conductor` in its environment (SPEC-0063 rule 4), which answers from evidence only and relays and approves nothing, as SPEC-0063's third question was ruled. SPEC-0059 rule 2's two starts (the conductor's start of the steward and the steward's start of the conductor, #1333) become the supervisor's starts when build (b) lands.
7. **One setting.** `[autopilot] mode = "off" | "assist" | "on"` in `agk.toml`, refused naming the setting when it holds another value. It replaces setting `auto_start`, `launch_adapter`, `[capacity]` and the watchdog's task separately: for one release after build (d) those settings are still read when `[autopilot]` is absent, and `agk doctor` warns `autopilot-settings` naming them; then they are read only from the new table.
   - **`off`:** nothing starts by itself; each pass prints the commands a person would run.
   - **`assist`:** the supervisor keeps the conductor and the steward going and starts a builder only after the owner's yes in the steward (`Q-S0064-2`, `Q-S0064-8`).
   - **`on`:** everything runs round the clock, within the stop rules of rule 12.
   - **The command.** `agk autopilot on|off|status` installs or removes the one scheduler entry, runs the machine checks of rule 11 and prints the status. A protected change to `agk.toml` (such as `mode`) still comes as a pull request with its ADR; the command prints that change and edits no tracked file.
8. **A cost budget, built but relaxed by default.** `[autopilot] daily_budget` is a whole number of tokens, or the day's spend once brief #1283's records exist, and is absent or `"off"` by default: then nothing is limited, and the day's spend is still shown in `agk status` and the daily list. When a project sets a figure, reaching it stops new build and fix jobs, lets running ones finish, keeps review and owner-answer jobs, and tells the owner once (one line in `agk status`, the daily list and one steward note). `agk autopilot budget off` relaxes it at once, for the rest of the UTC day with `--today` or until set again, with no file edit and no pull request: the relaxation is kept in `<git dir>/agk/autopilot.json` and printed in `agk status`. A spend that cannot be read is `unknown`, never 0 (`Q-S0064-6`).
9. **Crash-loop back-off.** A job that fails, or ends with no progress (no push, no post and no change of its summary), twice in a row for the same pull request is held: `held (failed twice)`, named in `agk status` and in the next conductor pass, and not retried until its pull request changes (a new head, a new comment by a listed author) or a person runs `agk autopilot retry <n>`. Restarts follow #1355's at most one per hour.
10. **Health figures.** Each pass appends one line to `agk-autopilot.jsonl` in the user's temp folder, never in the checkout: jobs started, ended, failed and held, the time from each event to its job's start, and, from #1283 once built, tokens per merged pull request (else `unknown`). `agk status --week` prints the week's figures. The file holds numbers, kinds and times only, never a comment's text or a secret.
11. **Machine checks.** `agk autopilot on` checks that the scheduler entry runs while nobody is signed in where the OS allows it, and that sleep is off or a wake timer is set while autopilot is on `(verify: per OS)`, that free memory holds one builder (`builder_memory_gb`), that `gh` is signed in, and that the adapter is set and runs. It warns, naming the setting, and never changes power settings itself.
12. **Clear stop rules.** The supervisor starts nothing new when no brief is ready and nothing waits on AGK; when every remaining item waits on the owner (parked, SPEC-0059 rule 10); when the project is paused (session rule 33); in `[flow] owner_rest_hours` for owner-only steps (`Q-S0064-3`); when free memory is below one builder; or when the GitHub limit is low (#1335's waits). It says so once in `agk status` and in the daily list, and checks again on every pass.
13. **By mode.**
    - **Local, one machine:** the scheduler runs the supervisor, and jobs are local processes.
    - **Local, several machines:** each machine runs its own supervisor with its own capacity; a job is claimed on GitHub before it starts (`taken:` and the lease), so two machines never run one job, and a supervisor never restarts a job another machine started until that job's take lapses (`Q-S0064-4`).
    - **CI mode:** the cloud launcher task is the supervisor and jobs are cloud sessions; no workflow, ruleset or required check changes.
    - **Personal mode (SPEC-0041):** the supervisor is optional; `agk next` runs one job in the foreground and ends; nothing is posted.
    - **Solo and team** change only who answers and approves (SPEC-0062, SPEC-0063), never how work runs.
14. **What is kept from work in flight.** Brief answer 2: SPEC-0059 rule 2's starts become the supervisor's when build (b) lands; #1355's process record and idle rule are the job record of build (a); #1310's summary and `watchdog --pass` are reused; #1335's limit waits are the supervisor's. Nothing of these is built twice.
15. **What changes, each by its build's ADR.** Brief answer 3: session rule 18 (builders no longer wait in a session) and session rule 10 (no session runs `watch`), `kit/templates/runtime/builder.txt` and `conductor.txt`, `.claude/agents/conductor.md` (no builder starts, no `/loop` needed), the two adapters (a background job mode with a log file), `conductor.py watchdog` (grows into the supervisor), `launch.py` (the supervisor's starter), `docs/guides/local-mode.md` and `docs/guides/getting-started.md`, and the new `[autopilot]` table. These touch the protected classes `config/`, `kit/`, `.claude/`, `scripts/agk/`, `tests/kit/`, `tests/kit_dev/` and `agk.toml`. This intake edits none of these files.
16. **The builds, in order.** Each is tests first, about 300 changed lines or fewer, from the default branch, after #1355 (merged), invented data only (`example.com`), a `[[testing.map]]` entry for each new script, and no workflow change.
    - (a) The job record (rule 3) and `agk status` (rule 5), with `agk status --week` and the health file (rule 10).
    - (b) The supervisor's reconcile pass for the conductor and the steward (rules 2, 6, 12 and 14), with its own ADR for `.claude/agents/conductor.md`. `Depends-on` (a).
    - (c) Builders as short jobs that end at ready and at each fix list and resume from the summary, the summary's fixed sections and their refusal, the fix-list rounds measured before and after, with the supervisor starting them on events and the back-off (rules 4 and 9), with its own ADR for session rules 10 and 18 and `builder.txt`. `Depends-on` (b).
    - (d) The `[autopilot]` table, `agk autopilot on|off|status|budget|retry` and the machine checks (rules 7, 8 and 11), with its own ADR. `Depends-on` (b).
    - (e) The adapters' background job mode and log files, for Windows and Linux, and `show_jobs` (rule 5). `Depends-on` (a).
    - (f) CI mode: the launcher as the supervisor; personal mode: `agk next` (rule 13). `Depends-on` (c) and (d).
17. **Measured goals.** Brief answer 5, in a recorded double with a fake clock (saved GitHub answers, a `gh` stub, a stub adapter and a stub runtime): no session is open while its pull request waits on a verdict or the owner; never two jobs of one name; an event (verdict, answer, merge) starts the pull request's next job within one pass; a quiet hour costs no model start; a builder killed mid-step is restarted within one pass after #1355's idle rule; a working summary missing a fixed section is refused; the fix-list rounds per pull request are measured before and after build (c); a job failing twice is held, not retried; with a budget set, spend stops new build jobs at it, and with the default or `budget off` nothing is stopped; on a 650-brief fixture one pass makes at most 10 counted GitHub calls when nothing changed; `agk autopilot on` takes one command and no file edit by hand on Windows and Linux.

## Tests

Saved GitHub answers, a `gh` stub, a stub adapter, a stub runtime and a fake clock only; no network; invented data only (`example.com`, sessions such as `cb-example-1`); each test carries the marker `REQ-071` with its criterion.

- Rules 2 and 3: a pass with a new verdict on a builder head starts exactly one job for that pull request through the stub adapter, a second pass starts none, a name with a live record is never started twice, a pass with nothing changed starts no model and counts at most 10 GitHub calls on the 650-brief fixture, and a session process with no job record, other than a person's own steward, is reported and never adopted as a job; REQ-071 AC1.
- Rules 4 and 9: a build job ends at ready with its `Report:` and summary, the next job starts only on the verdict, no job runs `session.py watch`, a summary missing one of its fixed sections is refused naming the section, a job with a fresh `lock.py` heartbeat is never stopped, and a job failing twice for one pull request is held until the head or a listed author's comment changes; REQ-071 AC2.
- Rules 3 and 5: jobs run with no tab and a log file each, `show_jobs = true` opens one that closes at the end, and `agk status` lists each job's kind, start and last event, the queue, the owner's waits, the held jobs and the quiet reason, and posts nothing; REQ-071 AC3.
- Rule 6: a waiting question with no steward record starts one steward job with `AGK_STEWARD_START=conductor`, which posts no relay and no approval, and an open steward means no start; REQ-071 AC4.
- Rule 7: `mode = "off"` starts nothing and prints the commands, `assist` keeps the conductor and the steward and starts no builder without the recorded yes, `on` starts all, another value is refused naming the setting, the old settings are read for one release with the `autopilot-settings` warning, and `agk autopilot on` edits no tracked file; REQ-071 AC5.
- Rule 8: with `daily_budget` absent or `"off"` nothing is stopped and the spend is shown, with a figure reached new build and fix jobs are not started while review and owner-answer jobs are, the owner is told once, `budget off` and `--today` relax it with no tracked file changed, and an unreadable spend is `unknown`, never 0; REQ-071 AC6.
- Rules 10 to 12: each pass appends one line to the temp-folder file and none to the checkout, the machine checks warn naming the setting and change no power setting, and each stop rule starts nothing and is said once; REQ-071 AC7.
- Rule 13: two machines' supervisors never run one job and one never restarts the other's before its take lapses, the CI launcher pass starts the same jobs as a local pass, `agk next` in personal mode runs one job and posts nothing, solo and team runs start the same jobs, and no test writes a workflow, the ruleset or a required check; REQ-071 AC8.

## Open questions

Each is a point the brief leaves open, or a name it cites that the code holds otherwise; the reading after it is the most conservative one, and the rules above apply it. `Q-S0064-1` is ruled as read, with two conditions, by the maintainer's answer on #1363 (comment 6900309481), and rule 4 holds the conditions; `Q-S0064-2` to `Q-S0064-8` are ruled as read by the maintainer's answer on #1363 (comment 6901019456). One file each under `docs/runs/decisions/`, and the rules above hold their readings. No question is open.

- Q-S0064-1: may a builder keep its session across fix lists when the machine has memory to spare? Reading: no; the first job runs from the take to ready, then one job per fix list (brief answer 6; rule 4). Ruled as read with two conditions: the working summary gets fixed sections and is refused when one is missing, and the fix-list rounds per pull request are measured before and after build (c), with one session allowed to continue across a fix list if the rounds rise. Brief answer 4's build (c) says "step jobs that end at each milestone", which answer 1 rules out ("not one per milestone, so a builder keeps its reasoning while it builds"); the rules follow answer 1.
- Q-S0064-2: is `assist` the default for a new project? Reading: yes; `on` only by the owner's choice, and a project with no `[autopilot]` table keeps today's settings for one release (brief answer 6; rule 7).
- Q-S0064-3: may jobs run during the owner's rest hours? Reading: yes for build and review jobs, no for owner-only steps (brief answer 6; rule 12).
- Q-S0064-4: may the supervisor of one machine restart a job another machine started? Reading: no, only after that job's take lapses (brief answer 6; rule 13).
- Q-S0064-5: SPEC-0058 (Approved, unbuilt) holds a long-running dispatcher service with short jobs per item, which the brief does not name. Reading: this spec does not edit SPEC-0058; the supervisor is a scheduler-run pass, not that service, it reuses SPEC-0058's job kinds and per-kind limits, and the job record is #1355's `.agk-session-pid`, not a second file under `<git dir>/agk/jobs/`; whether SPEC-0058's unbuilt builds are withdrawn is the owner's ruling (rule 1).
- Q-S0064-6: with a budget set, does a spend that cannot be read stop new build jobs? Reading: yes; the owner set a limit, so an `unknown` spend starts no new build or fix job and says so once, while review and owner-answer jobs still run; with the default or `budget off` nothing is stopped (rule 8).
- Q-S0064-7: the brief names `agk status`, `agk autopilot` and `agk next` and no script. Reading: one new installed script, `scripts/agk/autopilot.py`, holds them, as `agk doctor` is `doctor.py`, and the supervisor's pass stays `conductor.py watchdog --pass`, which brief answer 3 says grows into it (rules 2, 5 and 7).
- Q-S0064-8: in `assist`, how is the owner's yes to a builder start recorded? Reading: as the steward's relay of the owner's own words (SPEC-0059 rule 5's form, SPEC-0063 rule 6 in team mode), or the person's own `agk next --brief <n>`; a supervisor-started steward job, which relays nothing, never gives it (rules 6 and 7).
