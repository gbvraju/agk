# SPEC-0045: Each kind of work runs on the model it needs and its token usage is recorded

- Status: Draft
- Owner: reviewer group (a team from config/reviewers.yaml)
- Requirements: REQ-052

Status is `Draft` or `Approved`. An Approved spec is owned by its reviewer group; agents propose patches.

Written by the intake of one sentence (SPEC-0012), brief #591: "AGK runs each piece of work on the model and effort its complexity needs, starts small follow-ups with a lean prompt, and records the tokens each pull request used, without lowering any gate." The owner's decision, quoted as data from the brief (dated 2026-11-06 in the brief, chat): "go ahead ... choose the model and efforts based on the work or task complexity. Best token optimization without loosing speed and quality of the product." It is a ruled exception to plan #542's requirement freeze, limited to three parts (the model table, the lean prompts and escalation, the usage line); dashboards and budgets stay parked. It is generic: it names no project and no vendor, and every check of a build reads files and fixtures with no network. Plan #542 asks for a short spec: ten rules, with Tests bullets below. The points the brief leaves open are `Q-S0045-1` to `Q-S0045-14` below, each with the conservative reading the rules apply until a person rules. Negative cases: a malformed table, a brief that cannot be read and a missing usage line each lower nothing: they are refused naming the setting, give the highest kind, or count as `not reported`.

## Rules

1. **Nothing is lowered.** A tier, an effort or a kind chooses only which model a session runs on, at which effort, and what it reads first (rule 7). It never removes, skips or weakens a check, a test, a gate, a review, a verdict or a required reading of a full build, and never changes who reviews or who decides. With no `[models]` table each kind gets the defaults of rule 2, and nothing else changes from the default branch today.
2. **Kinds, tiers and efforts.** An optional `[models]` table in `agk.toml` maps a work kind to a tier and an effort, as `<kind> = { tier = "<tier>", effort = "<effort>" }`. The kinds are `design` (an intake, a spec, architecture, the merge path, security and guard work), `review` (the conductor's verdicts and every review agent), `build` (an ordinary build of an Approved spec), `small` (a brief of `Size: S` that changes no protected class other than the test folders, `Q-S0045-3`) and `mechanical` (a status commit, a merge of the default branch without a conflict, a body fix; `Q-S0045-5`). The tiers are `strongest`, `mid` and `fast`; the efforts are `low`, `medium` and `high` `(verify: the effort names a runtime accepts, Q-S0045-2)`. The defaults, which a kind absent from the table gets: `design` and `review` strongest at high; `build` strongest at medium; `small` and `mechanical` mid at low `(verify: that these are what the conductor uses today; no file of the repository records it, Q-S0045-14)`. A kind, tier or effort outside these lists, or a value that is not a string, is refused naming the setting (`setting: models.<kind>`), never the value. `review` set below `strongest` is refused (rule 6).
3. **Tiers, never vendor strings.** The `[models]` table names tiers only. A project maps a tier to its own model name in one place, an optional `[models.names]` table (`strongest = "<the project's model name>"`), and nowhere else (`Q-S0045-1`). The kit's own files never hold a model name: the kit's `agk.toml` and its templates carry no `[models.names]`, and without it the launch prompt names the tier and effort, and the person or the launch adapter picks the model.
4. **The kind from the brief.** `python3 scripts/agk/session.py kind --brief N` (GET only, posts nothing) prints one line, `kind: <kind>`, computed from the brief's `Size:` and `Touches:` lines alone by this rule, in order: a missing, repeated or unreadable `Size:` or `Touches:` line gives `design`; a `Touches:` glob that is `**`, or that matches `docs/requirements.md`, `docs/specs/`, `docs/adr/`, `constitution/`, `.github/`, `config/reviewers.yaml`, `.claude/hooks/`, `scripts/agk/merge_cleared.py`, `scripts/agk/route.py` or a guard file, gives `design` (`Q-S0045-4`); `Size: S` with every glob matching no protected class (`config/protected-paths.txt`) other than `tests/kit/` and `tests/kit_dev/` gives `small`; anything else gives `build`. `review` and `mechanical` are never printed for a brief. The conductor may raise a brief's kind (to `build` or `design`) and never lowers it; a session runs at the kind it was given, or at the kind `session.py kind` prints when it was given none.
5. **Escalation, never a quality loss.** A builder on a tier below `strongest` stops, pushes nothing more and posts `Report: <head> escalate <reason>` on its pull request (session rule 17) when the same check fails on two runs in a row (`Q-S0045-8`), when it meets a conflict it cannot resolve (session rule 15), or when its change would touch a protected class that its brief's `Touches:` does not name. The conductor then restarts the work one tier up (`fast` to `mid`, `mid` to `strongest`) with at least the effort of `build`, on the same branch and the same pull request (session rule 9), never a second one. A builder already on `strongest` never escalates: it asks with `Question:` (session rule 21) (`Q-S0045-7`). A builder whose prompt names no tier treats itself as below `strongest` (`Q-S0045-6`).
6. **Reviews.** A reviewer, the conductor and every review agent (`.claude/agents/`) run on `strongest`, at an effort no lower than `high` for a first review. A first review reads the whole diff. A re-review defaults to the diff from the head its last verdict named to the new head, plus the whole of each file that verdict's findings named (folds in #489); it reads the whole diff when that head is not an ancestor of the new head or when a merge of the default branch changed a file of the pull request's own diff (`Q-S0045-10`). The conductor may always read more; nothing here lets it read less on a first review.
7. **Lean prompts.** A `small` or `mechanical` session reads only `CLAUDE.md`, `constitution/principles.md` and `config/core-rules.md` (the core rules, which say the constitution is core and short), the brief or the follow-up message, and the files these name; it still runs session rule 33's pause check and session rule 31's pre-push run (`Q-S0045-9`). A `build`, `design` or `review` session keeps today's reading list unchanged. The launch prompt (`launch.py prompts`) and the conductor's follow-up name the kind, the tier, the effort and, for a lean session, the files to read.
8. **Usage recorded.** Every builder `Report:` line ends with `Usage: <n> tokens` when the runtime shows the figure, else `Usage: not shown`. The reader of SPEC-0033 rule 8 (`metrics.usage_of`, carried by `facts.py` and summed by `product_report.py`, REQ-040) sums the figures per pull request; a `Report:` with `Usage: not shown` or with no usage counts as `not reported`, never as 0 and never as an estimate. No new check refuses a `Report:` line: the comments are on GitHub and checks make no network call (`Q-S0045-11`). The sum per kind is printed by a read-only command of build (d) that reads the facts document; it adds no field to `report.json` or to the metrics columns, so no Approved spec changes (`Q-S0045-12`).
9. **Measured.** One week after build (d) lands, the same read-only command prints, for the 7 days before build (b) merged and the 7 days after build (d) merged, per kind: the merged pull requests, their summed and per-pull-request tokens (with the count that were `not reported`), the lead time (open to merge, hours) and the rework rate (fix-list verdicts per merged pull request), so a saving that cost quality is visible (`Q-S0045-13`). It prints and blocks nothing, and changes no setting.
10. **The builds, in order.** Each is tests first, about 300 changed lines or fewer, from the default branch, cites ADR-0289 and records its decisions under `Decisions taken:` (plan #542). A build that finds it must change an Approved spec stops and asks (amendment 121, reserved, is used only then).
    - (b) The `[models]` table, its refusals and `session.py kind` (rules 2 to 4): `agk.toml`, `scripts/agk/` (the table's reader, `session.py`), `tests/kit/`. No dependence.
    - (c) The conductor and builder instructions (rules 5 to 7): `.claude/agents/` (conductor, architect-review, reviewer, shadow), `config/session-rules.md` and `config/core-rules.md` (escalation, lean reading list), `CLAUDE.md` only if its compaction-recovery list needs the lean exception, `scripts/agk/launch.py` (the kind, tier and effort in a prompt), `tests/kit/`. `Depends-on` (b).
    - (d) The usage line and the sums (rules 8 and 9): the builder instructions' `Report:` form (in `config/session-rules.md` rule 17's text), the read-only sum by kind under `scripts/agk/`, `tests/kit/`. `Depends-on` (b).

## Open questions

Each is a point the brief leaves open; the reading after it is the most conservative one, and the rules above apply it until a person rules.

- Q-S0045-1: where does a project map a tier to its model name? Reading: one optional `[models.names]` table of `agk.toml`; the kit ships none and holds no model name, and without it the person or the launch adapter picks the model for the tier the prompt names (rule 3).
- Q-S0045-2: which effort names? Reading: `low`, `medium` and `high` only, marked `(verify)` until a runtime's documentation is read; any other value is refused (rule 2).
- Q-S0045-3: the brief says "an XS or S brief", but a brief's size is only `S`, `M` or `L` (`check_brief.py`, `session.brief_problems`). Reading: `small` is `Size: S` only; no `XS` size is added (rules 2 and 4).
- Q-S0045-4: which `Touches:` globs make a brief `design`? Reading: the list of rule 4 (the requirements, specs, ADRs, constitution, workflows, reviewers file, hooks, merge path and guard files) and `**`; a glob that may match any of them counts as matching (rule 4).
- Q-S0045-5: `mechanical` is not a brief's kind. Reading: the conductor names it in a follow-up message only for a status commit, a merge of the default branch without a conflict, or a body fix; a follow-up that needs any other change takes its brief's kind (rule 4).
- Q-S0045-6: a session may not see its own model. Reading: it acts on the tier its prompt names, never switches model itself, and with no tier named treats itself as below `strongest`, so it escalates rather than goes on (rule 5).
- Q-S0045-7: what happens to an escalation on `strongest`? Reading: none; the builder asks with `Question:` and waits (session rule 21) (rule 5).
- Q-S0045-8: what is "a failing check twice"? Reading: the same check failing on two runs in a row in the session, at the same head or at two heads, a flake included (rule 5).
- Q-S0045-9: does a lean session still read the constitution and run its pause check and pre-push run? Reading: yes; `config/core-rules.md` says the constitution is core and read whole, and the two runs are commands, not reading (rule 7).
- Q-S0045-10: when does a re-review read the whole diff? Reading: for a first review, when the last verdict's head is not an ancestor of the new head, and when a merge of the default branch changed a file of the pull request's own diff; otherwise the diff since that head plus each file its findings named (rule 6).
- Q-S0045-11: the brief's build (d) names "the usage line in the Report check", but no check of `Report:` lines exists, and checks make no network call (CLAUDE.md item 5). Reading: no new gate; the builder instructions require the line and the reader counts a missing figure as `not reported` (rule 8).
- Q-S0045-12: the brief calls the reader "the existing REQ-034 reader", but REQ-034 is the intake's kit version; the usage reader is SPEC-0033 rule 8's (REQ-040), in `metrics.py`, `facts.py` and `product_report.py`, and SPEC-0011 rule 72 closes the fields of `report.json`. Reading: the sum per kind is a separate read-only command, so no Approved spec changes and amendment 121 is not used; putting it in the weekly report is a later decision (rule 8).
- Q-S0045-13: which weeks does the measurement compare? Reading: the 7 days before build (b) merged and the 7 days after build (d) merged, with `not reported` counted, never estimated (rule 9).
- Q-S0045-14: the brief says the defaults are what the conductor uses today, but no file records a model or an effort. Reading: the defaults of rule 2, as the brief lists them, marked `(verify)` (rule 2).
