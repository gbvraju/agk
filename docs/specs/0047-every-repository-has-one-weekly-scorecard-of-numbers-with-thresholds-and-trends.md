# SPEC-0047: Every repository has one weekly scorecard of numbers with thresholds and trends

- Status: Approved
- Owner: reviewer group (a team from config/reviewers.yaml)
- Requirements: REQ-054

Status is `Draft` or `Approved`. An Approved spec is owned by its reviewer group; agents propose patches.

Written by the intake of one sentence (SPEC-0012), brief #649: "Every repository on AGK has one weekly scorecard of hard numbers with thresholds and trends, so that a slip in speed, quality, security or freshness opens an issue before anyone notices it, whether AGK is still being built, is frozen in use, or the world around it has moved on." It is item 10 of tracker #630, widened by the owner's direction, quoted as data from the brief (conductor chat, 2026-11-06): "this is the important AGK to sustain and stay ahead, solve the purpose otherwise it can go outdated soon, make it live or think beyond case 1 and case 2 also if it needed to go beyond". It is a ruled exception to plan #542's requirement freeze, like REQ-052 and REQ-053. It is generic: it names no project, and every check of a build reads files, fixtures and saved responses with no network. The points the brief leaves open are `Q-S0047-1` to `Q-S0047-22` below, each with the conservative reading the rules apply until a person rules.

## Why: three ways AGK degrades

- **Case 1, AGK keeps building itself.** Numbers slip one small step at a time, and each step passes review. Reading today's numbers against a hard line catches this.
- **Case 2, AGK is frozen and only used.** Nobody is watching, so a slip has no reader. Thresholds that open issues give it one.
- **Case 3, the world moves.** Models, runtimes, GitHub, scanners and practices change while AGK's pins, `(verify)` marks and residual due dates stand still, so AGK goes outdated without a single number slipping. Freshness numbers and trends catch this.

So the scorecard reads three kinds of signal, all numbers: a **level** (a number against a hard line), a **trend** (the same number against its own last four weeks: worse three weeks in a row is a finding even below the line, which is how slow drift is caught) and **freshness** (how far behind the world a pinned thing is, and how old an unverified assumption is). The scorecard changes nothing and blocks nothing; it opens issues. A threshold is a decision (an ADR), and nothing lowers one silently.

## Rules

1. **The metrics.** The scorecard has one row per metric, in this order, each a number of the week that ends on the run date (`--today YYYY-MM-DD`, default `date -u`), and higher is worse for every one of them. Where a reader exists on the default branch the build reuses it, named here as found in the code; where none does, the build adds it to `scripts/agk/scorecard.py` (`Q-S0047-1`).
   - `full_check_minutes`: the median duration in minutes of the full `governance` runs of the default branch (run name `governance full`, as `full_run.py` reads it).
   - `prepush_seconds`: the median seconds of the project's test step in those runs (`metrics.project_test_seconds`); a builder's local `prepush.py` run is never read, as it leaves no record.
   - `red_hours`: the hours the issue `The default branch is red` (SPEC-0032 rule 7, `route.py`) was open in the week.
   - `flaky_rate`: governance runs with more than one attempt whose last attempt passed, over all governance runs of the week, in percent (`Q-S0047-12`).
   - `fix_list_rate`: `Verdict: fix list` comments by a listed verdict author (the parse of `metrics.verdicts`) over pull requests merged in the week, in percent.
   - `lead_time_hours`: the median hours from open to merge of the pull requests merged in the week (`metrics.hours_between`, as `facts.flow_hours` reads `created` and `merged`).
   - `restore_hours`: the median hours from open to close of the issues `The default branch is red` closed in the week (`Q-S0047-13`).
   - `ci_minutes_per_merge`: the CI minutes of the week over the pull requests merged in it, as `minutes.py` computes `per_merged_pull` for a month, over a week.
   - `rule_words` and `rule_lines`: the words and rule lines an agent reads, the totals of `rules.py budget` (brief #647, ADR-0310) (`Q-S0047-14`).
   - `old_failure_issues`: open `found-bug` failure issues (SPEC-0046 rule 3, the `Failure-signature:` line) older than 7 days.
   - `verify_marks` and `verify_oldest_days`: the `(verify)` marks in specs with `Status: Approved`, and the age in days of the oldest one, dated by `git blame` of the default branch for the line that holds it (`Q-S0047-18`).
   - `residuals_past_due`: residual bullets and register lines whose `(due YYYY-MM-DD)` is before the run date, by the rule of the drift audit's D4 (`drift_audit.d4_documents` and `drift_audit.d4_register`).
   - `pins_behind` and `pins_oldest_gap_days`: the pinned tools and actions whose pin is behind their newest upstream release, and the largest gap in days between the pinned release and the newest (rule 8, `Q-S0047-11`).
   - `kit_releases_behind`: how many kit releases the project's `version` (`agk.toml`, equal to `kit_version` of the installed `kit/manifest.json`) is behind the newest kit release (`Q-S0047-10`).
   - `stale_guides`: the guides under `docs/guides/` whose last change on the default branch is older than the last change of a script they name (`Q-S0047-19`).
2. **Where the numbers come from.** Only the repository's own git history and files, and its issues, comments, pull requests and CI runs read with `gh api --method GET` (or saved responses with `--api-dir`, as `metrics.py` and `facts.py` take them), and, for upstream versions only, at most one GET per pinned tool or action and one for the kit's releases. The scorecard posts nothing and writes nothing except through rule 5's issue writer in the weekly job. No reader runs in a governance check, `make governance` or `prepush.py`, because checks make no network call (CLAUDE.md item 5); the scorecard runs in the weekly job only (rule 6), and on demand by a person as `python3 scripts/agk/scorecard.py` (read-only, GET only, prints the table and writes nothing). A value whose inputs cannot be read is `unknown`, never 0, as SPEC-0007 rule 10 says for `metrics.py` (`Q-S0047-2`).
3. **The settings.** An optional `[scorecard]` table of `agk.toml` holds, per metric, `<metric> = <number>` (its line) and two windows, `trend_weeks` (default 4) and `close_weeks` (default 2). Without the table every line is the kit default below; each default is marked `(verify)` until build (f) has measured four weeks of this repository's own numbers. A malformed table, an unknown key, a value that is not a number or a negative number is refused naming the setting (`setting: scorecard.<key>`), never the value (principle 8). Because `agk.toml` is protected, a changed line needs an ADR in the same pull request (CLAUDE.md item 3), so no line moves silently (`Q-S0047-3`). The kit defaults, all `(verify)`: `full_check_minutes = 20`, `prepush_seconds = 300` (the `[testing] budget_seconds` default), `red_hours = 4`, `flaky_rate = 2`, `fix_list_rate = 50`, `lead_time_hours = 48`, `restore_hours = 4`, `ci_minutes_per_merge = 30`, `rule_words` and `rule_lines` equal to the totals of `config/rule-budget.txt` where that file exists, `old_failure_issues = 0`, `verify_marks` none (a count is reported, the line is on the age), `verify_oldest_days = 90`, `residuals_past_due = 0`, `pins_behind` none (the line is on the gap), `pins_oldest_gap_days = 180`, `kit_releases_behind = 3` and `stale_guides = 0`. A metric with no line is reported and judged by its trend only.
4. **A finding.** A metric is a finding in a week when its value is above its line (a level finding) or when, within the last `trend_weeks` weeks, each of the last three weekly values is higher than the one before it (a trend finding, even below the line). An `unknown` value is never a finding and breaks a run of three; a week with no value is `unknown` (rule 7). A finding is the metric name, the kind (`level` or `trend`), the value, the line and the earlier weeks' values, numbers only.
5. **One issue per metric.** As SPEC-0046 keeps one issue per failure signature, the scorecard keeps one issue per metric name. A finding whose metric has no open scorecard issue opens one, titled `scorecard: <metric>`, labelled `agk-scorecard` and never `agk-brief` or `found-bug`, so `session.py next` never offers it (`Q-S0047-4`); a finding whose metric has an open issue adds one comment with that week's numbers and never opens a second issue. An open issue closes itself, as completed, after `close_weeks` consecutive weeks in which its metric was neither a level nor a trend finding; an `unknown` week counts as neither inside nor outside and resets nothing (`Q-S0047-16`). The issue and its comments hold numbers, the metric name, the line and the setting that sets it, and never a transcript, a log, a comment's text, a login or a path that names a person (`Q-S0047-20`). The text is passed through `guard.scan_text` (SPEC-0042 rule 10) before it is posted and is withheld, with `withheld: <kind> <count>`, when it finds anything.
6. **Where it runs.** The weekly drift audit (SPEC-0004) carries the scorecard as a listed section that never blocks: one job and one audit issue a week, with the scorecard's table as its last section before the note of SPEC-0004 rule 23, and the per-metric issues of rule 5 beside it. SPEC-0004 is Approved and today says the audit makes no network call and uses no `gh` (rule 3), writes only its one issue (rules 2 and 13), writes nothing on a clean run (rule 14), never closes an issue (rule 14) and runs no `gh issue comment` or `gh issue close` (rule 21); the scorecard needs each of those changed for its own step only, so the change is amendment 128 of SPEC-0004, which needs the owner's `Approve: SPEC-0004` line. `drift_audit.py` itself stays as it is: the scorecard is a separate step of the same job running `scorecard.py`, and the audit's D1 to D9 are unchanged (`Q-S0047-5`). The workflow change (the step, and `actions: read` for the CI runs, `Q-S0047-15`) is on the owner's hold list, so build (e) waits for the owner's yes and writes its own ADR (session rule 36). Until amendment 128 is approved and build (e) merges, the drift audit is unchanged and the scorecard runs only when a person starts it.
7. **Trend history.** The earlier weeks' numbers are read from the weekly audit issue, not from a file: the scorecard section of the audit issue's body carries the last `trend_weeks` weeks of every metric, and each run reads the previous body (as `drift_audit.py --previous FILE` reads the earlier coverage and mutation figures today) and writes the new body with the oldest week dropped. So no file of the repository grows. A week whose numbers are missing (the issue was closed by a person, the run did not happen, the body cannot be read) is `unknown`, never 0, and a metric with fewer than three known weeks has no trend finding (`Q-S0047-6`).
8. **Freshness readers.** The pinned things are the `uses:` lines of `.github/workflows/*.yml`, pinned to a full commit SHA with the release tag in a comment (SPEC-0004 rule 17), and the versions the project pins in `pyproject.toml` with `==` (`Q-S0047-11`). For each, one GET of the newest release of its upstream (`repos/<owner>/<name>/releases/latest` for an action; the package index's JSON for a Python package `(verify)`); an upstream that cannot be read is `unknown` for that pin, never `0 behind`. The gap in days is the newest release's date minus the pinned release's date. `verify_marks` reads only specs whose Status is `Approved`. The kit's releases are read with one GET of the kit's releases list; when the kit's repository cannot be resolved from the installed copy, `kit_releases_behind` is `unknown`.
9. **Freshness of AGK itself.** The kit's own repository runs the same scorecard every week, also while AGK is frozen, and its own lines are set by build (f). A metric past its line opens the issue of rule 5, and that issue is what tells the conductor to file a brief (`.claude/agents/conductor.md` reads open `agk-scorecard` issues as it reads `found-bug` ones; changing that file is build (e)'s ADR's or a later one's, `Q-S0047-8`). The kit's scorecard also has `rule_line_oldest_days`: the age of the oldest rule line in the agents' files, dated as rule 1 dates a `(verify)` mark; its line and its promotion step are those of the guard ladder (brief #645), so until the ladder is on the default branch the row is reported and has no line. This is how case 3 is caught while AGK is frozen: the weekly job keeps running in every project, AGK's own repository included, and GitHub's own notifications of the issue are its only messages: no mail, chat or other channel is added (`Q-S0047-17`).
10. **Privacy and the fleet.** A project's scorecard, its numbers and its issues stay in that project's own repository. The kit ships no collector, and no command of the kit sends a project's number, name or path anywhere else. A later decision, parked in the residual below, may let a project publish counts only, by the owner's choice, to a place the owner names; until then nothing of a project moves into the kit by itself. Tests use invented data (`example.com`) and saved responses; pilot and customer data is never read, quoted or used as a fixture (`Q-S0047-7`).
11. **The builds, in order.** Each is tests first, about 300 changed lines or fewer, from the default branch, records its decisions under `Decisions taken:` and cites `Covered-by: ADR-0311` once ADR-0311 is Accepted, except build (e), which changes a workflow and so writes its own ADR (session rule 36). A build that finds it must change an Approved spec stops and asks (`Q-S0047-9`).
    - (b) The readers that exist (rules 1 to 3): `scripts/agk/scorecard.py` (the level metrics of rule 1 from the readers of `metrics.py`, `facts.py`, `minutes.py`, `full_run.py` and `rules.py`, the table, `unknown`), the `[scorecard]` reader and its refusals in `scripts/agk/config.py`, `tests/kit/` with saved responses, the `[[testing.map]]` entry in `agk.toml` and `kit/manifest.json` (a new installed script). No dependence.
    - (c) The freshness readers (rules 1 and 8): `verify_marks`, `verify_oldest_days`, `residuals_past_due`, `pins_behind`, `pins_oldest_gap_days`, `kit_releases_behind` and `stale_guides` in `scorecard.py`, `tests/kit/` with saved release responses. `Depends-on` (b).
    - (d) Findings, trends and the issue writer (rules 4, 5 and 7): `scorecard.py findings` and `scorecard.py issues` (open, comment, close through `gh` with the job's token; the decisions in the tested script, as `drift_audit.choose_action` keeps them), the body section with the last four weeks, `tests/kit/` with saved responses and a `gh` stub. `Depends-on` (c).
    - (e) The weekly wiring (rule 6): amendment 128 of SPEC-0004 (`docs/runs/proposed-spec-amendments-128.md`), the scorecard step and `actions: read` in `.github/workflows/drift-audit.yml`, the `agk-scorecard` line of `.claude/agents/conductor.md`, `tests/kit/` (the workflow shape tests of SPEC-0004 rule 21 as amended), a changelog fragment. Its own ADR, the owner's `Approve: SPEC-0004` line and the owner's yes on its pull request. `Depends-on` (d).
    - (f) The kit's own lines (rules 3 and 9): the `[scorecard]` table in this repository's `agk.toml`, set from four weeks of its own numbers read from the audit issue, the `(verify)` marks of rule 3's defaults removed where measured, `tests/kit/`. `Depends-on` (e) and four weekly runs after it.

## Tests

Fixtures in `tmp_path`, saved GitHub responses and a `gh` stub only: no network, no install, invented data (`example.com`), and each test carries the marker `REQ-054` with its criterion. Rule 11's order is checked by review.

- Rules 1 and 2: saved runs, pull requests, comments and issues of one week give each level metric's value; a response that cannot be read gives `unknown`, never 0; `scorecard.py` makes only GET calls through the stub and writes no file (a before and after snapshot); no governance check or `prepush.py` step imports or runs it; REQ-054 AC1.
- Rule 3: no table gives the kit defaults; a malformed table, an unknown key, a string and a negative value are each refused naming `scorecard.<key>` and not the value; REQ-054 AC2.
- Rules 4 and 5: a value above its line opens one issue through the stub; a second week of it adds a comment and no second issue; three rising weeks below the line are a trend finding; an `unknown` week breaks the run; two weeks inside the line close the issue; the posted text holds numbers only, and a planted invented token in it is withheld with counts only; REQ-054 AC3.
- Rule 4, the negative case: every metric inside its line and no run of three gives no finding, no stub call that writes and no file; REQ-054 AC4.
- Rule 8: saved release responses with a pin two releases behind, a pin at the newest and an upstream that answers 404 give `pins_behind = 1`, the gap in days and `unknown` for the third; a Draft spec's `(verify)` mark is not counted; a guide older than a script it names counts, and one newer does not; at most one GET per pin; REQ-054 AC5.
- Rule 7: a saved previous body with three weeks gives the trend; the new body keeps four weeks and drops the oldest; a missing previous body gives `unknown` weeks and no trend finding; no tracked file changes; REQ-054 AC6.
- Rule 10: the stub sees calls to the project's own repository and the upstream release GETs only; no call carries a project's number, name or path to any other place; REQ-054 AC7.
- Rule 6: after build (e), the workflow shape test finds the scorecard step after the audit step, with `continue-on-error` or an exit that never fails the job, and the permissions `contents: read`, `issues: write` and `actions: read` only; before it, the workflow is unchanged; REQ-054 AC8.

## Proof

REQ-054 AC1: *the numbers, read with GETs only, never in a check.* Rules 1 and 2. REQ-054 AC2: *the lines are settings with defaults and change only by ADR.* Rule 3. REQ-054 AC3: *one issue per metric, opened on a level or trend finding, closed after two good weeks.* Rules 4 and 5. REQ-054 AC4: *a clean week writes nothing and blocks nothing.* Rules 4 and 5. REQ-054 AC5: *freshness is counted.* Rules 1 and 8. REQ-054 AC6: *the trend is read from the audit issue, and no file grows.* Rule 7. REQ-054 AC7: *a project's numbers stay in its repository.* Rule 10. REQ-054 AC8: *the weekly audit carries the scorecard after amendment 128.* Rules 6 and 9.

## Open questions

Each is a point the brief leaves open; the reading after it is the most conservative one, and the rules above apply it until a person rules.

- Q-S0047-1: which readers exist, and under which names? Reading: the names were checked against the default branch: `metrics.py` (`verdicts`, `hours_between`, `project_test_seconds`, `ci_fields`), `facts.py` (`flow_hours`), `minutes.py` (`per_merged_pull`, monthly), `full_run.py` (the `governance full` run name), `drift_audit.py` (`d4_documents`, `d4_register`), `rules.py` (`budget`) and `route.py` (the red-branch issue); `product_report.py` has `median_hours`, and `proof.py` reads no weekly number. Every other metric is new code in `scorecard.py`, which calls these and changes none of them (rule 1).
- Q-S0047-2: may a reader call the network? Reading: only the scorecard, in the weekly job or by a person, with GET requests; never a check, never `prepush.py`, never `make governance` (rule 2).
- Q-S0047-3: where do the lines live, and who changes them? Reading: a `[scorecard]` table of `agk.toml` with kit defaults marked `(verify)`; a change is a protected change with an ADR; a malformed value is refused naming the setting (rule 3).
- Q-S0047-4: which label does a scorecard issue carry? Reading: a new `agk-scorecard`, never `agk-brief` or `found-bug`, so no session takes it unassigned and a failure issue is never confused with it (rule 5).
- Q-S0047-5: the brief puts the scorecard in the drift audit, but SPEC-0004 (Approved) says the audit makes no network call, writes one issue only, writes nothing on a clean run, never closes or comments on an issue. Reading: `drift_audit.py` is unchanged; the scorecard is its own step of the same weekly job, and amendment 128 changes SPEC-0004 rules 2, 3, 13, 14 and 21 for that step only, with the owner's `Approve: SPEC-0004` (rule 6).
- Q-S0047-6: the brief reads the trend "from the past weekly audit issues", but SPEC-0004 rule 13 keeps one open audit issue and replaces its body each week, so past weeks are not separate issues. Reading: the audit issue's scorecard section carries the last four weeks, read from the previous body as `drift_audit.py --previous` does; a missing week is `unknown` (rule 7).
- Q-S0047-7: may numbers leave a project? Reading: no; the kit ships no collector, and the fleet view is a parked residual (rule 10).
- Q-S0047-8: who acts on a scorecard issue? Reading: the conductor files the brief, as it does for a `found-bug` issue; the line in `.claude/agents/conductor.md` is build (e)'s, and no command files a brief by itself (rule 9).
- Q-S0047-9: may builds cite `Covered-by: ADR-0311` as the brief asks? Reading: yes for (b), (c), (d) and (f), once it is Accepted; build (e) changes a workflow and `.claude/`, so it writes its own ADR (session rule 36) and waits for the owner's yes (rule 11).
- Q-S0047-10: where is "the newest kit release" read? Reading: one GET of the kit's releases; when the kit's repository cannot be resolved from the installed copy the value is `unknown`, and no kit repository name is written into a project (rule 8).
- Q-S0047-11: which pins count? Reading: the SHA-pinned `uses:` lines of the workflows and the `==` pins of `pyproject.toml`; nothing else, until a decision widens it (rule 8 and the residual).
- Q-S0047-12: what is "reruns that passed over runs"? Reading: governance runs of the week whose `run_attempt` is above 1 and whose last attempt passed, over all governance runs of the week; a rerun that failed is not a flake (rule 1).
- Q-S0047-13: how are `red_hours` and `restore_hours` measured? Reading: from the issue `The default branch is red` only: the hours it was open inside the week, and the median open-to-close hours of those closed in the week; a red run with no issue is not counted (rule 1).
- Q-S0047-14: `rules.py` is kit-only and never installed. Reading: `rule_words` and `rule_lines` are read only where `rules.py` is present (the kit's own repository); in an installed project they are `not applicable`, never 0, until a decision installs a reader (rule 1).
- Q-S0047-15: the CI runs need a read the audit workflow lacks. Reading: build (e) adds `actions: read` and nothing else to `drift-audit.yml`, on the owner's hold list (rule 6).
- Q-S0047-16: may the scorecard close an issue, when SPEC-0004 rule 14 says the audit never does? Reading: only its own `agk-scorecard` issues, after two weeks inside the line, and only once amendment 128 is approved; the audit issue itself is still never closed by a run (rules 5 and 6).
- Q-S0047-17: in case 2 nobody reads; what reaches a person? Reading: the issue, and GitHub's own notifications of it; the kit adds no mail, chat or push channel (rule 9).
- Q-S0047-18: which `(verify)` marks count, and how old is one? Reading: marks in Approved specs only, dated by `git blame` of the default branch for the line that holds it (rule 1).
- Q-S0047-19: when does a guide name a script, and when is it stale? Reading: a backticked path `scripts/agk/<name>.py` or `<name>.py` naming a script that exists; stale when the script's last commit on the default branch is newer than the guide's (rule 1).
- Q-S0047-20: what may an issue hold? Reading: numbers, the metric name, the kind, the line and the setting; no text, login or path of a person, and the guard scan withholds anything it finds (rule 5).
- Q-S0047-21: `session.py ids` printed higher numbers than the reserved ones. Reading: the brief reserves REQ-054, SPEC-0047, ADR-0311 and amendment 128, and they are used; the intake check runs with them (`--ids`).
- Q-S0047-22: the brief says "one job and one issue a week" and "one issue per metric". Reading: one weekly job and one audit issue a week, plus at most one open issue per metric beside it (rules 5 and 6).
