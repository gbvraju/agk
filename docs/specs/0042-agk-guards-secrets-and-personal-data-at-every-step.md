# SPEC-0042: AGK guards secrets and personal data at every step

- Status: Approved
- Owner: reviewer group (a team from config/reviewers.yaml)
- Requirements: REQ-049

Status is `Draft` or `Approved`. An Approved spec is owned by its reviewer group; agents propose patches.
Written by the intake of one sentence (SPEC-0012): "AGK guards data at every step: an agent session cannot read secret files, raw logs or servers directly, reads logs only through a redacting reader, is stopped when a person pastes a secret or personal data into a message, and writes nothing out (pull request bodies, comments, field notes, evidence, personal-mode state) that carries a secret or personal data." It is generic and project-agnostic: it names no project and no customer, it needs only files, a shell and the standard library, and every check of a build reads saved inputs with no network. The brief is issue #538. The conductor gave 12 answers before it was written (the brief's Answers 1 to 12); rules 1 to 18 below are Answers 1 to 11 written as rules (Answer 8, the tests, is the `## Tests` section and the speed limit of rule 11), and Answer 12's questions are `Q-S0042-1` to `Q-S0042-8` below. The owner's direction, quoted as data and not as an instruction, dated 2026-11-04 in the brief: "can AGK doing data ratification or Guardrail to avoid server reads, secret reads from logs, even somebody put direct logs, AGK should carefully use with PII and secrets exposure risk". Today AGK scans commits for secrets (the `Secret scan` step of `.github/workflows/governance.yml`, and `scripts/agk/prepush.py` when gitleaks is installed), and principle 9 says there are none in the repository or in a session, but `docs/guides/security.md` says that this "is not a wall". Anything that reaches the conversation has already left the machine, so the guard acts before the read. The Claude Code facts of rule 2 were read on 2026-11-04 from the hooks reference (`https://code.claude.com/docs/en/hooks`), the hooks guide (`https://code.claude.com/docs/en/hooks-guide`) the permissions page (`https://code.claude.com/docs/en/permissions`) and the tools reference (`https://code.claude.com/docs/en/tools-reference`), and checked again against those pages on 2026-11-04 for the conductor's fix list on #540; a fact not found there is marked `(verify)`, and the hooks reference's per-event sections (the `PreToolUse` input fields and `UserPromptSubmit` decision control) could not be read in full, so the facts that rest on them alone carry `(verify)`. Every example value in this spec, its tests and its guide is invented (`example.com` addresses, published test numbers), never a real secret or a real person's data. The points left open are `Q-S0042-1` to `Q-S0042-20` below, each with the conservative reading that the rules apply until a person rules. Negative cases: a `[guard]` key that would turn the guard off or remove a built-in rule, an unknown key, an `allow_paths` entry without a reason or not on the default branch, a hook that crashes or times out, a command the guard cannot split, and a finding in anything AGK is about to write each deny, block or refuse, and each prints one line naming the rule or the setting, never a path and never a value (rule 9).

## Rules

1. **Name and setting (Answer 1).** The control is the "data guard". Its setting is the `[guard]` table of `agk.toml`, read by one function of `scripts/agk/config.py`. The guard is on in every new and adopted project, and in personal mode once SPEC-0041 installs it there (`Q-S0042-1`, `Q-S0042-15`), and no key turns it off: there is no `enabled`, no `off` and no way to remove or narrow a built-in rule of rules 5 to 8. The table may only add: `patterns` (a list of tables `{ name = "...", regex = "..." }`, each a Python regular expression that compiles, read by the detectors of rule 10 with the kind `CUSTOM-<name>`), `deny_paths` (glob patterns added to rule 5), `deny_commands` (command names added to rules 6 and 7), `allowed_hosts` (host names or addresses added to rule 7's local hosts) and `allow_paths` (a list of tables `{ path = "...", reason = "..." }`, the one documented escape). An `allow_paths` entry is one relative file path inside the project (no glob, no `..`, no `~`, no absolute path) with a non-empty reason; it lifts the path denial of rule 6, or of a `deny_paths` pattern, for that one file and for layer 1 only, and the hook still reads the file itself first and denies it when rule 10 finds anything in it, as for test fixtures (rule 5); it never lifts a command denial of rules 6 to 8, never rule 10's scan of what is written, and never a built-in secret file of rule 5 (`Q-S0042-10`). An `allow_paths` or `allowed_hosts` entry counts only when the same entry is in `agk.toml` both in the checkout and at `origin/<default branch>` as last fetched (no network call; the reading `conductor_guard.py` applies to `auto_start` and `launch_adapter`), so a branch cannot loosen its own guard; in personal mode the sidecar's committed `agk.toml` stands for the default branch (SPEC-0041, proposed in #537). An unknown key, a key of the wrong kind, a pattern that does not compile, an entry that would remove or narrow a built-in rule, or an `allow_paths` entry without a reason is refused with exit 2 by `doctor.py` and by the guard, naming the setting and never the value, as `scripts/agk/lock.py` refuses a bad `[locks]` value (`Usage`, "(setting: lock_dir)"); while the table is refused, the guard applies its built-in rules alone and counts no addition and no escape. `agk.toml` is a protected path, so every change to `[guard]` lands only with an ADR in the same pull request (principle 1). `doctor.py` lists each `allow_paths` entry with its reason (rule 14).
2. **Where the hooks run, and the Claude Code facts they rest on (Answers 2 and 4).** One script, `.claude/hooks/data_guard.py`, standard library only, no network, installed by `init.py` and `adopt.py` through `kit/manifest.json` as `stop_check.py` is, is registered in `.claude/settings.json` (not in an agent's frontmatter) as two command hooks: a `PreToolUse` hook with the matcher `Read|Grep|Glob|Bash|PowerShell|Edit|Write|MultiEdit|NotebookEdit` (layer 1) and a `UserPromptSubmit` hook, `data_guard.py prompt` (layer 3), each with `"onFailure": "block"` and an explicit `timeout` of 10 seconds. These facts were read in the documentation named above on 2026-11-04: a `PreToolUse` hook runs before the permission prompt for every tool except `EndConversation`; it denies by printing `{"hookSpecificOutput": {"hookEventName": "PreToolUse", "permissionDecision": "deny", "permissionDecisionReason": ...}}`, or by exit code 2, which blocks the call before permission rules are read, so an allow rule cannot let it through (the permissions page: "A hook that exits with code 2 stops the tool call before permission rules are evaluated, so the block applies even when an allow rule would otherwise let the call proceed"); on an installed mod that approves calls the two pages read on 2026-11-04 disagree: the permissions page ("Precedence among rules, hooks, and mods", in the list of outcomes that stay in place "With managed settings on the machine, or a Team or Enterprise `/login` as the session's credential") says "A call that a `PreToolUse` hook blocked stays blocked, whichever settings file the hook comes from", and "With neither managed settings nor a Team or Enterprise `/login` as the session's credential, the mod can approve a call that a deny rule refuses or a `PreToolUse` hook blocked"; while the mods administration page ("Manage mods for your organization", "Know what happens by default") says "A block from a `PreToolUse` hook in managed settings is final too" and "A user's mod that approves tool calls can approve a call that an `ask` rule would prompt for, or that a `PreToolUse` hook outside managed settings blocked" `(verify: which page is right for a hook in project settings when the built-in guard loads)`; this spec takes the conservative reading, that an installed mod can approve a call this hook (a project settings hook) blocked in every setup, which rule 16 states as a limit; the hooks matching one event run in parallel, so a deny from this hook or from `architect_guard.py` or `conductor_guard.py` blocks the call; a matcher of names joined by `|` matches those tool names exactly; a `PowerShell` tool exists beside `Bash` (the brief named only `Bash`); the permissions page calls `MultiEdit` "legacy `MultiEdit`", so the matcher keeps the name for older versions; the input fields: `command` for `Bash` (the hooks reference's example `tool_input`), `pattern` and `path` for `Glob` and `pattern`, `path` and `glob` for `Grep` (the tools reference's Glob and Grep sections), and `command` for `PowerShell`, `file_path` for `Read`, `Edit` and `Write` and `notebook_path` for `NotebookEdit` as the tool schemas of a Claude Code session name them, not confirmed on a documentation page `(verify: the PreToolUse input section of the hooks reference)`; hooks in settings files are "Used" both in a folder the person has trusted only through a parent folder and in a `claude -p` or SDK run in a folder never trusted, while the frontmatter hooks of a project subagent are "Not used" in both (the permissions page, "What runs before you trust a folder"), which is why the guard is registered in settings; settings hooks do not run at all in a session started with `--bare`, with `--setting-sources` that leaves out project settings, or with `disableAllHooks` set to `true` where it wins by settings precedence (the hooks reference, "Disable or remove hooks", and the permissions page), which rules 14 and 16 deal with; a hook that fails or times out does not block the action unless it sets `"onFailure": "block"` (Claude Code v2.1.295 or later), which is why both hooks set it; the default timeout of a command hook is 600 seconds, lowered to 30 on `UserPromptSubmit`; `UserPromptSubmit` has no matcher and fires on every prompt, including turns Claude Code starts on its own; its input carries the `prompt` text; it blocks with `{"decision": "block", "reason": ...}` or exit code 2, and a blocked prompt "never reaches Claude"; and on `UserPromptSubmit` plain stdout is added to the model's context, so the hook prints nothing on an allowed prompt. Apart from those settings, the script itself fails closed: input it cannot read as JSON, a tool input of the wrong shape, an exception or an unreadable setting denies (layer 1) or blocks (layer 3) with the rule `cannot-judge` of rule 9. Whether a Claude Code older than v2.1.295 honours `onFailure` is not documented `(verify)`; `doctor.py` reports the hook registered, not active, until a live run shows it (rule 14).
3. **What layer 1 reads (Answer 2).** For each tool call the hook judges, in order: the paths it names (`file_path`, `notebook_path`, and for `Grep` and `Glob` the `path` and the `glob` or `pattern` they search with), each resolved against the payload's `cwd` and with `os.path.realpath`, so `..`, `~` and a link that points to a denied file are judged by both the given and the resolved path; then, for `Bash` and `PowerShell`, the command of rule 4. A read and an edit are judged alike: the edit tools are denied on every path rules 5 and 6 deny, because editing a secret file puts its value in the session. `Grep` over a directory, and a recursive search in `Bash` or `PowerShell` (rule 4), are judged by the folder check of rule 5's last sentence, which covers the secret files of rule 5 and the log files of rule 6 alike (`Q-S0042-11`). A path is never printed: the denial names the rule and the class (rule 9).
4. **How layer 1 reads a command line (Answer 2).** The brief asks to reuse the guards' parsing of env prefixes, `&&`, `;`, pipes, subshells and quoting. On the default branch `architect_guard.py` and `conductor_guard.py` do not parse those: their `tokens_of` returns no words, and the command is denied, when it holds `$`, a backquote, a newline, a `#` outside quotes (`hash_outside_quotes`, brief #351) or any operator word, because they are allow-lists. The data guard is a deny-list on an ordinary builder's commands, which use `&&` and pipes, so it reuses `tokens_of`'s lexer settings (`shlex.shlex(command, posix=True, punctuation_chars=True)`, `commenters = ""`, `whitespace_split = True`) and `hash_outside_quotes`, and instead of refusing it splits: the command is cut into simple commands at `&&`, `||`, `;`, `|`, `&`, newlines and parentheses (a redirection such as `2>&1` is not a cut), and each is judged. In each simple command it strips, before judging the command name, leading `NAME=value` assignments and the wrappers `env` (with its options), `sudo`, `doas`, `timeout`, `time`, `nice`, `nohup`, `stdbuf`, `command`, `builtin`, `exec`, `xargs` (with or without options) and `watch`; it judges the string argument of `bash -c`, `sh -c`, `zsh -c`, `dash -c`, `pwsh -Command` and `powershell -Command` and of `eval` again by this rule, to a depth of 3, and denies past that depth; it scans the code argument of an inline interpreter (`python`, `python3`, `node`, `perl`, `ruby`, `php` with `-c`, `-e` or `-r`, and `pwsh`/`powershell` script blocks) as text for the names and paths of rules 5 to 8 (so `python -c "open('.env')"` is denied); it judges every word that names a path by rules 5 and 6, a word with a glob character both by matching the glob against the denied names and by expanding it in `cwd`; it judges the targets of `<`, `>`, `>>` and `2>` redirections as paths; and it scans every word of the simple command after the command name, whatever program it is given to, for a denied file name of rules 5 and 6 as a substring, bounded on each side by the start or end of the word or by a character other than a letter, a digit, `.`, `_` or `-`, so a name inside an `awk`, `jq`, `sed` or `perl` program (`awk '{ while ((getline l < ".env") > 0) print l }'`) is denied as the word `.env` would be, and `.envrc` or `catalog.json` is not a match. A recursive search is judged by the folder check of rule 5: `grep`, `egrep` or `fgrep` with `-r`, `-R`, `--recursive` or `-d recurse`, `rg`, `ag`, `ack`, `git grep`, `Select-String` with `-Recurse` or a `Get-ChildItem -Recurse` piped to it, and `find` with `-exec`, `-execdir`, `-ok`, `-okdir` or a pipe into `xargs`, each over the folders it names, or over `cwd` when it names none, are denied when one of those folders holds a file of rule 5 or 6 (the permissions page: Read and Edit deny rules "don't apply to a command that reads files without naming them, such as `grep -r pattern .`", which is why the hook judges it); a search that names only files is judged by its words as above. A command it cannot split (unbalanced quotes, a command substitution `$(...)` or a backquote, a here-document, a process substitution) is judged on its raw text: it is denied when any denied name, path, command or secret-named variable of rules 5 to 8 appears anywhere in it, and is otherwise allowed. Rule 16 names what this cannot catch (a value built at run time, such as a path assembled from variables).
5. **Secret files (Answer 2).** Built in, matched on the final path component or the path as written, case-insensitively on every platform (the default file systems of Windows and macOS ignore case, so `cat .ENV` reads `.env`; a case-sensitive file system loses nothing by it), and the same holds for rule 6's names and for every `deny_paths` pattern: `.env` and `.env.*` except `.env.example` (`Q-S0042-8`); `*.pem`, `*.key`, `*.p12`, `*.pfx`; `id_*` with no extension or with the suffix `_sk` (`id_rsa`, `id_ed25519` and the like: the key file names of `~/.ssh/`, wherever they are; a source file such as `id_map.py` is not one), and everything under `~/.ssh/`, `~/.aws/`, `~/.azure/`, `~/.config/gcloud/` and `~/.kube/`; `.npmrc` and `.pypirc` when the file holds a token line (the hook reads the file itself and runs rule 10 on it; the session never sees it); `*.tfstate` and `*.tfstate.*`; `secrets.*`; and, as stores of the same kind, `~/.netrc`, `~/.git-credentials`, `~/.docker/config.json` and `~/.config/gh/` (`Q-S0042-18`). Each `deny_paths` pattern of rule 1 is added. A read of one of these files from git history, `git show <rev>:<path>` and `git cat-file <type or -p> <rev>:<path>`, is judged by the path after the `:` and denied like a read of the file (`Q-S0042-20`). A file under a test folder (`tests/`, `test/`, `spec/`, `__tests__/` and `fixtures/` at any depth) and `.env.example` are readable unless rule 10 finds a secret or personal data in them, which the hook checks by reading the file itself before it allows the read (`Q-S0042-8`). The folder check: `Grep` on a directory, and a recursive search of rule 4, is denied when the directory holds, at any depth, a file of this rule or a log file of rule 6, other than `.env.example` and the files under the test folders above in which rule 10 finds nothing (the hook scans each of those files itself before it allows the search, as it does for a direct read, so `grep -r . tests/` cannot read a fixture that a direct `Read` would deny; a file it cannot scan within the timeout of rule 2 denies the search with `cannot-judge`), whether or not git ignores it, because the search reads into files it is not named; the tools reference says "Grep respects `.gitignore`, so gitignored files are skipped", but the searchers of rule 4 do not, and a session can edit `.gitignore`, so an ignored file still counts (`Q-S0042-11`); `Glob` lists names, not contents, and is denied only when its own pattern names a file of this rule. The safe alternative the denial names: "ask the person for the one value you need, or for a cleaned copy".
6. **Raw logs (Answer 2).** Built in: a path ending `.log` or `.log.<n>`, or with a path component `logs`, read with any tool or command; and the commands `journalctl`, `dmesg`, `kubectl logs`, `docker logs`, `docker compose logs`, `docker-compose logs`, `podman logs`, `heroku logs`, `aws logs`, `gcloud logging`, `az monitor` and each `deny_commands` entry of rule 1. The one allowed reader is the project's own regular `scripts/agk/guard_logs.py` (rule 11) given a log file as its argument (`python3 scripts/agk/guard_logs.py <file>`, also written `agk logs <file>` in the guides, as `agk doctor` means `doctor.py`); its output may be piped onward. A log file under a test folder is readable as rule 5 says for test fixtures. The safe alternative the denial names: "`agk logs <file>`". An agent never reads a raw log, even with the person's approval in the session (`Q-S0042-4`); an `allow_paths` entry of rule 1 is not such an approval but a committed statement, with its reason and an ADR, that the named file is not a raw log (for example a cleaned copy written by `agk logs`, or a source file in a folder named `logs`), and the hook still checks its content (rule 1).
7. **Remote access (Answer 2).** Built in: `ssh`, `scp`, `sftp`, `mosh`, `telnet`, `rsync` to a remote (an argument of the form `host:path` or `rsync://`), `kubectl exec`, `kubectl cp`, `kubectl port-forward`, `docker exec` and `docker cp` on a context or host other than the local one, and the database clients `psql`, `mysql`, `mariadb`, `mongo`, `mongosh`, `redis-cli` and `sqlcmd` (and each `deny_commands` entry) to any host other than `localhost`, `127.0.0.1`, `::1` or an `allowed_hosts` entry of rule 1 (`Q-S0042-5`). A client's host is read from its options (`-h`, `--host`, `-H`, `-S`, `--server` as each client spells it) and from a connection string or URI argument; with no host given, from the client's host variable in the hook's environment (`PGHOST`, `MYSQL_HOST`, `REDIS_HOST` and the like), else the client's local default, which is allowed. A connection string that also carries a password is denied whatever its host, because the command line itself holds a secret (rule 8). The safe alternative the denial names: "ask the person to run it and give you a cleaned copy (`agk logs`)". Data piped in from a remote command is refused here, so `agk logs -` is for the person's own terminal (rule 11).
8. **Printing the environment (Answer 2).** Built in: `env` and `printenv` with no command to run (`env FOO=1 cmd` is the wrapper of rule 4, not a print), `printenv NAME` and `echo`, `printf`, `print` or `Write-Output` of `$NAME`, `${NAME}`, `$env:NAME` or `%NAME%` where `NAME` matches the secret-name pattern, `set` and `export -p`, `declare -p`, `declare -x` and `typeset -p` with no name, `Get-ChildItem env:` and `dir env:`, `cat`/`strings` of `/proc/<pid>/environ`, and `gh auth token`. The secret-name pattern, case-insensitive, on the name cut at `_`: a part that is `SECRET`, `TOKEN`, `PASSWORD`, `PASSWD`, `PWD`, `CREDENTIAL`, `CREDENTIALS` or `AUTH`, or a name that holds `PRIVATE_KEY`, `API_KEY` or `ACCESS_KEY`, or exactly `DATABASE_URL`; `PWD` and `OLDPWD` themselves (the shell's folders) do not match. Rule 14 uses the same pattern, except that it warns for `DATABASE_URL` only when its host is not one of rule 7. The safe alternative the denial names: "check that the variable is set with `test -n \"$NAME\"`", which prints nothing.
9. **The denial line (Answer 2).** A denial is one line, `data guard: <rule> (<class>): <safe alternative>`, where `<rule>` is one of `secret-file`, `raw-log`, `remote`, `environment`, `cannot-judge` and `<class>` names the kind (for example `secret-file (key file)`), passed as `permissionDecisionReason`. It never holds the path, the command, the host, a variable's value or a matched text, so a denial never leaks what it protects. Every denial is shown to the person and to the model, one line each (`Q-S0042-6`), and is recorded by rule 15.
10. **The detectors and `guard.scan_text` (Answers 3 and 5).** `scripts/agk/guard.py` (standard library only, no network, installed) holds the detectors and one function, `scan_text(text) -> list[Finding]`, where a `Finding` holds the kind, the line and column, and the length, never the matched text outside the process. Secrets: the patterns of the gitleaks default rule set, copied as data into `scripts/agk/guard_rules.json` with the release they came from (the same release the governance workflow pins) and the licence notice `(verify: the licence of the rule file and its notice)`, so no gitleaks program is needed at run time; and a string of at least 20 characters from a base64 or hex alphabet with a Shannon entropy of at least 4.0 bits per character for base64 and 3.0 for hex, standing next to a key-like name (`key`, `secret`, `token`, `password`, `passwd`, `pwd`, `auth`, `credential`, `api_key`, followed by `=`, `:` or `=>`, optionally quoted). Kinds: `JWT` (three base64url parts, the first decoding to JSON with `alg`), `TOKEN` (a bearer token after `Bearer ` or `Authorization:`) and `SECRET` (the rest). Personal data, the built-in list (`Q-S0042-3`): `EMAIL`; `PHONE` (an international number with `+` and 8 to 15 digits, and an Indian number of 10 digits starting 6 to 9 with an optional `+91` or `0`); `CARD` (13 to 19 digits, spaces or dashes allowed, passing the Luhn check); `AADHAAR` (12 digits, the first 2 to 9, spaces allowed every four, passing the Verhoeff check); `PAN` (five capital letters, four digits, one capital letter); `IP` (IPv4 and IPv6 as `ipaddress` parses them); and each `[guard] patterns` entry as `CUSTOM-<name>`. Not flagged on their own: UUIDs, git shas (7 to 40 hex), hex digests (32, 40, 64 or 128 hex), version strings that `ipaddress` does not parse, and `example.com`, `example.org` and `example.net` addresses (the invented data the kit's own rules require); each is flagged when it stands next to a key-like name. So that ordinary AGK text is not refused, these are excluded from the personal-data kinds: for `IP`, the loopback addresses (`127.0.0.0/8`, `::1`), the unspecified addresses (`0.0.0.0`, `::`) and the documentation ranges (`192.0.2.0/24`, `198.51.100.0/24`, `203.0.113.0/24`, `2001:db8::/32`); for `PHONE`, `CARD` and `AADHAAR`, a run of digits in the path or the fragment of an `http` or `https` URL, other than in the path's first segment (where `https://wa.me/` and the like put a phone number), and never in its query (from `?` to `#` or the next space) or in a URL of any other scheme (`tel:`, `sms:` and the rest); a run that follows `comment`, `run`, `id` or `id=` (case-insensitive, with at most one space or `:` between); and a run that follows `#` directly, with nothing between; as in "comment 6614307507", `#540`, "run 38890313928", `id 6634414373` and `https://github.example.com/o/r/actions/runs/38890313928`. The `id` and `id=` exclusion does not apply when the word before `id` names a personal kind (`aadhaar`, `phone`, `mobile`, `card` or `pan`, case-insensitive, with at most one space between), and no exclusion of this rule applies to a run that starts with `+` or that is grouped as an Aadhaar number (three groups of four digits joined by single spaces or dashes); and for `EMAIL`, an address whose local part is `noreply` or `no-reply` (any domain, as git and GitHub write them) and every address at `example.com`, `example.org` or `example.net`. A number those exclusions do not cover and that happens to pass the Luhn or Verhoeff check (about one in ten random 16- or 12-digit numbers does) is still flagged; the residual states it. The same detectors serve layers 2, 3 and 4.
11. **Layer 2, the redacting log reader (Answers 3 and 8).** `scripts/agk/guard_logs.py` (installed; `agk logs <file|->` in the guides) reads one log file, or standard input with `-`, and prints it with each finding of rule 10 replaced by a label, `[<KIND>-<n>]` (for example `[EMAIL-1]`, `[CARD-1]`, `[AADHAAR-1]`, `[IP-3]`, `[TOKEN-1]`, `[SECRET-1]`), numbered per kind in order of first appearance, so that the same value gets the same label everywhere in one run and different values different labels; the mapping is kept in memory only and never written or printed. Everything else of the line (time stamps, levels, field names, punctuation, line breaks) is printed unchanged, so the structure stays readable. `--max-lines N` (default 2,000) prints only the last `N` lines (the tail first: the newest lines are the ones a person debugs), and the labels are numbered over the lines printed. The last line is `agk logs: <kind> <count>, ...` (or `agk logs: no findings`), counts per kind only. Bytes that are not UTF-8 are read with replacement and never passed through raw. It opens no socket, runs no program and writes no file; a file it cannot read exits 2 naming the option, never the path's contents. Its speed is part of its contract: a 10 MB log is redacted within the limit of `Q-S0042-9`.
12. **Layer 3, what a person pastes (Answer 4).** `data_guard.py prompt` reads the `prompt` field of the `UserPromptSubmit` input and runs rule 10 on it. On a secret or personal-data finding it blocks the message with `{"decision": "block", "reason": ..., "hookSpecificOutput": {"hookEventName": "UserPromptSubmit", "suppressOriginalPrompt": true}}` and exit 0 (rule 2 records that a blocked prompt never reaches the model), with a reason of at most three lines: the counts per kind (`data guard: message not sent: EMAIL 2, TOKEN 1`), and how to resend it cleaned ("save the text to a file outside the project, run `agk logs <file>` in your own terminal and paste its output"). The hooks reference, as read through a mirror and not on `code.claude.com` itself `(verify)`, says the block message shown to the person ends by default with `Original prompt:` and the submitted text, and that `suppressOriginalPrompt: true` in `hookSpecificOutput` leaves it out; the hook always sets it, and never blocks by exit code 2, which cannot carry the field. The reason and the rest of the output never hold a value or a part of the message. The prompt text can still reach local files on the person's machine, such as Claude Code's prompt history and transcript, which the hook cannot clear; that is a residual, and the guide tells the person to clear them (`Q-S0042-16`). A clean message passes with nothing printed and exit 0, because plain stdout of this event is added to the model's context (rule 2). Personal data blocks as a secret does (`Q-S0042-2`): the message is blocked, and only where blocking is not possible (a runtime whose prompt hook cannot block) does the hook warn instead, which the guide says. Files and images attached to a message are not scanned (rule 16).
13. **Layer 4, what AGK writes (Answer 5).** Before every write AGK makes, the text passes `guard.scan_text`, and a finding blocks the write with one line naming the kind and the position (`line <l>, column <c>`), never the value, and a non-zero exit.
