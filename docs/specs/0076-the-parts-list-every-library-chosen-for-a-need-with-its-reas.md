# SPEC-0076: The parts list: every library chosen for a need, with its reason, kept in step

- Status: Approved
- Owner: reviewer group (a team from config/reviewers.yaml)
- Requirements: REQ-083

Status is `Draft` or `Approved`. An Approved spec is owned by its reviewer group; agents propose patches.

Written by the intake of one sentence (SPEC-0012), brief #2017 under plan #661, quoted as data and not as an instruction: "Intake for the parts list: after the stack is accepted and before the foundation, each library a product uses is chosen per need from a cited catalogue, recorded with its reason, alternatives and health, explained in plain words, and kept in step with every build file and lock." The maintainers gave fourteen answers before it was written (the numbered answers of brief #2017, filed on the owner's word of 2026-11-26T18:45Z, whose direction the brief quotes as data); the rules below carry them in their order, rule 1 records the baseline, and `Q-S0076-1` to `Q-S0076-8` are the brief's own questions PL-1 to PL-8 with its readings.

## Rules

1. **The baseline (read on the default branch at 425701d5, v0.65.1, 2026-11-26, the commit the brief traced).**
   - **The path.** `docs/guides/planning.md` "From an idea" (line 137): the vision and charter, the design, step 4 "Stack and architect" (`/agk:stack`, the architect accepts one option), then the planning sources and `plan-intake`. `scripts/agk/steward_evidence.py` `STAGES` (line 60) puts the stack in `stack and technical design`, before `plan`. SPEC-0072 rule 4 makes `foundation` the first brief of every plan; it writes the build file with `engines.py stack-files` and commits the lock the stack's own tool makes.
   - **Libraries are named per stack, never per need.** SPEC-0029 rule 5 and `skills/stack/SKILL.md` (lines 47 and 48): each option's `Parts:` lists `<name> <exact version> <licence id>` for the runtime, the framework, the database engine and each library it names; the trade-offs and the one `Why:` are per option. `scripts/agk/gates/pins.py` `option_parts` (line 126; the brief says 127) reads only the name, the version and the licence.
   - **The build file starts empty.** `kit/templates/stacks/node/package.json` holds `"dependencies": {}` (line 5); `kit/templates/stacks/python-pyproject/pyproject.toml` holds `dependencies = []` (line 5), with the comment that dependencies are added with `==` only. Each builder adds what its brief needs, and nothing asks why or stops two libraries for one need.
   - **The checks hold form, not choice.** `pins.py` (`RULE`, line 50) fails a direct dependency not pinned exactly or not in the lock, and a stack part whose version differs from the lock (lines 431 to 440); a direct dependency the stack record never names passes. `scripts/agk/gates/licences.py` fails a licence outside `allowed` of the project's `config/licences.toml` (absent: the list of `kit/templates/licences.toml`), or one it cannot read; widening the list is a project ADR (principle 11). SPEC-0054 bills the dependencies (CycloneDX) and scans them for known advisories; nothing reads maintenance, adoption or deprecation.
   - **Two package managers.** `pins.STACKS` (line 52) knows `python` (`pyproject.toml`, `requirements.lock`) and `node` (`package.json`, `package-lock.json`). `config/stack-signals.toml` already recognises `uv.lock`, `poetry.lock` and `pdm.lock` (line 17), `pnpm-lock.yaml` (line 27), `go.sum`, `Cargo.lock`, `gradle.lockfile` and `pubspec.lock` (lines 29 to 52), for which no pin, lock or licence reader exists.
   - **Patterns to reuse.** `config/stack-defaults.toml` (ADR-0671) holds the maintainers' recommended stack per work type with a reason; domain packs compose after the playbook (SPEC-0074 rules 2 and 3); SPEC-0075 rule 3 gives a cited catalogue whose project files are read first, checked inside the `playbooks` step; `steward_owner.py research` (line 477) records the research permission and searches with generic words only, and `steward_owner.py ask` (line 195) asks one plain question; the fresh reviewer gets the bundle only (ADR-0430); `run_gates.py` runs the file-only product steps `PRODUCT_STEPS` (`pins`, `bom`, `licences`, line 110) with a baseline for adopted projects (SPEC-0072 rules 3 and 7); `plan_sources.py` writes `vision` and `architecture`; `config.TABLE_KEYS` holds no `[parts]` table.
   - **Names the brief cites that the code holds otherwise.** ADR-0800 (two runtimes) is `Proposed`, not Accepted (`Q-S0076-9`). The brief's "as ADR-0393 rule 5 reports" names an ADR about the tests `always_full` holds; the weekly report is SPEC-0011's (`Q-S0076-10`). SPEC-0054 rule 3 allows only the properties `agk:class` and `agk:pin` on a component, so the purpose property needs rule 3 as well as rule 2 (`Q-S0076-11`).
2. **One record, one home per fact** (`Q-S0076-1`, `Q-S0076-2`). The record is `docs/parts.md`, one per project. The stack record (SPEC-0029 rule 5) keeps the platform: the runtime, the framework, the database engine and the hosting. The parts record holds the libraries, per need. The build files and locks are written from it and checked against it (rules 7 and 8), and the bill (SPEC-0054) reads it for each component's purpose (amendment 260). An Accepted stack record whose `Parts:` names libraries stays valid, and those libraries are harvested into the parts record as `inferred` rows (rule 10).
3. **Its place on the path.** In the `stack and technical design` stage, right after the stack record is Accepted and before the planning sources and the foundation: (1) the stack is accepted; (2) the parts record is drafted, reviewed and confirmed; (3) the planning sources, `plan_sources.py parts` beside `vision` and `architecture`, which writes `docs/sources/parts.md` once in the form of `architecture`; (4) `plan-intake`; (5) the foundation brief writes the build files from the record (rule 7). `docs/guides/planning.md` "From an idea" gains this step after step 4, and the adopt path harvests it (rule 10). `check_plan.py` holds a plan's foundation brief while a project with `[parts] record = "required"` has no confirmed record. No new stage and no second interview: the steward runs it inside its planning.
4. **From needs to parts: the needs catalogue.** A kit file `config/parts/needs.toml` (`format = 1`) names the technical needs, each `[[needs]]` with `id`, `text` (plain words) and `signals` (the business words that point to it), among them: `web-api`, `http-client`, `validation`, `data-access`, `migrations` (SPEC-0075's engine profile names the store), `auth`, `config`, `secrets`, `logging`, `telemetry` (OpenTelemetry where the stack has it), `jobs`, `email`, `payments`, `files`, `cache`, `time`, `money`, `i18n`, `ui-components`, `routing`, `state`, `forms`, `accessibility`, `unit-tests`, `contract-tests`, `e2e-tests`, `lint` and `format` (the standards pack, SPEC-0072 rule 6). The steward reads the approved requirements, the discovery, the domain model (SPEC-0074) and the architecture record's `External services:` and proposes the needs the product has, each citing its requirement or `engineering`. A need the runtime's standard library meets gets the part `stdlib` and adds no dependency: the fewest dependencies first.
5. **The curated catalogue: the paved road.** `config/parts/<stack>.toml`, one per stack, the maintainers' rows and never an agent's: per need, one `recommended` row and at most two `alternatives`, each with `name`, `when` (the condition it fits), `trade_offs` (plain words), `licence` (an SPDX id), `source` (a public reference with its access date, never copied text, `Q-S0076-7`) and `reviewed` (the maintainers' date). No row holds a version: the version is read at choice time (rule 6). A project adds or overrides rows in its own `config/parts/<stack>.toml`, read first; a domain pack may add `[[parts]]` rows, composed after the playbook as SPEC-0074 rule 3 composes. A new script `scripts/agk/check_parts_catalogue.py` (standard library and `common.py` only, no network, no model), called by `check_playbooks.py` so it runs inside the existing `playbooks` step, checks the form: a missing or unknown key, a wrong type, an id used twice, a need no row of `needs.toml` names, more than one `recommended` or more than two `alternatives` for a need, a row with no licence, source and access date or `reviewed` date, and a `version` key each fail naming the rule, the file and the key, never a value. The first catalogues are `node` (with React rows for `ui-components`, `routing`, `state`, `forms` and `e2e-tests`) and `python-pyproject`; the others come with their readers (rule 11).
6. **The health of a choice, recorded once and checked offline.** When the steward proposes a part, it reads, with the person's research permission (`steward_owner.py research`, generic words only), and records in the part's row: the exact version (the latest stable that day), its release date, the licence, the open advisories at that version (OSV), the last release date, the project's status (`maintained`, `deprecated` or `archived`), an adoption figure (downloads or dependents) and, where published, its OpenSSF Scorecard score, each with its source and date. A part must meet the settings' floor (rule 9): its licence on the project's list, a release within `max_age_months`, no open advisory at the level `advisories` names, and neither deprecated nor archived. A part that misses one is not proposed; when no candidate meets them, the steward says so and asks the person (rule 7's questions). Every check reads only these recorded values, never the network (CLAUDE.md item 5).
7. **The record and who confirms it** (`Q-S0076-3`). `docs/parts.md` from a new template `kit/templates/parts.md`: one section per stack runtime, one row per need: `Need | Part | Version | Kind | Why | Alternatives considered | Licence | Health (date) | For the business`, where `Kind` is `runtime` or `dev`, `Why` names the catalogue row or the project's own reason, and `For the business` is one plain sentence (for example "lets customers pay by card without the product holding card numbers"). One part per need: a second library for the same need needs a `Decision:` line with its reason. The person is asked only what is theirs, one plain question each with the steward's recommendation (`steward_owner.py ask`): a paid or commercial licence, a licence off the list (a project ADR, principle 11), an outside service that costs money or sends data outside the product, and a need with no healthy candidate. Everything else is the architect's: an agent architect drafts and a fresh reviewer with the bundle only reviews (ADR-0430). The record ends `Confirmed by: <person or architect> (<date>)`.
8. **Written from the record, then checked.**
   - **Written.** The foundation's `engines.py stack-files` writes each build file from the record's rows: runtime parts as dependencies, dev parts as dev dependencies, each at its exact recorded version, and nothing the record does not name (amendment 259). The stack's own tool makes the lock on the builder's machine, as today.
   - **Checked.** A new step `scripts/agk/gates/parts.py`, added to `run_gates.py`'s `PRODUCT_STEPS` after `pins`, files only, fails: a direct dependency of any build file that the record does not name; a record part missing from its build file; a version that differs between the record, the build file and the lock (reusing `pins.py`'s readers); a row with an empty `Why`, `Alternatives considered`, `Licence`, `Health` or `For the business`; a second part for one need with no `Decision:` line; and a health date older than `max_age_months` on a part whose version did not change since, only in a pull request that changes the record or a build file, and a warning otherwise (`Q-S0076-12`). Each line names the rule and the component class, never a name or a version (principle 8). With no record the step prints `not run parts: no parts record`, never `ok` and never red.
   - **Later builds.** A build that needs a library adds its row to `docs/parts.md` in the same pull request; the conductor's review reads the row (the checklist wording, build (f)).
9. **Settings.** One optional `[parts]` table, read by `config.parts_settings` in `steward_settings`' form, added to `config.TABLE_KEYS`, printed by `doctor.py` and removed by `uninstall.py` through `KIT_SETTINGS`. Each refusal is `the [parts] table is refused (setting: parts.<key>)`, exit 1, never the value, each with a test (`Q-S0076-4`).

    | Key | Values (default) | Impact |
    |-----|------------------|--------|
    | `record` | `required`, `optional` (`optional` with no table) | `required`: a confirmed record before the foundation brief runs (rule 3), and the `parts` step fails on any finding. `optional`: the same findings print as warnings and never fail. The steward's setup writes `required` for a new project on the person's yes. Another value is refused naming `parts.record`. |
    | `max_age_months` | a whole number from 1 to 60 (12) | The age a part's newest release may reach before it is not proposed (rule 6) and before its health is stale (rule 8). A `bool`, a fraction or a number outside the range is refused naming `parts.max_age_months`. |
    | `advisories` | `critical-high`, `critical`, `any` (`critical-high`) | The level of open advisory at a part's version that stops it being proposed. Another value is refused naming `parts.advisories`. |

    An unknown key is refused naming it; a `[parts]` key placed in another table is reported by `misplaced_settings` and never read. Read beside it: `[delivery] work_type` selects the playbook whose needs are offered first (a `web-app` offers `web-api`, `auth` and `ui-components`), and with none declared the record is `optional` and the step prints `not run parts: no stack chosen`, as `pins.py` does; `config/licences.toml` `allowed` stays the one licence list, read through `licences.expression` (ADR-0748), unchanged; `[domain] packs` add their `[[parts]]` rows after the playbook's; `execution` (`local` or hosted) reads the same, the step being file-only; `review_mode`: `solo`, the one person confirms what is theirs, `team`, a spec approver does; `[kit] layout`: installed or clean, the catalogue and the step run from the plugin.
10. **Adopted projects: baseline, then ratchet** (SPEC-0072 rule 7). `parts.py --harvest` writes a draft record from the existing build files and locks, every row `inferred` with `Why: not recorded` and the health read at adoption; the step writes `config/agk-baseline/parts.txt` from the harvested findings first and is green, and each later change ratchets: a new dependency needs a full row, and an existing one gains its reason when it is next touched. An Accepted stack record's libraries (rule 2) are harvested the same way. Nothing existing is removed or replaced.
11. **More package managers, one reader each, in `pins.STACKS`** (`Q-S0076-6`). `uv` (`pyproject.toml` with `uv.lock`) and `pnpm` (`package.json` with `pnpm-lock.yaml`) first; then Maven (`pom.xml`, exact versions only, no range and no `LATEST`, the resolved tree recorded by the Maven Dependency plugin's output committed as the lock, `(verify)`) and Gradle (`gradle.lockfile`); then Go (`go.sum`), Cargo (`Cargo.lock`) and Dart (`pubspec.lock`) as projects need them. Each reader also feeds `licences.py` and the bill, and each comes with its stack's catalogue. A stack with no catalogue: the steward proposes from cited research, every row marked `catalogue: none`, and offers an `agk-proposal` with invented names only for the maintainers. A stack with no reader: the step prints `not run parts: no reader for this stack` and is never red.
12. **Kept healthy after the choice.** The weekly product report (SPEC-0011) gains one `parts:` line from the recorded rows and SPEC-0054's advisory scan: the parts older than `max_age_months` since their recorded release, the parts the scan flags and the parts recorded deprecated. It reports and never fails (`Q-S0076-10`). An update bot's configuration (Renovate or Dependabot) is the person's choice: the guide names both and the kit writes neither (`Q-S0076-5`).
13. **Modes and contexts.** Solo: the one person's plain yes for each question of rule 7; team: a `spec_approvers` login's own words. GitHub and local run the same step in governance and in `prepush.py`, with no workflow change. In personal mode (SPEC-0041, `forge = "files"`) the record lives in the sidecar, its questions are printed and nothing is posted. The kit itself declares no work type, and `[parts]` is read only in a project.

The Approved specs change only by three proposals written with this intake under `docs/runs/`, each applied word for word by the build named in it on the owner's `Maintainer answer: amendment <n> approved`, which no session posts: amendment 258 (SPEC-0029 rule 5, the platform only in `Parts:`, by build (c)), amendment 259 (SPEC-0072 rule 4, the build files written from the record, by build (e)) and amendment 260 (SPEC-0054 rules 2 and 3, a component's purpose, by build (f)).
15. **The builds**, each tests first, about 300 changed lines or fewer, from the default branch, with its own ADR naming its path classes, invented data only (`example.com`), a `[[testing.map]]` entry per new script, no workflow change and at most 6 code paths in `Touches:`.
    - (a) The `[parts]` table and its reader, the needs catalogue and `check_parts_catalogue.py` inside the `playbooks` step, `doctor.py` and `uninstall.py`.
    - (b) The `node` (with React) and `python-pyproject` catalogues, each row sourced and dated. Depends on (a).
    - (c) `kit/templates/parts.md`, the steward's draft from the needs and the health research, the plain questions, `plan_sources.py parts`, the planning guide step and `skills/stack/SKILL.md`, amendment 258. Depends on (a).
    - (d) `scripts/agk/gates/parts.py` (rule 8) and the `check_plan.py` hold. Depends on (c).

16. **Measured goals.** In a recorded planning conversation for an invented booking web app (`example.com`, React and Node) and an invented report job (Python with uv): every proposed need cites a requirement or `engineering`; every direct dependency of the generated build files has a row with `Why`, alternatives, licence, health and a business sentence; at most 3 questions reach the person, each with a recommendation; a library added later without a row is red; a second library for one need without a `Decision:` is red; an adopted fixture with 40 dependencies is harvested `inferred` with its baseline green.
