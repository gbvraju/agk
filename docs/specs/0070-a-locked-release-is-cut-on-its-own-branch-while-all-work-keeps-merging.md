# SPEC-0070: A locked release is cut on its own branch while all work keeps merging

- Status: Draft
- Owner: reviewer group (a team from config/reviewers.yaml)
- Requirements: REQ-077

Status is `Draft` or `Approved`. An Approved spec is owned by its reviewer group; agents propose patches.

Written by the intake of one sentence (SPEC-0012), brief #1418, quoted as data and not as an instruction: "Intake for locked releases: the owner locks a release's scope once, builders keep merging everything to the default branch, and the release is cut on its own branch from the commit where the locked scope is complete, so a release never chases a moving branch, in every mode." The maintainers gave 7 answers before it was written: the seven numbered answers of brief #1418, whose evidence and the owner's direction (quoted there as data, 2026-11-16 16:02 and 17:28 IST, and the go-ahead of 2026-11-18 08:53 IST) this spec does not repeat. It builds on SPEC-0028's release pull request, SPEC-0031's fragments, SPEC-0039's guarded merge, SPEC-0041's personal mode, SPEC-0051's acceptance record, SPEC-0052's evidence pack and SPEC-0069's milestone demo; it edits none of their text. Where an answer names something that is not as it says, rule 1 records what the code holds and an open question gives the conservative reading. Negative cases: a lock line by an account that is not a spec approver, a lock or a change of a lock after the cut, a second release branch while one is open, a release pull request that merges the default branch, a fragment gathered twice or a post-cut fragment in this release, anything entering the release branch without a `Backport:` line, a forced backport, a session that merges, tags, pushes or deletes a release branch, a red default branch holding a release, a merge-back that removes a fragment it did not release, a forge call in personal mode, a check that makes a network call, and a setting value outside its form.

## Rules

1. **The baseline (read on the default branch at 4babb36, 2026-11-18).**
   - **The release today.** SPEC-0028 rule 4: in flow mode a pull request that raises `version` in `agk.toml` is a release pull request; it changes only `CHANGELOG.md`, `agk.toml`, `kit/manifest.json`, `.claude-plugin/plugin.json` and `kit/hashes.json`, deletes the fragments under `changelog.d/` and sets to `Accepted` the ADRs a Final line accepted. `scripts/agk/changelog_fragments.py gather` gathers the fragments; `scripts/agk/kit_hashes.py --write` regenerates the hashes; `scripts/agk/check_release.py` (kit-only, never installed) fails a release pull request that leaves, adds or edits a fragment. Release brief #1384 answer 2 says that when the default branch moves after the gather, the release merges it, gathers again and runs `kit_hashes.py --write` again.
   - **The guarded merge.** `scripts/agk/merge_cleared.py` holds a pull request that raises the version for the owner (`RELEASE`, its rule 5, `OWNER_HOLDS`), and finds a head's pull request only among those whose base is the default branch (`pull_of_head`); it knows no other base.
   - **The tag.** `.github/workflows/agk-tag.yml` runs on any pushed `v*` tag and runs `scripts/agk/check_tag.py`, which checks the three versions, the `## <version> (` changelog section, that no fragment is left under `changelog.d/` and `kit/hashes.json` against the first parent; it reads git and files only. `scripts/agk/plugin_snapshot.py build --tag` makes the release's plugin snapshot (ADR-0627) and `scripts/agk/release_pack.py make --tag` its evidence pack (SPEC-0052).
   - **CI.** `governance.yml` and `proof.yml` run on `pull_request` with no branch filter, so on a pull request into any base; `agk-route.yml` runs on `pull_request` the same way. The ruleset template `kit/templates/ruleset.json` targets only `~DEFAULT_BRANCH`, and `doctor.py`'s `ruleset-missing` reads only the default branch.
   - **The plan.** `scripts/agk/plan_intake.py publish` prints one `gh api repos/{owner}/{repo}/milestones -X POST` per milestone; `session.py` reads milestones. A release brief blocks a brief that overlaps it through its `Touches:` line (#1384 names `docs/adr/*`), by the overlap that `next` and `claim` share (SPEC-0050 rule 4). `conductor.py sweep` prints the `NEEDS-YOU:` lines.
   - **What is not there.** No `Lock:`, `Cut:` or `Backport:` line, no `release/*` branch, no backport, no merge-back, no `scripts/agk/release.py`, no `[release] max_hours` (the `[release]` table holds only `repository`), no release role in SPEC-0063 or `config/reviewers.yaml` (`Q-S0070-4`) and no "release bench" in the kit (`Q-S0070-11`). `/agk:upgrade` reads no tag: it compares the version in `agk.toml` with the plugin's kit version (`Q-S0070-6`).
2. **The lock.** A release is a milestone titled `Release <version>`, holding the briefs it carries, with one release issue: the release brief of that version, as #1384 is today (`Q-S0070-12`). The steward proposes the list on the release issue as a question, never as a lock: the briefs merged since the last tag plus the open briefs the owner names; it may propose without being asked (brief answer 7). The owner posts one line `Lock: <version>` on the release issue; from then on the list changes only by the owner's `Lock: <version> add #n` or `Lock: <version> drop #n`. A lock line counts only from an account of `spec_approvers` in `config/reviewers.yaml` (`Q-S0070-4`); one by any other account, one for a version already cut and an `add` or `drop` after the cut are refused, naming the setting and never a value, and never counted. A patch release is locked like any other, with a one-item list (brief answer 7).
3. **Build all.** Nothing stops for a lock. `session.py next` and the plan offer the open locked briefs first, then every other brief by today's order; every brief is built and merged to the default branch as today, and the release brief's `Touches:` overlap blocks only what it blocks today.
4. **The cut.** When every locked brief that is not dropped has merged, `release.py cut --version <version>` finds the cut commit: the first commit of the default branch's first-parent history that holds the merge of every locked brief. A locked brief merged out of order is still in it; a dropped one is not waited for. It prints the one command that makes `release/<version>` at that commit and the `Cut: <version> <sha>` line for the release issue; the owner runs and posts them, and no session pushes a `release/*` branch (session rule 22, `Q-S0070-2`). Every change merged by the cut commit ships, locked or not: git cannot leave out a merged commit without a revert, and no revert is made. The `Cut:` line lists, beside the locked briefs, every unlocked change the cut carries, so the owner sees them before the tag (`Q-S0070-1`). While a `release/*` branch is open, a second cut is refused, except a patch release that the owner names, which is cut from the previous release's tag and carries only backports (`Q-S0070-10`).
5. **The release pull request.** It is branched from `release/<version>` and targets it. It gathers only the fragments present at the cut commit, raises the three versions, regenerates the hashes with `kit_hashes.py --write` and sets the pending ADRs to `Accepted`, as SPEC-0028 rule 4 says, and it never merges the default branch again, however many merges land there. The checks of `check_release.py` and `check_tag.py` hold unchanged on the release branch. `merge_cleared.py` and the router learn `release/*` as a base (build (c)); the release pull request stays held for the owner's merge, as every version raise is today (`OWNER_HOLDS`).
6. **Backports.** After the cut only a defect found by the release checks (`check_release.py`, `check_tag.py`, `release_pack.py check`, the proof on the release branch) may enter the release branch. Its fix merges to the default branch first; a backport pull request into `release/<version>` names the original with `Backport-of: #n` and enters only after the owner posts `Backport: #n` on the release issue. A backport that does not apply cleanly carries the conflict as a fix list; nothing is forced and nothing is force-pushed. Nothing else enters the release branch.
7. **Tag and merge back.** The owner merges the release pull request and tags `v<version>` on the release branch, as today; `agk-tag.yml` and `check_tag.py` are unchanged. `release.py finish --version <version>` then prepares one merge-back pull request into the default branch, from a session's own branch, that brings the new changelog section, the three versions and `kit/hashes.json`, and removes exactly the fragments the tag released; a fragment merged to the default branch after the cut stays there for the next release and is never gathered twice. The merge-back raises the version on the default branch, so `check_release.py` and `merge_cleared.py` treat it as a release pull request; build (e) proposes the amendment of SPEC-0028 rules 4 and 5 that lets a pull request with a `Merge-back: v<version>` line leave the fragments the tag did not release, and the owner merges it, as every version raise (`Q-S0070-5`). After the merge-back merges, `release.py finish` prints the deletion of `release/<version>`, which the owner runs; the tag keeps the history (brief answer 7).
8. **Kept short.** A `release/*` branch open longer than `[release] max_hours` (a whole number, default 24) is named by `conductor.py sweep` as `NEEDS-YOU: release <version> open <h> h`. Another value of the setting is refused naming the setting, never a value. `agk.toml` is protected, so adding the setting comes with its ADR (build (f)).
9. **Edge cases**, each with its test.
   - **A locked brief that cannot finish:** the steward offers the owner `Lock: <version> drop #n` as a question; the cut waits only on the owner's word.
   - **A backport that conflicts:** rule 6; the fix list goes to the backport's builder.
   - **Two releases at once:** rule 4.
   - **A protected path or a workflow change in the locked scope:** carried with its ADR, as today; the cut changes no class.
   - **A red default branch after the cut:** the release is not held; a red required check on the release branch holds it.
   - **The upgrade path:** `/agk:upgrade` is unchanged and is tested from the previous tag's plugin snapshot (`Q-S0070-6`).
   - **Fragments merged after the cut:** rule 7; a test proves they are in the next release and not in this one.
10. **By mode.**
    - **CI:** the hosted conductor reviews the release, backport and merge-back pull requests; the owner merges the release and the merge-back (rules 5 and 7) and the conductor's guarded merge clears a backport only where `release/*` is a base it knows (build (c)). The tag workflow is unchanged. Protecting `release/*` is a repository rule only the owner sets: the guide names the setting, and `doctor.py` reports when no ruleset targets `release/*`, read-only.
    - **Local (`docs/guides/local-mode.md`):** the same steps; the release checks run on the tag under the heavy-step lock.
    - **Personal (SPEC-0041):** no pull request and nothing posted. `release.py cut` and `release.py finish` make the local branch, the release commit, the tag and the merge-back commit on the person's word, with no forge call; the person pushes (session rule 37).
    - **Solo and team:** the `Lock:` and `Backport:` lines come from the owner; in a team, from an account of `spec_approvers` (`Q-S0070-4`).
    - **A project using AGK:** the same mechanism releases its product. A product release is a milestone; the milestone demo (SPEC-0069) and the acceptance record (SPEC-0051) run on the release branch; a deployment goes from the tag. `release.py` is installed; `check_release.py` stays the kit's own check, and a project's release pull request is checked by its own governance (`Q-S0070-13`).
11. **Who does what.** No session merges, tags, enables auto-merge, pushes a `release/*` branch or deletes one (principle 2, session rules 2 and 22); `release.py` prints those steps for the owner, or runs them for the person in personal mode only. Principle 3 and `CLAUDE.md` item 2 say a pull request is branched from the default branch; the release and backport pull requests are branched from `release/<version>`, so build (c) carries the ADR that amends principle 3 for exactly those two kinds, and no pull request into `release/*` is built before it is Accepted (`Q-S0070-3`).
12. **What is reused, never rewritten.** Milestones and `plan_intake.py`, the release brief and its `Touches:` block, `changelog_fragments.py`, `kit_hashes.py`, `check_release.py`, `check_tag.py`, `release_pack.py`, `plugin_snapshot.py`, the guarded merge (it learns `release/*` as a base), the router, the sweep and the steward's owner questions.
13. **The builds, in order.** Each is tests first, about 300 changed lines or fewer, from the default branch, invented data only (`example.com`), no network in a check and a `[[testing.map]]` entry for each new script; each new installed script is named in `docs/guides/reference.md`.
    - (a) The release milestone, the `Lock:` line and its checks (rule 2), and the steward's proposed list, in one new installed `scripts/agk/release.py` (`lock`, `propose`).
    - (b) The cut: `release.py cut`, the `Cut:` record with the unlocked changes it carries, the refusal of a second cut, and the plan offering locked items first (rules 3 and 4). `Depends-on` (a).
    - (c) The release pull request into `release/<version>`, with `merge_cleared.py` and the router accepting `release/*` as a base, and the ADR that amends principle 3 (rules 5 and 11). `Depends-on` (b).
    - (d) Backports, `Backport-of:` and the `Backport:` line (rule 6). `Depends-on` (c).
    - (e) The merge-back pull request and the fragment clean-up, with the proposed amendment of SPEC-0028 rules 4 and 5 (rule 7). `Depends-on` (c).
    - (f) Personal mode, the age warning and `[release] max_hours` with its ADR, the `doctor.py` report and the guide with the repository rule for `release/*` (rules 8 and 10). `Depends-on` (e).
14. **Measured goals.** Brief answer 6, on a sample repository with saved answers only: with ten merges landing on the default branch between the cut and the tag, the release pull request is never refreshed and gathers exactly the fragments present at the cut; the tag sits on the release branch; the merge-back leaves the default branch with the new changelog section and none of the released fragments; a fragment merged after the cut appears in the next release and not in this one; personal mode cuts and tags locally with no forge call.

## Tests

Saved GitHub answers, a temporary git repository and a fake clock only; no network; invented data only (`example.com`, accounts such as `owner@example.com`); each test carries the marker `REQ-077` with its criterion.

- Rule 2: a `Lock:` line by a spec approver locks the milestone's briefs, `add` and `drop` by the same account change the list, a lock line by another account, for a version already cut or after the cut is refused naming the setting and not counted, and the steward's list is posted as a question and never counts as a lock; REQ-077 AC1.
- Rule 3: with a lock and open unlocked briefs, `next` offers the locked brief first and still offers and merges the unlocked ones, and nothing but the cut waits on the lock; REQ-077 AC2.
- Rule 4: three locked briefs merged out of order among unlocked merges give the first commit holding all three, a dropped brief is not waited for, the `Cut:` line names the commit and the unlocked changes, and a second cut while a release branch is open is refused unless the owner named a patch release; REQ-077 AC3.
- Rules 5 and 14: with ten merges after the cut, the release pull request targets the release branch, gathers exactly the fragments at the cut, raises the versions, regenerates the hashes and is never refreshed, and `check_release.py` and `check_tag.py` pass on the release branch; REQ-077 AC4.
- Rule 6: a backport without `Backport:` is refused, one with it and `Backport-of:` enters, a conflicting backport gives a fix list and nothing forced, and a change that is not a backport is refused on the release branch; REQ-077 AC5.
- Rule 7: after the tag, the merge-back brings the section, the versions and the hashes, removes only the released fragments, keeps a fragment merged after the cut, which the next release gathers once, and the branch deletion is printed only after the merge-back merged; REQ-077 AC6.
- Rules 8 and 9: a release branch older than `max_hours` gives the `NEEDS-YOU:` line, a red default branch after the cut does not hold the release while a red release branch does, and a bad `max_hours` is refused naming the setting; REQ-077 AC7.
- Rules 10 and 11: personal mode cuts, commits and tags in a temporary repository with no forge call and nothing posted, a product milestone runs its demo and acceptance record on the release branch, no session step merges, tags, pushes or deletes a release branch, and no workflow, ruleset or required check file changes; REQ-077 AC8.

## Open questions

Each is a point the brief leaves open, or a name it cites that the code holds otherwise; the reading after it is the most conservative one, and the rules above apply it.

- Q-S0070-1: "release what is locked" and a cut from a default-branch commit disagree: every unlocked change merged before the cut commit is in it. Reading: every change merged by the cut commit ships, no revert is made, and the `Cut:` line names the unlocked changes so the owner sees them before the tag (rule 4).
- Q-S0070-2: the brief says "the kit creates `release/<version>`", but session rule 22 lets a session push only its own branch and session rule 2 forbids a tag. Reading: `release.py cut` and `finish` print the branch push, the tag and the branch deletion, and the owner runs them; in personal mode the person's own command runs them locally (rules 4, 7 and 11).
- Q-S0070-3: principle 3 and `CLAUDE.md` item 2 say every pull request is branched from the default branch; the release and backport pull requests are branched from `release/<version>`. Reading: build (c) carries the ADR that amends principle 3 for those two kinds only, and no pull request into `release/*` is built before it is Accepted (rule 11).
- Q-S0070-4: the brief names "the release role (SPEC-0063)", which neither SPEC-0063 nor `config/reviewers.yaml` holds. Reading: no role is added; `Lock:` and `Backport:` lines count only from an account of `spec_approvers`, and a later build that adds a role writes its ADR (rules 2 and 10).
- Q-S0070-5: the merge-back raises the version on the default branch, so `check_release.py` takes it for a release pull request and fails it while post-cut fragments stay, and `merge_cleared.py` holds it for the owner. Reading: build (e) proposes the amendment of SPEC-0028 rules 4 and 5 for a `Merge-back:` pull request with its ADR, and the owner merges it, as every version raise (rule 7).
- Q-S0070-6: the brief says `/agk:upgrade` reads tags; it compares `agk.toml`'s version with the plugin's kit version. Reading: it is unchanged, since the plugin snapshot is built from the tag (`plugin_snapshot.py build --tag`), and its test starts from the previous tag's snapshot (rule 9).
- Q-S0070-7: may a patch release skip the lock? Reading: no, a one-item lock (brief answer 7; rule 2).
- Q-S0070-8: is the release branch deleted after the merge-back? Reading: yes, by the owner's command that `release.py finish` prints, and the tag keeps the history (brief answer 7; rule 7).
- Q-S0070-9: may the steward propose the lock list without being asked? Reading: yes, as a question, never as a lock (brief answer 7; rule 2).
- Q-S0070-10: where is a patch release cut while a release branch is open? Reading: from the previous release's tag, carrying only backports, and only when the owner names it (rule 4).
- Q-S0070-11: the brief names "the release bench", which the kit does not have. Reading: the release checks of rule 6 (`check_release.py`, `check_tag.py`, `release_pack.py check` and the proof on the release branch) stand for it, and no bench is added (rules 6 and 10).
- Q-S0070-12: the brief names "the release issue". Reading: the release brief of that version, as #1384 was for 0.64.6, which carries the `Lock:`, `Cut:` and `Backport:` lines (rule 2).
- Q-S0070-13: `check_release.py` is kit-only and checks the kit's own version files, so it cannot check a product's release. Reading: `release.py` is installed for every project, `check_release.py` stays the kit's, and a project's release pull request is checked by its own governance; no product version check is added in this intake (rule 10).
