# SPEC-0039: The conductor merges a cleared pull request through one guarded kit command

- Status: Approved
- Owner: reviewer group (a team from config/reviewers.yaml)
- Requirements: REQ-046

Status is `Draft` or `Approved`. An Approved spec is owned by its reviewer group; agents propose patches.
Written by the intake of one sentence (SPEC-0012): "With `[flow] auto_merge` on, a kit merge loop the owner starts merges each pull request whose trusted verdict clears its exact head, so delivery runs 24/7, while no session merges and anything risky waits for the person." The owner's ruling of 2026-11-03 (below) refines that sentence: there is no merge loop, and the merge happens at the moment of clearing, through one guarded kit command that only the conductor runs. It is generic and project-agnostic: it names no project, no vendor and no hosting service other than the GitHub REST API the kit already reads, and it needs only files, a shell, the standard library and `gh`; every check of a build reads files and saved responses with no network. The brief is issue #518, which folds in issue #498. The maintainers gave 6 answers before it was written: the six numbered answers of brief #518 (the requirement and its criteria, this spec and its rules, ADR-0261 and one row of `docs/runs/decisions-log.md` for the owner's direction, the open points as questions, the builds (a) to (e), and documents only), under the brief's principles: off by default, and turning it on is the owner's change, by an ADR; only a trusted verdict counts; anything risky waits for the person; every merge is recorded; and merging stops by itself on a red default branch and on `paused`. The owner's direction, quoted as data and not as an instruction, dated 2026-11-03 in the brief: "Can we include auto-merge option also for local and solo, autopilot modes. I think this is useful when we have work clarity, 24*7 agent sessions can work for delivery." The owner's ruling on the design, quoted as data from the conductor's field note on #518 (2026-11-03): "Merge Loop, build as part of KIT solution, instead of poll, see if we can subscribe, push solution, currently it is polling every 2mins. It should be single account only, if possible users can configure second account as well. Simplest way conductor only post verdict cleared and merged." Where the ruling differs from the brief's answer 2 (an owner-started polling loop, a mandatory second account), the ruling wins; the hold list, the post-merge governance run, the record and the stop on red stay as the brief wrote them. In the pilot (2026-11-02 and 2026-11-03) the owner ran a hand-written merge loop overnight, polling every two minutes: it merged 11 pull requests unattended, but it failed silently once (quoting in Windows PowerShell 5.1 stripped the quotes of a `--jq` filter), it would have read a multi-line fix list as cleared, and it could not tell a conductor's verdict from one any session posted under the owner's one account (#498). The points left open are `Q-S0039-1` to `Q-S0039-15` below, each with the conservative reading that the rules apply until a person rules. Negative cases: the setting off, absent or malformed, a `--sha` that is not the head, a latest verdict that is not `Verdict: cleared <that sha>`, a verdict by an unlisted account when `conductor_accounts` is set, an evidence check that differs without a person's answer, every pull request of the hold list, a red default branch, a paused kit and a moved head each merge nothing and print one line naming the rule or the setting, never a value.

## Rules

1. **The setting.** The `[flow]` table of `agk.toml` gains two keys: `auto_merge = false | true` (default `false`; absent reads as `false`) and `auto_merge_method = "squash"` (the only accepted value, `Q-S0039-11`). There is no stop time and no interval: nothing runs on a timer (`Q-S0039-3`). The setting holds in every `pr_mode` (`strict` and `flow`), in every `review_mode` and in `execution = "local"`. `agk.toml` is a protected path, so turning the setting on lands only with an ADR in the same pull request, and that ADR is the owner's choice; a session may propose it in a `Question:` and never writes, changes or removes the keys itself (`CLAUDE.md item 1`). `doctor.py` prints one line `auto-merge: off` or `auto-merge: on, method squash`, and fails a malformed value naming the setting and never the value. With `auto_merge` off, absent or malformed, or with another method, `merge_cleared.py` merges nothing and prints one line naming the setting. The setting is read from the default branch of the remote as last fetched, never from a pull request's head. The kit's template `kit/templates/agk.toml` carries the two keys commented, with `auto_merge = false`; this repository's `agk.toml` carries the same commented lines and does not turn the setting on.
2. **One guarded command, run at the moment of clearing.** `scripts/agk/merge_cleared.py` is installed. With `auto_merge = true`, the conductor, in the same act as posting `Verdict: cleared <sha>` on a pull request, runs exactly `python3 scripts/agk/merge_cleared.py --pr <n> --sha <the 40-character sha>` (`python` on Windows where `python3` is not on the path), the project's own regular file of the checkout's default branch, never a copy from a pull request. It works the same on POSIX and on Windows, with the standard library and `gh api` through the REST API only: it passes every argument as a list with no shell, so no quoting of a shell (cmd, PowerShell or a POSIX shell) can change a filter, and it reads JSON itself instead of passing `--jq` expressions. It re-checks rules 3 to 5 at the moment it runs, merges by rule 6, and prints one line: `merge-cleared #<n> <sha12>: merged <merge sha12>` or `merge-cleared #<n> <sha12>: held: <reason>` or `merge-cleared #<n> <sha12>: refused: <reason>`, the reason named by rule or setting, never by a value. It exits 0 on a merge, 3 on a hold or a refusal that a later pass may clear (head moved, checks pending, default branch red, paused, GitHub unreachable), 1 on a refusal it cannot explain and 4 on a read GitHub cannot answer five times in a row (as session rule 21 counts). A read that fails is never read as an empty list or as a pass. There is no polling loop: the command runs once per clearing and ends.
3. **A trusted verdict.** A pull request's verdict is the latest comment whose first line starts `Verdict:`. The command merges only when that first line reads exactly `Verdict: cleared <sha>`, where `<sha>` is the full 40-character lower-case sha given as `--sha` and is the pull request's head at the moment the command runs, with nothing before or after on that line. A `Verdict:` comment on its own merges nothing: trust rests on who can run the guarded command (rule 8), not on who posted the comment, so a stray `Verdict:` by a builder clears nothing, and a newer comment starting `Verdict:` by any account hides an older cleared one, so it can only hold a pull request. One account is the default (`Q-S0039-1`). The optional key `conductor_accounts` of `config/reviewers.yaml` (a list of GitHub logins, absent or empty by default) is the second-account option: when it lists at least one login, the command also requires the verdict's author to be listed, and refuses, naming the setting and never a value, an entry that is the placeholder `@REPLACE-ME` or is listed in `spec_approvers` (`Q-S0039-10`). A verdict for another head, a short sha, a verdict with more text on its first line (`Verdict: cleared <sha>, after ...`) and a multi-line fix list never merge, with one exception (amendment 118, ADR-0277): a covered fix list of SPEC-0021 whose first line is `Verdict: fix list <sha>` with that full 40-character sha and whose every `Final:` line is `docs/adr/<file> Proposed -> Accepted` clears the head like `Verdict: cleared <sha>` (SPEC-0021 rule 3a) when each named ADR is among the pull request's files (added or modified, from the files read for rule 5) and the command reads it at the head (one GET each) as `Proposed`; it holds naming rule 3 otherwise, and on a merge it passes the squash commit message `ADR-nnnn Accepted (Final <comment id>)`, one line per ADR, and the line `Merged-by: merge_cleared.py`. `verdict_authors` and session rule 1 do not change.
4. **Evidence.** A cleared verdict merges only with evidence for its head. In local mode (`execution = "local"`, or the one open local-mode record issue of `docs/guides/local-mode.md`) the verdict's body holds a `Local evidence:` line that names the same head and an `Evidence check: agrees, head <sha12>` that matches the head's first 12 characters (`Q-S0039-5`). In CI mode, every check of `required_checks` has a latest run on that head that ended `success`. An `Evidence check: differs` merges only when a comment whose first line is `Maintainer answer:` by an account in `spec_approvers`, posted after the verdict, names that head and says it accepts the difference; otherwise the pull request is held. A required check that is red or missing in CI mode, or a `Local evidence:` line for another head, holds the pull request; a pending one is rule 10's.
5. **The hold list.** The command never merges these; each waits for the person, and the line of rule 2 names its reason by rule, never by a value:
   - a release pull request: one whose diff changes `version` in `agk.toml` or `kit_version` in `kit/manifest.json` (`release`);
   - a pull request whose body has an `Approval: SPEC-nnnn` line for a spec that has no `Approve:` line by an account in `spec_approvers` naming that head (`spec approval`), or whose label is `agk:approve`;
   - one that changes a file under `constitution/`, `config/reviewers.yaml`, the ruleset files (`kit/templates/ruleset.json` and `scripts/agk/ruleset.py`) or `.github/workflows/` (`protected class <class>`);
   - one labelled `agk:hold` (`hold label`);
   - a draft (`draft`);
   - one whose `Depends-on: #n` names a pull request or brief not yet merged or closed as completed (`depends-on`, `Q-S0039-8`);
   - one whose mergeable state is `dirty` or `unknown` (`conflict`);
   - anything at all while the default branch is red (SPEC-0032 rule 7: the open issue `The default branch is red`, or the red run of rule 6) or while the kit is `paused` (`paused = true` on the default branch of the remote).
6. **The pinned merge and what follows.** The merge is one REST call, `PUT repos/{owner}/{repo}/pulls/<n>/merge` with `sha=<the verdict's head>` and `merge_method=squash`, so a head that moved after the verdict is refused by GitHub and the command prints `refused: head moved`. After each merge the command fetches the default branch into a temporary worktree outside the checkout and runs `make governance` there under the heavy-step lock (`python3 scripts/agk/lock.py run --name heavy --session merge-cleared -- env -i PATH="$PATH" HOME=<scratch> make -C <worktree> governance AGK_BASE=<parent of the merge commit>`, the bounded run of SPEC-0030 rule 6, so that no token reaches the merged code), then removes the worktree. If governance is red, it files one priority-0 brief by the router's red-branch path (the issue `The default branch is red` of SPEC-0032 rule 7, opened or updated through the same function of `route.py`, with the failing step and the merge commit and no cause, `Q-S0039-6`), prints `merge-cleared: stopped: default branch red after #<n>` and exits 1; that open issue holds every later merge (rule 5) until the router or a person closes it. It never reverts.
7. **The record.** Every merge is recorded by one line, `Auto merge: #<n> <merge sha> <UTC time> <verdict link>`, posted as a comment on the one open local-mode record issue while it is open, otherwise on the one open issue labelled `agk-auto-merge` that the owner opens once (the guide says how). With neither issue open, the command merges nothing and says so. It never writes a file, so `docs/runs/auto-merge-log.md` is not written by the command; a person or a later report may gather the lines into it (`Q-S0039-7`). In local mode the line also serves as the guide's `Local merge:` record.
8. **The one exception to session rule 2.** Only the conductor role may merge, and only through `merge_cleared.py`. `.claude/hooks/conductor_guard.py` allows exactly the command of rule 2, the project's own regular file, two options in that order, a pull request number and a 40-character lower-case sha, and only when `auto_merge = true` in both the checkout and `origin/<default branch>` as last fetched (as it reads `auto_start`); every other merge path stays denied to the conductor (`gh api` with `PUT`, `gh pr merge`, any other script). Builders stay blocked from any merge, `merge_cleared.py` included (`Q-S0039-15`). Principle 2 of the constitution and session rule 2 each gain one sentence naming this exception and nothing more, in build (b) (`Q-S0039-14`). The command never tags, never approves a review, never posts a `Verdict:`, `Approve:`, `Confirmed:` or `Maintainer answer:` line, never changes a workflow or the ruleset, never edits or commits a file of the checkout, never force-pushes, never pushes to any branch and never runs a command, script or `make` target from a pull request's head (governance runs only on the default branch after the merge, by rule 6). It reads secrets from nowhere: `gh` holds the login.
9. **Retry without a timer.** A merge that could not run when the pull request was cleared (exit 3: the default branch red, the kit paused, checks pending, GitHub unreachable, the machine asleep) is retried by the conductor's next review pass, which events already wake (session rule 10, `session.py review-queue`), not by a timer loop. `session.py review-queue` lists, with `auto_merge = true`, each open pull request whose latest verdict is `Verdict: cleared <its head>` and that has no record line, as `cleared, not merged`, and the conductor runs the command of rule 2 for each again. The command takes a named lock `merge-cleared` with `lock.py` for its run, so two runs on one machine never merge at once (`Q-S0039-2`); a merge pinned to a sha cannot merge one head twice. Inbound webhooks to a local machine are out of scope (`Q-S0039-13`).
10. **The CI path.** In CI mode, when the required checks of the cleared head are not all ended yet, the same command, instead of merging, turns on GitHub's own auto-merge for that pull request with `squash`, pinned to the cleared head where GitHub allows it, and prints `merge-cleared #<n> <sha12>: auto-merge on`; GitHub then merges when the checks end green. Where GitHub offers that only through GraphQL, the command does not call it and exits 3 with `held: checks pending`, and rule 9's retry merges once they are green (`Q-S0039-12`). The record line of rule 7 is posted by the next review pass that sees the merge. The CI path adds no workflow job, no secret and no ruleset change, and it merges nothing the local path would not merge.
11. **The guide.** `docs/guides/auto-merge.md` says, for the owner: what the setting does and does not do; that one account is the default and how to add a second account for the conductor and list it in `conductor_accounts` (`Q-S0039-1`); how to open the `agk-auto-merge` issue; how the conductor runs the command on Windows (PowerShell and cmd) and on POSIX; what each line of rule 2 means; and how to stop merging (set `auto_merge = false` by an ADR, or `paused = true`). `docs/guides/local-mode.md` gains one paragraph pointing to it.
12. **The builds, in order.** After this intake, the builds below are filed, each of about 600 changed lines of code and tests or fewer, each from the default branch with its own ADR naming the protected classes it changes and citing ADR-0261, and one fragment under `changelog.d/` where it changes a file the installer writes (SPEC-0031). A `Depends-on` is declared for a shared file and for a logical dependence alike. When this intake merges, #498 is closed with a pointer to it.
    - (a) **The setting and the verdict reader** (rules 1 and 3): `scripts/agk/merge_cleared.py` (new, installed: reading the setting and judging the latest verdict, no merge yet), `scripts/agk/reviewers.py` (reading the optional `conductor_accounts`), `scripts/agk/doctor.py`, `kit/templates/agk.toml` and `agk.toml` (the commented keys, off), `kit/manifest.json`, `tests/kit/test_merge_cleared_verdict.py`. `config/reviewers.yaml` is not changed: the key is optional and absent. No dependence.
    - (b) **`merge_cleared.py` with its re-checks, the pinned merge and the guard change** (rules 2, 4, 5, 8 and 9): `scripts/agk/merge_cleared.py` (the re-checks, the evidence, the hold list, the pinned merge, the `merge-cleared` lock, the lines and exit codes), `.claude/hooks/conductor_guard.py` (allowing exactly that command), the builders' deny of the command (`Q-S0039-15`), `scripts/agk/session.py` (`review-queue` listing `cleared, not merged`), `constitution/principles.md` (principle 2) and `config/session-rules.md` (rule 2), one sentence each naming the exception, `.claude/agents/conductor.md` (running the command in the act of clearing), `tests/kit/test_merge_cleared_run.py` and `tests/kit/test_conductor_guard.py`. Because it changes `constitution/`, it is on the hold list itself and a person merges it. `Depends-on` (a).
    - (c) **After the merge** (rules 6 and 7): `scripts/agk/merge_cleared.py` (the governance run under the heavy lock, the red-branch stop, the record line), `scripts/agk/route.py` (the red-branch issue writer made callable, unchanged in behaviour), `tests/kit/test_merge_cleared_after.py`. `Depends-on` (b).
    - (d) **The CI path** (rule 10): `scripts/agk/merge_cleared.py` (pending checks: GitHub's auto-merge where REST allows it, else held), `tests/kit/test_merge_cleared_ci.py`. No workflow changes. `Depends-on` (c).
    - (e) **The guide** (rule 11): `docs/guides/auto-merge.md`, `docs/guides/local-mode.md`, `tests/kit/test_auto_merge_guide.py`. `Depends-on` (c).

## Proof

REQ-046 AC1: *auto-merge is off unless the owner turns it on, and it means the same in every mode.* Rule 1. REQ-046 AC2: *a merge needs a cleared verdict for the exact head, a comment alone merges nothing, and a second account can be required.* Rule 3. REQ-046 AC3: *a clearing verdict merges only with evidence for the exact head it names.* Rule 4. REQ-046 AC4: *anything risky waits for the person.* Rule 5. REQ-046 AC5: *the merge is one guarded command that only the conductor runs, at the moment of clearing, the same on every platform, merging only the head it judged, and retried by the next pass instead of a timer.* Rules 2, 8 and 9. REQ-046 AC6: *a merge that breaks the default branch stops further merges, and every merge is recorded.* Rules 6 and 7. REQ-046 AC7: *the CI path is the same rule, the owner can set it up from the guide, and builders never merge.* Rules 10 to 12.

## Residual

- 2026-11-03: with one account (the default), GitHub records every comment under the owner's login, so the command trusts that the conductor ran it, which only the guard of rule 8 and the builders' deny hold; a session that ignored its rules and ran the command under that login could merge a pull request it cleared itself. The second account of `conductor_accounts` narrows this to the conductor's login, which the guide says to keep out of every builder session; nothing in the kit can check that (due 2026-12-31).
- 2026-11-03: two conductors on two machines are not detected; a pinned merge prevents a double merge of one head, but not two merges of different pull requests in one minute before governance runs (due 2026-12-31).
- 2026-11-03: in local mode the evidence the command reads is the conductor's `Evidence check:` line; it does not re-run the evidence check itself, so it is as good as the conductor's run (due 2026-12-31).
- 2026-11-03: a merge cleared while the conductor is not running waits until its next review pass; with no pass, nothing merges (the safe side) (due 2026-12-31).

## Open questions

Each is a point the brief or the ruling leaves open; the reading after it is the most conservative one, and the rules above apply it until a person rules.

- Q-S0039-1: how does the conductor get its own account? Reading, after the owner's ruling: one account by default, the owner's, and no second account is needed for anything to merge; a second account (a second GitHub user the owner creates, with write access and no admin, not a GitHub App, because an App needs hosting) is the owner's choice, and listing it in `conductor_accounts` makes the command require it (rules 3 and 11).
- Q-S0039-2: may the command merge while the owner is signed in elsewhere (another terminal, the browser, another machine)? Reading: yes, because its rules do not depend on where else the owner is signed in, and a merge pinned to a sha cannot merge a moved head; two runs on one machine are held apart by the `merge-cleared` lock, and two conductors on two machines are the owner's to avoid, named in the guide and the residual (rule 9).
- Q-S0039-3: may `auto_merge_stop` be "never"? Reading, after the owner's ruling: the question falls away, because there is no loop and no stop setting; nothing runs on a timer, and merging stops with `auto_merge = false` (by an ADR), `paused = true` or a red default branch (rules 1 and 5).
- Q-S0039-4: are batch smoke runs (the pilot's demo-safe lines) an optional extra gate? Reading: not in builds (a) to (e); the command merges one pull request per run and runs governance after each, and a smoke gate is a later brief with its own setting, off by default; nothing here runs a smoke command.
- Q-S0039-5: the brief names a `matches` evidence check, while `evidence.py check` prints `agrees` or `differs`. Reading: `Evidence check: agrees` for the verdict's head is the `matches` the brief means; `evidence.py` and its output do not change (rule 4).
- Q-S0039-6: the router runs only on GitHub Actions, so in local mode no router opens the red-branch issue. Reading: the command opens or updates that same issue through the router's own function, with the same title, label and `Priority: 0`, so there is still one issue, and the router updates or closes it when Actions runs again; the command names no cause (rule 6).
- Q-S0039-7: the brief offers `docs/runs/auto-merge-log.md` on a branch, or a comment on the record issue, while it also says the merge path never edits a file. Reading: the command never writes or pushes a file; each merge is one comment on the open local-mode record issue, else on the one open `agk-auto-merge` issue, and with neither the command merges nothing (rule 7).
- Q-S0039-8: is a pull request held whose `Depends-on: #n` has not merged, or whose mergeable state is dirty or unknown? Reading: yes, both wait, as they would for a person (rule 5).
- Q-S0039-9: may a session turn the setting on, or run the command for a builder? Reading: no; the keys change only in a pull request with the owner's ADR, only the conductor runs the command, and a builder never runs it (rules 1 and 8).
- Q-S0039-10: with `conductor_accounts` set, how does the command know the listed account is not the builders'? Reading: the builders push from the owner's account, which is a spec approver, so the command refuses a listed account that is in `spec_approvers` or is the placeholder; a setup where builders push from another account is the owner's to keep apart, as the guide says (rule 3).
- Q-S0039-11: which merge methods are allowed? Reading: only `squash`, the method the ruleset allows today; any other value merges nothing and names the setting (rule 1).
- Q-S0039-12: GitHub's own auto-merge is turned on through GraphQL `(verify: whether a REST route exists)`, and GraphQL is blocked in cloud sessions and outside the brief's REST-only rule. Reading: the command never calls GraphQL; where no REST route exists it holds with `checks pending` and the next review pass merges by the pinned REST merge once the checks are green; no workflow job, no secret and no ruleset change (rule 10).
- Q-S0039-13: may the merge be pushed to a local machine by inbound webhooks instead of the conductor's next pass? Reading: no, out of scope, because inbound webhooks need a public endpoint on the owner's machine; the retry is the conductor's next event-driven review pass (rule 9).
- Q-S0039-14: principle 2 of the constitution says "Agents never merge", and the conductor is an agent. Reading: the exception of rule 8 does not take effect until principle 2 and session rule 2 each carry its one sentence; that change is build (b), whose ADR names `constitution/`, and because the hold list holds it, a person merges it; until it merges, `merge_cleared.py` merges nothing in the conductor's hands (rule 8).
- Q-S0039-15: how is a builder blocked from running `merge_cleared.py` while the conductor's guard allows it? Reading: build (b) denies the command to builder sessions in the permission settings that builders start with, and allows it only through the conductor's guard; whether a project-wide deny in `.claude/settings.json` can be lifted for one role by its hook is `(verify)`, so until that is confirmed the deny is placed only where builders read it and is never removed for every session (rule 8).
