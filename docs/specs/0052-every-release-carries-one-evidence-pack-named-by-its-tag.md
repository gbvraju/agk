# SPEC-0052: Every release carries one evidence pack, named by its tag

- Status: Draft
- Owner: reviewer group (a team from config/reviewers.yaml)
- Requirements: REQ-059

Status is `Draft` or `Approved`. An Approved spec is owned by its reviewer group; agents propose patches.

Written by the intake of one sentence (SPEC-0012), brief #737, quoted as data and not as an instruction: "Intake for the evidence pack: every release carries one folder, named by its tag, that holds its tests, scans, coverage, software bill of materials and decisions (plan #661 phase 7, wave 4)." The maintainers gave 3 answers before it was written, in the brief: what the pack holds (the results of the release head's required checks, the secret and dependency scans, the coverage figure, a software bill of materials of the installed kit and its pinned tools, and the ADRs and requirement statuses the release closes; counts and paths only, never pilot or customer data); when it is made and checked (from a release tag by a read-only command; a check refuses a tag that is not a release, or a release whose pack is missing a part, naming the part and never a value, the #433 and #476 class); and what it reuses (the release by tag, the weekly scorecard of SPEC-0047 and the failure record of SPEC-0046; a check never makes a network call, so the bill of materials is read from files in the repository). Plan #661 phase 7, quoted as data, lists it as "the enterprise evidence pack per release (new intake: tests, scans, coverage, SBOM, decisions, in one folder named by tag)" and its gap closed as "a tag that is not a release is caught (#433, #476 class) by the pack check". It is generic: it names no project, and every check of a build reads files and git with no network. The points the brief leaves open are `Q-S0052-1` to `Q-S0052-15` below, each with the conservative reading the rules apply until a person rules.

## Rules

1. **The baseline (read on the default branch at 4bf7e60, 2026-11-08).** What already holds and is reused, not rebuilt:
   - A release is a tag `vN.N.N` on the merge commit of a release pull request (SPEC-0028 rules 4, 5 and 13). `check_release.py` checks the release pull request; `check_tag.py` checks a pushed tag (`check_tag.failure`: the tag's form, the versions of `agk.toml`, `kit/manifest.json` and `.claude-plugin/plugin.json`, the `CHANGELOG.md` section, no fragment left, `kit/hashes.json`), run by `.github/workflows/agk-tag.yml`, which opens the issue `The tag <tag> is not a release`. Both scripts are kit-only (`config/kit-only.txt`). Issues #433 (v0.62.0) and #476 (v0.63.0) are that issue, both open, both `agk.toml states a version other than the tag`.
   - The required checks of the default branch are the ruleset's (`kit/templates/ruleset.json`: the one context `governance`). The secret scan is the pinned gitleaks step of `.github/workflows/governance.yml` (`GITLEAKS_VERSION` and `GITLEAKS_SHA256`, ADR-0171). The CI test tools are pinned in `config/ci-tools.txt` (ADR-0328). No dependency scanner is configured anywhere: measured with `grep -rn -i -E "pip-audit|osv-scanner|dependency-review|trivy|grype" .github config agk.toml kit/templates scripts/agk`, which prints nothing.
   - The coverage figure is the project's `coverage` command of `agk.toml`, run only by the weekly drift audit (SPEC-0004, D9), whose report is the body of the one open issue labelled `agk-drift-audit` with the line `- D9 coverage | ... | covered <n>%` (`drift_audit.PREVIOUS_COVERAGE`). The command may install its tools, so it is never run by a check.
   - The weekly scorecard (SPEC-0047, `scorecard.py`) reads its numbers with GET only, prints them and writes nothing; its readers `scorecard.action_pins` (the SHA-pinned `uses:` lines of the workflows) and `scorecard.python_pins` (the `==` pins of `pyproject.toml`) read files only. Its weekly section lives in the audit issue's body (SPEC-0047 rule 7).
   - The failure record (SPEC-0046 rule 7) is the `Fixes-failure: #<issue>` line and its four record lines in a merged pull request's body; failure issues are labelled `found-bug` and carry a `Failure-signature:` line.
   - The installed kit is `kit/manifest.json` (its `kit_version` and its file lists) and its digests per release are `kit/hashes.json` (`kit_hashes.py`).
   - `scripts/agk/evidence.py` is the local evidence record of a pre-push run (ADR-0233), not this pack; the names stay apart (`Q-S0052-1`).
2. **The pack.** One folder `<out>/<tag>/` per release, where `<tag>` is the release tag and `<out>` the folder a person names. It holds exactly six files: `tests.json`, `scans.json`, `coverage.json`, `bom.json`, `decisions.json` (the five parts) and `pack.json` (the index: `schema` 1, the tag, the tagged commit's full ID, the date the pack was made from `date -u`, and each part's file name and SHA-256). Every part is JSON with a `schema` 1 field and the fields its rule names, and nothing else. A generated pack is never committed (principle 5): the command refuses an `<out>` inside the repository that git does not ignore, naming the path class, and nothing in the kit uploads it, attaches it to a release or posts it (`Q-S0052-2`, `Q-S0052-3`).
3. **The command.** `python3 scripts/agk/release_pack.py make --tag <tag> --out DIR [--api-dir DIR] [--repo OWNER/REPO]` reads the tagged commit with local `git` (never checking it out over the work tree), reads GitHub with `gh api --method GET` only, or saved responses with `--api-dir` as `scorecard.py` takes them, posts nothing, changes no file of the repository and writes only `<out>/<tag>/`. It first applies the release test of rule 4 and writes nothing when it fails. A folder `<out>/<tag>/` that already exists is refused, naming the path class, never replaced (`Q-S0052-4`). The script is installed with the kit (the parity rule, ADR-0326: the kit-only list may only shrink), and it starts no other program than `git` and `gh` (`Q-S0052-5`).
4. **The release test.** A tag is a release when the repository has `kit/manifest.json` and `check_tag.py` at the tagged commit and `check_tag.failure` finds nothing on that commit, read from the tag's files with local `git`: its form `vN.N.N`, the versions of `agk.toml`, `kit/manifest.json` and `.claude-plugin/plugin.json`, the `CHANGELOG.md` section, no fragment left and `kit/hashes.json`. A repository without them (a project, where `version` of `agk.toml` names the installed kit and not the project's release) has no release test yet: `make` and `check` refuse with `refused: this repository has no release test (path class kit/)` and write nothing, and a project's own release test is a later intake's (`Q-S0052-15`). A tag that is not a release is refused by `make` and by `check` with one line `refused: the tag is not a release (<the failing check, as check_tag names it>)`, exit 1, naming the rule and never a version or a value (principle 8). This is the #433 and #476 class: such a tag gets no pack, and the pack check refuses it again (`Q-S0052-6`).
5. **The tests part (`tests.json`).** The required checks of the default branch, read with one GET of the branch's rules (`repos/{owner}/{repo}/rules/branches/<default>` `(verify)`), and for each its name and the conclusion of its latest check run on the tagged commit (one GET of `commits/<sha>/check-runs`): `success`, `failure`, another conclusion GitHub gives, or `unknown` when it cannot be read, never `success`. A test count is given per check only where the check run's output states it as `<n> passed` (and `<n> failed`, `<n> skipped`); otherwise `unknown`, never 0 (`Q-S0052-7`).
6. **The scans part (`scans.json`).** One entry per scan, `secret` and `dependency`, each with its scanner, its pinned version as the repository's files state it at the tag, and its outcome on the tagged commit (the conclusion of the step or job that runs it, read with GET of the run's jobs): `passed`, `failed`, `unknown`, or `not run`. A scan that no file or setting configures is recorded as `not run` with the scanner `none`, never as passed; today that is the dependency scan (rule 1). A release whose dependency scan is `not run` is not refused for that: whether a release needs one is the supply-chain intake's decision, plan #661 phase 7 (`Q-S0052-8`).
7. **The coverage part (`coverage.json`).** The covered percentage of the `- D9 coverage` line in the body of the open `agk-drift-audit` issue (one GET), with that report's date, when the report's date is at or before the tag's commit date; otherwise, or when the line or the issue cannot be read, `unknown`, never 0. The command never runs the coverage command, which may install tools and is not read-only (`Q-S0052-9`).
8. **The bill of materials (`bom.json`).** Read from the repository's files at the tagged commit with `git show`, with no network call: the kit's `kit_version` and each file that `kit/manifest.json` installs, with its SHA-256 at the tag; each pinned tool with its pin (the lines of `config/ci-tools.txt`, the `==` pins of `pyproject.toml` as `scorecard.python_pins` reads them, and the pinned scanner of rule 6); and each SHA-pinned action with its release tag and SHA, as `scorecard.action_pins` reads them. A file the bill names that cannot be read at the tag is refused, naming the path class, and no pack is written. The format is the kit's own JSON of these fields; a standard format (SPDX or CycloneDX) is left to the supply-chain intake (`Q-S0052-10`).
9. **The decisions part (`decisions.json`).** Between the previous release tag (the highest `vN.N.N` tag below this one that passes rule 4; none means the repository's first commit) and this tag, read with local `git` except where named: the ADRs whose `Status:` is `Accepted` at this tag and was not at the previous one, by number; the requirements whose `Status:` line in `docs/requirements.md` differs, by id with both statuses; the `found-bug` issues named by a `Fixes-failure:` line of a pull request merged between the two tags, by number with their state (GET of the merged pull requests and of each issue); and the scorecard week of the tag, the rows of the scorecard section of the audit issue's body for the week that holds the tag's date, as metric names and values, or `unknown`. The tags skipped because they are not releases are listed by name (`Q-S0052-11`, `Q-S0052-12`).
10. **The pack check.** `python3 scripts/agk/release_pack.py check <out>/<tag>` reads the folder and the repository's git only, with no network call, and prints `ok pack`, or one `FAIL pack: <part> <reason>` line per problem and exits 1, naming the part and never a value: a part missing, a file that is not one of the six, a part that is not JSON of its form (a missing or extra field, a `schema` other than 1), a SHA-256 in `pack.json` that does not match its part, a tag or commit in `pack.json` other than the folder's name and the tag's commit, a tag that fails rule 4, and a part in which the data guard (`guard.scan_text`) finds anything. A required check whose conclusion is `failure` or `unknown`, or a scan `failed` or `unknown`, prints one `warn pack: <part> <name> <outcome>` line and does not fail the check: the pack records the release, it does not judge it (`Q-S0052-13`). No governance step, `make governance` or `prepush.py` runs it.
11. **Privacy, and what does not change.** A pack holds ids, names of checks, tools and files, statuses, digests and counts only: never a log, a transcript, a test's output, a person's login or any pilot or customer data, and the data guard of rule 10 refuses a part that holds one. The kit ships no pack of its own and no pack of a project moves into the kit. No workflow, ruleset, required check, `constitution/`, `config/reviewers.yaml` or `.github/CODEOWNERS` changes; running `make` from `.github/workflows/agk-tag.yml`, or attaching a pack to a GitHub release, is a later change that needs the owner's yes for the workflow and a write it would add (`Q-S0052-3`, `Q-S0052-14`).
12. **The builds, in order.** Each is tests first, about 300 changed lines or fewer, from the default branch, records its decisions under `Decisions taken:` and cites ADR-0343 with `Covered-by: ADR-0343` once it is Accepted (session rule 36). A `Depends-on` is declared for a shared file and for a logical dependence alike.
    - (b) The form and the check (rules 2, 4 and 10): `scripts/agk/release_pack.py` with `check` and the release test, its entry in `kit/manifest.json`, one `[[testing.map]]` entry in `agk.toml`, one `changelog.d/` fragment, `tests/kit/test_release_pack.py` with pack folders and git fixtures in `tmp_path`.
    - (c) The parts read from git (rules 3, 8 and 9 without GitHub): `make` with the bill of materials and the ADR and requirement lists of the decisions part, the output-folder refusals, the same test file. `Depends-on` (b).
    - (d) The parts read from GitHub (rules 5, 6, 7 and the GitHub fields of rule 9): the tests, scans and coverage parts, the failure issues and the scorecard week, with saved responses through `--api-dir` and a `gh` stub that answers GET only. `Depends-on` (c).

## Tests

Fixtures in `tmp_path`, local git repositories, saved GitHub responses and a `gh` stub only: no network, no install, invented data (`example.com`), and each test carries the marker `REQ-059` with its criterion. Rule 12's order is checked by review.

- Rules 2 and 3: `make` on a release tag of a fixture with saved responses writes `<out>/<tag>/` with exactly the six files, `pack.json` holding each part's digest; only GET requests reach the stub and nothing is posted; an `<out>` inside the repository that git does not ignore is refused naming the path class and nothing is written; an existing `<out>/<tag>/` is refused and left unchanged; REQ-059 AC1.
- Rule 4: in a kit fixture, a tag whose `agk.toml` states another version, a tag not of the form `vN.N.N` and a tag with a fragment left are each refused by `make` and by `check` with the rule line naming the failing check, which holds no version; a fixture without `kit/manifest.json` is refused naming the path class; no folder is written; REQ-059 AC2.
- Rule 5: saved responses with the required check `governance` concluded `success` give that entry, with the counts where the output states `<n> passed`; a check run that is missing, or a rules response that cannot be read, gives `unknown` and never `success`; a run whose output states no count gives `unknown`, never 0; REQ-059 AC3.
- Rule 6: the pinned secret scanner's version is read from the fixture's workflow file and its outcome from the saved jobs; a fixture with no dependency scanner records `not run` with the scanner `none`; a job that cannot be read records `unknown`; REQ-059 AC4.
- Rule 7: an audit body with `- D9 coverage | ... | covered 81.5%` dated before the tag gives 81.5 with that date; a report dated after the tag, a body without the line or an issue that cannot be read gives `unknown`, never 0; the coverage command of the fixture's `agk.toml` is never started (a stub command that writes a marker file leaves none); REQ-059 AC5.
- Rule 8: a fixture tag gives each installed file of its `kit/manifest.json` with the SHA-256 of its content at the tag, the pins of `config/ci-tools.txt` and `pyproject.toml` and the SHA-pinned actions; a file changed after the tag gives its content at the tag; a manifest that names a file missing at the tag is refused naming the path class, with no pack written; no socket is opened (a test that makes `socket.socket` raise); REQ-059 AC6.
- Rule 9: two release tags with an ADR flipped to `Accepted` and a requirement moved from `planned` to `done` between them list exactly those; a tag between them that is not a release is skipped and listed; a saved merged pull request with `Fixes-failure: #12` lists issue 12 with its state; the scorecard week is the one that holds the tag's date, or `unknown`; no part holds a login or a line of a body other than the ids, names and values listed; REQ-059 AC7.
- Rule 10: a complete pack prints `ok pack`; removing a part, adding a seventh file, removing a field, changing `schema`, changing one byte of a part, naming another commit in `pack.json`, and putting a secret-like invented string built at run time into a part each give one `FAIL pack:` line naming the part and not the value; a pack with a required check `failure` prints a `warn pack:` line and `ok pack`; the check opens no socket and no governance step calls it; REQ-059 AC8.

## Proof

REQ-059 AC1: *the pack is one folder named by its tag, made read-only, never committed.* Rules 2 and 3. REQ-059 AC2: *a tag that is not a release gets no pack and is refused.* Rule 4. REQ-059 AC3: *the required checks are recorded, unknown is never passed.* Rule 5. REQ-059 AC4: *both scans are recorded, a scan not run is never passed.* Rule 6. REQ-059 AC5: *the coverage figure is read, never run, never 0.* Rule 7. REQ-059 AC6: *the bill of materials comes from files at the tag.* Rule 8. REQ-059 AC7: *the decisions are ids, statuses and counts between two releases.* Rule 9. REQ-059 AC8: *the offline check refuses an incomplete or altered pack.* Rules 10 and 11.

## Residual

- 2026-11-08: no dependency scanner exists, so every pack records the dependency scan as `not run` until the supply-chain intake of plan #661 phase 7 adds one (due 2027-01-31).
- 2026-11-08: the audit issue holds only its latest report, so a pack made after the next weekly report records coverage and the scorecard week as `unknown`; a pack is best made on the day of the tag, and nothing makes it then until a workflow runs `make` with the owner's yes (due 2026-12-31).
- 2026-11-08: a pack outside the repository can be lost or edited; the digests of `pack.json` show an edit only against a copy of the index kept elsewhere, and where the pack is kept is the owner's call (due 2026-12-31).

## Open questions

Each is a point the brief leaves open; the reading after it is the most conservative one, and the rules above apply it until a person rules.

- Q-S0052-1: what is the command called? Reading: `scripts/agk/release_pack.py`, because `scripts/agk/evidence.py` already names the local evidence record of a pre-push run and one name for two things would mislead (rule 1).
- Q-S0052-2: where does the folder live? Reading: under a folder the person names with `--out`, outside the repository or git-ignored, and never committed, because a pack is generated and principle 5 forbids committing generated files (rule 2).
- Q-S0052-3: is the pack attached to the GitHub release or made by the tag workflow? Reading: neither in these builds; each is a write or a workflow change that needs the owner's yes, so a person runs `make` (rules 2 and 11).
- Q-S0052-4: may a pack be made again over an old one? Reading: no; an existing folder is refused and left as it is, so a pack is never silently replaced (rule 3).
- Q-S0052-5: is the script kit-only or installed? Reading: installed, because the parity list of kit-only files may only shrink (ADR-0326); until a project has a release test (`Q-S0052-15`) it refuses there and makes nothing, and the kit-only `check_tag.py` is read only where `kit/manifest.json` is (rules 3 and 4).
- Q-S0052-6: what is "a tag that is not a release"? Reading: a tag that `check_tag.failure` fails on its own commit, which holds the #433 and #476 class (`agk.toml` states another version); the pack reuses that test and writes no second one (rule 4).
- Q-S0052-7: which checks are "the release head's required checks", and where do test counts come from? Reading: the default branch's required checks as GitHub's branch rules state them `(verify)`, with the latest check run on the tagged commit; a count only where the run's output states it, else `unknown` (rule 5).
- Q-S0052-8: must a release have a dependency scan? Reading: no, not in this spec; the pack records `not run` and the supply-chain intake of plan #661 phase 7 decides whether a scanner is required (rule 6).
- Q-S0052-9: where does the coverage figure come from? Reading: the weekly audit's D9 line, dated at or before the tag, else `unknown`; the coverage command is never run, because it may install tools (rule 7).
- Q-S0052-10: which bill-of-materials format? Reading: the kit's own JSON of names, versions, pins and digests; SPDX or CycloneDX is the supply-chain intake's choice, so this spec does not choose one (rule 8).
- Q-S0052-11: which decisions does "the release closes" mean? Reading: the ADRs that became `Accepted` and the requirements whose status changed between the previous release tag and this one, the failure issues whose fix record merged in that range, and the scorecard week of the tag (rule 9).
- Q-S0052-12: what is the previous release when some tags are not releases (v0.62.0 and v0.63.0 today)? Reading: the highest lower tag that passes rule 4; the tags skipped are listed by name, so the range is never silently widened (rule 9).
- Q-S0052-13: does the pack check refuse a release whose required check failed? Reading: no; it refuses a pack that is missing or altered and a tag that is not a release, as the brief says, and prints a `warn pack:` line for a failed or unknown check or scan, because refusing a release on its results is a new gate the brief does not give (rule 10).
- Q-S0052-14: may the pack hold a test's output or a person's login? Reading: no; counts, ids, names, statuses and digests only, and the data guard refuses a part with a finding (rule 11).
- Q-S0052-15: does a project get a pack? Reading: not yet; a project's `version` names the installed kit, so the kit's release test does not fit it, and the command refuses there naming the path class until a later intake gives a project's release test (rule 4).
