# SPEC-0055: The right tests for each stack, run at the right time by a map that learns

- Status: Approved
- Owner: reviewer group (a team from config/reviewers.yaml)
- Requirements: REQ-062

Status is `Draft` or `Approved`. An Approved spec is owned by its reviewer group; agents propose patches.

Written by the intake of one sentence (SPEC-0012), brief #774: "Intake for project testing by stack: a project's front end, back end, mobile and other parts each run the right tests at the right time, a pull request runs only what its change can break, and AGK learns from every test the selection missed." The maintainers gave 9 answers before it was written (the answers of the brief, one to nine, which are rules 1 to 14 below). The owner's direction, quoted as data from the brief (2026-11-08 13:46 IST): "when we use AGK installed on Projects there can be different ways of tests FE, BE, Mobile, etc. How AGK will solve that ... internal AGK is different and AGK in projects is different. We need to find the differentiator while designing the solution, how can it be remembered"; the owner's yes to file it (13:50 IST): "Yes, go ahead". The measurement behind it, read from the governance logs of 2026-11-08 by the writer of this spec: of 13 `governance full` pull request runs from 06:20Z to 08:10Z, the 10 whose logs held a `regression:` line were 5 full for `always_full .github/workflows/**`, 4 full for unmapped files under the `balanced` profile and 1 documentation only, so a full run because of an unmapped data file is reproduced, and no run in that sample was in `selected` mode. It is generic: it names no project, tests use invented data (`example.com`), and every check of a build reads files, git and saved outputs with no network. Every existing name the rules cite was read on the default branch at a0bb432 (2026-11-08), except those a rule says are not on the default branch at a0bb432: `front_door.py detect` and `failures.py run` (rules 10 and 13), and, of SPEC-0041, `personal.py`, `/agk:personal-adopt` and the floor, where only `personal_state.py` and `kit/templates/personal.toml` exist (rules 10, 13 and 14); where the brief's wording differs from the code, the rule follows the code and says so. A fact about a runner or a build tool that was not confirmed here is marked `(verify)`. The points left open are `Q-S0055-1` to `Q-S0055-17` below, each with the conservative reading the rules apply until a person rules. Negative cases: a malformed setting, a missing environment, a map that cannot be built, a report that cannot be read and a metric that cannot be read each change nothing that runs for the worse: they run more, or print one line naming the setting and never a value.

Each rule states how it works in four places: **AGK itself** (this repository), and a **project** in **GitHub mode** (CI runs), **local mode** (no CI runs: the one open local-mode record issue, or `execution = "local"`) and **personal mode** (`forge = "files"`, SPEC-0041: nothing of AGK in the product repository).

## Rules

1. **The difference, and how it is remembered.** AGK itself has one area (`[proof.kit]`), one language, one runner (pytest), a curated map (the `[[testing.map]]` entries of `agk.toml`, written by hand) and tests of its own checks. A project has many stacks and test levels, a map that must be generated and must learn, and test costs that depend on the environment. There is one mechanism and two sources of data, never two code paths: no script asks whether it runs in the kit. The difference is held in one optional setting, `[testing] map_source`, `"curated"` (the default) or `"generated"`, and it is remembered in three places: every selection of a repository that sets the key prints `tests: map curated` or `tests: map generated` as its first line, the weekly report (rule 14) names the source beside its numbers, and `docs/guides/testing.md` opens with the two sentences above (`Q-S0055-1`).
   - AGK itself: sets `map_source = "curated"` in build (a), one line of `agk.toml`, so its runs print the line; its `[[testing.map]]` entries do not change by this rule.
   - Project, GitHub: `generated` once a person sets it (rule 13); until then `curated`, as today.
   - Project, local: the same as GitHub, the same setting.
   - Project, personal: the setting lives in the sidecar's `agk.toml`, with the same meaning.
2. **Nothing is lowered, but for one stated narrowing.** SPEC-0044 rule 1 stands: no rule here removes, skips or narrows what the default branch runs, a release pull request runs every level (rule 10), and `pr_tests` stays `"full"` by default. Each new key is optional; with every one absent, `prepush.py`, `project_tests.py`, `proof.py`, `impact.py` and `test_plan.py` print and run exactly what the default branch does today, but for rule 6. Rule 6 is the one stated narrowing of a pull request's run, it has no setting, and it applies to every repository with a `[testing]` table, AGK on `curated` included: under the `balanced` profile, a changed file no entry covers selects the tests that name it where today it makes the selection full. The default branch and a release pull request still run everything, so what that narrowing misses fails there and is a selection miss (rule 11). Rule 6 aside, a selection only ever adds to what it would otherwise select: a generated entry, a link (rule 7) and a learned entry (rule 12) add tests and never remove one. A malformed key is refused naming the setting (`setting: testing.map_source`), never the value.
   - AGK itself: `map_source` is the only new key it sets; `pr_tests = "selected"` stays, and its map changes only by build (b) (rule 6).
   - Project, GitHub: `pr_tests = "selected"` remains the project's own choice, in a protected file, with an ADR.
   - Project, local: the same; the full runs of rule 10 stand in for CI's.
   - Project, personal: the floor of SPEC-0041 rule 18 is unchanged and no setting here lowers it.
3. **Areas with levels.** A `[proof]` area may hold levels, `[proof.<area>.levels.<level>]`, where `<level>` is one of `unit`, `integration`, `e2e`, `visual`, `contract`, `device`, `performance`, `security` or the project's own name (letters, digits, `-` and `_`). A level has `command` (with `{files}` to receive the selected test files, or without it to run the whole level), `when` (a non-empty list of `pr`, `main`, `nightly`, `release`), and optional `env` (rule 4), `dirs`, `patterns`, `cwd` (each defaulting to the area's, whose own keys stay required), `junit` (rule 8) and `rerun` (rule 9). `AREA_KEYS` in `common.py` gains `levels`, and an area with no `levels` is one implicit level `unit` whose `when` is every event, so today's areas read as they do. A `when` that names only `pr` is refused naming the setting, because such a level would never have a full run (`Q-S0055-2`). A test file belongs to the first level whose `dirs` and `patterns` it matches, in table order; a test file of an area in no level of that area is refused by `test_plan.py` naming the setting, never left out (`Q-S0055-3`).
   - AGK itself: `[proof.kit]` stays as it is, one implicit `unit` level.
   - Project, GitHub: `pr` is the selection on a pull request, `main` a push to the default branch, `nightly` the project's scheduled run, `release` a release pull request.
   - Project, local: `pr` is `prepush.py`'s selection; `main` and `release` are the run before the merge, and `nightly` the once-a-day run (rule 10).
   - Project, personal: `pr` is the selection of the gate's quick run; `main`, `release` and `nightly` are the run of rule 10; no level's command is written into the product.
4. **The environment a level needs.** `env` is a list of names a project chooses (`browser`, `database`, `emulator`, `macos`, `services`, or its own). What a machine has is the environment variable `AGK_TEST_ENV` (a comma-separated list; absent means none), which the workflow or the person sets; a level whose `env` is empty always runs. A level whose `env` names something absent is not run, the run prints `not run: <area>:<level> (env <name>)`, and it is counted `not run`, never passed (`Q-S0055-4`). A level with `env` set runs under the heavy-step lock where sessions share a machine (session rule 31), and the kit starts, installs and provisions nothing: it reads a name.
   - AGK itself: no level, so no environment; `AGK_TEST_ENV` is unset and nothing changes.
   - Project, GitHub: the project's workflow sets `AGK_TEST_ENV` per job, a macOS job for the `macos` levels; a workflow file changes only by the project's own rule.
   - Project, local: the developer's machine sets it; a missing simulator is `not run` here and the level's next run is rule 10's.
   - Project, personal: the same as local; the value is never stored in the product.
5. **A generated map.** `python3 scripts/agk/test_map.py build` (new, installed, standard library only, no network, reads the tree at the head) writes the selection map from each stack's own dependency facts: Python imports (`ast`), the JavaScript or TypeScript import graph (import and require lines, read as text, and `tsconfig.json` paths `(verify)`), Gradle modules (`settings.gradle` and the `project(...)` dependencies, at module granularity), Xcode targets (`project.pbxproj`, read as text, at target granularity `(verify)`) and Go packages (the import lines and `go.mod`, at package granularity). Folder conventions are the fallback for a stack it cannot read (`src/a/b.ts` beside `src/a/b.test.ts`, a module's `src/test/` folder). The same tree gives the same bytes. A generated map is never committed (principle 5): it is written to the git-ignored file `.agk-test-map.toml`, whose first line names the tree it was built from (the commit's tree id), and rebuilt by `impact.py`'s callers when `map_source = "generated"` and the file is missing or its first line names another tree, so two commits with one tree give the same bytes; a stack that cannot be read adds no entries and its files are unmapped, so rule 6 applies to them (`Q-S0055-5`). With `generated`, the selection is the union of the generated map, the project's own `[testing] map` and the learned entries (rule 12) (`Q-S0055-6`). Its entries have the same shape as `[testing] map`, so `impact.py` reads them unchanged.
   - AGK itself: not used: `curated`, and its data-file coverage comes from build (b) (rule 6).
   - Project, GitHub: built in CI before the selection; the build's seconds are part of the test step.
   - Project, local: built in `prepush.py` before the selection.
   - Project, personal: built from the product clone, read-only, into the sidecar's `cache/` (ignored, SPEC-0041 rule 2); the sidecar's `test-map.toml` keeps its own meaning (requirements to test ids, SPEC-0041 rule 16) and is a different file.
6. **A file the map does not cover.** For a changed file that no entry covers, `impact.py` selects the test files that name its path or its folder, and turns the selection full only when no test names it; it prints `unmapped: <path> -> <k> tests that name it`. It has no setting and is the narrowing rule 2 names. The `thorough` profile and `always_full` are unchanged. This is brief #773, which becomes build (b), with its answers 1 to 5 as written there and its reserved ADR-0359; its hold stays until the owner releases it.
   - AGK itself: this is the change that stops a data file (`kit/manifest.json`, `config/playbooks/*.toml`) making a run full; brief #773's `[[testing.map]]` additions and its map-whole check apply here.
   - Project, GitHub: the same reading in `Project tests`, and `doctor.py` lists the unmapped files.
   - Project, local: the same in `prepush.py`.
   - Project, personal: the same in the gate's quick run; the floor's run is whole (rule 2).
7. **Links across areas.** A change in one area can require another area's tests. `[[testing.links]]` entries, `{ code = ["<glob>", ...], run = ["<area>:<level>", ...] }`, are declared once in `agk.toml`; `test_map.py build` also derives one for a schema file (an OpenAPI, GraphQL or protobuf file `(verify)`) that a file of another area imports or generates from, naming that area's `contract` level when it has one (`Q-S0055-7`). A declared and a derived link are a union. A link selects its level on the pull request even when its `when` has no `pr`; a `{files}` level runs that level's selected tests or, with none, all of it. A linked level whose environment is absent fails the test step in CI, naming the setting `testing.links`, because a declared requirement was not met, and on a developer's machine is `not run` (`Q-S0055-8`). A link never removes a test.
   - AGK itself: one area, so no link.
   - Project, GitHub: the failure of the missing environment above is what keeps a link honest.
   - Project, local: `not run` in `prepush.py`, and the run of rule 10 runs it.
   - Project, personal: the same as local; a link is in the sidecar's `agk.toml`.
8. **One interface for results.** The JUnit XML report of every runner is the one interface: a level's `junit` (a path or a glob, relative to its `cwd`) or else `[testing] junit`. It feeds per-file timing (`impact.run_timing`, SPEC-0044 rule 2), the failed-test ids of `project_tests.py`'s rerun, the failure signature of SPEC-0046 rule 3 (`failures.failed_tests`) and the flake strikes of `flakes.py`, so none needs pytest. Runners reach it their own way: pytest's `--junit-xml`, vitest's junit reporter, jest with a junit reporter, Gradle's XML test results (a folder of files, hence the glob), xcodebuild through a report converter, and Go through a converter `(verify, each)`. The kit adds no flag and installs no reporter, as SPEC-0044 rule 2 holds. A level with no report has timing `unknown`, no rerun and no strike, and nothing fails for that reason. The test id keeps pytest's form for pytest and is `<classname>::<name>` otherwise (`Q-S0055-9`).
   - AGK itself: unchanged; it sets no `junit`, its ids stay pytest's, and rule 11 reads its failures from the run's output.
   - Project, GitHub: per level, in the job that ran it.
   - Project, local: per level, in the run on the developer's machine.
   - Project, personal: the same; ids go to `records/` of the sidecar and never to the product.
9. **Rerun and quarantine by level.** `rerun`, a level's command with `{id}` for one test id, lets `project_tests.py` rerun a failed test alone for any runner, under `[testing] rerun_alone` (ADR-0323) and its limits (at most ten). Without `rerun`, pytest reruns as today and any other runner exits as today. A pass alone is one strike by `flakes.py add`, and a failure alone is a real failure. Quarantine stays what `flakes.py` lists: this spec adds no quarantine, and no status in the ledger changes what a run fails on (`Q-S0055-10`).
   - AGK itself: unchanged.
   - Project, GitHub: the strike is written in the CI run and printed; the ledger change is committed by a person or a session, as today.
   - Project, local: the ledger of the project, on the machine's run.
   - Project, personal: the ledger is `docs/runs/flakes.md` of the sidecar, read by `flakes.py` with the sidecar as root.
10. **Where the full suite runs, by mode.** The full suite is every level whose `when` names the run's event, or `project_tests` for a project without levels.
    - AGK itself: on the default branch after the merge, and on a release pull request, as `project_tests.py` and `.github/workflows/governance.yml` do today.
    - Project, GitHub: the same: `main` levels on a push to the default branch and `release` levels on a release pull request; a project's `nightly` levels run on its own schedule, which is a workflow of the project and needs that project's yes (`Q-S0055-11`).
    - Project, local: before the merge, in `merge_cleared.py`, which with local mode on runs the `main` levels in place of the `[testing] pre_merge_tests` list (an amendment of SPEC-0039 rule 6, proposed at build (g), `Q-S0055-12`), and once a day by `failures.py run --on default` (SPEC-0046 rule 12, build (i) of that spec, not on the default branch at a0bb432), which the project's own scheduler starts and an agent session cannot. `doctor.py` prints the age of the last full run, and over 24 hours prints `tests: last full run older than a day (setting: execution)`.
    - Project, personal: before the developer's push, by the floor (SPEC-0041 rule 18, build (h) of that spec, not on the default branch at a0bb432), which runs the whole `test_command`; and once a day by `personal.py full --due` (new, in a script that SPEC-0041 build (d) first adds and that is not on the default branch at a0bb432), which runs the same whole command on the clone's head when the last record in `records/` is older than 24 hours and writes one record there. Nothing leaves the machine.
11. **A selection miss is recorded.** When a full run fails a test that the selection of a change skipped, AGK records a selection miss. The change is read from the merged pull requests since the last green full run, and the selection is recomputed for each from its merge base and head, with the map as of its head (`test_map.py build` is deterministic, rule 5). A miss is not recorded for a test that passes alone (a flake, rule 9), for a test that failed before the change (the previous full run's report, or its output where it has none), or for a level whose `when` has no `pr` (not selectable: counted as `level not on pull requests`, rule 14). With several merges in the range, every candidate is named and no link is proposed (`Q-S0055-13`).
    - AGK itself: the push run of `governance`, which writes no JUnit report (rule 8): the `agk-test` target of `kit/agk-kit.mk` keeps the suite's output and `failures.failed_tests` reads the `FAILED <id>` lines from it, with no `[testing] junit` and no workflow change.
    - Project, GitHub: in the job of the push run, from the level's report (rule 8) or, with none, the run's output; the miss goes on the failure issue (SPEC-0046 rule 3) as one line `Selection-miss: <test id> <changed path>`, when `[failures] issues` is on, and into the step summary and the log otherwise.
    - Project, local: in the run of rule 10; the same lines.
    - Project, personal: in `personal.py full`, one JSON line in `records/selection-misses.jsonl` of the sidecar.
12. **The map learns.** `python3 scripts/agk/test_map.py learn --miss <test id> --changed <path>` writes one entry, `{ code = "<changed path>", tests = ["<test file>"], seen = "YYYY-MM-DD" }`, and one row of the miss, to `docs/runs/test-links.toml`, the learned entries that every `impact.py` selection reads (`Q-S0055-14`). The pull request that fixes the failure (`Fixes-failure:`, SPEC-0046 rule 7) carries it, or, with no failure issue, one brief filed for it. CI opens no pull request (`Q-S0055-15`). A learned entry only adds tests, is never removed automatically, and the count of them is reported (rule 14) so a map that only grows is visible. A person removes an entry by a pull request that says why.
    - AGK itself: the same file and rule, beside its curated `[[testing.map]]`, so a learned entry needs no ADR.
    - Project, GitHub: the same.
    - Project, local: the same, through the person's or the session's pull request.
    - Project, personal: `records/test-links.toml` in the sidecar, read in place of the file above, committed there; nothing is written to the product and no pull request is opened (SPEC-0041 rule 20).
13. **Setup.** Stack detection (plan #661, wave 2; `front_door.py detect` is not on the default branch at a0bb432 and no brief holds it yet) proposes the areas, levels, commands and a first map; until it lands, `adopt.detect_tests` and the lockfiles are the source, and `python3 scripts/agk/test_map.py propose` prints the proposal and writes nothing (`Q-S0055-16`). Setting `map_source`, `[proof]` and `pr_tests` stays a person's change with an ADR (`agk.toml` is protected). `doctor.py` reports the share of changed files the map covers, over the last 20 merges, as `tests: map covers <p>% of changed files (last <n> merges)`, and it fails nothing.
    - AGK itself: `doctor.py` reports the share for its curated map; no proposal is written.
    - Project, GitHub: `adopt.py` calls `propose` and shows it; the person chooses.
    - Project, local: the same.
    - Project, personal: `/agk:personal-adopt` (SPEC-0041 build (g), not on the default branch at a0bb432) shows the proposal; the person's yes writes the sidecar's `agk.toml`, and only that.
14. **Measured.** The weekly report (`metrics.py`; a metric of SPEC-0047's scorecard only by an amendment that build (j) proposes) gives, with the source of rule 1 beside them: minutes of the test step per pull request (the reader `metrics.project_test_seconds` extended to the `Tests of the checks` step for AGK itself, and `Project tests` for a project), the share of pull request runs in `selected` mode, the miss rate (selection misses of rule 11 over full runs that failed, read from `docs/runs/test-links.toml` and the failure issues), the count of learned entries, and full runs by reason (`always_full`, `unmapped`, `thorough`, `level not on pull requests`). A number that cannot be read is `unknown`, never 0 (SPEC-0007 rule 10). It reports for AGK itself and for each project, each from its own repository; nothing of a project reaches AGK (SPEC-0046 rule 10) (`Q-S0055-17`).
    - AGK itself: from its governance runs.
    - Project, GitHub: from its governance runs.
    - Project, local: from the records of its local runs; a number with no record is `unknown`.
    - Project, personal: `personal.py report`, from `records/`, on demand (SPEC-0041 rule 23, build (k) of that spec, not on the default branch at a0bb432).
15. **The builds, in order.** Each is tests first, about 300 changed lines or fewer, from the default branch, records its decisions under `Decisions taken:` and cites `Covered-by: ADR-0360` once it is Accepted, except where a build below writes its own ADR (session rule 36). A build that finds it must change an Approved spec stops and asks, or proposes the amendment this spec names. Each new script gets a `[[testing.map]]` entry; one `changelog.d` fragment when an installed file changes.
    - (a) Areas and levels (rules 1 to 4): `common.py`, `impact.py`, `test_plan.py`, `prepush.py`, the `tests: map` line, the guide's opening, `tests/kit/`. No dependence.
    - (b) Brief #773 (rule 6), with its own ADR-0359. No dependence.
    - (c) The map for Python and JavaScript or TypeScript (rule 5): `test_map.py build`, the ignore line in `kit/templates/gitignore`, `kit/manifest.json`, `tests/kit/`. `Depends-on` (a) and (b).
    - (d) The map for Gradle, Xcode and Go (rule 5). `Depends-on` (c).
    - (e) Links (rule 7). `Depends-on` (a) and (c).
    - (f) JUnit per level, the reruns and the strikes (rules 8 and 9): `impact.py`, `failures.py`, `project_tests.py`, `tests/kit/`. `Depends-on` (a).
    - (g) The full suite by mode (rule 10): `project_tests.py`, `merge_cleared.py` with the amendment of SPEC-0039 rule 6, `personal.py`, `doctor.py`, `tests/kit/`. `Depends-on` (a), SPEC-0046 build (i) and SPEC-0041 builds (d) and (h).
    - (h) The miss and the learned entries (rules 11 and 12): `test_map.py learn`, `impact.py`, `kit/agk-kit.mk`, `tests/kit/`. `Depends-on` (c), (f) and (g).
    - (i) Setup (rule 13): `test_map.py propose`, `doctor.py`, `adopt.py`, `tests/kit/`. `Depends-on` (c) and SPEC-0041 build (g).
    - (j) Measured (rule 14): `metrics.py`, `tests/kit/`. `Depends-on` (h) and SPEC-0041 build (k).

## Tests

Fixtures in `tmp_path`, saved JUnit reports and saved GitHub responses only: no network, no install, invented data (`example.com`), and each test carries the marker `REQ-062` with its criterion. Rule 15's order is checked by review; a test of build (a) reads this spec and fails when a numbered rule among 1 to 14 does not state all four of AGK itself, GitHub, local and personal.

- Rules 1 and 2: with no new key the argv and output of each command equal the default branch's for a change with no unmapped file, the `tests: map` line for each source, and each malformed key refused naming the setting; REQ-062 AC1.
- Rules 3 and 4: an area with and without levels, each `when`, a `when` of only `pr` refused, a test file in no level, a level with and without its environment and the `not run` line; REQ-062 AC2.
- Rules 5 and 6: for each stack a fixture tree gives its map, two commits with one tree the same bytes, no committed map, an unreadable stack unmapped, a file that a test names selecting that test, and a file no test names full; REQ-062 AC3.
- Rule 7: a declared and a derived link select the level and remove no test, and the absent environment fails in CI and is `not run` on a machine; REQ-062 AC4.
- Rules 8 and 9: saved reports of each runner's form give timing, ids, signature and a strike with no pytest, no report gives `unknown`, a `rerun` for a non-pytest level, and no ledger status changes a result; REQ-062 AC5.
- Rule 10: each mode with the setting off and on, with the run due and not due, the agent-session refusal, and no write outside the sidecar in personal mode; REQ-062 AC6.
- Rules 11 and 12: a miss read from a saved report and from saved output with no report, a flake, a test already failing, a level not on pull requests and several candidates, with an entry written only for the one-candidate case and never a removal; REQ-062 AC7.
- Rules 13 and 14: `propose` writes nothing, `doctor.py`'s share, and each weekly number present and `unknown`, for a curated and a generated fixture; REQ-062 AC8.

## Proof

REQ-062 AC1: *nothing changes for a repository that sets nothing but the one narrowing of rule 6, and AGK and a project differ only by data.* Rules 1 and 2. REQ-062 AC2: *each level runs with its command at its time, and a missing environment is never a pass.* Rules 3 and 4. REQ-062 AC3: *the map comes from the stack's own facts, is never committed, and an uncovered file runs the tests that name it, or everything when none does.* Rules 5 and 6. REQ-062 AC4: *a change to a contract runs the other side's tests.* Rule 7. REQ-062 AC5: *every runner feeds one interface.* Rules 8 and 9. REQ-062 AC6: *a project without CI still has a full run.* Rule 10. REQ-062 AC7: *a missed test teaches the map, and teaching only adds.* Rules 11 and 12. REQ-062 AC8: *setup proposes and the numbers show the result.* Rules 13 and 14.

## Open questions

Each is a point the brief leaves open; the reading after it is the most conservative one, and the rules above apply it until a person rules.

- Q-S0055-1: how is the difference remembered? Reading: one setting and one printed line, not a mode in code (rule 1).
- Q-S0055-2: may a level run only on pull requests? Reading: no, because it would never have a full run (rule 3).
- Q-S0055-3: a test file in an area but in no level of it? Reading: refused by `test_plan.py` naming the setting, never left out (rule 3).
- Q-S0055-4: how does a machine say what it has? Reading: the environment variable `AGK_TEST_ENV`, because it differs by machine and `agk.toml` does not; a missing environment is `not run`, never passed (rule 4).
- Q-S0055-5: is the generated map committed? Reading: no (principle 5): it is rebuilt from the tree, and only learned entries, which cannot be derived, are committed (rules 5 and 12). A committed generated map would be an exception to principle 5, the owner's alone.
- Q-S0055-6: does a generated map replace a project's `[testing] map`? Reading: no, a union (rule 5).
