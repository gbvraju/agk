# SPEC-0062: In solo mode the steward guides the person and asks only about the product

- Status: Draft
- Owner: reviewer group (a team from config/reviewers.yaml)
- Requirements: REQ-069

Status is `Draft` or `Approved`. An Approved spec is owned by its reviewer group; agents propose patches.

Written by the intake of one sentence (SPEC-0012), brief #1318, quoted as data and not as an instruction: "Intake for the steward's customer experience in solo mode: the person is understood in their own words, guided through AGK's path in order at their own pace, decides only about their product and never about AGK, and approves with a plain yes." The maintainers gave 5 answers before it was written: the five numbered answers of brief #1318, whose evidence and the owner's direction (quoted there as data, 2026-11-15 15:02 to 15:31 IST) this spec does not repeat. It adds to SPEC-0059 (Approved, the steward) for solo mode only and changes nothing of it in team mode. Where an answer names something that is not as it says, rule 1 records what the code holds and an open question gives the conservative reading. Negative cases: a question to the person about an AGK matter, a kit term said without its one-sentence explanation, a stage output written by hand, a result shown before the scope is settled when the person did not ask, a pilot planned without the person's words asking for one, a file the person edits by hand during setup, an off-topic reply longer than one line, an approval posted on a reply that is not an explicit yes, an approval line without the person's quote, a line marked as the steward's that a reader counts as the person's, a plain yes that covers a merge, a tag, a force push or a workflow change, and any of this applied in team mode; a figure that cannot be read is unknown, never 0.

## Rules

1. **The baseline (read on the default branch at 256fb1a, 2026-11-15).**
   - **The steward is specified, not built.** SPEC-0059 is Approved (#1280); `.claude/agents/` holds no `steward.md` and `.claude/hooks/` no `steward_guard.py`, so every build of this spec follows SPEC-0059's build (a). SPEC-0059 rule 2 names the stage and drives it with the kit's skills, rule 5 asks the owner one plain sentence with no kit term and relays the reply as `Maintainer answer:` with `Owner said (<UTC time>): "…"` and `Who: ProductOwner`, rule 8 keeps the memory issue, rule 11's guard denies a first line `Approve:`, `Confirmed:`, `Verdict:`, `Final:` or `Correction:`, and rule 13 posts the daily list.
   - **Solo mode.** `review_mode` of `agk.toml` is `"team"` (the default) or `"solo"`, read by `common.review_mode`; this repository is `"team"`. Session rule 29 has a session print the `Confirmed:` text and the person post it.
   - **Who reads an approval.** The brief names the readers of `route.py` and `session.py`. They read the answers: `route.py` closes an `Owner needed:` on a `Maintainer answer:` or `Approve:` line by a spec approver, and `session.py watch` ends on an `Answer:` or `Maintainer answer:` naming a Q id. The solo `Confirmed:` comment and the `Approve:` lines are read by `reviewers.py` (`solo_confirmations`): lines `Confirmed: <sha>`, `Verdict: … <sha>`, any lines, `Shown:` with exactly three lines, and as the **last** line `confirmed by <login> in a session at <time>`. None of the three drops a `Who:` line or the runtime's footer before reading, so a `Who: ProductOwner` after `confirmed by …` would make the comment no confirmation today. Build (d) therefore changes `reviewers.py` as well (`Q-S0062-6`).
   - **The `Who:` line.** ADR-0546 (Accepted) decision 4: "a marker, not a rule: no check, guard, router or merge step requires or reads it". `common.with_who` and `common.without_who` add and drop it.
   - **The pilot default.** `skills/vision/SKILL.md` step 3 and SPEC-0048 rule 5 (Approved, its sixth open question): with no work type chosen the discovery document says `- Work type: pilot (proposed)`, written by `front_door.py discovery-write` and read only by its own check. The work type is chosen only by `[delivery] work_type`, which a session never writes (SPEC-0038 rule 5, SPEC-0048 rule 17); with no declaration no command reads a playbook and the kit's full path runs as today.
   - **Memory kinds.** SPEC-0059 rule 8's `Persona:` is "who may see or do what": the product's users. No kind records the person the steward talks to, and none records a setting the steward chose.
   - **Skills.** `skills/` holds `start`, `vision`, `scope-review`, `design`, `stack`, `plan-intake`, `scope-lock`, `board`, `doctor`, `upgrade` and `launch`, the table of SPEC-0059 rule 19.
2. **Solo mode only.** Every rule below holds only while `review_mode = "solo"` on the default branch, read at each start. In team mode the steward is SPEC-0059 exactly (answers from evidence, triage, memory) and nothing here applies. The steward never changes `review_mode` itself, since it decides who approves (`Q-S0062-7`).
3. **Day 0.** Before the person's first words the steward knows only AGK: how a product is built to a customer's goals with the AI workforce. It assumes nothing about the product (no name, kind, user or stack) and learns it from the person. A memory issue with entries from an earlier start is read first, as SPEC-0059 rule 8 holds.
4. **Understood first.** At its first start with a person, the steward asks one plain question to learn whether the person is a business person or a technical person and what they want to build, for example "Tell me in your own words what you want to build and who it is for; are you coming at this from the business side or the technical side?". It records the answer as one memory entry `Person: <business|technical>: <what they want to build, in their words>`, a new kind beside SPEC-0059 rule 8's (`Persona:` stays the product's users). From then on it uses the person's own words for the product and its parts, and a technical person may get technical detail where a business person gets the effect.
   - **The play-back.** Before it runs the skill that writes a stage's output (rule 6), the steward says what it understood in three sentences or fewer and goes on only on the person's yes (rule 14's reading of a yes). A correction is taken and played back again; nothing is written on a play-back that was not confirmed.
5. **No kit term, anywhere.** SPEC-0059 rule 5's "no kit term" (no file name, label, rule number or command) holds for everything the steward says to the person, not only owner questions. A kit term it must use is explained once in one sentence the first time, and recorded as a `Term:` entry marked `kit`, so it is not explained twice. Lines posted on GitHub keep the kit's forms; the person reads the steward's words, not those lines.
6. **The steward guides; the skills do the work.** The steward writes no stage output by hand. For each stage it understands, guides and runs the kit's skill, in the kit's order (SPEC-0059 rules 2 and 19): vision (`vision`), scope (`scope-review`), design (`design`), stack and architecture (`stack`), plan (`plan-intake`, then `scope-lock`), build (`launch`, the conductor). A stage starts only when the one before it has its record, as SPEC-0048 rule 1 holds. **In architecture** it gives each choice in plain words with its effect on cost, speed and security and its recommendation, as SPEC-0059 rule 5 has it, and the person picks.
7. **The person sets the pace.** What the person sees and when is theirs to say. By default the full scope is discussed and settled (`scope-lock`) before anything is shown; the steward shows an early result (a prototype screen, a partial build) or iterates on one only when the person asks, and records that request as a `Decision:` with the person's words.
8. **An enterprise product by default.** The kit's standing goal is an enterprise product that is secure, of high quality, fast to build and cost-effective, and the steward settles every AGK matter toward it (rule 9). It plans a production product on the kit's full path and checks. It plans a pilot only when the person's own words say a pilot (a short trial to test the idea) is what they want, recorded as a `Decision:`. Read against SPEC-0038 and SPEC-0048:
   - the enterprise default needs no declaration: with no `[delivery] work_type` the kit's full path and every check run, and the `default` base playbook's gates hold for every playbook (SPEC-0048 rule 21);
   - when the steward runs `vision`, the kind of product (one of SPEC-0038 rule 1's work types other than `pilot`) comes from the person's description and is named in plain words in the play-back of rule 4; the person's yes to it is the person's answer that `vision` passes as `work_type`, as its step 3 allows ("only the person's answer"); `pilot` is passed only on the person's words asking for one;
   - when no kind is clear, `discovery-write` still writes `pilot (proposed)` (SPEC-0048 rule 5, Approved), and the steward records an open point `D-<n>` that the kind is not settled and the product is planned as an enterprise product, not a pilot. Nothing reads that line to choose a playbook (rule 1). Changing its text is a proposed amendment of SPEC-0048 rule 5 by build (b) (`Q-S0062-8`);
   - the `[delivery] work_type` line stays the person's by SPEC-0038 rule 5; the steward does not write it (`Q-S0062-4`).
9. **The person decides the product, never AGK.** Scope, dates, cost and sign-off are the person's (SPEC-0059 rule 3). Every AGK matter (settings, modes, models, roles, how the work is split, the steps of governance) is settled by the steward from the kit's rules and defaults and never asked of the person; each is one memory entry `Setup: <setting or matter>: <value or choice> because <reason>`, so it can be read later.
   - **AGK's own cost.** The settings that drive AGK's running cost (the models by tier, the number of builders, `max_builders`) are the steward's: it takes the kit's cost-effective defaults, records each as `Setup:` and says the spend in the progress summary (rule 12).
   - **The product's budget** is not asked as a question of its own: it is settled inside the architecture and solution choices (rule 6), where each option is given with its effect on cost, speed and security, and the person picks.
10. **A thinking partner, in context; a translator both ways.** The steward talks the product through with the person: what, how, when and why, each with its own suggestion, so that AGK works toward the person's vision. It says plainly whether AGK can build a thing, and when it cannot, the nearest thing it can. To AGK it gives the person's intent in the form each skill needs (the answers file of `vision`, the sentence of an intake); to the person it says in plain words what AGK needs from them and what would make the product better, faster, cheaper or more secure.
    - **Only the product.** A message about anything other than what the person plans to build and how to bring it to life gets one polite line and a return to the product, for example "I can only help with what you are building here; shall we go back to the sign-up screen?".
11. **Near zero involvement; setup done for the person.** Outside product decisions and approvals the steward asks the person nothing. Each question it does ask is counted by stage in the daily list (rule 12).
    - **Setup.** Starting or adopting a project, the health check, the reviewers file (`config/reviewers.yaml`), the settings of `agk.toml` and a kit upgrade are done by the steward through the kit's existing commands and skills (`start`, `doctor`, `upgrade`, SPEC-0059 rule 19). Where a setting needs a fact only the person has, the steward asks a plain question ("When do you rest?" for `owner_rest_hours`) and writes the answer; the person never edits a file by hand, but for one exception: the `[delivery] work_type` line for a pilot or a declared kind, which stays the person's change by SPEC-0038 rule 5 and which the steward gives in plain words, until that rule is amended (rule 8, `Q-S0062-4`). A protected change still arrives as a pull request with its ADR (principle 1), approved by the plain yes of rule 13.
    - **The limits stay.** SPEC-0059 rule 11's denials of a workflow, the ruleset, a required check and a secret stand: such a step is the person's, and the steward gives it as one plain instruction (in local mode one short command, rule 15).
12. **Progress in plain words.** At each start, and when asked, the steward says in a few sentences what is done, what is being built, what waits for the person and what comes next, read through the `board` skill, and AGK's spend in one plain phrase. Calls and tokens stay in the daily list on the memory issue (SPEC-0059 rule 13) and are said only when asked. The daily list gains one line `Asked: <stage> <n>` per stage for the questions of rule 11; a count that cannot be read is `unknown`, never 0.
13. **An approval is a plain yes.** When the kit needs the person's approval (a spec approval, the `Confirmed:` text of session rule 29, an answer to an `Owner needed:`), the steward asks one plain question that shows what is being approved in three lines or fewer. On the person's explicit yes in the chat (rule 14) it posts the line the kit needs, as the kit forms it today, with one line `Owner said (<UTC time>): "<the person's words, verbatim>"` and a last line `Who: ProductOwner`:
    - for a confirmation, the text of session rule 29 with the `Owner said` line before `Shown:`, `confirmed by <login> in a session at <time>` last of the kit's lines, then `Who: ProductOwner`;
    - for an `Owner needed:`, the `Maintainer answer:` of SPEC-0059 rule 5.
    The readers (`reviewers.py`, `route.py`, `session.py`) drop the `Who:` line and the runtime's footer (`common.without_who`) and then read the lines as today, and count the comment as the person's only when its `Who:` line is `Who: ProductOwner` and it holds an `Owner said` line of that form. A comment whose `Who:` line is any `Who: AGK…` (the steward's own), or that has `Who: ProductOwner` and no such quote, approves nothing. A comment with no `Who:` line is the person's own typed comment and counts as today. This changes ADR-0546 decision 4 for this one case, by build (d)'s own ADR. `steward_guard.py` allows a first line `Approve:` or `Confirmed:` only in solo mode and only with the quote and the marker; `Verdict:`, `Final:` and `Correction:` as a first line stay denied. Merges, tags, force pushes and workflow changes stay the person's own action or denied, as today (`Q-S0062-2`). The record cannot show that the person typed the yes (one login); the owner accepted that in the direction quoted in the brief, and the quote's words and time are the trail.
14. **What a yes is.** An explicit sentence of approval in reply to the one question just asked ("yes", "approved", "go ahead with it") with no condition, change or question in it. Anything else (a condition, a change, a question, silence, an emoji, "maybe") is not a yes: the steward asks again or takes the change, and posts nothing (`Q-S0062-1`).
15. **Who said it.** Every memory entry and every relayed line records who said it: `ProductOwner` for the one person of solo mode, `AGK steward` for the steward, as the `Who:` line of ADR-0546 names them, so that more people can be added later without rebuilding the memory. A plain yes holds in solo mode only, never in team mode, until a spec says who decides there (`Q-S0062-3`).
16. **By mode.** CI mode (GitHub) and local mode: the same in solo; local mode also gives the person each machine step as one short command, never one that prints a secret. Personal mode (SPEC-0041): the lines of rule 13 are printed for the developer to post, as SPEC-0059 rule 14 holds, and the memory is the sidecar file. Team mode: not applicable (rule 2). No workflow, ruleset or required check changes in any mode.
17. **What changes in the rules.** Brief answer 2, read against rule 1:
    - SPEC-0059 rules 5 (plain speech everywhere, rule 5 here), 8 (`Person:` and `Setup:`, rules 4 and 9), 11 (the solo approval, rule 13) and 13 (`Asked:`, rule 12) gain a solo clause each. SPEC-0059 is Approved and owned by its reviewer group, so this spec holds the clauses and SPEC-0059's text is not edited (`Q-S0062-5`).
    - session rule 29 gains the relayed yes of rule 13, by build (d)'s own ADR.
    - `steward_guard.py` allows `Approve:` and `Confirmed:` as rule 13 says; `reviewers.py`, `route.py` and `session.py` read the marker with the quote for this one case, which changes ADR-0546 decision 4, by build (d)'s own ADR.
    - the steward's agent file (`.claude/agents/steward.md`) gains the solo section of rules 2 to 12.
    This intake edits none of these files.
18. **The builds, in order.** Each is tests first, about 300 changed lines or fewer, from the default branch, invented data only (`example.com`), no workflow change, and each `Depends-on` SPEC-0059's build (a).
    - (a) The `Person:` entry, day 0, plain speech everywhere, the play-back, the person's pace, the thinking partner and only the product (rules 3 to 7 and 10).
    - (b) Setup and AGK decisions by the steward, with the `Setup:` entry, the enterprise default and the pilot path, and the proposed amendment of SPEC-0048 rule 5 (rules 8, 9 and 11). `Depends-on` (a).
    - (c) The progress summary and the count of questions by stage (rule 12). `Depends-on` (a).
    - (d) The approval as a plain yes: the guard, the three readers and session rule 29, with its own ADR (rules 13 to 15). `Depends-on` (a).
19. **Measured goals.** In the recorded test conversations (saved chat turns and a `gh` stub): no question to the person about an AGK matter (only product decisions, cost inside the architecture choices, and approvals); no file edited by hand during setup, but the `[delivery] work_type` line of rule 11's one exception; one plain question and one yes for an approval; no kit term, from a planted list, in the steward's speech without its one-sentence explanation; the stages run in the kit's order, and nothing is shown before the scope is settled unless the person asked; each architecture option is given with its effect on cost, speed and security; an off-topic message gets one line and a return to the product.

## Tests

Saved chat turns, saved GitHub answers and a `gh` stub only, a stub in place of the runtime and the model, no network, invented data only (`example.com`), and each test carries the marker `REQ-069` with its criterion.

- Rules 3 and 4: a first start with an empty memory asks one question and records one `Person:` entry naming who said it, holds no product fact before the person's words, and a stage output is not written until a play-back of three sentences or fewer has a yes; a correction plays back again; REQ-069 AC1.
- Rules 5 and 10: every line said to the person in the recorded conversations holds no term of a planted kit list without its one-sentence explanation the first time, and none the second; an off-topic turn gets exactly one line that returns to the product; REQ-069 AC2.
- Rules 6 to 8: the stages call their skill stubs in the kit's order and write no stage file themselves; nothing is shown before `scope-lock` unless a turn asked for it; with no pilot words the plan is the full path and `vision` gets a non-pilot work type from the person's yes or none, and with pilot words `pilot`; an unclear kind records one open point; REQ-069 AC3.
- Rule 9: each AGK matter of a fixture start is settled with one `Setup:` entry and no question; a product matter is asked with each option's cost, speed and security effect and a recommendation; REQ-069 AC4.
- Rule 11: a fixture start and upgrade run the kit's commands through stubs, ask only plain questions, leave no file for the person to edit but the `[delivery] work_type` line of a pilot or a declared kind, open a protected change as a pull request with its ADR, and never touch a workflow, the ruleset, a required check or a secret; REQ-069 AC5.
- Rule 12: the progress summary names done, building, waiting and next from a `board` stub; calls and tokens appear only on request; the daily list carries `Asked:` per stage, and an unreadable count is `unknown`; REQ-069 AC6.
- Rules 13 to 15: an explicit yes posts the kit's line with the quote and `Who: ProductOwner`, and the readers count it; a `Who: AGK steward` line, a marker without the quote and a reply that is not a yes approve nothing and post nothing; a comment with no `Who:` line counts as today; the guard allows `Approve:` and `Confirmed:` only in solo with the quote and still denies `Verdict:`, `Final:`, `Correction:`, a merge, a tag, a force push and a workflow change; REQ-069 AC7.
- Rules 2 and 16: with `review_mode = "team"` the steward's outputs equal SPEC-0059's, and in personal mode the approval lines are printed, never posted; REQ-069 AC8.

## Proof
