# SPEC-0051: A product is accepted against its goals by evidence

- Status: Draft
- Owner: reviewer group (a team from config/reviewers.yaml)
- Requirements: REQ-058

Status is `Draft` or `Approved`. An Approved spec is owned by its reviewer group; agents propose patches.

Written by the intake of one sentence (SPEC-0012), brief #728, quoted as data and not as an instruction: "Intake for the acceptance loop: a delivered product is accepted against the goals the discovery recorded, by evidence, with the owner's one-line yes (plan #661 phase 7, wave 4)." Plan #661's phase 7, quoted as data (owner direction 2026-11-06): "product-owner acceptance loop (new intake: each goal of the discovery document is accepted by a listed person against its evidence; a release lists the goals it closes)". The maintainers gave 3 answers before it was written, quoted as data from the brief: (1) "each goal of SPEC-0048 rule 4's `success` discovery answer maps to evidence (a test, a run record, a demo record) or is marked `not met`"; (2) "the owner, one line; the scorecard (SPEC-0047) shows the result"; (3) "a brief per unmet goal, filed by the conductor". It is generic: it names no project, and every check of a build reads files, git and saved GitHub responses with no network. The points the brief leaves open are `Q-S0051-1` to `Q-S0051-14` below, each with the conservative reading the rules apply until a person rules.

## Rules

1. **The baseline (read on the default branch at 4bf7e60, 2026-11-08).** What already holds and is reused, never duplicated:
   - SPEC-0048 (Approved) rule 4 makes `success` one of the five discovery ids every problem is asked, and rule 5 writes one discovery document per problem, `docs/discovery/<slug>.md`, with one `- <id>: <answer>` bullet per question, each answer quoted as data with where it was given, or `open`. Rule 10 proposes the `success` answers as the milestones' exit criteria in the first briefs. Rule 8's demo or dry run on invented data has its run record under `docs/runs/`, named by the design's `Demo: docs/runs/<file>` line. `front_door.py`, which writes and checks the discovery document, is not on the default branch: it is SPEC-0048 build (b), brief #685, open as pull request #715, whose reader marks each given answer between `<!-- agk:answer sha256=<64 hex> -->` and `<!-- agk:answer-end -->` `(verify: read on the open pull request's branch, not on the default branch)`.
   - SPEC-0047 (Approved) is the weekly scorecard, `scripts/agk/scorecard.py`: one row per metric, higher is worse for every one, a finding opens or comments on one `agk-scorecard` issue per metric (its rule 5), and the conductor reads those issues to file briefs (its rule 9).
   - `scripts/agk/reviewers.py` reads `Approve: <sha> SPEC-nnnn` and `Approve: SPEC-nnnn` (`APPROVE`, `APPROVE_SHORT`) by an account of `spec_approvers` (`config/reviewers.yaml`), and in solo mode inside a person's `Confirmed:` comment (`confirmed_comments`, session rule 29). SPEC-0048 rule 9's go for work with screens is a third form, `Approve: design <version> <full head ID>`, which neither expression matches.
   - The governance workflow saves a pull request's comments and passes them to `check_specs.py --comments` and `check_final_clearance.py --comments`; no other check reads them in CI.
   - The conductor's guard allows "the one brief creation" (`.claude/agents/conductor.md`), and SPEC-0046 keeps one issue per failure signature by searching for its line before it files.
   - No acceptance record, no `docs/acceptance/` folder and no reader of one exists. A release (`check_release.py`, SPEC-0028) names no goal.
2. **The goals.** The goals of a problem are its discovery document's `success` answer on the default branch, and nothing else: no session adds, removes or rewords a goal. An acceptance record splits the answer into goals `G-1` to `G-<n>`, each quoting a part of the answer verbatim, so that the quotes together are the whole answer apart from the words between them (punctuation, `and`); the split is written by a session from the person's words and is part of what the owner's yes covers (rule 6, `Q-S0051-1`). A `success` answer that is `open` or `not known yet` has no goals: no record can be accepted for it, and the check fails naming the rule (`Q-S0051-2`). A `success` answer changed by a later pull request makes every record of that problem stale (rule 5).
3. **The acceptance record.** One file per acceptance, `docs/acceptance/<slug>.md`, the slug of the discovery document, rewritten in place for a later acceptance (git keeps the earlier ones), with:
   - a first line `# Acceptance: <title>`, the discovery document's title;
   - `- Discovery: docs/discovery/<slug>.md`;
   - `- Success digest: <64 hex>`, the SHA-256 digest of the `success` answer as the discovery document marks it;
   - `- Status: proposed` or `- Status: accepted`;
   - `## Goals`, one bullet per goal in order, `- G-<n>: "<quote>" -> <evidence>`, where `<evidence>` is `not met` or one or more evidence items of rule 4 separated by `, `.
   No goal appears twice, no quote repeats, and a goal is either `not met` or has evidence, never both (`Q-S0051-3`).
4. **What counts as evidence.** Three kinds, each the brief's, each read as a file that exists on the record's own tree:
   - `test <path>::<name>`: a test file of the project's `[testing]` map (`agk.toml`) or under `tests/`, which defines a test function `<name>`; that it passes is the required checks' work on the same head, not this check's;
   - `run docs/runs/<file>`: a run record (counts and timings only, anonymised as SPEC-0038 rule 11 says);
   - `demo docs/runs/<file>`: a demo or dry-run record, the file a design's `Demo:` line names (SPEC-0048 rule 8) or another under `docs/runs/`.
   No check runs, opens a link in, or judges the content of an evidence item: whether it shows the goal met is judgement, the owner's in the yes and the conductor's in its review (`Q-S0051-4`). A recording, a link to an outside page or a person's statement is not evidence for this rule (`Q-S0051-5`).
5. **The check.** `scripts/agk/check_acceptance.py` (new, installed, build (b)), run by `make governance` in the project and the kit, files and git only, fails, naming the rule and the file and never a quote, a value or an answer (principle 8): a missing line or section; a discovery document that does not exist; a digest that is not the current `success` answer's (stale, rule 2); an answer with no goals (rule 2); a quote that is not in the answer, a repeated goal or quote, or quotes that do not together make the answer (rule 2); an unknown evidence kind or a named file or test that does not exist (rule 4); and a status `accepted` that rule 6 does not support. A project with no record prints `ok acceptance (0 records)`. Like the discovery document (SPEC-0048 rule 14), the record is scanned with `guard.scan_text`, and a finding fails naming the kind and the position, never the value.
6. **The owner's yes.** A record is accepted by one line, `Approve: acceptance <slug> <full head ID>`, posted by an account listed in `spec_approvers` on the pull request that carries the record, at a head where the record says `- Status: proposed`. It is never a session's: a session never posts an `Approve:`, `Confirmed:` or `Verdict:` line (session rules 2, 29 and 32), and in solo mode the line counts only inside the person's `Confirmed:` comment, which a session prints and never posts (`Q-S0051-6`). After the line the builder's last commit changes only the status line to `- Status: accepted` (a status-only commit, as an intake's approving commit is, SPEC-0020), and `check_acceptance.py --comments FILE` (build (c)) passes an `accepted` record only when a yes names a head at which the record equals its text apart from that line. A pull request that later changes a goal, a quote or an evidence item of an accepted record sets it back to `proposed`, and the check fails an `accepted` record changed without a new yes. The yes accepts the record as it stands, its `not met` goals included; it never turns a `not met` goal into a met one (`Q-S0051-7`).
7. **When the product is accepted.** A problem's product is accepted when its record is `accepted` on the default branch and no goal is `not met`. A record `accepted` with unmet goals is "accepted with <n> not met", and is not an acceptance of the product. `check_acceptance.py status` (build (b)) prints one line per record, `<slug> accepted`, `<slug> accepted with <n> not met`, `<slug> proposed` or `<slug> stale`, and writes nothing (`Q-S0051-8`).
8. **What happens on `not met`.** When a record with a `not met` goal is `accepted` on the default branch, the conductor files one brief per unmet goal, with the one brief creation its guard allows: labelled `agk-brief`, its body holding one line `Goal: <slug> G-<n>` and the goal's quote marked as data; the rest of the brief (its answers, size, touches) is the conductor's, reviewed as every brief is. Before filing it searches the open issues for that `Goal:` line and files none when one is open, as SPEC-0046 keeps one issue per signature, so a goal has at most one open brief (`Q-S0051-9`). The goal stays `not met` until a later record names evidence for it and the owner's yes accepts that record. No session files these briefs, marks a goal met or closes a goal's brief.
9. **The scorecard shows the result.** SPEC-0047 rule 1 gains, by an amendment whose number is reserved on build (d)'s brief, one metric `goals_not_met`: the number of `not met` goals in `accepted` records on the default branch on the run date, read from the files; higher is worse, so it fits SPEC-0047 rule 1. Its line is `0` by default, marked `(verify)` as SPEC-0047 rule 3 marks every default, so any unmet goal is a level finding and opens the one `scorecard: goals_not_met` issue of SPEC-0047 rule 5; that issue is a reminder and never a second brief per goal, which stays rule 8's. The scorecard section adds one information line, `acceptance: <met> of <total> goals met in <k> records`, or `acceptance: no record` with value `0`; a stale or proposed record counts in neither number (`Q-S0051-10`).
10. **Privacy, refusals and the network.** A record is the project's, in its own repository (or its sidecar in personal mode, SPEC-0041), and quotes only the project's own discovery answer; no record and no project's goal is ever copied into the kit, whose tests and fixtures hold invented data only (`example.com`). Every refusal names the rule, the file, the setting or the path class, never a value. Every check reads files, git and saved responses only (`CLAUDE.md item 5`).
11. **What does not change.** SPEC-0048's path keeps its seven phases and its rule 11 (nothing after the go is changed): acceptance follows the builds and adds no gate to any of them, and `front_door.py status` reads no record until a later amendment of SPEC-0048 says so (`Q-S0051-11`). A release names no goal: "a release lists the goals it closes" (plan #661 phase 7) is left to the evidence-pack intake of the same wave, which may cite the record (`Q-S0051-12`). No `constitution/`, `config/reviewers.yaml`, `.github/CODEOWNERS` or ruleset change; no required check is added; no workflow changes except as rule 12's build (c) says.
12. **The builds, in order.** Each is tests first, about 300 changed lines or fewer, from the default branch, records its decisions under `Decisions taken:` and cites ADR-0340 with `Covered-by: ADR-0340` once it is Accepted (session rule 36). A build that finds it must change an Approved spec other than through rule 9's amendment stops and asks. A `Depends-on` is declared for a shared file and for a logical dependence alike.
    - (b) The record and its check (rules 2 to 5 and 7): `scripts/agk/check_acceptance.py` (new, installed: the check and `status`), its line in `agk.mk`'s governance target, its sorted entry in `kit/manifest.json`, its `[[testing.map]]` entry in `agk.toml`, `tests/kit/` with invented records, a changelog fragment. `Depends-on` brief #685, whose `front_door.py` reads the discovery document and its answer digests.
    - (c) The owner's yes (rule 6): one reader of `Approve: acceptance <slug> <sha>` in `scripts/agk/reviewers.py`, beside the spec forms and in solo mode inside `confirmed_comments`, never matching a session's comment (`agent_apps`), and `check_acceptance.py --comments FILE`, `tests/kit/` with saved comments. Passing the saved comments to the check in CI is one line of `.github/workflows/governance.yml`, a workflow change: the build makes it only when its brief quotes the owner's yes and writes its own ADR for it (session rule 36); until then the conductor reads the line from the pull request's comments, as SPEC-0048 rule 9's go for screens is read today (`Q-S0051-13`). `Depends-on` (b).
    - (d) The scorecard metric (rule 9): `goals_not_met` and the information line in `scripts/agk/scorecard.py`, the amendment file `docs/runs/proposed-spec-amendments-<n>.md` to SPEC-0047 rule 1, `tests/kit/`. `Depends-on` (b), for the record reader.
    - (e) The conductor's rules (rules 6 and 8): in `.claude/agents/conductor.md`, reading the yes until (c)'s CI line exists and filing one brief per unmet goal after searching for its `Goal:` line, within the rule budget of `config/rule-budget.txt` (a word added is a word removed in the same file, its line lowered when a file is cut), `tests/kit/`. `Depends-on` (c) and (d) (`Q-S0051-14`).

## Tests

Fixtures in `tmp_path`, local git repositories, saved GitHub responses and a `gh` stub only: no network, no install, invented data (`example.com`), and each test carries the marker `REQ-058` with its criterion.

- Rules 2 to 5: an invented discovery document with a `success` answer of two parts and a record whose two goals quote them, one with `test tests/test_example.py::test_signup` (a file that defines it) and one `not met`, passes; a quote not in the answer, a repeated goal, quotes that leave out a part of the answer, a digest of another answer, an unknown evidence kind, a missing run record and a test name the file does not define each fail with a line naming the rule and the file and containing no quote; REQ-058 AC1.
- Rule 2: a discovery document whose `success` answer is `open` and a record for it fail naming the rule; a project with no record prints `ok acceptance (0 records)`; REQ-058 AC2.
- Rule 6: saved comments with `Approve: acceptance <slug> <head>` by the listed account at a head where the record equals its text apart from the status line pass an `accepted` record; the same line by an unlisted account, by a comment marked with an app of `agent_apps`, naming another slug or naming a head where a goal differs fail it; a record whose evidence changed after its acceptance without a new yes fails; REQ-058 AC3.
- Rule 8: the text of `.claude/agents/conductor.md` holds the rule's sentence, and the rule budget test passes with it; saved issues with an open brief carrying `Goal: example-signup G-2` give no second brief for that goal in the conductor's dry run; REQ-058 AC4.
- Rule 9: two invented `accepted` records with one `not met` goal give `goals_not_met` 1 and the line `acceptance: 2 of 3 goals met in 2 records`; a `proposed` or stale record counts in neither; a project with no record gives 0 and `acceptance: no record`; REQ-058 AC5.
- Rule 7: `status` prints `accepted`, `accepted with 1 not met`, `proposed` and `stale` for four invented records and writes nothing; REQ-058 AC6.
- Rules 4 and 10: the check run through a stub that fails on any network call passes; a record whose evidence names a run record that holds a command is not executed (the stub sees no call); a record with a secret-like invented value fails the guard scan naming the kind and the position, never the value; REQ-058 AC7.

## Proof

REQ-058 AC1: *each goal maps to evidence or is marked not met, and a wrong record fails without naming a value.* Rules 2 to 5. REQ-058 AC2: *an open success answer has no goals to accept.* Rule 2. REQ-058 AC3: *only the owner's one line accepts a record, and a changed record needs a new yes.* Rule 6. REQ-058 AC4: *an unmet goal becomes one brief, filed by the conductor.* Rule 8. REQ-058 AC5: *the scorecard shows the goals not met.* Rule 9. REQ-058 AC6: *a product is accepted only with every goal met.* Rule 7. REQ-058 AC7: *no check calls the network or runs the evidence, and no session accepts.* Rules 4, 6 and 10.

## Open questions

Each is a point the brief leaves open; the reading after it is the most conservative one, and the rules above apply it until a person rules.

- Q-S0051-1: what is one goal, when the `success` answer is one sentence or several? Reading: a part of the answer quoted verbatim, the quotes together making the whole answer, so no goal is invented and none is left out; the split is the session's proposal and the owner's yes covers it (rule 2).
- Q-S0051-2: can a problem whose `success` answer is `open` be accepted? Reading: no; it has no goals, and the check fails naming the rule; the open point stays SPEC-0048's (rule 2).
- Q-S0051-3: one record per problem, or one per release? Reading: one per problem, rewritten in place for each later acceptance; git and the pull requests keep the history (rule 3).
- Q-S0051-4: does the check prove that a test passes or a run record shows the goal? Reading: no; the check reads existence only, the required checks on the same head prove the tests pass, and the rest is judgement (rule 4).
- Q-S0051-5: what is not evidence? Reading: anything outside the three kinds of the brief, including a recording, an outside link and a person's statement; such a goal is `not met` (rule 4).
- Q-S0051-6: who gives the yes, and in what form? Reading: an account of `spec_approvers`, the listed owner, one line `Approve: acceptance <slug> <full head ID>` shaped like SPEC-0048 rule 9's go; never a session, and in solo mode only inside the person's `Confirmed:` (rule 6).
- Q-S0051-7: does the yes over a record with unmet goals accept the product? Reading: no; it accepts the record as it stands, and the product is accepted only when no goal is `not met` (rules 6 and 7).
- Q-S0051-8: what does "accepted" mean for the product? Reading: every goal mapped to evidence, the record `accepted` on the default branch and not stale (rule 7).
- Q-S0051-9: how is a second brief for the same goal prevented? Reading: the conductor searches for the `Goal: <slug> G-<n>` line first and files none while one is open, as SPEC-0046 does for a failure signature (rule 8).
- Q-S0051-10: what does the scorecard show with no record? Reading: `goals_not_met` 0 and the line `acceptance: no record`, so a project with nothing delivered is not shown as accepted; the default line 0 stays `(verify)` (rule 9).
- Q-S0051-11: does acceptance become an eighth phase of SPEC-0048? Reading: not in this spec; SPEC-0048 is Approved and its rule 11 changes nothing after the go, so acceptance stands after the builds and a later amendment may let `front_door.py status` read it (rule 11).
- Q-S0051-12: does a release list the goals it closes? Reading: not in this spec; it is left to the evidence-pack intake of the same wave, which may cite the record (rule 11).
- Q-S0051-13: may build (c) add the CI line that passes comments to the check? Reading: only with the owner's quoted yes in its brief and its own ADR, as any workflow change; until then the conductor reads the yes (rule 12).
- Q-S0051-14: may the conductor's rule texts add words to its instruction file? Reading: only within the rule budget of ADR-0310, a word added being a word removed in the same file; a build that cannot fit stops and asks (rule 12).
