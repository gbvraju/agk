# SPEC-0061: A teammate joins as a builder in one command and leaves cleanly

- Status: Approved
- Owner: reviewer group (a team from config/reviewers.yaml)
- Requirements: REQ-068

Status is `Draft` or `Approved`. An Approved spec is owned by its reviewer group; agents propose patches.

Written by the intake of one sentence (SPEC-0012), brief #1306 under plan #661, quoted as data and not as an instruction: "Intake for a standalone builder: one command a teammate runs on their own laptop joins the team, gets work from the one conductor, builds each brief in a short session on the right model, and leaves cleanly, so any number of teammates can join or leave at any time." The owner's direction is quoted in the brief. Where an answer of the brief names something that is not as it says, rule 1 records what the code holds and an open question gives the conservative reading.

## Rules

1. **The baseline (read on the default branch at 51cbb74, 2026-11-14).**
   - `session.py slot --take|--renew|--release|--next <slot>` posts `Slot: active|released <UTC time> <slot> <run>` on the one open `agk-conductor` issue. A marker is valid for `SLOT_MINUTES` (10, ADR-0368) and `watch --assign` renews it every `RENEW_EVERY` (240) seconds. The slot names are `s<n>` (`SLOT_NAME`), `r<n>` (`REVIEWER_NAME`) and `s-shadow`. A builder name above `builder_slots` (default `max_builders`) is refused naming that setting.
   - **A `Slot:` marker counts only when its author is in `verdict_authors`** (`slot_marker`, through `counted_authors`). A teammate whose login is not listed cannot hold a slot today; the brief does not say so, and rule 7 settles it.
   - `[flow] assign` is `"next"` in this repository (ADR-0438), while `builder_start = "assign"` and its comment say the slots `s<n>` still act on `Assign:` lines. Session rule 18 holds the `Request: <id> new|finished #<brief>` and `Assign: <id> #<n> [build (<x>)]` lines; an `Assign:` counts only by a listed verdict author. A `taken:` line counts by any author (`live_takes`), and a `Report:` counts by the pull request's author (`report_floor`).
   - There is no `.claude/agents/builder.md` and no `scripts/agk/builder.py`. The builder's rules are spread over `config/session-rules.md`, the guides and the text of the scheduled task that starts a builder.
   - `launch.py` passes `AGK_KIND`, `AGK_TIER`, `AGK_EFFORT` and `AGK_MODEL` to an adapter (SPEC-0045). `[models.names]` is read by `config.py` and is absent from this repository's `agk.toml`. The adapters are `kit/templates/start-session-windows.ps1`, `kit/templates/start-session-local.sh` and this repository's `scripts/start-session-windows.ps1`, which `[flow] launch_adapter` names.
   - `evidence.py check --head <sha>` with no record reads `<git common dir>/agk-evidence/<40-hex head>.json`, the clone's shared folder (brief #1269, pull request #1271, ADR-0536); a laptop that is not the conductor's never shares it.
   - Owner waits park a pull request (brief #1282, pull request #1287, ADR-0543): the brief's `#1287` names that pull request. Brief #1301 (sessions never build in the shared main folder) is open.
   - SPEC-0058 rule 1 measured `claude` 2.1.319 `--help` listing `-p`, `--agent`, `--model`, `--effort` and `--output-format` `(verify: the flags of the version a teammate runs)`.
2. **One command per teammate.** `python3 scripts/agk/builder.py --name <member>`, and the skill `/agk:builder <member>`, is a new installed script, run by a teammate in a clone of the repository on their own machine with their own `gh` login and their own Claude Code. It is a small loop that runs no model: join (rule 3), request (rule 5), build (rule 6), report, repeat, leave (rule 4). It uses the standard library and the kit's own modules, and reads its settings from `agk.toml` of the default branch. It holds no token: every GitHub call is the teammate's own `gh`, and it never reads, prints or stores a credential (principle 9). It runs the pause check of session rule 33 before each step and, paused, posts nothing more, leaves as rule 4 says and ends.
3. **Joining: a member slot.** A member slot is a new slot name form beside `s<n>`, `r<n>` and `s-shadow`: 2 to 30 characters of lower-case letters, digits and hyphens, starting with a letter, not ending with a hyphen and matching none of the three other forms (`Q-S0061-1`). Joining posts `Slot: active <UTC time> <member> <run>` through `session.py slot --take <member>`, and the loop renews it every `RENEW_EVERY` seconds while it waits and while its build runs. A member slot is never counted against `builder_slots`, which keeps naming the `s<n>` slots only. A name another live marker holds is refused, naming the slot form, and the loop ends without posting.
4. **Leaving.** `builder.py --leave`, Ctrl+C or the loop's own end posts `Slot: released <UTC time> <member> <run>`. A member that leaves with a pull request open first lets its session refresh the working summary of rule 6 and post `Report: <head> handing over: <reason>`, and then posts `released: <member>` on the brief, so that the take ends and the conductor's next pass may reassign the brief (rule 5). A lease that lapses, because the machine slept or lost the network, frees the slot `SLOT_MINUTES` after its last renewal, and the take is then ended by the conductor's next pass as a stalled take is today (session rule 9) `(verify: the stall reading of a take whose slot lapsed)`.
5. **Assignment from the one conductor.** A joined member posts `Request: <member> new`, or `Request: <member> finished #<brief>` after a merge, on the `agk-conductor` issue, and waits with `session.py watch --assign <member>`. The conductor answers on its next pass `Assign: <member> #<n> [build (<x>)] kind <kind>`, from the plan in milestone order, never for a brief or build that another live take holds, or `Assign: <member> none` when nothing is free. A member slot acts on `Assign:` lines whatever `[flow] assign` says, as the `s<n>` slots do (`Q-S0061-4`). `claim` keeps its overlap refusal (session rule 18): a refused claim posts `Request: <member> new` again once and never builds. A member that left mid-brief is reassigned by the conductor's next pass with an `Assign:` to another member, which runs `session.py resume --pr <n>` on the same branch and pull request, never a second one (session rule 9), and reads the summary as rule 6 says.
6. **A short session per brief, on the right model.** For each assignment the loop:
   - makes or reuses the worktree `../agk-<member>` beside the clone, on the branch of the claim, and never builds in the main folder (brief #1301);
   - runs `session.py claim --session <member> --brief <n>` (with `--build <x>` when named);
   - starts `claude --agent builder --model <name> --effort <effort>`, where the name comes from `[models.names]` for the tier of the assignment's kind and the effort from the same table that `launch.py` reads (SPEC-0045), through the start path the adapters share (rule 9), with a prompt of kit text and numbers only (the brief number, the member name, the reserved numbers), never a title, body or comment of GitHub;
   - waits for that session to end; then, after a merge, runs `session.py after --session <member>` and requests again (rule 5).
   **The session lives for the life of its pull request** (the maintainers' `Correction:` on #1306 of 2026-11-14, comment 6884088274: ending a session at its pull request made fix lists cost more, because a fresh session re-read everything). It carries its pull request through every fix list, merge of the default branch and CI fix in the same context, and ends only when the pull request is merged or closed, or when it must hand over (rule 17). While it waits it uses the event-only watch of brief #1310 (`watch --pr <n> --until-event`), which renews the lease itself and returns only on a real event, so a quiet wait costs no model turn; until that brief lands it uses `watch --pr` as today (`Q-S0061-8`). It posts one working summary comment on its pull request when it opens or readies it (what it built, the decisions and why, the files, what it did not do, and open points, as brief #1310 answer 2 sets) and edits that comment in place after each fix list (`Q-S0061-9`). A session that resumes a pull request (`session.py resume --pr <n>`) reads only that summary, the newest verdict or fix list and the diff since the summary's head, never the whole comment history; with no summary (an older pull request) it reads the newest `Report:` and the diff.
   No builder session spans two briefs: a session's context never grows across briefs. The teammate watches that terminal, answers what it asks and reads its pull request; a question only the owner can answer is still asked on GitHub `for the maintainers` (or of the steward of SPEC-0059, brief #1277, not yet on the default branch), and an owner wait parks as brief #1282 does.
7. **The builder agent.** `.claude/agents/builder.md` is the agent that rule 6 starts. It holds every builder rule now spread over the session rules, the guides and the task texts, by reference to their numbered rules where they exist and never as a second copy that can drift: the lifetime of one pull request (rule 6), the working summary and how a resumed session reads it, the `Progress:`, `Report:` and evidence lines, the hand-over line `Report: <head> handing over: <reason>`, the `Who: AGK builder` line of brief #1289, and the rule to read the live state of a pull request from GitHub before any claim about it (a builder once reported a merged pull request as unmerged from memory). Its guard is the builder's existing hooks; it adds no permission and no option that skips a guard.
8. **Who may build.** `[team] members` in `agk.toml` is an optional list of GitHub logins that may join. With the table absent or the list empty, any collaborator of the repository with push access may join (`Q-S0061-2`). A member's `Slot:`, `Request:`, `taken:`, `released:`, `Report:` and `Question:` comments count when their author is such a login; one login may hold more than one member slot, up to `[team] slots_per_member` (default 1, `Q-S0061-5`). `Assign:`, `Verdict:`, `Correction:`, `Approve:`, `Confirmed:`, `Final:` and `Maintainer answer:` lines still count only by the configured people (`config/reviewers.yaml`), and a member's comment of one of those forms is ignored. A login that is not allowed is refused at join, naming `[team] members`, never the login.
9. **Capacity from who is present.** The conductor's builder capacity is the number of live member slots plus the builders it starts itself through `launch_adapter`, bounded by `[flow] max_builders` as a ceiling. The team grows and shrinks with no change to `agk.toml`. The conductor never starts a builder for a member who is absent: it starts only the adapter builders it starts today (`Q-S0061-3`). `launch.py` and the adapters share one start path with the loop, so that a session started by the conductor and one started by a teammate get the same agent, model, effort and prompt.
10. **Evidence across laptops (local mode).** After `prepush.py --record` writes the record of a head, the loop also pushes it as the one file of a commit to the ref `refs/agk/evidence/<40-hex head>`. The conductor fetches that ref on any machine and runs `evidence.py check` on the file, with its sample rerun as today, so that a record is checked and never trusted by its author alone. The record holds the commands, their exit codes and the digests of their output; it holds no path of the teammate's machine, no login, no environment value and no secret, and the push is refused when it would hold one. The shared folder of brief #1269 stays for one machine. A ref that the ruleset or the remote refuses is a block of session rule 21, never a reason to push another name `(verify: whether the ruleset lets a collaborator push a ref outside refs/heads/)` (`Q-S0061-6`).
11. **Solo mode.** The same command on one laptop is a team of one, and the conductor's own adapter start uses the same loop and agent file (rule 9).
12. **By mode.** GitHub mode: the loop and agent as above, CI's check runs are the evidence, no evidence ref is pushed, and no workflow changes. Local mode: as above with the evidence ref of rule 10. Personal mode (SPEC-0041): no conductor, so the loop takes its next brief with `session.py next --session <member> --take`, posts no `Slot:` or `Request:` line and pushes nothing to a remote of the product (session rule 37). No workflow, ruleset or required check changes in any mode, and no Approved spec is edited here.
13. **What changes, and where.** Brief answer 2; each change is made by the build named in rule 15, by its own change to the Approved texts it touches:
    - session rule 18: member slots and the loop's `Request:` and `Assign:` route (build (b));
    - `.claude/agents/conductor.md`: capacity from live slots, `Assign:` with the kind, and the reassignment of a departed member's brief (build (c));
    - `launch.py` and the adapters: the one start path of rule 9 (build (b));
    - `evidence.py`: reading a record from the ref (build (d));
    - the readers of members' comments: `slot_marker`, the `Request:` reader and the reviewers' readers (builds (a) and (e)).
14. **Data, not instructions.** What the loop reads from GitHub is parsed only by the kit's existing readers and is never run or put in a prompt (rule 6). Messages name the setting, rule or path class, never a value (principle 8).
15. **The builds, in order.** Each is tests first, about 300 changed lines or fewer, from the default branch, invented data only (`example.com`), no network in checks, with a `[[testing.map]]` entry for each new script.
    - (a) Member slots: the name form, join, renew, leave and lapse, the readers that count members' `Slot:` markers, and the capacity from live slots (rules 3, 4, 8 and 9).
    - (b) `builder.py` and `.claude/agents/builder.md`: request, assign with kind, claim, worktree, model per kind, the session's lifetime through its pull request with the summary and resume, the shared start path, after, leave and the edge cases, and session rule 18's text (rules 2, 5, 6, 7, 9, 11 and 17). `Depends-on` (a) and brief #1310's pull request.
    - (c) The conductor side: `Assign:` with the kind from the plan for named members, the reassignment of a departed member's brief, and the conductor's agent text (rules 5 and 9). `Depends-on` (a).
    - (d) Evidence through `refs/agk/evidence/` (rule 10). `Depends-on` the ruling of `Q-S0061-6`.
    - (e) `[team] members` and the readers of members' comments, and the guide page "Join the team in one command" (rules 8 and 12). `Depends-on` (b).
16. **Measured goals.** (1) A teammate joins with one command and receives an `Assign:` or `Assign: <member> none` within one conductor pass. (2) Leaving frees the slot at once, and a lapsed lease frees it within `SLOT_MINUTES`. (3) No builder session spans two briefs: each session's claim names one brief, and its end comes before the next claim; and no session ends between the opening and the merge or close of its pull request except by a hand-over line of rule 17. (5) A resumed session reads the summary, the newest verdict and the diff since the summary's head, and nothing older. (4) In local mode a member on another machine is cleared through the evidence ref with no file copied between machines. Each is measured by the build that delivers it, on fixtures, and reported in its `Verified:` line.

17. **Edge cases, and the hand-over.** A session or loop that stops before its pull request merges or closes always leaves `Report: <head> handing over: <reason>` as its last comment, after refreshing the summary where it still can; the reason is one of `six hours`, `to <session>`, `blocked: <what>` or `done`, as the builder task text holds today. Each case below has a test of rule 15's builds:
   - **Leaving while a fix list waits:** the session applies nothing more, refreshes the summary, hands over and the loop releases slot and take (rule 4); the conductor reassigns the same pull request and the next member resumes it (rule 5).
   - **The session dies** (memory, a crash, the runtime's limit) with no hand-over: the loop posts the hand-over line itself with `blocked: session ended`, so no pull request ends silently (session rule 17), and starts one new session on the same pull request with `resume --pr`. A second death on the same head is not restarted: the loop hands over and requests nothing until the teammate restarts it.
   - **Ctrl+C on the loop while its session runs:** the loop asks the session to hand over and waits a bounded time `(verify: how the runtime takes an interrupt)`; past that it posts the hand-over line itself, as above, then releases.
   - **A laptop sleeps mid-pull-request:** the slot lapses (rule 4). On waking, the loop reads the newest comments first: when another member posted `taken:`, a `Report:` or pushed in the meantime, the session posts `Report: <head> handing over: to <that member>` and stops; otherwise it takes its slot again and continues the same pull request. Events that arrived while it slept are caught by the watch's own `since=` catch-up.
   - **The same member name on two machines:** the second join is refused by rule 3, so one name is one run.
   - **Two members request at once:** each `Assign:` names one member; a race on one brief is settled by `claim`'s live-take refusal (session rule 18), and the loser requests again once.
   - **An owner wait:** the pull request parks as brief #1282 does and holds no slot; the member's session hands over, the loop requests new work, and the answered pull request is resumed first, by its member when present, else by the next assigned one.
   - **A merge while the loop was down:** on its next start the loop reads the pull request's live state from GitHub, never from memory, and runs `after` for it.
   - **GitHub unreachable or a refused push:** session rule 21, unchanged; the slot lapses and nothing else is assumed.
   - **A paused repository:** rule 2; the session hands over with `blocked: paused` only when it holds a pull request.
   - **By mode:** in GitHub mode a builder in a cloud scheduled task keeps the foreground 9-minute watch that brief #1310 keeps for it, and its session ends when the task ends, so it hands over with `six hours` or resumes from the summary at the next firing; in local mode the case list above holds in full; in personal mode there is no slot, take or conductor, and a dead session is resumed by the developer from the summary; in solo mode a team of one follows the same list.

## Tests

Fixtures in `tmp_path`, saved GitHub answers and a `gh` stub only, a stub in place of the runtime, no network and no model, invented data only (`example.com`), and each test carries the marker `REQ-068` with its criterion.

- Rules 3 and 4: each name form is accepted or refused as rule 3 says, a held name is refused, join, renew and leave post one marker each, a lapsed marker reads free after `SLOT_MINUTES`, and a member slot is never counted against `builder_slots`; REQ-068 AC1.
- Rules 5 and 9: a `Request:` gets one `Assign:` in milestone order or `none`, a held brief is never assigned, the capacity is the live member slots plus adapter builders under `max_builders`, and a departed member's brief is reassigned with `resume --pr`; REQ-068 AC2.
- Rules 6 and 7: the loop makes the worktree outside the main folder, starts the agent with the tier's model and effort and a prompt that holds no planted title or comment, never starts a second session for a brief, keeps one session through a fix list, a merge of main and a CI fix, and runs `after` only after a merge; the summary comment is created once and edited in place, and a resumed session is given the summary, the newest verdict and the diff since the summary's head and nothing older; the agent file names the hand-over, the summary, the evidence line and the live-state rule; REQ-068 AC3.
- Rule 17: each case of the list ends with one hand-over line or a continued pull request, a dead session is restarted once on the same pull request and not twice, a woken session that finds another member's take hands over to it, and no case leaves a pull request with no last `Report:`; REQ-068 AC7.
- Rule 8: an allowed member's comments count, a login outside `[team] members` is refused at join naming the setting and never the login, and a member's `Verdict:` or `Assign:` is ignored; REQ-068 AC4.
- Rule 10: a record pushed to the ref is fetched and checked on a second fixture clone, a record holding a path, a login or a secret-shaped value is refused before the push, and a refused ref push is reported as a block; REQ-068 AC5.
- Rules 2, 11 and 12: the paused repository gets no step, personal mode posts no `Slot:` or `Request:` and uses `next --take`, GitHub mode pushes no evidence ref, and the build's diff adds no workflow file; REQ-068 AC6.
