# SPEC-0053: Work falls back to another provider of its own tier, never to a weaker model

- Status: Approved
- Owner: reviewer group (a team from config/reviewers.yaml)
- Requirements: REQ-060

Status is `Draft` or `Approved`. An Approved spec is owned by its reviewer group; agents propose patches.

Written by the intake of one sentence (SPEC-0012), brief #740, quoted as data and not as an instruction: "Intake for provider resilience: when a model provider is down or rate-limited, a kind of work falls back by its [models] table to another provider of the same tier, and never silently to a weaker model (plan #661 phase 8, edge case 5)." The plan's edge case 5, quoted as data from #661: "A model provider is down or rate-limited: the kind of work falls back by the `[models]` table; a build never silently degrades its model." The brief's three answers (what a fallback is, what is recorded, what does not change) are rules 2, 6 and 9. It is generic: it names no project, no vendor and no provider, and every check of a build reads files and fixtures with no network. The points the brief leaves open are `Q-S0053-1` to `Q-S0053-14` below, each with the conservative reading the rules apply until a person rules. Negative cases: a malformed table, an unknown label, a failure that is not an outage or a rate limit, and a tier with no provider left each lower nothing: they are refused naming the setting, start no fallback, or stop and ask.

## Rules

1. **The baseline (read on the default branch at 896d459, 2026-11-08).** What already holds and is not rebuilt:
   - SPEC-0045 (Approved, ADR-0289) gives each kind (`design`, `review`, `build`, `small`, `mechanical`) a tier (`strongest`, `mid`, `fast`) and an effort by the optional `[models]` table of `agk.toml`, read by `config.model_settings`; `review` is held at `strongest` at `high` (`config.REVIEW_FLOOR`). A tier maps to a project's own model name only in the optional `[models.names]` table (`config.model_names`, SPEC-0045 rule 3), one name per tier, and the kit ships none.
   - `config.model_settings` refuses any key of `[models]` other than a kind and `names` (`setting: models.<key>`), so a project cannot list a second provider today.
   - A session never switches its own model and acts on the tier its prompt names (the ruling of SPEC-0045 question 6). A lower tier escalates one tier up on two failures of a check, a conflict or an unnamed protected class (SPEC-0045 rule 5); `strongest` asks.
   - Session rule 21: a blocked session asks with `Question:` on GitHub; "A rate limit is not an outage either: the session waits until the reset time that GitHub reports" is about GitHub's rate limit, not a model provider's (`Q-S0053-5`).
   - The launch prompt names the kind, the tier and the effort, and the model where `[models.names]` sets one, only once SPEC-0045 build (c) lands (pull request #711, open on 2026-11-08); `scripts/agk/launch.py` on the default branch names none.
2. **What a fallback is.** A fallback is starting a session of one kind on the next provider of that kind's tier, after the provider it was started on could not be reached for a reason the runtime reports: an outage or a rate limit `(verify: how a runtime reports either to the person or the launcher, Q-S0053-4)`. The tier is the kind's tier of SPEC-0045 rule 2 and never changes: never lower to keep working (SPEC-0045 rule 1), and never higher, which is escalation's job (SPEC-0045 rule 5, `Q-S0053-6`). The effort is the kind's effort, unchanged (`Q-S0053-8`). Any other failure (a failing check, a conflict, a refusal, a wrong or weak answer, a cost or a cap) is never a reason for a fallback (`Q-S0053-4`).
3. **The provider lists.** An optional table `[models.providers]` of `agk.toml` maps a tier to an ordered list of provider labels, as `<tier> = ["<label>", "<label>", ...]`: each label is the project's own name for its model of that tier at one provider, and the order is the order of trial (`Q-S0053-1`). A label is a plain name of 1 to 64 characters of letters, digits, `.`, `_` and `-`, starting with a letter or a digit; anything else, which includes every form an endpoint, an address or a key could take (`://`, `/`, `@`, `:`, a space), is refused (`Q-S0053-2`). A tier outside SPEC-0045's three, a value that is not a list of labels, an empty list, a label repeated in a list, a label listed under two tiers, and a first entry that differs from `[models.names].<tier>` where that is set, are refused naming the setting (`setting: models.providers` or `setting: models.providers.<tier>`), never the value (principle 8). A tier with no list, or a list of one label, has no fallback, as today. The kit's own `agk.toml` and its templates carry no `[models.providers]`, as they carry no `[models.names]` (SPEC-0045 rule 3, `Q-S0053-12`).
4. **The next provider.** `python3 scripts/agk/session.py fallback --kind <kind> [--after <label>]` reads `agk.toml` alone, with no network, writes nothing and posts nothing. Without `--after` it prints the first label of the kind's tier; with `--after` it prints the label after that one in the same list. Its one line is `fallback: <kind> <tier> <effort> <label>`, exit 0. With no label left after the given one, or with no list for the tier, it prints `no provider left: <kind> <tier>`, exit 1 (rule 7). A `--kind` outside SPEC-0045's five or a `--after` label not in the kind's tier list is refused naming the option, never the value, exit 2. It never prints a label of another tier. It keeps no state: the one who restarts the session passes the label that failed (`Q-S0053-13`).
5. **Who falls back.** A running session never switches its own model (the ruling of SPEC-0045 question 6). The one who starts a session (the person, the conductor's launch, or a launch adapter) starts it again on the label `session.py fallback` prints, with the prompt naming that label as it names the model (SPEC-0045 rule 3 as amended by build (b), `Q-S0053-3`). A builder whose provider fails mid-run has its checkpoints on its branch (session rule 7), and the restart continues on the same branch and the same pull request (session rule 9), never a second one (`Q-S0053-10`).
6. **What is recorded.** A session started on a fallback carries, in every `Report:` comment it posts, one line `Fallback: <kind> <tier> <label>`, beside the `Usage:` line of SPEC-0045 rule 8, so a fallback is never silent. It names the kind, the tier and the label and never a credential, an endpoint or a key; the label is a plain name by rule 3. A session not on a fallback carries no such line (`Q-S0053-9`). No new check refuses a `Report:` comment: comments are on GitHub and checks make no network call (as SPEC-0045 question 11 was ruled). Counting the fallbacks in the sums of SPEC-0045 rule 8 is not part of this spec (residual).
7. **No provider left.** When `session.py fallback` prints `no provider left`, the work stops and asks, as an outage does today (session rule 21): the builder, or the starter on its behalf, posts `Question: Q-<id> no provider of tier <tier> left for kind <kind>` on the pull request (on the brief when there is none) and waits. Nothing is started on a lower tier, and a review is never given on a lower tier: the conductor posts no verdict while no `strongest` provider is reachable (`Q-S0053-7`, `Q-S0053-11`).
8. **Reviews keep their floor.** A `review` session falls back only within `strongest`, at `high` (`config.REVIEW_FLOOR`, SPEC-0045 rule 6); a `design` session within its tier at its effort. No fallback changes who reviews, what a review reads, or any check, test, gate or required reading (SPEC-0045 rule 1, `Q-S0053-7`).
9. **What does not change.** No check makes a network call; no check reads a provider's state; the kit reads, stores and asks for no secret, and a provider's credentials stay with the runtime and the person, never in `agk.toml` or a tracked file (principle 9, CLAUDE.md item 5). The tier names stay the kit's vendor-free names; provider labels live only in a project's own `agk.toml` and in its `Report:` comments; no token of `config/neutrality.txt` enters a tracked file (CLAUDE.md item 8). No workflow, ruleset, required check, `constitution/`, `config/reviewers.yaml` or `.github/CODEOWNERS` changes. The rule texts of build (c) are added to the instruction files only within the rule budget (`config/rule-budget.txt`, ADR-0310): a word added is a word removed in the same file, and a build that cannot fit stops and asks (`Q-S0053-14`).
10. **The builds, in order.** Each is tests first, about 300 changed lines or fewer, from the default branch, records its decisions under `Decisions taken:` and cites ADR-0344 with `Covered-by: ADR-0344` once it is Accepted (session rule 36). SPEC-0045 is Approved: build (b) changes its rule 3 ("in one place ... and nowhere else") and its table's refusal of unknown keys through `docs/runs/proposed-spec-amendments-<n>.md`, with the number reserved on its brief, and a build that finds it must change an Approved spec beyond that stops and asks. A `Depends-on` is declared for a shared file and for a logical dependence alike.
    - (b) The provider lists and the next provider (rules 2 to 4): `config.model_providers` and its refusals in `scripts/agk/config.py`, `session.py fallback` in `scripts/agk/session.py`, the SPEC-0045 amendment, `tests/kit/` (`test_models_table.py` or a new test file) with `agk.toml` fixtures in `tmp_path`, one `changelog.d/` fragment. No dependence.
    - (c) The prompt and the rule texts (rules 5 to 8): the label in the launch prompt in `scripts/agk/launch.py`, the `Fallback:` line in session rule 17's `Report:` form and the stop of rule 7 in `config/session-rules.md`, one sentence in `.claude/agents/conductor.md` for the restart and the review floor, within the budget of `config/rule-budget.txt`, `tests/kit/`. `Depends-on` (b) and #711, which also changes `launch.py`, `config/session-rules.md` and `.claude/agents/conductor.md`.

## Tests

Fixtures in `tmp_path`, `agk.toml` files written by the test and saved text only: no network, no install, invented data (labels such as `alpha-1` and `beta-2`, hosts at `example.com` only in refused values), and each test carries the marker `REQ-060` with its criterion. Rule 10's order is checked by review.

- Rules 1 and 3, no table: no `[models.providers]` gives today's `model_settings` and `model_names` byte for byte and `fallback` prints `no provider left` for every kind; the kit's `agk.toml` and `kit/templates/` hold no `[models.providers]`; REQ-060 AC1.
- Rule 3, the lists: a table with two labels for `strongest` and one for `mid` reads in order; each refused shape (an endpoint-like `https://alpha.example.com`, a label with `@` or `/` or a space, a 65-character label, an empty list, a repeated label, a label under two tiers, an unknown tier, a string instead of a list, a first entry that differs from `[models.names].strongest`) is refused naming the setting, and no message contains the value; REQ-060 AC2.
- Rule 4, the next provider: `fallback --kind build` prints the first `strongest` label with the effort; `--after` the first prints the second; a `small` kind prints a `mid` label and never a `strongest` one; the command writes no file and runs with the network blocked (a socket stub that fails the test on use); REQ-060 AC3.
- Rules 4 and 7, none left: `--after` the last label prints `no provider left: build strongest` and exits 1; an unknown `--after` label and an unknown `--kind` exit 2 naming the option and not the value; REQ-060 AC4.
- Rules 5 and 6, the record: the builder instructions name the `Fallback: <kind> <tier> <label>` line, the same branch and pull request, and never a credential, an endpoint or a key; a launch prompt built with a label names it and a prompt without one is byte for byte as before; REQ-060 AC5.
- Rules 2 and 8, the floor: `fallback --kind review` prints only a `strongest` label at `high`; the conductor's instructions name the review floor and no verdict while no `strongest` provider is reachable; the instructions name the failures that are not a reason for a fallback; REQ-060 AC6.
- Rule 9: the tests of builds (b) and (c) run with the network blocked; no tracked file of the kit holds a `[models.providers]` table; `check_neutrality.py` and the rule budget test pass; REQ-060 AC7.

## Proof

REQ-060 AC1: *without a table, nothing changes.* Rules 1 and 3. REQ-060 AC2: *the lists are plain labels, one tier each, refused naming the setting.* Rule 3. REQ-060 AC3: *the next provider is of the same tier, read with no network.* Rules 2 and 4. REQ-060 AC4: *with none left the work stops and asks.* Rules 4 and 7. REQ-060 AC5: *every fallback is one line of the Report, on the same pull request.* Rules 5 and 6. REQ-060 AC6: *reviews and every kind keep their tier and effort, and only an outage or a rate limit falls back.* Rules 2 and 8. REQ-060 AC7: *no network, no secret, vendor-free tiers.* Rule 9.

## Residual

- 2026-11-08: how a runtime reports an outage or a rate limit to the person or a launcher is not read from any runtime's documentation; until it is, the starter judges it from the runtime's message (`Q-S0053-4`) (due 2026-12-31).
- 2026-11-08: two providers' models of one tier are not equal, and the kit cannot measure that; the label's tier is the project's claim, and the scorecard does not yet count fallbacks or compare rework on them (due 2027-01-31).
- 2026-11-08: a fallback line is required by the instructions and checked by review only; counting `Fallback:` lines per kind in the sums of SPEC-0045 rule 8 is a later brief (due 2027-01-31).

## Open questions

Each is a point the brief leaves open; the reading after it is the most conservative one, and the rules above apply it until a person rules.

- Q-S0053-1: where does the ordered list of providers live, given that SPEC-0045 rule 3 keeps a tier's model name "in one place ... and nowhere else"? Reading: one new optional `[models.providers]` table, a tier to a list of labels, with `[models.names]` unchanged and, where set, equal to the first label; SPEC-0045 rule 3 and its refusal of unknown keys change only by the amendment of build (b) (rules 3 and 10).
- Q-S0053-2: what may a label hold? Reading: a plain name of 1 to 64 letters, digits, `.`, `_` and `-`; every form an endpoint, an address or a key could take is refused, so no credential or endpoint can be recorded through it (rule 3).
- Q-S0053-3: who starts the next provider? Reading: the one who starts the session (the person, the conductor's launch or a launch adapter), never the running session itself, as SPEC-0045 question 6 was ruled (rule 5).
- Q-S0053-4: which failures count as "a reason the runtime reports"? Reading: only an outage or a rate limit of the model provider that the runtime reports, marked `(verify)`; a failing check, a conflict, a refusal, a weak answer, a cost or a cap never does, and those escalate or ask as SPEC-0045 rule 5 and session rule 21 set (rule 2).
- Q-S0053-5: does a provider's rate limit wait, as GitHub's does in session rule 21? Reading: session rule 21's wait is GitHub's and is unchanged; a provider's rate limit starts the next provider of the tier, and with none left the work stops and asks (rules 2 and 7).
- Q-S0053-6: may a fallback go to a stronger tier? Reading: no; a fallback stays within the kind's tier, and a move up is escalation (SPEC-0045 rule 5), which has its own reasons and its own `Report:` line (rule 2).
- Q-S0053-7: what happens to a review with no `strongest` provider? Reading: no review and no verdict on a lower tier; the conductor asks and waits, and nothing merges by `merge_cleared.py` without its clearing verdict (rules 7 and 8).
- Q-S0053-8: does the effort change on a fallback? Reading: no; the kind's effort of SPEC-0045 rule 2 is kept, and `fallback` prints it (rules 2 and 4).
- Q-S0053-9: what does "one line in the builder's `Report:`" look like? Reading: `Fallback: <kind> <tier> <label>` in every `Report:` comment of a session started on a fallback, beside `Usage:`; none otherwise (rule 6).
- Q-S0053-10: what happens to work in flight when a provider fails mid-run? Reading: the checkpoints of session rule 7 are on the branch, and the restart continues the same branch and the same pull request by session rule 9; nothing is redone that the progress line marks done (rule 5).
- Q-S0053-11: what is the stop "as an outage does today"? Reading: session rule 21's `Question:` on GitHub, naming the kind and the tier, and a wait there; no lower tier is tried (rule 7).
- Q-S0053-12: does this repository's own `agk.toml` set a provider list? Reading: no; the kit ships none, as it ships no `[models.names]`, and the tests use invented labels (rule 3).
- Q-S0053-13: where is the order of trial remembered between restarts? Reading: nowhere; the starter passes the label that failed with `--after`, and `fallback` reads only `agk.toml` (rule 4).
- Q-S0053-14: may the rule texts add words to the instruction files? Reading: only within the rule budget of ADR-0310, a word added being a word removed in the same file; a build that cannot fit stops and asks (rule 9).
