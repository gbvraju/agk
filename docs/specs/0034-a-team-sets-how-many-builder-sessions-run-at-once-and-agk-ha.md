# SPEC-0034: Parallel builder sessions get briefs by capacity, overlap, reserved numbers and claims, and every pull request traces to a brief and a requirement

- Status: Approved
- Owner: reviewer group (a team from config/reviewers.yaml)
- Requirements: REQ-041

Status is `Draft` or `Approved`. An Approved spec is owned by its reviewer group; agents propose patches.
Written by the intake of one sentence (SPEC-0012): "A team sets how many builder sessions run at once, and AGK hands each session a brief that no open pull request overlaps, with its numbers reserved, so parallel work starts by itself, rarely conflicts, and every pull request traces to a brief and a requirement." It is generic and project-agnostic: it names no project, no runtime and no launcher, and it holds for every repository the kit is installed in. It amends SPEC-0030 rules 2 to 4 (the build does it by a proposal, rule 13). Evidence (the parallel run of 2026-10-24/25, recorded on issue #163): three ADR number collisions, four changelog conflicts that stopped CI, three pushes onto a branch that already conflicted, a session idle 21 minutes with green CI and a commit owed, seven finished briefs left open because no pull request named its brief, and no label, so `next` would have found no work. Each was solved by a person noticing.
The maintainers gave 12 answers before it was written, in the brief of issue #176 and its comment of 2026-10-24 and not as interview questions: (1) `agk.toml` gains `[flow]` with `max_builders` (default 3) and `claim_hours` (default 4), a builder pull request being an open pull request whose body has a `Brief: #n` line, and `session.py next` takes no brief while that many are open; (2) the brief shape gains `Advances:`, `Touches:` and `Priority:`, checked by `check_brief.py` (also against `docs/`) and by `next`; (3) `next` skips a brief whose `Touches:` globs overlap an open builder pull request or a taken brief, and orders the rest by Priority, `Depends-on` closed, then age; (4) `session.py ids` prints the next free numbers counted with every open builder pull request's added files and the reservations of taken briefs, and `next` reserves a brief's numbers in its `taken:` comment; (5) a `taken:` comment with no pull request after `claim_hours` expires and `released:` frees a brief at once; (6) `session.py demand` prints how many sessions a launcher may start, and AGK ships no launcher; (7) conflicts are prevented before they happen: shared append-only files stop being shared (#171), `session.py push-check` runs before every push, and a session resolves only mechanical conflicts; (8) a session wakes on CI, which SPEC-0032 rule 3 already meets by the change of a label; (9) every builder pull request body has `Brief: #n`, and the part that sets a requirement `done` has `Closes #n`; (10) the weekly report gains a `Flow` section; (11) the work is intake first, then four builds (a) to (d) under about 600 changed lines each; (12) the tests use fixtures in `tmp_path` and saved copies of GitHub responses. The comment of 2026-10-24 adds that a session puts its questions and reports on its pull request as `Question:` and `Report:` comments (rule 11).

## Rules

1. **The capacity.** `agk.toml` may have a `[flow]` table with `max_builders` (an integer of 1 or more, default 3) and `claim_hours` (an integer of 1 or more, default 4). A builder pull request is an open pull request whose body has a line `Brief: #n`. `session.py next` counts them with `GET` on the pull requests and, when the count is `max_builders` or more, takes no brief, posts nothing, prints `full <open>/<max>` and exits 1. `agk.toml` is protected, so a change of the table needs an ADR in the same pull request (principle 1). An invalid value is refused naming the setting and never the value.
2. **The brief shape.** A brief (SPEC-0030 rule 4) gains three lines: `Advances: REQ-n` (one or more, in one line, separated by commas; `Advances: new` for an intake brief), `Touches:` with one or more repository path globs separated by commas, and `Priority: 1`, `2` or `3` (default 2 when the line is absent). `check_brief.py` and `session.py next` apply the same function. `check_brief.py FILE --root DIR` also fails a brief whose `Advances:` names a requirement that is not a `### REQ-n` section of `docs/requirements.md` under `DIR`, reading files only; without `--root` it checks the shape alone. A brief with no `Advances:` or no `Touches:` fails naming the rule and what is missing and never the sentence.
3. **The overlap.** `next` skips, and says why on one line each, a brief whose `Touches:` globs match a path changed by an open builder pull request (`GET pulls/N/files`) or match the `Touches:` of a brief that is taken and has no builder pull request yet. Paths listed as shared-mechanical in rule 7 never count as an overlap. Among the briefs left it orders by `Priority` (1 first), then those whose `Depends-on` issues are all closed, then the oldest issue, and takes the first.
4. **The numbers.** `session.py ids` prints one JSON line with the next free `req`, `spec` and `adr` numbers counted from the default branch, from the files every open builder pull request adds, and from the reservations of taken briefs. `next` reserves the numbers a brief needs, as the counts its `Advances:` implies (`Advances: new` needs a requirement, a spec and an ADR; a build needs an ADR), in its one `taken:` comment (`taken: <id> <date> reserves ADR-0105`). When a session runs them, `intake.py`, `playbook.py start-ids` and `engines.py stack-ids` take their numbers from `session.py ids`; their offline default stays the default branch. `check_numbers.py` stays offline and unchanged, and `intake.py renumber` stays the fallback.
5. **The claim.** A `taken:` comment with no builder pull request naming the brief after `claim_hours` is expired: `next` treats the brief as free and its new `taken:` comment says `retakes`. A session that ends without a pull request posts one comment `released: <id>`, and the brief is free at once. A live take is never taken twice.
6. **The demand.** `session.py demand` prints one JSON line `{"ready": r, "open": o, "max": m, "start": s}`, with `r` the briefs `next` would not skip, `o` the open builder pull requests, `m` the `max_builders` and `s = min(r, m - o)` (0 when negative). AGK ships no launcher and no session starts, stops or reviews another. The guide shows the contract with two examples, a scheduled task of a session runtime and a CI schedule, that start `s` sessions, each running `session.py next` and ending on `no brief` or `full`.
7. **The conflicts.** (a) Shared append-only files stop being shared: a build adds a changelog file of its own (SPEC-0031) and leaves the generated table to the release (ADR-0108); this is built, and this spec adds nothing. The files that count as shared-mechanical are the ones `config/session-rules.md` lists; its first list is the files marked `merge=union` in `.gitattributes` and `changelog.d/`; `kit/hashes.json` is a release file that a build never edits (SPEC-0031), not a file a build resolves. (b) `session.py push-check` fetches the default branch, runs `git merge-tree` of the head against it and exits 1 naming the conflicting files, and exits 0 and prints nothing else when there is none; `config/session-rules.md` requires it before every push, and on a conflict the session merges the default branch first and never rebases or force-pushes. (c) A session resolves only a mechanical conflict: an appended line in a shared-mechanical file, a file a kit script regenerates, and a number moved by `intake.py renumber`; any other conflict ends the work with one comment `conflict needs a person: <files>` and no push.
8. **The waking.** A session wakes on CI through the change of label of SPEC-0032 rule 3 (`agk:ci-running` to `agk:ci-red` or `agk:review`), which meets answer 8 of the brief; this spec adds no `ci` end to `session.py watch`.
9. **The tracing.** Every builder pull request body has `Brief: #n`. The part that sets a requirement to `done` in `docs/build-state.md` also has `Closes #n`. `check_pr_body.py` fails a body without `Brief:` when the repository has an `agk-brief` issue in the saved copy it reads, and a body that sets a requirement to `done` without `Closes #n`, naming the rule and never a value. `doctor` reports a missing `agk-brief` label as a finding (GET only, as its other checks).
10. **The flow in the report.** The facts record, for the week, from the files and the saved GitHub copies the report already reads: the open builder pull requests against `max_builders`; the median hours from `taken:` to the pull request, from the pull request to the first verdict, from the verdict to `cleared` and from `cleared` to the merge; the conflicts, the renumbers and the retakes; the open briefs with no pull request for 7 days; and the requirements with no open brief. The report gains a `Flow` section with these, and the last two as At risk lines. A figure that cannot be read is `unknown`, never 0.
11. **The comments of a session.** A session puts its questions and its reports on its pull request. A comment whose first line is `Question: Q-<id> <text>` asks the conductor; a comment whose first line is `Report: <head> <what changed and the CI>` reports a push. The conductor answers only by a `Verdict:` comment naming the head, which ends `watch` as before, and the session restarts `watch` after every push and every event, so no person carries messages between them. `config/session-rules.md` gains the two shapes and `.claude/agents/conductor.md` says that the conductor reads `Question:` and `Report:` comments and answers each by a verdict.
12. **No network in a check; the only POSTs.** `session.py` is the only script of this spec that calls GitHub, through `gh api`; its POSTs are the comments of `taken:`, `released:`, `conflict needs a person:`, `Question:` and `Report:`. `check_brief.py`, `check_pr_body.py`, `check_numbers.py`, the report and the facts read files only. No agent merges, no session starts or reviews another.
13. **How it changes.** SPEC-0030 rules 2 to 4 are Approved: the build changes them by `docs/runs/proposed-spec-amendments-N.md`, applied by its ADR, which names each protected class it touches (`agk.toml`, `config/`, `.claude/`, `scripts/agk/`, `tests/kit/`, `tests/kit_dev/`, `kit/`). Four builds in flow mode (SPEC-0031), each from the default branch, tests first, under about 600 changed lines of code and tests, with its own ADR: (a) the brief shape, `check_brief.py`, `check_pr_body.py` and the doctor finding (rules 2 and 9); (b) `session.py`: capacity, overlap, ids and reservations, claims, demand and push-check (rules 1, 3 to 6 and 7b); (c) the session rules and the guide's launcher contract (rules 6, 7c and 11); (d) the `Flow` section of the report (rule 10), which waits for an ADR that opens K5 for it (see the residual). Rule 7a is built.
14. **The tests.** Fixtures in `tmp_path` and saved JSON copies of GitHub responses through a `gh` stub on `PATH`: a full pool; an overlapping and a non-overlapping brief; a brief whose requirement does not exist; reserved numbers skipped by `ids`; an expired and a released claim; `demand` at zero, partial and full; `push-check` clean and conflicting; a body without `Brief:`, and one that sets `done` without `Closes`; the Flow figures from a fixture week; the texts of the rules file and the role file. No network and no model.

### Independent pull requests (from SPEC-0025)

Rules 17 to 27 are the rules of SPEC-0025 (a team runs independent pull requests in parallel without colliding, REQ-032), moved here by `docs/runs/proposed-spec-amendments-108.md`, applied by ADR-0246 (brief #387), so that the rules for running work in parallel live in one spec. Rule n of SPEC-0025 is rule n + 16 here; numbers 15 and 16 are left to the new rules that amendments 88 and 89 propose. Their text is unchanged, and rule 24 (SPEC-0025 rule 8) carries the release model in the text SPEC-0028 gave it (amendment 50, item 2). Inside rules 17 to 27, "rule n" or "rules n to m" with no spec named means the SPEC-0025 number, rule n + 16 here, and "parts 1 to 5", "part (a)" to "(c)" and "answer 7" are those of SPEC-0025. SPEC-0025 keeps its number, its history and one pointer line per rule; its `## Tests`, `## Proof` and `## Residual` sections stay there.

17. **Duplicate numbers fail.** A governance check (`check_numbers.py`, installed) fails when two requirements in `docs/requirements.md`, two specs in `docs/specs/` or two ADRs in `docs/adr/` carry the same number in the checked-out tree. In CI that tree is the pull request's merge commit, so a collision with the default branch shows there. The message names the rule and the duplicated id and never a title. It reads files only. The first pull request to merge keeps its numbers.
18. **Renumbering is a command, never a hand edit.** `python3 scripts/agk/intake.py renumber <id>` takes an id of the pull request's own requirement (`REQ-nnn`), spec or ADR, moves the pull request's own requirement, spec and ADR to the next free numbers on the default branch (read from `origin/<default branch>` as `ids` does), renames the files, rewrites the ids inside the pull request's own files and every reference the pull request adds, and changes nothing that is on the default branch. It prints what it moved. A second run changes nothing. It refuses when the work tree is dirty or when an id is not the pull request's own.
19. **The append-only logs merge as a union.** The shipped `.gitattributes` template marks `docs/runs/decisions-log.md`, `docs/runs/residuals.md` and the catch logs (`docs/runs/architect-catches-*.md`) `merge=union`, so two pull requests that each append a line merge without a conflict. It does not mark `docs/requirements.md`, whose status lines change in place. At the build the behaviour of GitHub's merge conflict check is measured; if it does not honour `merge=union`, the build raises a question with the measured behaviour and two options (keep union for local rebases only, or one file per log entry with a generated index) and builds neither until it is ruled.
20. **No self-clearance.** When two or more verdict authors are listed (SPEC-0021 rule 5), a verdict by the pull request's own author does not count: it clears nothing, covers nothing and is not a review round, for the metrics, the facts and `check_final_clearance.py`. The workflow passes the pull request's author login to the checks; the metrics read it from the pull request record. With one listed author nothing changes.
21. **Declared dependence.** A pull request body may carry lines `Depends-on: #n`. A governance check fails while any named pull request is not merged, naming the rule and the number. The workflow fetches the state of each named pull request with a read-only GET into a file (as it fetches the comments); the check reads that file, and without it prints `skipped (no states file)` and passes.
22. **The mode.** `agk.toml` gains `pr_mode = "strict" | "flow"`, default `strict`. In strict mode a person has one open pull request at a time: a check fails on a pull request whose author has an older open pull request (the lowest number wins), and a `Depends-on` line fails the check. In flow mode any number of pull requests may be open and `Depends-on` is allowed. The workflow fetches the author's open pull requests with a read-only GET into a file; the check reads it, and without it prints `skipped (no open pull requests file)` and passes. `agk.toml` is protected, so a change of mode needs an ADR in the same pull request. `doctor` reports the mode, and the getting-started guide says that new projects start strict and switch by ADR once the team knows the method.
23. **The workflow reads and writes files only.** The workflow keeps the permissions `contents`, `pull-requests` and `issues`, each `read`. Every new fetch is a step with `gh api --method GET` that writes a file in the runner's temporary directory; a check reads files and git, and makes no network call.
24. **This repository.** Parts 1 to 5 are built for every project. After they are released a separate pull request switches this repository to `flow` by an ADR; until then this repository stays strict, with the maintainers' docs-only exception of 2026-10-24. The release model, as SPEC-0028 amended it (amendment 50, item 2): Kit build pull requests do not bump the version in flow mode; one release pull request bumps `agk.toml`, `kit/manifest.json` and the plugin together, moves the Unreleased lines of `CHANGELOG.md` under the new version and adds the new row of `kit/hashes.json`; `scripts/agk/check_release.py` checks it (SPEC-0028 rules 4 and 5).
25. **Not built.** A cap on the number of open pull requests in flow mode (the report's "changes waiting for a review", with their age, shows the queue), a server or a database, any network call in a check.
26. **How it is built.** The build is a kit change in three parts, each with a bump, an ADR that names the protected classes, the hashes, and its tests first: (a) the duplicate-number check and `intake.py renumber` (rules 1 and 2); (b) the `.gitattributes` lines, after the verification of rule 3; (c) the author rule, `Depends-on` and `pr_mode` with their workflow fetches (rules 4 to 7). The Approved specs this touches are changed by `docs/runs/proposed-spec-amendments-N.md`, applied by the part's ADR: SPEC-0021 rule 5 (the author), SPEC-0007 (the review rounds), SPEC-0012 (`renumber`), SPEC-0002 and SPEC-0001 (the `.gitattributes` and `agk.toml` templates), SPEC-0003 or the doctor spec (the mode). Each part is measured first and split at about 600 changed lines of code and tests; part (c) is the likeliest to need a split.
27. **The tests.** Fixtures in `tmp_path`: trees with and without duplicate numbers; `renumber` on a pull request branch behind a merge on the default branch, twice; the `.gitattributes` template; verdicts by the pull request's author with one and with two listed authors; bodies with `Depends-on` lines with and without the states file in each mode; the open pull requests file for an author with an older pull request; the mode in `agk.toml` and `doctor`; the workflow for its permissions, its GET-only fetches and the absence of any write. No network and no model.

## Tests

- Rule 1: a full pool prints `full 3/3`, exits 1 and posts nothing; two open take the first free brief; an invalid value is refused without the value; REQ-041 AC1.
- Rule 2: a brief missing a line, and one whose `Advances:` names an absent requirement, fail; `Advances: new` and an existing requirement pass; REQ-041 AC2.
- Rule 3: an overlapping brief is skipped with its reason, a shared-mechanical path never overlaps, the order is Priority, `Depends-on`, age; REQ-041 AC3.
- Rule 4: `ids` skips the numbers of open pull requests and of reservations, `next` writes the reservation, `check_numbers.py` is unchanged; REQ-041 AC4.
- Rule 5: an expired take is retaken with `retakes`, a released brief is free, a live take is not taken twice; REQ-041 AC5.
- Rule 6: `demand` at zero, partial and full, and the guide shows the contract; REQ-041 AC6.
- Rules 7 and 11: `push-check` clean and conflicting, and the texts of the rules file and the conductor role; REQ-041 AC7.
- Rules 9 and 10: a body without `Brief:`, one that sets `done` without `Closes`, the doctor finding, and the Flow figures from a fixture week; REQ-041 AC8.
