# SPEC-0037: A design phase delivers a click-through prototype on a default UX standard, signed off once and held to by every build

- Status: Draft
- Owner: reviewer group (a team from config/reviewers.yaml)
- Requirements: REQ-044

Status is `Draft` or `Approved`. An Approved spec is owned by its reviewer group; agents propose patches.
Written by the intake of one sentence (SPEC-0012): "A project's design phase delivers a click-through prototype for demos and sign-off, built on a modern default UX standard the kit ships, covering every screen and state of the spec; the person's sign-off freezes one version, and every UI build is held to it." It is generic and project-agnostic: it names no project, no vendor, no framework and no runtime, and it needs only files, a shell and, where one is found, a headless browser that runs offline. The plan is issue #365 (six parts) and the brief is issue #366 (four answers, the conductor's proposals). The maintainers answered 3 questions before it was written: the person ruled the three open questions of #365 on 2026-10-30 (18:05Z, the conductor's field note on #365, recorded in `docs/runs/decisions-log.md`), choosing the proposals: (1) the prototype uses the kit's own small, hashed, offline navigation runtime, which gives a state bar and demo mode on every screen; (2) a build must match the frozen version's structure within a small pixel tolerance, and any drift is named in the verdict and judged by the conductor, never failed automatically; (3) the pilot regenerates v1 from the inventory on the new standard, carrying its theme over. The points the brief and the rulings leave open are `Q-S0037-1` to `Q-S0037-11` below, each with the conservative reading that the rules apply until a person rules. Today `/agk:design` (REQ-036 AC5 to AC7, SPEC-0029 rules 6 and 7) writes a theme and a folder of one static page, and `check_design.py` checks its tokens, its contrast and that it has no script; in the pilot that gave no baseline, states found late and nothing that froze at sign-off. Negative cases: a theme that overrides more than its block, an inventory without a row counted by the person's `Approve: inventory` line, a new mockup folder, a script that is not the runtime file, a colour outside the tokens, a contrast too low, a placeholder, data outside the fixture set, a missing state or a broken link, a changed signed-off version and a UI brief without a `Screens:` line all fail naming the rule, and a reflow test that could not run reads `not run`, never passed; a design comparison fails nothing by itself, and no session ever approves a design.

## Rules

1. **The default UX standard.** The kit ships one design standard as templates, vendor-neutral and with no framework: `kit/templates/design-standard.css` (the tokens) and `kit/templates/design-patterns.md` (the pattern library). The tokens are colour roles (background, surface, text, muted text, border, accent and its text, focus, success, warning, danger and info, each with its text colour) for light and for dark; a type scale; a spacing scale; radii; elevations; motion durations, with every motion turned off under `prefers-reduced-motion: reduce`; and the breakpoints, from 360 px (phone) to 1440 px (wide desktop) (`Q-S0037-1`). The standard meets WCAG 2.2 AA in its own tokens: visible focus on every control (`:focus-visible`), targets of at least 44 by 44 px, focus order that follows the reading order, contrast of at least 4.5:1 for text and 3:1 for large text and UI parts, in both modes. The pattern library names the patterns app shell and navigation, list with filter and sort, detail, form with validation, table, dashboard, wizard, search, settings, notifications and confirmation dialog, and gives each its `default` state and the six required states `empty`, `loading`, `error`, `no-permission`, `long-content` and `success`. Each pattern is markup and classes of the standard only, with no colour, size or font of its own.
2. **What a project overrides.** `docs/design/theme.md` keeps the brand record of SPEC-0029 rule 6 (one source line per value) and overrides only its theme block (the brand colour roles, the font stacks and the logo) and its layout block (density `compact`, `comfortable` or `spacious`, and alignment `start` or `centre`) (`Q-S0037-2`). `check_design.py` fails a theme that sets any other token or rule of the standard, naming the rule and never the token's value; the contrast of rule 7 is computed from the tokens after the overrides, in both modes. **An existing theme is not broken.** A theme of the SPEC-0029 format (its one token block sets `--bg`, `--fg`, `--muted`, `--accent` and `--accent-fg`, with no line `Standard: agk design standard <n>`) is an old-format theme: `check_design.py` checks it, and the mockup folders it points to, exactly as SPEC-0029 rule 7 does today, and rule 2 does not apply to it. A theme moves to the standard by gaining the `Standard:` line, and `/agk:design prototype` moves it so when it writes the first version (rule 12), mapping the old tokens to the roles of rule 1 unchanged in value: `--bg` to background, `--fg` to text, `--muted` to muted text, `--accent` to accent and `--accent-fg` to accent text, in light and in dark, with the brand record and its source lines carried over. This amends SPEC-0029 rule 6 (what the theme holds) and rule 7 (what the check reads) for a theme with the `Standard:` line only; rule 12 amends rule 6 for the folder that is written.
3. **The screen and state inventory.** `/agk:design inventory` makes `docs/design/inventory.md` in two steps. First the script (`scripts/agk/design.py inventory`, files only, no model) writes the skeleton: one section for each requirement of `docs/requirements.md`, headed by its id and title and listing the specs that name it, with its slots empty. Then the session, or the design engine of SPEC-0029 rule 3 where one is set, fills the slots from the requirements and the specs, and from nothing else: each requirement's screens, or `no screen: <reason>`; and one entry for each screen, with its id (a lower-case slug), its flow, the pattern of rule 1 it uses, the screens it links to, and its states: `default`, the six required states, and any other a spec names. A required state that does not apply to a screen is listed as `n/a: <reason>`, never left out. The script never fills a slot, and the check, not the script, decides that the inventory is complete. The person agrees the inventory with a comment on its pull request whose first line is `Approve: inventory <full head ID>`, by an account listed in `spec_approvers`; after it the session appends one `inventory` row to `docs/design/signoffs.md` (the digest of `inventory.md` as rule 9 computes a digest, the head, the date and the link of the comment), and `check_final_clearance.py` counts that row only with the person's line on the head it names (`Q-S0037-3`). A session never posts that line. Nothing is drawn before it is there: `/agk:design prototype` refuses an inventory whose digest has no `inventory` row in `docs/design/signoffs.md`, naming the rule. `check_design.py` fails an inventory with an empty slot, or an inventory in which a requirement of `docs/requirements.md` has neither a screen nor a `no screen:` reason, or in which a screen lacks a required state, naming the rule and the screen.
4. **The click-through prototype.** `/agk:design prototype` (`scripts/agk/design.py prototype`) writes `docs/design/prototype/<version>/`, where a version is `v1`, `v2` and so on, the next free one (`Q-S0037-4`), from the standard, the theme and the approved inventory, and from nothing else. The folder holds `index.html` (the flows and the start of each demo path), one page `<screen>--<state>.html` for each screen and state of the inventory, `standard.css` (the kit's standard, unchanged), `theme.css` (the overrides of rule 2), `agk-prototype.js` (rule 5), `demo.md` (the demo path of each flow, one sentence for the presenter per step) and `README.md`. Pages link to one another with plain relative links as the flows link, so that the prototype works by clicking, opened from the files, with no build step and no server. Every page carries a state bar: one plain link to the page of each state of the same screen. A page with the runtime turned off still works by its links.
5. **The kit's runtime (ruling 1).** The prototype's one script is the kit's runtime, `kit/templates/design-prototype/agk-prototype.js`, copied unchanged into each version folder: a small, versioned, offline navigation helper that adds keyboard access to the state bar and the demo mode (step forward and back through a flow, the presenter's sentence shown for each step). It makes no request of any kind (no `fetch`, `XMLHttpRequest`, `WebSocket`, `EventSource`, `import`, `sendBeacon`, worker or storage), changes no data and is loaded by one `<script src="agk-prototype.js"></script>` element at the end of each page. A project adds no script. **REQ-036 AC6 changes so:** the no-script rule of `check_design.py` allows, in a prototype version folder only, exactly that file and that element, verified by the SHA-256 hash of the file, which `check_design.py` holds as a list of the runtime's released hashes (`Q-S0037-5`); an inline script, an event handler attribute, a `javascript:` link, any other script file, or a runtime file whose hash is not listed fails as before, naming the rule and the screen. **REQ-036 AC6 also changes for links:** in a prototype version folder only, each page may load exactly two stylesheets, by `<link rel="stylesheet" href="standard.css">` and `<link rel="stylesheet" href="theme.css">`, files of the same folder; any other `link` element, a stylesheet from another folder or host, `@import` and `url()` of anything outside the folder still fail as an external request or a loaded resource, and the one-token-block rule of a mockup page does not apply to a prototype page, whose tokens are in those two files. A mockup folder of `docs/design/mockups/` still allows no script and no `link` at all.
6. **Invented data only.** The kit ships one fixture set, `kit/templates/design-prototype/fixtures.json`: invented people, organisations, addresses, amounts and dates, email addresses and links on `example.com`, `example.org` or `example.net` only, and long values for the `long-content` state. A prototype's data comes from it and from nothing else, never from `private/`, `reference/` or any real record. `check_design.py` fails a page that holds an email address, a link host or a phone number that is not in the fixture set, naming the rule and the screen, never the value (`Q-S0037-6`).
7. **The design checks before any demo.** `check_design.py` (installed, files only, no network and no model) checks each prototype version folder and fails, naming the rule and the screen and never a value, on: a screen or state of the inventory with no page, or a page for none; a link that does not resolve to a file of the same version folder; a script that is not the runtime of rule 5; an external request or a loaded resource from outside the folder; a colour outside the tokens; a contrast below 4.5:1 for text or 3:1 for large text and UI parts, in light or dark; a placeholder (text in square brackets, `lorem ipsum`, `TODO`, `TBD`); data outside the fixture set (rule 6); a form control without a label, an image without alt text, a page without exactly one `h1` or with a skipped heading level, a page without `lang`, a positive `tabindex`, or no `:focus-visible` style; and, statically, a page without the viewport line or with a fixed width wider than 360 px outside a media query. The checks enforce the standard (tokens, states, accessibility, layout) and never taste: how a page looks within the theme is the person's call.
8. **Reflow and screenshots.** Where a headless browser is found on the machine, `scripts/agk/design.py screenshots --version <version>` opens each page from the files, offline, at each breakpoint of rule 1 in light and dark, records any page whose document is wider than the viewport (a sideways scroll), which `check_design.py` then fails naming the rule, the screen and the breakpoint, and writes the screenshots for the record into `docs/design/prototype/<version>/screenshots/`. It records the reflow result in `docs/design/prototype/<version>/screenshots/reflow.json` (one entry per page, breakpoint and mode: `ok`, `sideways` or `not run`), which `check_design.py` reads; being under `screenshots/`, it is outside the signed-off digest (rule 9), so a later run neither unfreezes a version nor needs a new one. `screenshots/` is written only by this command, never by hand. Without a headless browser the command says so and succeeds, and the reflow test reads `not run`, never passed; a demo checklist that lists it says `not run` (`Q-S0037-7`).
9. **Sign-off freezes a version.** The person signs off one version with a comment on the prototype's pull request whose first line is `Approve: design <version> <full head ID>`, by an account listed in `spec_approvers` (`config/reviewers.yaml`); a line by another account, or one that names another head, does not count, and a session never posts it. In solo mode (`review_mode = "solo"`) the line also counts inside the person's `Confirmed:` comment, as `Approve:` lines do today (session rule 29), and the session prints it for the person and never posts it. After it, the session appends one `design` row to `docs/design/signoffs.md` (the version, the digest, the head, the date from `date -u` and the link of the comment), in a commit that changes only that file, as a verdict's `Final:` commit does (SPEC-0032 rule 5). A row of `docs/design/signoffs.md`, `inventory` or `design`, counts only with a listed person's `Approve: inventory` or `Approve: design` line on the head it names, which `check_final_clearance.py` checks from the saved comments; `check_design.py` reads the rows and compares the digests, and no check writes anything. The digest is the SHA-256 of the sorted list of `<path> <SHA-256 of the file>` lines of every file of the version folder except `screenshots/`. Once signed off a version is frozen: `check_design.py` fails any change, addition or removal in its folder (a digest that no longer matches), naming the rule and the version. A change after sign-off is a change request: a new version folder, made by `/agk:design prototype`, with its own pull request and its own `Approve: design` line, never an edit in place.
10. **The `Screens:` line of a UI brief.** A brief that changes UI names the signed-off version and the screens and states it implements in one line `Screens: <version> <screen>/<state>, <screen>/<state>, ...`, where `<state>` may be `*` for every state of the screen in the inventory. A brief is a UI brief when a glob of its `Touches:` line matches a glob of `ui_paths` in the `[design]` table of `agk.toml` (`Q-S0037-8`). `scripts/agk/check_brief.py`, which reads the project with `--root`, refuses a UI brief without the line, with a version that `docs/design/signoffs.md` does not list, or with a screen or state that the version's inventory does not have, naming the rule and never a value. A project without `ui_paths` has no UI briefs, and `doctor` reports the setting as absent when `docs/design/prototype/` exists.
11. **Builds held to the signed-off version (ruling 2).** Before it marks its pull request ready, the builder of a UI build runs `scripts/agk/design_compare.py --version <version> --screens <the brief's Screens line>` itself (a kit-only script that the session runs, as it runs `design.py`; `proof.py` and the CI proof job do not change), which renders each named screen and state with the project's `render` command of the `[design]` table (a command of the project that writes the built page for a screen and state into a folder) and compares it with the page of the frozen version in three ways: the structure (the landmarks, the heading outline, the controls and their labels, and the links in order), the tokens used (the custom properties of the standard that the page uses), and, where a headless browser is found, a screenshot diff at each breakpoint, in light and dark, against the share of differing pixels allowed by `pixel_tolerance` of the `[design]` table (`Q-S0037-9`). It prints one line per screen and state, `match` or `drift: structure|tokens|pixels` (several may be named), or `pixels: not run` without a browser, and it exits 0 on drift: it fails nothing by itself. The builder puts the lines in its pull request body as `Design match:` lines, which `check_pr_body.py` does not check (`Q-S0037-11`); the conductor reads them for every UI brief, asks for them when they are missing, and judges every drift and its verdict names every screen and state that drifted, with a fix item or a reason to accept it (`.claude/agents/conductor.md`). A build that changes no screen named by a `Screens:` line runs no comparison.
12. **The existing folders and v1 (ruling 3).** **REQ-036 AC5 changes so:** the design folder that `/agk:design` writes becomes `docs/design/prototype/<version>/`, written by `/agk:design prototype`. `/agk:design <name>` no longer writes a new mockup folder: it refuses, naming the rule and pointing to `/agk:design prototype`, and the existing folders of `docs/design/mockups/` are only read and checked (`Q-S0037-10`). **REQ-036 AC7 changes so:** the evidence line of the theme may point to `docs/design/prototype/<version>/` as well as to a mockup folder; a prototype version reads approved only when `docs/design/signoffs.md` has its row with a matching digest, and otherwise reads `not approved yet`, which is information and not a failure. Existing mockup folders are read and checked as before (SPEC-0029 rule 7); nothing converts them. A project that moves onto the standard regenerates `v1` from its approved inventory, and `/agk:design prototype` carries the brand record of the existing `docs/design/theme.md` over unchanged.
13. **What never happens.** No real data, name or text from `private/` or `reference/` in a theme, an inventory, a fixture or a prototype. No network request from a prototype, a design command or a design check, and no script other than the kit's hashed runtime. No session approves a design, an inventory or a version: sign-off is only the person's `Approve: design` line, and the `Approve: inventory` line is the person's. No design check blocks on taste. Refusals name the rule and the screen (or the version or the breakpoint), never a value. Nothing in the kit names a project or a vendor.
14. **The builds, in order.** After this intake, the conductor splits #365 into these builds, each of about 600 changed lines of code and tests or fewer, each from the default branch with its own ADR naming the protected classes it changes and one fragment under `changelog.d/` where it changes a file the installer writes (SPEC-0031). A new module that the installed `check_design.py` imports is added to `verbatim` in `kit/manifest.json`, and its tests go in `tests/kit/`; a kit-only script's tests go in `tests/kit_dev/`. A `Depends-on` is declared for a shared file and for a logical dependence (a build that reads what another one makes) alike; builds with neither run in parallel.
    - (a) **The standard** (rules 1 and 2, the old-format theme): `kit/templates/design-standard.css`, `kit/templates/design-patterns.md`, `kit/templates/design-theme.md`, `scripts/agk/design_standard.py` (new, installed), `scripts/agk/check_design.py`, `kit/manifest.json`, `tests/kit/test_design_standard.py`. No dependence.

## Tests

Fixtures in `tmp_path` and saved copies only: no network, no model, invented data.

- Rules 1 and 2: an old-format theme and its mockup folder are checked exactly as before, and its five tokens map to the five roles unchanged in value when it moves; the standard has every colour role in light and dark, the scales, the reduced-motion rule and the breakpoints, every pattern has its seven states, and its own tokens pass 4.5:1 and 3:1; a theme that overrides the brand colours, the fonts, density and alignment passes, and one that sets a spacing token or a rule of the standard fails naming the rule and never the value; REQ-044 AC1.
- Rule 3: the skeleton written from fixture requirements and specs has one section per requirement with its slots empty, and fails the check until filled; a filled fixture inventory maps each requirement to screens or to `no screen:`, and each screen to its flow and states; an empty slot, a requirement left out and a missing state fail naming the rule and the screen, and the prototype command refuses an inventory whose digest has no `inventory` row; REQ-044 AC2.
- Rules 4 to 6: a prototype written from a fixture inventory has one page for each screen and state, a state bar of plain links, `demo.md` with one sentence per step, the runtime file unchanged and data only from the fixture set; the runtime's text has none of the request names of rule 5; REQ-044 AC3.
- Rules 5, 7 and 8: one fixture version that passes, and one for each failure of rule 7 (a missing state, a broken link, an inline script, an edited runtime, an unknown runtime hash, a colour outside the tokens, a low contrast in dark only, a placeholder, an email outside the fixture set, a control without a label, a skipped heading, a fixed width), each failing naming the rule and the screen and never the value; a reflow without a browser reads `not run`; a prototype page that links `standard.css` and `theme.css` of its folder passes, and one that links another stylesheet fails; a mockup folder with a script or a `link` still fails and one without passes as before; `/agk:design <name>` refuses to write a new mockup folder; REQ-044 AC4.
- Rules 3, 9, 10 and 12: a `signoffs.md` row with an `Approve: design` or `Approve: inventory` line by a listed account on the head it names counts, inside a solo-mode `Confirmed:` comment too, and a row with a line by an unlisted account, on another head or with no line does not, and no check writes a file; the digest of a fixture folder is stable and one changed byte changes it; a signed-off version with a changed, added or removed file fails naming the version; a theme whose evidence line points to a version without its row reads `not approved yet`; a UI brief without `Screens:`, with an unknown version or with an unknown screen is refused, and a brief whose `Touches:` matches no `ui_paths` glob is not a UI brief; REQ-044 AC5.
- Rules 8 and 11: a rendered fixture screen equal to the frozen page reads `match`, one with a heading changed reads `drift: structure`, one with a token changed reads `drift: tokens`, the exit is 0 on drift, and without a browser the line reads `pixels: not run`; the text of the conductor's role file says the verdict names every screen and state that drifted; the text of the skill and of `design.py` says `screenshots/` is written only by `design.py screenshots`; REQ-044 AC6.

## Open questions

Each is a point the brief and the rulings leave open; the reading after it is the most conservative one, and the rules above apply it until a person rules.

- Q-S0037-1: which breakpoints? Reading: six, 360, 600, 900, 1200 and 1440 px, from phone to wide desktop, set in the standard and not by a project (rule 1).
- Q-S0037-2: may a project change alignment as well as density? The outcome of #365 says "its density and alignment", part 1 says "the theme block and density". Reading: both, as two settings of one layout block with a fixed list of values each, and nothing else (rule 2).
- Q-S0037-3: how does the person agree the inventory? Reading: by a comment `Approve: inventory <full head ID>` by an account in `spec_approvers` on the inventory's pull request, recorded as an `inventory` row with the digest of `inventory.md`, because a line written into the file cannot be tied to an account (rules 3 and 9).
- Q-S0037-4: how is a version named? Reading: `v1`, `v2` and so on, the next free number, never a date or a name chosen by the session (rule 4).
- Q-S0037-5: where is the runtime's hash held? Reading: as a list of released hashes inside the installed `check_design.py` (or its installed module), with a test that the kit's file has the newest one, because `kit/hashes.json` is a release file that a build never edits (session rule 14) and an installed check cannot read the kit (rule 5).
