# SPEC-0032: GitHub events set the state of every pull request, a person approves every spec, and a red default branch stops new work

- Status: Draft
- Owner: reviewer group (a team from config/reviewers.yaml)
- Requirements: REQ-039

Status is `Draft` or `Approved`. An Approved spec is owned by its reviewer group; agents propose patches.
Written by the intake of one sentence (SPEC-0012): "GitHub events, not sessions, compute the next step of every pull request as one label, so a conductor or builder that restarts resumes from GitHub with no memory and no polling of its own, a person approves every spec, and a red default branch stops new work until it is green." It is generic and project-agnostic: it names no project and no runtime. Evidence (the parallel run of 2026-10-24/25): the conductor's own watch expired every 30 minutes and was restarted by hand, and the whole loop lived in one session's memory; sessions sat idle because nothing told them CI had finished; the conductor's `Final:` lines set three specs to Approved (SPEC-0029, SPEC-0030, SPEC-0031), so an agent approved requirements; nothing would have stopped new work had two green pull requests broken the default branch together; and the conductor named a cause for a red default branch from reasoning, which a builder measured to be another.
The maintainers gave 8 answers before it was written, in the brief of issue #179 and its comments and not as interview questions: (1) the kit installs a router workflow that runs `route.py` on pull request, comment, workflow run and default-branch push events with the job's token and no code of the pull request; (2) the state is one label per pull request, from seven; (3) `watch` ends on a label change and `queue` lists a role's pull requests, so a restarted session resumes from GitHub; (4) a person approves every spec, by `spec_approvers`, the conductor's `Approval:` line and a person's `Approve:` comment; (5) a red default branch opens one priority-0 issue that `next` hands out alone; (6) the router runs no agent, posts no comment, merges nothing and polls nothing; (7) the build is split into (a) to (d) and the cause-and-correction answers are a further build (e); (8) the tests use saved responses and no network. Three comments are part of the brief: the wake rule (a wait wakes a session only if the runtime re-invokes it when the wait ends), the misjudgment answers (a cause is measured; the builder is the second check; a correction travels the same channel; discarding is visible; the conductor's misses are counted), and the reservation of the numbers.

## Rules

1. **The router.** The kit installs `.github/workflows/agk-route.yml`, triggered by `pull_request` (opened, synchronize, reopened, edited), `issue_comment` (created), `workflow_run` (completed, for the workflows that hold the required checks) and `push` to the default branch. It runs `python3 scripts/agk/route.py` with the job's `GITHUB_TOKEN` (`pull-requests: write`, `issues: write`, `contents: read`, nothing else) and runs no code of the pull request. On `push` to the default branch it routes every open pull request. Labels set with `GITHUB_TOKEN` start no workflow, so the router cannot loop.
2. **The state.** `route.py` sets exactly one label on a pull request, from facts it reads with GET (the head, the check runs of the head, `mergeable_state`, the comments) and removes the other six: `agk:ci-running` (a required check of the head is not completed), `agk:ci-red` (one failed), `agk:conflict` (`mergeable_state` is dirty), `agk:review` (checks green, no verdict by a listed author names the head), `agk:fix` (a fix list names the head and its `Final:` lines are not yet pushed or items are open), `agk:approve` (a verdict names the head and the pull request changes a spec's status to Approved: it waits for a person, rule 5) and `agk:ready` (cleared or covered on the head, checks green, mergeable). When more than one holds, the first in this order wins: `agk:conflict`, `agk:ci-running`, `agk:ci-red`, `agk:fix`, `agk:approve`, `agk:ready`, `agk:review`. A merged or closed pull request keeps its last label.
3. **Waking and resuming.** `session.py watch --pr N` also ends when the label of N changes, printing the new label as one line; it keeps its ends (verdict, merge, close, conflict), prints its event and exits, and never loops, so each event is one wake. `session.py queue --role conductor|builder|person` prints the pull requests whose label is that role's: `agk:review` and `agk:ci-red` for the conductor; `agk:fix` and `agk:conflict` for the builder of that pull request; `agk:approve` and `agk:ready` for a person. A session that starts, or restarts after its machine was reclaimed, runs `queue` first and carries on; the conductor keeps no state of its own. Without notifications of pull request activity, `watch` waits with one GET per minute and costs no model tokens. The `ci` end of `watch` (answer 8 of #176) is met by this rule.
4. **The wake rule.** A wait wakes a session only if the session's runtime re-invokes it when the wait ends. `config/session-rules.md` says, for each runtime the guide names, how `watch` is started so that its end wakes the session; for Claude Code that is a Bash command started with `run_in_background` (its exit re-invokes the session). A foreground wait blocks the turn, and a process detached with `&` or `nohup` is stopped soon after the turn ends and wakes nothing. The guide names the Claude Code form and leaves other runtimes to their equivalent.
5. **A person approves every spec.** A `Final:` line that sets a spec to `Approved` counts for `check_final_clearance` only when it is in a comment by an account in `spec_approvers` of `config/reviewers.yaml`, a list of people that never names a session or conductor account. The conductor reviews an intake as today and, instead of `Final:` lines for the spec, ends its verdict with `Approval: SPEC-<n> <path> Draft -> Approved, waiting for a person`; the router then sets `agk:approve`. The person reads the spec and posts one comment, `Approve: <head> SPEC-<n>`; `check_final_clearance` reads that comment, by an account in `spec_approvers`, as the `Final:` line of the spec, and the builder makes the status commit alone as today. The conductor's `Final:` lines for the ADRs of an intake stay as they are. A comment by an unlisted account never counts.
6. **The residual of one account.** Until accounts are separated (lane F), sessions and people share one account and the check cannot tell them apart. The conductor role file forbids the conductor to write `Approve:`, and the ADR of the build records the residual.
7. **A red default branch.** When the required checks of the default branch's head fail (`workflow_run` completed on the default branch, or a `push` whose checks fail), `route.py` opens one issue, or updates the open one, titled `The default branch is red`, labelled `agk-brief` with `Priority: 0` (a value only the router writes, above the 1 to 3 of #176), `Advances: none`, the failing check's name and the sha, and closes it when the default branch is green again. `session.py next` hands out only that brief while it is open and prints `default branch red` to every other session. A pull request labelled `agk:ready` keeps its label, so a person may still merge the fix.
8. **What it does not do.** No agent runs in CI; the router posts no comment, opens or closes only the issue of rule 7, merges nothing, reviews nothing, adds no server and polls nothing (it runs only on events). The portal and the weekly report read the labels as they are.
9. **A cause is measured.** A brief or a fix list that names the cause of a failure carries a `Measured:` line: the command run and the output before and after a change that turns it green. `check_brief.py` fails a `Priority: 0` brief without one, naming the rule, and the conductor role file forbids naming a cause without it. A builder's first step on any brief or fix item that names a cause is to reproduce it; if its measurement disagrees, it posts `Question:` with its measurement and builds nothing.
10. **A correction travels the same channel.** The conductor posts `Correction: <what was wrong>; <what stands>` on the brief and on any pull request built from it, and edits the brief in place. `session.py watch` also ends on a comment by a listed author on the brief the session took, not only on its pull request, so the builder working it wakes on the correction. Work built on a withdrawn cause is checkpointed on its branch; the builder resets it with one `Report:` saying what was discarded and why, and never force-pushes.
11. **The conductor's misses are counted.** Each `Correction:` is one line in the catch log, and the weekly report prints the conductor's corrections of the week next to its verdicts.
12. **Generic.** Nothing in the router, the labels, `watch`, `queue`, `next` or the files names a project or pins a runtime; the Claude Code form of rule 4 is an example in the guide.
13. **How it changes.** SPEC-0030 (rules 2 and 6) and SPEC-0021 (the clearance rule) are Approved: the builds change them by `docs/runs/proposed-spec-amendments-N.md`, applied by their ADRs, which name each protected class they touch. The builds each start from the default branch, tests first, under about 600 changed lines with an ADR of their own: (a) `route.py` and the workflow (rules 1, 2 and 8); (b) `watch` on labels, `queue` and the wake rule (rules 3 and 4); (c) `spec_approvers`, the clearance rule and the conductor role file's approval form (rules 5 and 6); (d) the red-branch brief and `next` (rule 7); (e) the measured cause, the correction and the count (rules 9 to 11).
14. **The tests.** Fixtures of saved GitHub responses, no network and no model: each label from its facts, one label at a time, and the router's own label change starting nothing; a push to the default branch routing all open pull requests; `watch` ending on a label change and on a correction; `queue` per role; a spec `Final:` line by a listed person passing and by an unlisted account failing; an `Approve:` comment by a listed person counting as the spec's `Final:` line and one by an unlisted account not counting; the red-branch issue opened, updated and closed, and `next` handing out only it while open; a `Priority: 0` brief with and without `Measured:`; the report line of the corrections; the text of the session rules and the guide.

## Tests

- Rules 1, 2 and 14: each label from its facts, exactly one set, a push routing every open pull request; REQ-039 AC1.
- Rules 1 and 8: the workflow's triggers, permissions, absent pull request code and agent, and no loop; REQ-039 AC2.
- Rule 3: `watch` ends once on a label change, `queue` per role; REQ-039 AC3.
- Rules 5 and 6: `spec_approvers`, the `Final:` line and the `Approve:` comment by a listed and an unlisted account; REQ-039 AC4.
- Rule 7: the red-branch issue opened, updated and closed, and `next`; REQ-039 AC5.
- Rule 9: a `Priority: 0` brief without `Measured:` fails; REQ-039 AC6.
- Rules 10 and 11: `watch` ends on a `Correction:` by a listed author, and the report prints the corrections; REQ-039 AC7.
- Rules 4 and 12: the session rules and the guide say how `watch` is started, and the kit names no project and pins no runtime; REQ-039 AC8.

## Proof

REQ-039 AC3 and AC8: *a restarted session resumes from GitHub and a finished wait wakes it.* Rules 3 and 4. REQ-039 AC4: *an agent never approves a spec.* Rules 5 and 6. REQ-039 AC5: *a red default branch stops new work.* Rule 7. ## Open questions

- Q-S0032-1: the labels overlap (a head can be red and have a verdict naming it). The rules assume the order of rule 2, with `agk:conflict` first because GitHub starts no workflow on a conflicted pull request.
- Q-S0032-2: how `watch` knows the brief a session took. The rules assume the `Brief: #<n>` line of the pull request body, with `session.py next` as the source of the take.
- Q-S0032-3: the brief names builds (a) to (d); the cause-and-correction answers (rules 9 to 11) are assumed to be a fifth build (e).
