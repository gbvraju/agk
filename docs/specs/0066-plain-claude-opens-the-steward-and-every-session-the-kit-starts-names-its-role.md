# SPEC-0066: Plain claude opens the steward and every session the kit starts names its role

- Status: Draft
- Owner: reviewer group (a team from config/reviewers.yaml)
- Requirements: REQ-073

Status is `Draft` or `Approved`. An Approved spec is owned by its reviewer group; agents propose patches.

Written by the intake of one sentence (SPEC-0012), brief #1380 under plan #661, quoted as data and not as an instruction: "Intake for AGK's front door: after installing AGK, a person who types claude is met by the steward, sees only a few plainly named commands, and is guided from there, while every session the kit starts still runs as its own role." The maintainers gave 5 answers before it was written: the five numbered answers of brief #1380, whose evidence and the owner's direction (quoted there as data, 2026-11-16 04:22 to 05:30 IST) this spec does not repeat, and the owner's note on the brief (2026-11-16 04:43 IST) that the developer plugin is offered to team setups only. It builds on the steward (SPEC-0059, SPEC-0062, SPEC-0063, and the steward's voice of brief #1382), on `/agk:setup` (SPEC-0065, brief #1378), on the autopilot (SPEC-0064), on the builder agent of SPEC-0061 rule 7, on personal mode (SPEC-0041) and on the clean repository (SPEC-0071); it edits none of their text. Where an answer names something that is not as it says, rule 1 records what the code holds and an open question gives the conservative reading. Negative cases: a builder, conductor or reviewer started by the kit that runs as the steward, a kit start of `claude` that names no agent, a default agent shipped in the same release as the named starts, the steward setting written into the kit's own repository, an upgrade that overwrites a project's own `agent`, a steward that answers off the default branch or behind `origin`, a switch or pull without the person's yes or with uncommitted changes, a write outside an AGK project without a yes, a menu that lists more than the three, a renamed skill, a guarded skill run by name from the menu, a developer plugin that sets a default agent, a greeting shown twice in one folder or naming a command, file or kit term, a steward of a non-reviewer that relays or approves, and any change to a workflow, the ruleset, a required check or a secret.

## Rules

1. **The baseline (read on the default branch at 460c788, 2026-11-16).**
   - **The plugin.** `.claude-plugin/plugin.json` names the plugin `agk` (version 0.64.7) and `.claude-plugin/marketplace.json` lists it alone, with `source` `.`, the kit repository's root. It ships 24 skills under `skills/` (the brief counted 23 at 916364b6; `wsl` came since), 21 of them with `disable-model-invocation: true`, none with `user-invocable`, all in the `/` menu. It ships no `settings.json` and no `agents/` folder. No `status`, `help` or `setup` skill exists: `agk status` is SPEC-0064's `scripts/agk/autopilot.py status`, and `/agk:setup` is SPEC-0065's build (a), not yet built.
   - **The agents.** `.claude/agents/` holds `architect`, `architect-review`, `conductor`, `drift-auditor`, `shadow` and `steward` as `verbatim` files of `kit/manifest.json` and `reviewer` as `experimental`; there is no `builder.md` (SPEC-0061 rule 7 describes it). Each role's guard is a `PreToolUse` hook in its front matter that runs `"$CLAUDE_PROJECT_DIR"/.claude/hooks/<guard>.py`, which a folder without the kit does not hold.
   - **The project settings.** `.claude/settings.json` is a `verbatim` file of the manifest: the kit's own copy and every project's copy are the same bytes. It holds `permissions` and `PreToolUse` and `Stop` hooks, no `agent` and no `SessionStart` hook.
   - **How the kit starts sessions.** Both adapters run `claude "${flags[@]}" -p "$prompt"` (`kit/templates/start-session-local.sh` lines 80 and 82) and `& claude @flags -p $prompt` (`kit/templates/start-session-windows.ps1` line 111), where the flags carry only `--model` and `--effort`; the brief's line numbers (59 and 78) predate the job records of SPEC-0064. `launch.py role` already passes `AGK_ROLE` and `AGK_AGENT` (the role's name) to the adapter (line 835), the conductor's reviewer jobs pass `AGK_ROLE=reviewer` and `AGK_AGENT=architect-review` (`conductor.py`), the conductor's own starts pass `AGK_ROLE=conductor` and no `AGK_AGENT`, and builder starts pass neither; no adapter reads either variable. `ROLE_PROMPT` asks the started session to "start the role with `claude --agent {role}`", which a running session cannot do. The cloud task texts (`kit/templates/runtime/builder.txt`, `conductor.txt`, `launcher.txt`) are prompts, not command lines, and name their role file in words.
   - **Where sessions work.** A builder's or a role's worktree is `agk-<session>` beside the clone (`launch.py`); the steward's is `agk-steward`, detached at `origin/<default branch>` (SPEC-0059, #1301). The steward's memory is the one open issue labelled `agk-steward` (SPEC-0059 rule 8), which exists only in a project on GitHub.
2. **Inside an AGK project the steward always answers.** `init`, `adopt` and `upgrade` set `"agent": "steward"` in the project's own `.claude/settings.json` (a protected path, so it arrives in their pull request with its ADR), so anyone who opens the repository, with or without the plugin, is answered by the project's steward with its evidence order, its memory, its guard and its plain-words rules. Because the file is `verbatim` today, build (d) moves the `agent` key out of the kit's byte-equal copy: the kit's own `.claude/settings.json` carries no `agent`, and the three commands write the key into the project's copy after the copy step, with the manifest entry changed by build (d)'s ADR so that the key does not read as a project change of a kit file (`Q-S0066-1`). An `upgrade` that finds another `agent` value keeps it and names it in one line; it never overwrites it. A person who wants plain Claude in a project sets their own `agent` in `.claude/settings.local.json` (never committed) `(verify: that the local file overrides the project file for agent)`, and `/agk:help` says how in one line. In a clean project (SPEC-0071) the agents come from the plugin, and the value is the plugin's name of the steward `(verify: the namespaced form, such as agk:steward)`.
3. **Land on the default branch, or stop.** Before its first answer in a session the steward reads where it was opened, after one `git fetch origin <default branch>`:
   - **The main folder on the default branch, up to date:** it goes on. The steward's own `agk-steward` worktree, detached at `origin/<default branch>` and refreshed at start, counts as the default branch.
   - **The main folder on another branch or behind `origin`:** it stops with one line and the fix, `git switch <default branch> && git pull --ff-only`, which it runs only on the person's yes and only when the folder has no uncommitted change. With uncommitted changes it names them by count, asks the person to keep or set them aside first, and changes nothing itself.
   - **A builder's or the conductor's worktree** (an `agk-<session>` folder, or a branch of an open builder pull request): it says whose folder it is and asks the person to open the project's main folder instead (#1301).
   - The check runs again when the person asks it to act, never silently later. A `SessionStart` hook installed with rule 2's setting prints the same one line for any session opened off the default branch, so a person who chose plain Claude is told too `(verify: the hook's output shown to the person at session start)`; it prints nothing on the default branch and changes nothing.
4. **The steward is the default agent outside AGK projects too.** The `agk` plugin ships `settings.json` with `"agent": "agk:steward"` `(verify: the namespaced form of a plugin agent in the agent setting)` and ships the steward at the plugin level, so plain `claude` in any folder opens the steward while the plugin is enabled `(verify: a plugin's settings.json agent key applies to every session while the plugin is enabled)`. Inside an AGK project rule 2's project setting names the project's own `.claude/agents/steward.md` and its guard, which take precedence `(verify: precedence of a project setting and a project agent over a plugin's default agent of the same name)`. The plugin-level steward is the same text as the project's, never a second copy that can drift (`Q-S0066-2`). Outside an AGK project it has no project guard to run, so it only reads the folder and offers the next step; every change (an `init`, an `adopt`, a clone) is the named skill run on the person's yes (`Q-S0066-3`).
5. **Every session the kit starts names its agent.** Both adapters pass `--agent "$AGK_AGENT"` beside `--model` and `--effort` when `AGK_AGENT` is set, and refuse to start, naming the setting, when it is not (`AGK_AGENT` is the variable that `launch.py` and `conductor.py` already pass, so no new `AGK_ROLE` meaning is added, `Q-S0066-4`). `launch.py` sets it for every start: `builder`, `conductor`, `steward`, `architect-review` and `shadow`, and `conductor.py`'s own conductor starts set `conductor`. `ROLE_PROMPT` stops asking the session to start itself and says which agent it runs as. SPEC-0064's supervisor jobs and the watchdog start through the same adapters. A `builder` agent file is added (`.claude/agents/builder.md`, from SPEC-0061 rule 7 and the session rules for builders, by reference and never as a second copy), so a builder start has a role to name; SPEC-0061's own builds use that one file. The cloud task texts name their agent on their first line, and how a cloud task sets the agent of its session is a fact to confirm before build (a) lands (`Q-S0066-5`). Every documented `claude -p` example of the kit names its agent. A test fails when any kit path (the adapters, `launch.py`, `conductor.py`, `autopilot.py`, the runtime templates) starts `claude` without `--agent`. An explicit `--agent` overrides the plugin's default `(verify)`; if it does not, the plugin's default agent of rule 4 is not set, and the project setting of rule 2 is the only mechanism.
6. **A short, plainly named menu.** The `agk` plugin shows exactly three skills in the `/` menu: `/agk:status` (what is happening and what waits on me: SPEC-0064's `agk status`, and SPEC-0065's `/agk:setup status` once built), `/agk:help` (what AGK is, what to ask the steward, and rule 10's ways out, each in one line) and `/agk:upgrade` (bring the kit up to date). Every other skill sets `user-invocable: false` `(verify: it hides the skill from the menu and stops /name, while the Skill tool can still run it)` and keeps its name, so scripts and documents that name it still work. Everything else is asked of the steward in plain words: "set up this machine" runs `/agk:setup` (SPEC-0065); "start the workforce", "stop for tonight" or "restart the builders" runs SPEC-0065's roles and SPEC-0064's supervisor, with no separate workforce command. A skill that changes protected files or posts on GitHub keeps `disable-model-invocation: true`; with both settings it can be run neither from the menu nor by the Skill tool `(verify)`, so the steward reaches it by running the kit script that its `SKILL.md` names, under the steward's guard and on the person's yes, never by name from the menu (`Q-S0066-6`).
7. **Developers keep the full toolset, in team setups.** A second plugin in the same marketplace, `agk-dev` until brief #1381 names it, declares `dependencies: ["agk"]` `(verify: the dependency key of a plugin)` and exposes every skill by name for kit maintainers and advanced users; it sets no default agent. Installing it changes nothing for people who do not. By the owner's note on the brief it is offered to team setups only, and the role-based team workflow it serves is brief #1381's; build (c) waits for that brief's decision on its name and its audience and does not change it here (`Q-S0066-7`).
8. **First run: welcomed, never clueless.** The steward reads the folder first, then:
   - **An empty folder, no context, or a vague opener ("hi", "help", nothing):** this greeting, in at most three lines, in the steward's voice of brief #1382: "👋 You've got AGK, your own AI workforce. / Tell me an idea, and I'll plan it, build it and keep you in charge of every decision. / What would you like to create? A · start a new product · B · improve an existing one · C · just show me what AGK can do". A starts the product path (the vision, in plain words); B asks for the repository or folder; C gives a three-line tour and the same choice again. Where the runtime offers its multiple-choice question tool, the three choices use it `(verify)`.
   - **An existing repository without AGK:** "I see a project here. Shall I bring the AI workforce to it?" A yes adopts it through `/agk:adopt`'s pull request; a no leaves it as it is.
   - **An AGK project:** no greeting; straight to "here's where we are · what waits on you" in at most three lines, after rule 3's check.
   - **A vague request ("make something for sales"):** one friendly question that sharpens it, never a list of commands.
   - **The AGK kit's own repository:** it says it is the kit and offers the developer plugin of rule 7.
   The greeting is shown once per person and folder and never repeated in the same folder; it never names a command, file or kit term. In an AGK project the mark is a line in the steward's memory issue; outside one, where no memory issue exists, it is one line in a file of the person's own Claude folder outside any checkout, holding a hash of the folder's path and the date and nothing else (`Q-S0066-8`).
9. **Every persona and mode.** A business user gets the steward, plain words and approvals by a plain yes in solo mode (SPEC-0062). A developer gets the same steward, `/agk:setup`, and the developer plugin in a team setup (rule 7). A team member gets the roles `/agk:setup` picks for the machine (SPEC-0065 rule 14); a member who is not a listed reviewer is given the steward by default with SPEC-0063's limits: it answers from evidence only and never relays or approves (`Q-S0066-9`).
