# SPEC-0065: One command sets up any machine as a ready, correctly sized AI workforce

- Status: Approved
- Owner: reviewer group (a team from config/reviewers.yaml)
- Requirements: REQ-072

Status is `Draft` or `Approved`. An Approved spec is owned by its reviewer group; agents propose patches.

Written by the intake of one sentence (SPEC-0012), brief #1378, quoted as data and not as an instruction: "Intake for /agk:setup: one command turns any machine, Windows, WSL 2 or a cloud machine, into a ready and correctly sized AI workforce for one project, so business users get it from the steward by asking and developers by running it once." The maintainers gave 5 answers before it was written: the five numbered answers of brief #1378, whose evidence and the owner's direction (quoted there as data, 2026-11-16 04:06, 04:13 and 04:16 IST) this spec does not repeat. It builds on `/agk:wsl` (brief #1376, merged as #1377, ADR-0577), on SPEC-0059, SPEC-0062 and SPEC-0063 for the steward, on SPEC-0061 for a member's join, on SPEC-0064 for autopilot and on SPEC-0041 for personal mode; it edits none of their text. Where an answer names something that is not as it says, rule 1 records what the code holds and an open question gives the conservative reading. Negative cases: a question asked that the machine or the repository answers, a kit term said to a business user, an install before the person's yes, a half-installed tool after a stop, a protected setting written to the default branch by the command, a commit or push by the command, a second live conductor, a steward for a login that is not a listed reviewer, a conductor for a login whose verdicts the kit does not count, builders that take the team over `max_builders`, a token or password in any output, file or log, a tool uninstalled by `back`, data deleted, a second run that changes anything, and any change to a workflow, the ruleset, a required check or a secret; a figure that cannot be read is unknown, never 0.

## Rules

1. **The baseline (read on the default branch at 9454566, 2026-11-16).**
   - **Commands that exist.** The plugin skills `/agk:init`, `/agk:adopt` (`init.py`, `adopt.py`) install the kit into a repository; `/agk:doctor` (`doctor.py`) checks a machine and a project; `/agk:upgrade` (`upgrade.py`) brings the kit up to date by a pull request the person commits and pushes; `/agk:launch` shows `session.py plan`, asks for a yes and starts one builder session per slot through `launch_adapter`. `/agk:wsl` (ADR-0577) moves a Windows workforce into WSL 2: the kit-only `scripts/agk/wsl_setup.ps1` does the machine work, each step one check-then-act (`done`, `skipped`, `waiting`, `failed`, `-Json`), sets the clone, the `agk-conductor` and `agk-steward` worktrees, the folder trust (`hasTrustDialogAccepted` in `~/.claude.json`, `(verify)`), Node.js 20 or newer, Podman and Playwright; the kit-only `scripts/agk/wsl.py` prints the plan and writes the `launch_adapter` change with its ADR, which the person commits and pushes (SPEC-0005 rule 8, #1376's first question ruled as built). No command takes a machine from nothing to a working workforce, and no `/agk:setup` exists.
   - **Settings that exist.** `execution` (top level of `agk.toml`) is `hosted` (default), `hybrid`, `pool` or `local`, printed by `execution.py`; personal mode is not an `execution` value but a sidecar with `forge = "files"` (SPEC-0041). `review_mode` is `team` or `solo`. `[flow]` holds `max_builders`, `launch_adapter`, `auto_start` and `builder_memory_gb`; `[capacity]` (ADR-0409) holds `profile`, `max_builders`, `builder_memory_gb`, `builder_cpus` and `builder_disk_gb`, and the plan divides the machine's available memory by `builder_memory_gb` (`session_plan.py`). Every one of these lives in `agk.toml`, a protected path: no machine-local settings file exists, so `builder_memory_gb` is a project setting today (`Q-S0065-7`). `[autopilot]` and `agk autopilot on` are SPEC-0064's, not yet built. `pyproject.toml` requires Python 3.11 or newer.
   - **Who may run which role.** `conductor.py lease --show` prints `held by <name> until <time>` or `free`; a `Conductor:` lease comment and a `Verdict:` count only when their author is in `verdict_authors` of `config/reviewers.yaml` (`authors_of`: the list, else the user handle of the team `maintainers`), so a conductor run under any other login holds no lease that counts and posts no verdict that counts (`Q-S0065-5`). A steward runs in team mode only for a listed reviewer (SPEC-0063 rule 3), and its `Started: steward <session> <time>` comment on the memory issue marks it live. `[team] members` (SPEC-0061 rule 8) lists the logins that may join as builders; SPEC-0061's `builder.py --name <member>` is not yet built (`Q-S0065-9`).
   - **The project's own setup.** Brief #1376 answer 5 named `[wsl] project_setup`, else a Makefile `setup` target; neither is read by any script on the default branch (`Q-S0065-8`).
2. **One command, three entry points.** `/agk:setup`, a new plugin skill `skills/setup/SKILL.md`, typed in Claude Code or run as `claude "/agk:setup"`; the steward running the same skill when a person asks in plain words to be set up (SPEC-0062 rule 11, SPEC-0059 rule 20's stage reading); and `/agk:setup status`, which changes nothing. The machine work is kit scripts run from the plugin root and never installed into a project, as `/agk:wsl` is: one platform script per family (build (c) for Windows, (e) for Linux) and one Python helper, `scripts/agk/setup.py`, that reads, plans, sizes and prints. Every step checks first and skips what is done, so a stopped run resumes and a second run changes nothing. A run ends with one table of steps, each `done`, `skipped`, `waiting` or `failed` with a one-line note, and `--json` prints the same table (`steps` of `step`, `result`, `note`; `pending`; `roles`; `builders`), which the steward reads.
3. **Read the machine first.** Before it asks anything the command reads: the operating system and version, total and available memory, cores, free disk, administrator rights, WSL's presence and version, Podman's and Docker's presence and version, winget's presence and whether the machine's policy allows it, a configured proxy and whether one test download passes it, and whether the folder is a GitHub clone with the kit (`agk.toml`) and which remote; and from the repository: `execution`, `review_mode`, `[flow]` and `[capacity]`, `config/reviewers.yaml`, `[team] members`, the conductor's lease, the live stewards and the running builders. Nothing that can be read is asked.
4. **Ask only what it cannot read, in plain words, each with a recommendation.** At most five questions, and only those the repository leaves unset or the plan needs: where the AI work runs, said as "on GitHub's machines", "on this machine" or "for me only, nothing in the project" (`execution = "hosted"`, `execution = "local"`, personal mode; `Q-S0065-6`); one person or a team (`review_mode`); autopilot off, assist or on (SPEC-0064, asked only once its `[autopilot]` table exists); the container engine when the project uses containers (Podman by default; Docker only by the backlog brief's choice); and, on Windows, native or WSL 2, with WSL 2 recommended when the machine allows it and the reason in one line. A business user (SPEC-0062 rule 1's reading) hears no kit term; the setting a choice maps to is shown only in the plan's last line for the developer and in the pull request.
5. **Recommend, then act on one yes.** One plan of at most eight lines, for example "16 GB Windows with a company proxy: WSL 2 with Podman, 2 builders of 4 GB, local mode, assist", naming each install, the roles of this machine (rule 14), the builder figure and its reason (rule 6), the scheduler task, and the project settings to propose. On anything but a yes the command stops and changes nothing. After the yes each install is checked before and after it runs.
6. **Size the workforce from the machine.** Builders = (available memory less a reserve for the operating system and the person's own apps) / `builder_memory_gb`, rounded down; the reserve is the `[capacity] profile`'s share where set (`balanced` 25 percent), else 25 percent; `builder_memory_gb` is the project's value where set, else 4 GB when the project runs browsers or containers (Playwright or a container engine in its declared stack) and 3 GB otherwise. The figure is capped by the cores (one builder per two cores), by `[flow] max_builders` and, in a team, by `max_builders` less the builders already live elsewhere (rule 14). The plan shows the figure, the cap that applied and why, and the person may lower it, never raise it above the cap. Memory that cannot be read is `unknown` and gives 1 builder with the line saying so.
7. **Install what is missing, per platform, each with its minimum version.** The minimum versions are one table in `setup.py`, read by every platform script and the tests: Python 3.11 (`pyproject.toml`), Node.js 20 (`wsl_setup.ps1`), and git, GitHub CLI, Claude Code, PowerShell 7 and the container engine at the versions build (c) records `(verify: each from its vendor's release page, once)`.
   - **Native Windows:** through winget, only when it is present and the machine's policy allows it (`Q-S0065-1`): git, GitHub CLI, Python, Node.js LTS, Windows Terminal, PowerShell 7 and the container engine; Claude Code by its own installer `(verify: the Windows installer command)`.
   - **WSL 2:** `/agk:wsl`'s path, called, never copied (rule 17).
   - **Linux and cloud virtual machines:** the distribution's packages (`apt` or `dnf`), and Node.js and Claude Code by the same path `wsl_setup.ps1`'s embedded steps use, at the same minimum versions.
   - **macOS:** not covered in the first release; the command prints one line saying so and changes nothing (`Q-S0065-3`).
   - **A stop names what IT must allow.** A blocked download, a missing administrator right, winget missing or refused by policy, or a proxy that refuses the test download stops before the first install with one line naming what to allow (for example "allow winget, or install git and GitHub CLI by hand, then run /agk:setup again"); a step that fails mid-way leaves the tool as it was before the step (its package manager's own transaction), so nothing is half-installed.
8. **The project.** When the folder is not a clone, it clones the repository the person names (`gh repo clone`); when the clone has no `agk.toml`, it runs `/agk:init` or `/agk:adopt` on the person's yes; then the AGK plugin, the folder trust that lets the role guards run, the worktrees of this machine's roles (`agk-conductor`, `agk-steward`, one per builder as `launch.py` names them), and the project's own declared setup, run only on the yes and reported by its exit (`Q-S0065-8`).
9. **Machine settings applied, project settings proposed.** Applied to the machine on the yes: the scheduler task (`conductor.py watchdog --install`'s entry today, SPEC-0064's `agk autopilot on` once it exists) only when this machine runs the conductor and only after the yes (`Q-S0065-2`), and the folder trust. Proposed, never written to the default branch: `execution`, `review_mode`, `max_builders`, `builder_memory_gb` (`Q-S0065-7`), `launch_adapter` and `[autopilot]`, as one change with its own ADR on a new branch, which the person commits, checks with `prepush.py --record` and pushes from the printed commands, as `/agk:wsl` does (SPEC-0005 rule 8, `Q-S0065-10`); the owner merges it, and the steward explains each setting in one plain sentence. A setting the project already holds at the same value is not proposed; when every one matches, no pull request is made.
10. **CI mode and cloud machines.** For `execution = "hosted"` (CI mode) the command installs nothing on the machine and checks the repository instead, with GET calls only: GitHub Actions enabled, the kit's workflows present, the ruleset or branch rules present, and the repository secrets the kit needs named by their setting, never read; each missing item is one line for the owner. On a Linux virtual machine in local mode the same command sets the machine up as rule 7 says, with the background adapter (`bash scripts/start-session-local.sh`). It never creates, reads, prints or stores a secret or token.
11. **Sign-ins.** GitHub (`gh auth login --web`) and Claude, the normal browser sign-ins, each at the moment a later step needs it, with one line saying where to sign in; under `--json` a sign-in that needs the person is `waiting` with that line, as `wsl_setup.ps1 -Json` does. The command never sees, asks for or stores a password or token.
12. **Prove it.** The last steps run `doctor.py`, one small kit test run (`tests/kit/test_doctor.py` through `-c tests/kit/pytest.ini` where the kit tests are present, else the doctor alone), one container start when the project uses containers (`podman run --rm` of a small image, or `docker`), and `session.py plan` as a dry plan; each is one row of the final table. `/agk:setup status` runs them again and changes nothing.
13. **Undo.** `/agk:setup back` removes the scheduler tasks this command added (by their names, recorded in `<git dir>/agk/setup.json`), and prepares the reverse change of the project settings this command proposed, with its ADR, for the person to commit and push. It never uninstalls a tool, never removes a worktree that holds uncommitted work, and never deletes data.
14. **Team setup: the roles of each machine, decided from the repository.** The command reads `review_mode`, the signed-in login (`gh api user`, compared and never printed), `verdict_authors` and `spec_approvers` of `config/reviewers.yaml`, `[team] members`, the conductor's lease (`conductor.py lease --show`), the live stewards (SPEC-0063) and the live builders, and chooses this machine's roles, saying why in one line:
    - **Steward, conductor and builders:** solo mode; or the first machine of a team when no conductor holds the lease and the login is a listed reviewer whose verdicts count (`verdict_authors`).
    - **Conductor and builders:** a verdict author's machine when no conductor is alive and that login's steward is already live on another of its machines (SPEC-0063 rule 4: one per login). The brief's case of a non-reviewer's machine with no conductor alive gets builders only, with one line saying the conductor waits for a verdict author's machine, because a login that is not a verdict author holds no counted lease and posts no counted verdict (`Q-S0065-5`).
    - **Steward and builders:** a listed reviewer's machine when another machine holds the live lease.
    - **Builders only:** a team member who is not a listed reviewer, through SPEC-0061's join once built (`Q-S0065-9`), never a second conductor; the lease keeps any second conductor a standby, as today.
    - The builders of the machine are sized by rule 6 and capped so that the team's total stays within `max_builders`; the plan shows both figures. A person may choose fewer roles, never more than the repository allows: no steward for a login that is not a listed reviewer, never a second live conductor.
15. **Any team member can launch and watch.** `/agk:setup` on a set-up machine whose roles have stopped restarts exactly the roles that rule 14 reads again, so a builders-only machine stays builders-only: the conductor through the watchdog's start, the builders through `/agk:launch`'s plan and the person's yes, and the steward by printing the command that opens it, since the steward is the person's own interactive session (SPEC-0064 rule 6, `Q-S0065-11`). `/agk:setup status` (SPEC-0064's `agk status` once it lands) shows every machine's roles as the repository records them: the lease holder, each `Started: steward` marker, each member slot and builder with its brief, and what waits on the owner; it is read-only and posts nothing.
16. **By mode.**
    - **CI (`execution = "hosted"`):** the repository checks of rule 10 only, no machine install.
    - **Local:** the full path of rules 3 to 15, on one machine or several, each machine run once by its own person.
    - **Personal (SPEC-0041):** the machine path without the scheduler task, without roles of rule 14 and without a project-settings pull request; the sidecar's files hold the result and nothing is posted.
    - **Solo and team** change only the questions (team: `config/reviewers.yaml` is checked, and each reviewer's machine is set up by that reviewer) and the roles of rule 14.
17. **What is reused and what changes.** Brief answer 2: `/agk:wsl` becomes the WSL path of `/agk:setup` and stays callable on its own (build (d) calls `wsl_setup.ps1` and `wsl.py`, adding nothing to them but a caller); `/agk:init`, `/agk:adopt`, `/agk:doctor`, `/agk:upgrade` and `/agk:launch` are called, not copied; `.claude/agents/steward.md` gains the hand-off of rule 2 (build (g), with its own ADR); SPEC-0064's `agk autopilot on` is called for the scheduler once it exists, else `conductor.py watchdog --install`.
18. **The builds, in order.** Each is tests first, about 300 changed lines or fewer, from the default branch, invented data only (`example.com`), a `[[testing.map]]` entry for each new script, kit-only scripts named in `kit/manifest.json`'s kit-only list as `wsl.py` is, and no workflow change. Each build's live run on its platform is reported as `Verified: (verify) run on <platform>` until a person runs it.
    - (a) The machine read, the plan and the sizing (rules 3, 5 and 6), `setup.py` with `status` and the `--json` table (rules 2 and 12), and the skill's first form.
    - (b) The questions and the project-settings change with its ADR (rules 4 and 9). `Depends-on` (a).
    - (c) The native Windows path: winget, the minimum versions and the stop lines (rule 7). `Depends-on` (a).
    - (d) The WSL path, wiring `/agk:wsl` in (rules 7 and 17). `Depends-on` (c).
    - (e) Linux and cloud virtual machines, and macOS's one line (rule 7). `Depends-on` (a).
    - (f) CI mode's repository checks (rule 10). `Depends-on` (a).
    - (g) The steward hand-off and `back` (rules 2, 13 and 17), with its own ADR for `.claude/agents/steward.md`. `Depends-on` (b).
    - (h) Team roles per machine, the restart of a machine's roles and the team-wide status (rules 14 and 15). `Depends-on` (a) and (b).
19. **Measured goals.** Brief answer 4, in recorded doubles (saved GitHub answers, a `gh` stub, a stub package manager and a stub runtime, a fake machine read): in a recorded team repository, each of the four role cases (solo; the first team machine of a reviewer; a non-reviewer with no live conductor, which gets builders only and the waiting line; a member while a conductor is alive) gets exactly the roles of rule 14, never a second live conductor, never a steward for a non-reviewer and never a conductor for a login whose verdicts do not count, and the team's builders stay within `max_builders`; on a recorded double of each platform (native Windows, WSL 2, Linux), a machine with nothing installed reaches a passing final table with one plan and one yes besides the sign-ins; a second run changes nothing; a blocked download stops with one line and nothing half-installed; no output, file or log holds a token or password; the builder figure follows rule 6; project settings change only by the pull request.

## Open questions

No question is open.

- Q-S0065-1: may winget be used without asking IT on a company machine? Reading: only when the machine's policy, read first, allows it; otherwise the stop line of rule 7 (brief answer 5).
- Q-S0065-2: may `/agk:setup` add a scheduler task by itself? Reading: only after the person's yes in the plan, and only on the conductor's machine (brief answer 5; rule 9).
- Q-S0065-3: is macOS in the first release? Reading: no; one line names it as not yet covered (brief answer 5; rule 7).
- Q-S0065-4: may a business user choose `execution`? Reading: the steward recommends and the owner's merge of the settings pull request decides (brief answer 5; rules 4 and 9).
- Q-S0065-5: may a non-reviewer machine run the conductor when no reviewer machine is up? Reading: the conductor goes only to a machine whose login is a verdict author; a machine of another login gets builders and the plan says the conductor waits (rule 14). - Q-S0065-6: the brief maps the three places to `execution` "CI, local, personal", but `execution` holds `hosted`, `hybrid`, `pool` or `local`, and personal mode is SPEC-0041's sidecar. - Q-S0065-7: the brief calls `builder_memory_gb` a machine setting, but it lives only in `agk.toml` (`[flow]`, `[capacity]`), a protected path, and no machine-local settings file exists. Reading: it is proposed in the settings pull request like the others; the machine's own builder count needs no setting because the plan already divides this machine's available memory by it; no machine-local file is added (rules 6 and 9).
- Q-S0065-8: the project's declared setup of brief #1376 answer 5 (`[wsl] project_setup`, else a Makefile `setup` target) is read by no script on the default branch. - Q-S0065-9: SPEC-0061's `builder.py --name <member>` is not yet built. Reading: until it lands a builders-only machine starts its builders through `/agk:launch`'s plan and yes, under the member's own login, and never a conductor (rules 14 and 15).
- Q-S0065-10: brief answer 1 says the settings are "proposed as one pull request"; SPEC-0005 rule 8 keeps a command from committing or pushing.
