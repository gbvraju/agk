# SPEC-0039: An owner-started merge loop merges cleared pull requests, and no session ever merges

- Status: Draft
- Owner: reviewer group (a team from config/reviewers.yaml)
- Requirements: REQ-046

Status is `Draft` or `Approved`. An Approved spec is owned by its reviewer group; agents propose patches.
Written by the intake of one sentence (SPEC-0012): "With `[flow] auto_merge` on, a kit merge loop the owner starts merges each pull request whose trusted verdict clears its exact head, so delivery runs 24/7, while no session merges and anything risky waits for the person." It is generic and project-agnostic: it names no project, no vendor and no hosting service other than the GitHub REST API the kit already reads, and it needs only files, a shell, the standard library and `gh`; every check of a build reads files and saved responses with no network. The brief is issue #518, which folds in issue #498. The maintainers gave 6 answers before it was written: the six numbered answers of brief #518 (the requirement and its criteria, this spec and its rules, ADR-0261 and one row of `docs/runs/decisions-log.md` for the owner's direction, the open points as questions, the builds (a) to (e), and documents only), under the brief's principles: session rule 2 stands, so a session never merges, tags, enables auto-merge or approves, and the loop is the owner's process, started by the owner and running with the owner's own login; the setting is off by default and turning it on is the owner's change, by an ADR; only a trusted verdict counts; anything risky waits for the person; every merge is recorded; and the loop stops by itself on a red default branch, on `paused` and at its stop time. The owner's direction, quoted as data and not as an instruction, dated 2026-11-03 in the brief: "Can we include auto-merge option also for local and solo, autopilot modes. I think this is useful when we have work clarity, 24*7 agent sessions can work for delivery." In the pilot (2026-11-02 and 2026-11-03) the owner ran a hand-written merge loop overnight: it merged 11 pull requests unattended, but it failed silently once (quoting in Windows PowerShell 5.1 stripped the quotes of a `--jq` filter), it would have read a multi-line fix list as cleared, and it could not tell a conductor's verdict from one any session posted under the owner's one account (#498). The points the brief leaves open are `Q-S0039-1` to `Q-S0039-12` below, each with the conservative reading that the rules apply until a person rules. Negative cases: the setting off, absent or malformed, no conductor account, a verdict by another account, for another head, with a short sha or with more on its first line, an evidence check that differs without a person's answer, every pull request of the hold list, a red default branch, a paused kit, a passed stop time and a moved head each merge nothing and print one line naming the rule or the setting, never a value.

## Rules

1. **The setting.** The `[flow]` table of `agk.toml` gains three keys: `auto_merge = false | true` (default `false`; absent reads as `false`), `auto_merge_stop` (a local time `HH:MM` within the next 24 hours, or a whole number of hours from 1 to 24 from the loop's start, `Q-S0039-3`) and `auto_merge_method = "squash"` (the only accepted value, `Q-S0039-11`). The setting holds in every `pr_mode` (`strict` and `flow`), in every `review_mode` and in `execution = "local"`. `agk.toml` is a protected path, so turning the setting on lands only with an ADR in the same pull request, and that ADR is the owner's choice; a session may propose it in a `Question:` and never writes, changes or removes the keys itself (`CLAUDE.md item 1`). `doctor.py` prints one line `auto-merge: off` or `auto-merge: on, stop <stop>, method squash`, and fails a malformed value naming the setting and never the value. With `auto_merge` off, absent or malformed, with no `auto_merge_stop` or with another method, `merge_loop.py run` merges nothing and prints one line naming the setting. The kit's template `kit/templates/agk.toml` carries the three keys commented, with `auto_merge = false`; this repository's `agk.toml` carries the same commented lines and does not turn the setting on.
2. **The loop.** `scripts/agk/merge_loop.py` is installed. The owner starts it in their own terminal with their own logged-in `gh`: `python3 scripts/agk/merge_loop.py run` (`python` on Windows where `python3` is not on the path). It works the same on POSIX and on Windows, with the standard library and `gh api` through the REST API only: it passes every argument as a list with no shell, so no quoting of a shell (cmd, PowerShell or a POSIX shell) can change a filter, and it reads JSON itself instead of passing `--jq` expressions. It refuses to start inside an agent session, as `local_mode.py enter --write` does, and the kit's settings deny `merge_loop.py run` to a session. Each pass reads the open pull requests, judges each by rules 3 to 5 in the order the merge queue gives (the oldest trusted verdict first), merges at most one pull request, and prints one heartbeat line: `merge-loop <UTC time> pass <n>: merged #<n> <sha12> | waiting: <k> held, <m> uncleared | stopped: <reason>`. It waits `auto_merge_interval` seconds between passes (60 by default, at least 30). It ends with one line and exit 0 at its stop time, and with one line and a non-zero exit on a red default branch (rule 6), on `paused` (session rule 33, read from the default branch of the remote), on a read GitHub cannot answer five times in a row (exit 4, as session rule 21 counts) and on a refused merge it cannot explain (exit 1). A read that fails is never read as an empty list.
3. **A trusted verdict.** A pull request's verdict is the latest comment whose first line starts `Verdict:`. It is trusted only when all of these hold: its first line reads exactly `Verdict: cleared <sha>`, where `<sha>` is the full 40-character lower-case head sha of the pull request at the time of the pass, with nothing before or after on that line; and its author is listed in a new key `conductor_accounts` of `config/reviewers.yaml` (a list of GitHub logins, empty by default). The loop refuses, naming the setting and never a value, a `conductor_accounts` entry that is the login the loop runs as (`gh api user`), that is listed in `spec_approvers`, or that is the placeholder `@REPLACE-ME`: the builders push from the owner's account, so a conductor account must be another one (`Q-S0039-1`, `Q-S0039-10`). With no conductor account listed, the loop merges nothing and prints `merge-loop: conductor_accounts is empty; nothing merges`. A verdict by any other account, a verdict for another head, a short sha, a verdict with more text on its first line (`Verdict: cleared <sha>, after ...`) and a multi-line fix list are not trusted, and the pull request waits. A newer comment starting `Verdict:` by any account (trusted or not) hides an older trusted one, so a builder's mistaken `Verdict:` holds a pull request, never clears it. `conductor_accounts` is read by the loop only; `verdict_authors` and session rule 1 do not change.
4. **Evidence.** A trusted verdict merges only with evidence for its head. In local mode (`execution = "local"`, or the one open local-mode record issue of `docs/guides/local-mode.md`) the verdict's body holds a `Local evidence:` line that names the same head and an `Evidence check: agrees, head <sha12>` that matches the head's first 12 characters (`Q-S0039-5`). In CI mode, every check of `required_checks` has a latest run on that head that ended `success`. An `Evidence check: differs` merges only when a comment whose first line is `Maintainer answer:` by an account in `spec_approvers`, posted after the verdict, names that head and says it accepts the difference; otherwise the pull request waits. A required check that is red, pending or missing in CI mode, or a `Local evidence:` line for another head, holds the pull request.
5. **The hold list.** The loop never merges these; each waits for the person, and the heartbeat names its reason by rule, never by a value:
   - a release pull request: one whose diff changes `version` in `agk.toml` or `kit_version` in `kit/manifest.json` (`release`);
   - a pull request whose body has an `Approval: SPEC-nnnn` line for a spec that has no `Approve:` line by an account in `spec_approvers` naming that head (`spec approval`), or whose label is `agk:approve`;
   - one that changes a file under `constitution/`, `config/reviewers.yaml`, the ruleset files (`kit/templates/ruleset.json` and `scripts/agk/ruleset.py`) or `.github/workflows/` (`protected class <class>`);
   - one labelled `agk:hold` (`hold label`);
   - a draft (`draft`);
   - one whose `Depends-on: #n` names a pull request or brief not yet merged or closed as completed (`depends-on`, `Q-S0039-8`);
   - one whose mergeable state is `dirty` or `unknown` (`conflict`);
   - anything at all while the default branch is red (SPEC-0032 rule 7: the open issue `The default branch is red`, or the loop's own red run of rule 6), or while the kit is `paused` (`paused = true` on the default branch of the remote); the loop then stops instead of waiting.
6. **The pinned merge and what follows.** The merge is one REST call, `PUT repos/{owner}/{repo}/pulls/<n>/merge` with `sha=<the verdict's head>` and `merge_method=squash`, so a head that moved after the verdict is refused by GitHub and the loop prints `head moved` and waits. After each merge the loop fetches the default branch into a temporary worktree outside the checkout and runs `make governance` there under the heavy-step lock (`python3 scripts/agk/lock.py run --name heavy --session merge-loop -- make governance AGK_BASE=<parent of the merge commit>`), then removes the worktree. If governance is red, the loop stops merging at once, files one priority-0 brief by the router's red-branch path (the issue `The default branch is red` of SPEC-0032 rule 7, opened or updated through the same function of `route.py`, with the failing step and the merge commit and no cause, `Q-S0039-6`), prints `merge-loop: stopped: default branch red after #<n>` and ends with exit 1. It never reverts.
7. **The record.** Every merge is recorded by one line, `Auto merge: #<n> <merge sha> <UTC time> <verdict link>`, posted as a comment on the one open local-mode record issue while it is open, otherwise on the one open issue labelled `agk-auto-merge` that the owner opens once (the guide says how). With neither issue open, the loop merges nothing and says so. The loop never writes a file, so `docs/runs/auto-merge-log.md` is not written by the loop; a person or a later report may gather the lines into it (`Q-S0039-7`). In local mode the line also serves as the guide's `Local merge:` record.
8. **What the loop never does.** It never tags, never approves a review, never posts a `Verdict:`, `Approve:`, `Confirmed:` or `Maintainer answer:` line, never enables or disables auto-merge on GitHub, never changes a workflow or the ruleset, never edits or commits a file of the checkout, never force-pushes, never pushes to any branch and never runs a command, script or `make` target from a pull request's head (governance runs only on the default branch after the merge). It reads secrets from nowhere: `gh` holds the owner's login. Session rule 2 stands unchanged: no session merges, and a session that reads a heartbeat or a record line acts on it only as session rule 32 allows a `Tell:`.
9. **One loop.** The loop takes a named lock `merge-loop` with `lock.py` for its whole run, so a second loop on the same machine waits or exits with the holder's line (`Q-S0039-2`). Two loops on two machines are the owner's to avoid; a merge pinned to a sha cannot merge one head twice, and the second loop's merge of a moved head is refused.
10. **The CI path.** In CI mode, instead of the loop, the governance workflow may run the same step (`python3 scripts/agk/merge_loop.py once`, one pass of rules 3 to 7) as a separate job after the required checks of a pull request end green, only when `auto_merge = true` on the default branch. The job runs the default branch's copy of the script, never the pull request's, with the job's token and only the permissions that merge needs; it adds no secret and changes no ruleset, and a merge the ruleset refuses is printed and not retried (`Q-S0039-12`). The CI path merges nothing the loop would not merge.
11. **The guide.** `docs/guides/auto-merge.md` says, for the owner: what the setting does and does not do; how to set up the conductor's own account (a second GitHub user the owner creates, with write access only, listed in `conductor_accounts`, whose login the conductor session uses to post verdicts, `Q-S0039-1`); how to open the `agk-auto-merge` issue; how to start and stop the loop on Windows (PowerShell and cmd) and on POSIX, in a terminal the owner keeps open; and how to read the heartbeat and the stop lines. `docs/guides/local-mode.md` gains one paragraph pointing to it.
12. **The builds, in order.** After this intake, the builds below are filed, each of about 600 changed lines of code and tests or fewer, each from the default branch with its own ADR naming the protected classes it changes and citing ADR-0261, and one fragment under `changelog.d/` where it changes a file the installer writes (SPEC-0031). A `Depends-on` is declared for a shared file and for a logical dependence alike. When this intake merges, #498 is closed with a pointer to it.
    - (a) **The setting and the trusted-verdict reader** (rules 1 and 3): `scripts/agk/merge_loop.py` (new, installed: reading the setting and judging a verdict, no merge yet), `scripts/agk/reviewers.py` (reading `conductor_accounts`), `scripts/agk/doctor.py`, `config/reviewers.yaml` (the empty key), `kit/templates/agk.toml` and `agk.toml` (the commented keys, off), `kit/manifest.json`, `tests/kit/test_merge_loop_verdict.py`. No dependence.
    - (b) **The loop** (rules 2, 4, 5, 8 and 9): `scripts/agk/merge_loop.py` (`run`, the heartbeat, the pinned merge, the stop time, the evidence and the hold list), `.claude/settings.json` (denying `merge_loop.py run` to a session), `tests/kit/test_merge_loop_run.py`. `Depends-on` (a).
    - (c) **After the merge** (rules 6 and 7): `scripts/agk/merge_loop.py` (the governance run under the heavy lock, the red-branch stop, the record line), `scripts/agk/route.py` (the red-branch issue writer made callable, unchanged in behaviour), `tests/kit/test_merge_loop_after.py`. `Depends-on` (b).
    - (d) **The CI path** (rule 10): `.github/workflows/governance.yml` (which the kit ships as listed in `kit/manifest.json`), `agk.mk` (only if the workflow calls a target), `tests/kit/test_merge_loop_ci.py`. `Depends-on` (c).
    - (e) **The guide** (rule 11): `docs/guides/auto-merge.md`, `docs/guides/local-mode.md`, `tests/kit/test_auto_merge_guide.py`. `Depends-on` (c).

## Tests

Fixtures in `tmp_path` and saved GitHub responses only: no network, no `gh`, invented data (logins and addresses at `example.com`).

- Rule 1: `[flow]` with `auto_merge` absent, `false`, `true`, a stop of `07:30`, of `8`, of `0`, of `25` and of `never`, and a method of `squash` and of `merge`, each read in `strict` and `flow` and with `execution = "local"`; only a well-formed `true` with a stop and `squash` lets a pass merge, every other case merges nothing and prints a line naming the setting and never its value; `doctor.py` prints the line of rule 1; REQ-046 AC1.
- Rule 3: saved comment lists where the latest `Verdict:` is `Verdict: cleared <40 chars>` by a listed conductor account (trusted), by the loop's own login, by an account in `spec_approvers`, by an unlisted account, for the previous head, with a 12-character sha, with text after the sha, and a multi-line fix list (none trusted), and a trusted verdict hidden by a newer untrusted one; an empty `conductor_accounts` merges nothing and names the setting; REQ-046 AC2.
- Rule 4: a trusted verdict with `Evidence check: agrees` for its head (merged), for another head (held), `differs` with no answer (held), `differs` with a `Maintainer answer:` by a spec approver for that head (merged) and by another account (held); in CI mode, saved check runs all `success` (merged), one `failure`, one pending and one missing (held); REQ-046 AC3.
- Rule 5: saved pull requests that raise `version`, have an unapproved `Approval:` line, change each listed path class, carry `agk:hold`, are drafts, have an unmerged `Depends-on` or a dirty mergeable state each print their reason and are never merged; with the red-branch issue open or `paused = true` on the saved default branch the loop stops; REQ-046 AC4.
- Rules 2, 8 and 9: a fake `gh` that records its argument lists shows one heartbeat per pass, the merge call carrying `sha=` and `merge_method=squash`, a saved `409` for a moved head printed as `head moved`, a stop at the stop time with exit 0, a refusal inside an agent session, a second loop waiting on the `merge-loop` lock, and no call that tags, approves, edits a file, pushes or runs a command from a pull request; the same argument lists on a fake Windows platform, with no shell and no `--jq`; REQ-046 AC5.
- Rules 6 and 7: after a saved merge, a governance stub that exits 0 lets the next pass run and posts one record line on the record issue (or on the `agk-auto-merge` issue); a stub that exits 1 stops the loop, writes the red-branch issue through the router's function and prints the stop line; with neither record issue open nothing merges; the loop writes no file and pushes nothing; REQ-046 AC6.
- Rules 10 and 11: the workflow's merge job runs the default branch's script with only the permissions it lists and only when the setting is on, and on the saved responses of the tests above it merges exactly what the loop merges; the guide names the conductor account setup and the Windows and POSIX commands; `config/session-rules.md` rule 2 is unchanged; REQ-046 AC7.

## Proof

REQ-046 AC1: *auto-merge is off unless the owner turns it on, and it means the same in every mode.* Rule 1. REQ-046 AC2: *only the conductor's own account can clear a pull request for the loop, so a builder cannot clear its own work.* Rule 3. REQ-046 AC3: *a clearing verdict merges only with evidence for the exact head it names.* Rule 4. REQ-046 AC4: *anything risky waits for the person.* Rule 5. REQ-046 AC5: *the loop is one kit script that behaves the same on every platform, shows that it is alive, merges only the head it judged and does nothing else.* Rules 2, 8 and 9. REQ-046 AC6: *a merge that breaks the default branch stops the loop, and every merge is recorded.* Rules 6 and 7. REQ-046 AC7: *the CI path is the same rule in another place, the owner can set it up from the guide, and no session ever merges.* Rules 10 to 12.

## Residual

- 2026-11-03: GitHub records the conductor's verdict under whatever login posted it; the loop trusts the login, so a conductor account whose credentials reach a builder's session would let that builder clear work. The guide says to keep the conductor's login out of every builder session; nothing in the kit can check it (due 2026-12-31).
- 2026-11-03: two loops on two machines are not detected; a pinned merge prevents a double merge of one head, but not two merges of different pull requests in one minute before governance runs (due 2026-12-31).
- 2026-11-03: in local mode the evidence the loop reads is the conductor's `Evidence check:` line; the loop does not re-run the evidence check itself, so it is as good as the conductor's run (due 2026-12-31).

## Open questions

Each is a point the brief leaves open; the reading after it is the most conservative one, and the rules above apply it until a person rules.

- Q-S0039-1: how does the conductor get its own account: a second GitHub user or a GitHub App with comment-only rights? Reading: a second GitHub user, set up by the owner, with write access and no admin, listed in `conductor_accounts`, because an App needs hosting; the builders keep pushing from the owner's account, and the loop refuses a conductor account that is its own login or a spec approver (rules 3 and 11).
- Q-S0039-2: may the loop merge while the owner is signed in elsewhere (another terminal, the browser, another machine)? Reading: yes, because the loop's rules do not depend on where else the owner is signed in, and a merge pinned to a sha cannot merge a moved head; one loop per machine is held by the `merge-loop` lock, and two machines running loops is the owner's to avoid, named in the guide and the residual (rule 9).
- Q-S0039-3: may `auto_merge_stop` be "never"? Reading: no; a stop is required, either a local time within the next 24 hours or 1 to 24 hours, so a loop runs at most a day and the owner restarts it; "24/7" is met by restarting it daily, and a missing or "never" stop merges nothing (rule 1).
- Q-S0039-4: are batch smoke runs (the pilot's demo-safe lines) an optional extra gate? Reading: not in builds (a) to (e); the loop merges one pull request per pass and runs governance after each, and a smoke gate is a later brief with its own setting, off by default; nothing here runs a smoke command.
- Q-S0039-5: the brief names a `matches` evidence check, while `evidence.py check` prints `agrees` or `differs`. Reading: `Evidence check: agrees` for the verdict's head is the `matches` the brief means; `evidence.py` and its output do not change (rule 4).
- Q-S0039-6: the router runs only on GitHub Actions, so in local mode no router opens the red-branch issue. Reading: the loop opens or updates that same issue through the router's own function, with the same title, label and `Priority: 0`, so there is still one issue, and the router updates or closes it when Actions runs again; the loop names no cause (rule 6).
- Q-S0039-7: the brief offers `docs/runs/auto-merge-log.md` on a branch, or a comment on the record issue, while it also says the loop never edits a file. Reading: the loop never writes or pushes a file; each merge is one comment on the open local-mode record issue, else on the one open `agk-auto-merge` issue, and with neither the loop merges nothing (rule 7).
- Q-S0039-8: does the loop hold a pull request whose `Depends-on: #n` has not merged, or whose mergeable state is dirty or unknown? Reading: yes, both wait, as they would for a person (rule 5).
- Q-S0039-9: may a session turn the setting on, or start the loop for the owner? Reading: no; the keys change only in a pull request with the owner's ADR, the loop refuses to start inside an agent session, and the kit's settings deny it to a session (rules 1, 2 and 8).
- Q-S0039-10: how does the loop know which account the builders push from? Reading: the builders push from the owner's account, which is the account the loop runs as, so the loop refuses a conductor account equal to its own login or listed in `spec_approvers`; a setup where builders push from another account lists nothing new and is the owner's to keep apart, as the guide says (rule 3).
- Q-S0039-11: which merge methods are allowed? Reading: only `squash`, the method the ruleset allows today; any other value merges nothing and names the setting (rule 1).
- Q-S0039-12: which token does the CI path merge with? Reading: the job's own token with only the permissions that merge needs, in a separate job that runs the default branch's script; no secret is added and the ruleset is not changed, so where the ruleset refuses that token the CI path merges nothing and says so, and the owner uses the loop instead (rule 10). The workflow change is build (d) with its own ADR.
