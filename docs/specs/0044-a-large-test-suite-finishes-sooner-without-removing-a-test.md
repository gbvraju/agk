# SPEC-0044: A large test suite finishes sooner without removing a test

- Status: Draft
- Owner: reviewer group (a team from config/reviewers.yaml)
- Requirements: REQ-051

Status is `Draft` or `Approved`. An Approved spec is owned by its reviewer group; agents propose patches.

Written by the intake of one sentence (SPEC-0012), brief #543: "AGK makes a large test suite finish sooner without removing any test: it records how long each test file takes, runs the suite in parallel workers where the project allows it, picks the smoke run after a merge by what changed, and suggests `proof_timeout` from measured time." The owner's direction, quoted as data from the brief (2026-11-04, chat): "too much time in testing only"; plan #542 puts this first and freezes the requirement set at REQ-051. The facts are counts and timings from a pilot (#523): a back-end suite of about 1,460 tests at about 2 s each took about 51 minutes in one process; one afternoon spent about 1 h 50 on two full runs and about 35 minutes on smoke runs after merges; the pilot's `proof_timeout` was below the suite's time (#494, warned since #509). It is generic: it names no project, and every check of a build reads files and fixtures with no network. Plan #542 asks for a short spec: twelve rules, each with one Tests bullet below. The points the brief leaves open are `Q-S0044-1` to `Q-S0044-10` below, each with the conservative reading the rules apply until a person rules. Negative cases: a missing timing source, a missing plugin, a malformed setting and a missing record each change nothing that runs, and print one line naming the setting, never a value.

## Rules

1. **Nothing is lowered.** No rule here removes, skips, retries away or quarantines a test, or narrows what the default branch runs: CI's push run, a release pull request and `pr_tests = "full"` run the full suite exactly as `project_tests.py` does today. Each new key of the `[testing]` table (`junit`, `workers`, `parallel_command`, `slow_suite_seconds`, `smoke`) is optional, and with every one absent each command prints and runs what the default branch does today. `impact.testing_table` refuses a key outside its list today, so each build adds its keys there; a malformed value is refused naming the setting (`setting: testing.workers`), never the value. A test that fails only under parallel workers is a flake for `docs/runs/flakes.md` (`flakes.py`), never a reason to lower `workers` quietly.
2. **Where per-file timing comes from.** The kit adds no flag to a project's command for timing (`Q-S0044-7`). For a pytest run it reads the durations table that pytest prints when the project's own command passes `--durations=0`, summing the `call`, `setup` and `teardown` lines of each test by its file; for any runner it reads the JUnit XML report at the path `[testing] junit` names (relative to the run's folder), summing the `time` attribute of each `testcase` by its `file` attribute or, without one, its `classname`. With neither, the run's timing is `unknown`. A report that cannot be parsed is `unknown` with one line naming the setting.
3. **Timing in the record, the manifest and the readers.** `prepush.py --record` adds to each run of the tests step a `timing` object: `files` (path and seconds, slowest first, at most 50), `total_seconds` and `source` (`durations`, `junit` or `unknown`); the record stays `schema: 1`, and `evidence.py`, which refuses a field outside schema 1 today, accepts this one optional field and never re-runs or compares it. `proof.py --manifest` adds one line per run, `- timing: <total> s over <n> files (<source>)` or `- per-file timing: unknown`. `lock.py status` prints, after a result line whose record file (SPEC-0040 rule 4, written by its later queue builds) holds a total, one separate line `  timing <total> s (<source>)`, so SPEC-0040 rule 7's fixed `result` line is unchanged, and prints nothing more before those builds; `session.py plan` shows it on its own line after the queue's estimate; the estimate itself stays SPEC-0040 rule 7's median of past `run_seconds` (`Q-S0044-9`). Nothing fails because timing is missing.
4. **Parallel workers for pytest.** `[testing] workers` is `1` (the default, `Q-S0044-1`), `"auto"` (the machine's CPU count, at least 1) or a positive whole number. With more than one worker, a test command whose program is `pytest` or `<python> -m pytest` gains `-n <workers>` at the end, in `prepush.py`'s tests step and in `project_tests.py`, only when `import xdist` succeeds with that command's interpreter (`<python>`, or `python3` for a bare `pytest`, `(verify: a bare pytest may run under another interpreter)`) in the run's folder. Otherwise it runs single and prints once `tests: pytest-xdist is not importable, running in one process (setting: testing.workers)`. The kit never installs the plugin (`Q-S0044-2`). Proof's red-then-green runs stay single (`Q-S0044-8`). `evidence.py` rebuilds the same argv, so a record made with workers still agrees.
5. **Parallel workers for other runners.** For a command that is not pytest, with more than one worker, `[testing] parallel_command` (a string with an optional `{workers}`, filled with the number) replaces `project_tests` for the full run; an area's `[proof]` command is never replaced. With `workers` above 1 and no `parallel_command`, a non-pytest run runs single and prints one line naming `testing.parallel_command`.
6. **The same result.** On the same tree, a parallel run gives the same counts of passed, failed and skipped tests and the same exit code as the single run. The spec's test checks this on every kit test run, never skipped: a fixture project of the kit, invented, with one failing and one skipped test, carries a fake `xdist` package on its own path (a pytest plugin that accepts `-n <N>` and runs the test files in N child pytest processes, split by file, and sums their counts and exit codes), so `import xdist` succeeds with no install, and the test runs it with `workers = 1` and `workers = 2`.
7. **A slow single-process suite.** `doctor.py --record FILE` reads one prepush record (`Q-S0044-6`); when its `full` run took longer than `[testing] slow_suite_seconds` (600 by default; a different setting from `budget_seconds`, which the metrics read) and `workers` is `1`, it prints `tests: the full suite took <n> s in one process, more than slow_suite_seconds (<m> s); see the testing guide on workers (setting: testing.workers)`. It is an information line and fails nothing. Without `--record` it prints nothing about the suite.
8. **The smoke run by change kind.** `scripts/agk/smoke.py [--base REF] [--head REF] [--run]` (new, installed) chooses the after-merge smoke run from the changed paths, by default of the last merge on the default branch, and prints the choice with its reason; with `--run` it runs it under the heavy-step lock. `[testing] smoke` is a list of `{ kind = "frontend" | "contract", code = [<globs>], command = "<command>" }`. When every changed file that is not documentation (`impact.is_doc`) matches the `code` of one kind, that kind's command runs: the front-end build, type check and tests, or the contract tests (contract and mock files). Any other change, a file of `always_full`, or files of two kinds choose the full smoke (`project_tests`). Documentation only chooses nothing (`Q-S0044-3`). CI's push run and the release run do not change (rule 1): this is the smoke run a person or the conductor starts after a merge, never a gate (`Q-S0044-8`). The change-kind choice is never the evidence of SPEC-0038 rule 10's web-app gate "an e2e smoke run per merge batch" (`judgement`); that gate and its run record stay as SPEC-0038 says, so no Approved spec changes.
9. **`proof_timeout` from measurement.** With `--record FILE` holding a `full` run, `doctor.py` prints `tests: proof_timeout <m> s; the recorded full suite took <n> s (record <sha12>); a value of about <v> s leaves headroom (setting: proof_timeout)`, with `<v>` = ceil(n × 1.5 / 60) × 60, the formula of prepush's warning (ADR-0258, `Q-S0044-4`). It never writes `agk.toml`; changing the setting stays a person's change with an ADR.
10. **Front-end test folders** (#484). `adopt.detect_tests` also detects the name patterns `*.test.ts`, `*.test.tsx`, `*.spec.ts` and `*.spec.tsx`, and the topmost folders that hold them, among them `__tests__/`, `e2e/` and `cypress/` folders. Its output for a project with none of them is unchanged, and it only adds. `test_dirs` are folder prefixes and `test_patterns` file-name patterns, not path globs, so `src/**/__tests__/` is detected as the folders found and never written as a glob. The defaults of `common.DEFAULT_CONFIG` do not change. For a project already adopted, `adopt.py` reuses the stamped `test_dirs` and `test_patterns` and never rewrites them (`Q-S0044-10`), so `doctor.py` prints, when the stamped folders and patterns match no test file while the front-end patterns above would match at least one, `tests: test_dirs and test_patterns match no test file; <n> files match the front-end test patterns (setting: test_dirs)`. It is an information line, fails nothing and writes nothing.
11. **Honest measurement.** `docs/guides/testing.md` gains a section that says to measure the suite before and after a change of these settings (with a prepush record of each), shows per-worker database names with pytest-xdist's `worker_id` fixture for a suite that creates databases, names `workers`, `parallel_command`, `junit`, `slow_suite_seconds` and `smoke` as suggestions, never as a lowered gate, and says that a flake found under workers goes to the ledger. The `web-app` playbook names the same settings in its text as suggestions, in whichever build first writes `config/playbooks/web-app.toml`; no key is added to the playbook format of SPEC-0038.
12. **The builds, in order.** Each is tests first, about 400 changed lines or fewer, from the default branch, cites ADR-0270 and records its decisions under `Decisions taken:` (plan #542), with a short ADR of its own only because the protected-path check needs one in the same pull request (ADR-0270 decision 5); a build that changes a file the installer writes adds one fragment under `changelog.d/`.
    - (a) Per-file timing and the readers (rules 2 and 3): `scripts/agk/impact.py` (`junit`), `prepush.py`, `proof.py`, `evidence.py`, `lock.py` or `heavy_queue.py`, `session_plan.py`, `tests/kit/`. No dependence.
    - (b) Workers (rules 4 to 7): `impact.py`, `prepush.py`, `project_tests.py`, `evidence.py`, `doctor.py`, a fixture project under `tests/kit/`. `Depends-on` (a), for the shared files.
    - (c) Smoke by change kind (rule 8): `scripts/agk/smoke.py` (new), `impact.py`, `kit/manifest.json`, `tests/kit/`. `Depends-on` (b).
    - (d) The `proof_timeout` suggestion and the front-end test folders (rules 9 and 10): `doctor.py`, `adopt.py`, `tests/kit/`. `Depends-on` (b).
    - (e) The guide and the playbook lines (rule 11): `docs/guides/testing.md`, `tests/kit/`. `Depends-on` (c) and (d).

## Tests

Fixtures in `tmp_path`, saved outputs and fake interpreters only: no network, no install, invented data (`example.com`), and each test carries the marker `REQ-051` with its criterion. Rule 12's builds are checked by review.

- Rule 1: with no new key, the argv and output of `prepush.py`, `project_tests.py` and `proof.py` on a fixture project equal the default branch's; each malformed key is refused naming the setting; REQ-051 AC2.
- Rule 2: saved pytest outputs with and without the durations table, JUnit files with `file`, with only `classname`, malformed and missing; each gives the per-file sums or `unknown`; REQ-051 AC1.
- Rule 3: a fixture run writes the `timing` object; a record without it and one with it both pass `evidence.py check`; the manifest line in both forms; the separate status and plan lines with and without a total, SPEC-0040's `result` line byte for byte unchanged and the estimate unchanged; REQ-051 AC1.
- Rule 4: `workers` absent, `1`, `"auto"`, `4`, `0` and `"many"`; a fake interpreter with and without `xdist`; the argv gains `-n 4` only with the plugin, and the one line without it; `evidence.py` agrees on a record made with workers; REQ-051 AC2.
- Rule 5: a non-pytest fixture with and without `parallel_command`, `{workers}` filled in, an area command left unchanged; REQ-051 AC2.
- Rule 6: the fixture project's two runs, the second through the fake `xdist`, compared count by count and by exit code, with no skip; REQ-051 AC3.
- Rule 7: records with a full run above and below the setting, with `workers` 1 and 4, and no record; REQ-051 AC5.
- Rule 8: fixture merges of back-end, front-end only, contract only, mock only, docs only, front-end plus contract, and a front-end file under `always_full`, each printing its choice; no `[testing] smoke` chooses the full smoke; `project_tests.py`'s push choice unchanged; REQ-051 AC4.
- Rule 9: a record of 3,060 s suggests 4,620 s; with no full run nothing is printed; `agk.toml` is unchanged after the run; REQ-051 AC5.
- Rule 10: fixture trees with Python tests only (output unchanged), and with each front-end layout (folders and patterns added, nothing removed); an adopted fixture whose stamped keys match no test file and whose front-end files do, which prints doctor's line and keeps the stamp, and one whose stamped keys match, which prints nothing; REQ-051 AC6.
- Rule 11: the guide names each setting, the measure-before-and-after rule and `worker_id`; it holds no wording that skips or lowers a test; REQ-051 AC6.

## Proof

REQ-051 AC1: *per-file timing is recorded where the runner gives it, and missing timing fails nothing.* Rules 2 and 3. REQ-051 AC2: *workers are opt-in, and a missing plugin runs single with one line.* Rules 1, 4 and 5. REQ-051 AC3: *a parallel run gives the same result.* Rule 6. REQ-051 AC4: *the smoke run after a merge follows what changed, and the default branch's full suite does not change.* Rule 8. REQ-051 AC5: *doctor reports a slow single-process suite and suggests `proof_timeout` from a record, and changes nothing.* Rules 7 and 9. REQ-051 AC6: *front-end tests are found, and the guide measures and lowers nothing.* Rules 10 and 11.

## Residual

- 2026-11-04: per-file timing depends on the runner's own output; a runner with neither a durations table nor JUnit XML stays `unknown` (due 2026-12-31).
- 2026-11-04: rule 6 proves equal results on a kit fixture, not on a project's suite; a suite whose tests share state can still differ under workers, which the guide's measure-before-and-after rule and the flake ledger catch (due 2026-12-31).

## Open questions

Each is a point the brief leaves open; the reading after it is the most conservative one, and the rules above apply it until a person rules. Q-S0044-1 to Q-S0044-5 are the brief's own questions with its readings.

- Q-S0044-1: should parallel workers default to `1` or `auto`? Reading: `1`, so a project opts in after measuring (rule 4).
- Q-S0044-2: may AGK install `pytest-xdist`? Reading: no; it prints that the plugin is missing, and the guide says how to add it (rules 4 and 11).
- Q-S0044-3: should the smoke run skip docs-only merges? Reading: yes, nothing runs, unless a file matches `always_full` (rule 8).
- Q-S0044-4: what is the `proof_timeout` headroom? Reading: 1.5 times, rounded up to the minute, the formula prepush's warning already uses (rule 9).
- Q-S0044-5: should earlier-phase regression tests run on a schedule instead of on every full selection (#523 idea 3)? Reading: not in this spec; plan #542 parks it, and the full selection is unchanged (rule 1).
- Q-S0044-6: where does `doctor.py` find a record? Records are written wherever `--record FILE` points, and doctor reads none today. Reading: only the file given as `doctor.py --record FILE`; doctor never searches for one and never guesses a path (rules 7 and 9).
- Q-S0044-7: the brief says "whichever is already produced" for pytest's durations or JUnit XML, but the kit runs the project's own command and adds neither. Reading: the kit adds no timing flag; it reads the durations table when the project's command prints it, and the JUnit report at `[testing] junit`, and is otherwise `unknown` (rule 2).
- Q-S0044-8: may proof's red-then-green runs, or the after-merge smoke run, use workers or act as a gate? Reading: no; proof stays single, and `smoke.py` is a run a person or the conductor starts, which blocks nothing (rules 4 and 8).
- Q-S0044-9: do the readers of rule 3 change an Approved spec (SPEC-0040 rule 7, SPEC-0034 rule 15)? Reading: no; each prints a separate line after what those rules print, never inside SPEC-0040 rule 7's `result` line, and changes no formula, so proposed amendment 116 is not used.
- Q-S0044-10: should the front-end detection of rule 10 reach a project that is already adopted, whose stamp `adopt.py` reuses? Reading: `adopt.py` never rewrites the stamped `test_dirs` and `test_patterns`; `doctor.py` prints one information line when they match no test file and the front-end patterns would (#484), and the person changes the setting (rule 10).
