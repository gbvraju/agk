# SPEC-0043: A project's plan is drafted from its sources and tracked with calibrated ranges

- Status: Approved
- Owner: reviewer group (a team from config/reviewers.yaml)
- Requirements: REQ-050

Status is `Draft` or `Approved`. An Approved spec is owned by its reviewer group; agents propose patches.

Written by the intake of one sentence (SPEC-0012): "From a project's source documents (SOW, BRD, PRD, design links), AGK drafts the scope, milestones, requirements, specs and briefs with traceability to each source line, estimates every milestone as a calibrated range, tracks the plan against actual progress with a forecast and controlled scope change, and runs the plan in phases with agile ceremonies (planning, daily status, review, retrospective)." The sentence is longer than the limit of `intake.py ids` (rule 1 of SPEC-0012) and is quoted whole as the brief gives it. It is generic and project-agnostic: it names no project, no customer and no vendor, it needs only files, git and a shell, it uses the standard library only, on Windows and POSIX, and no check reads the network. The brief is issue #539. The maintainers gave 11 answers before it was written: the eleven numbered answers of brief #539 (the conductor's design), written here as rules 1 to 27, and answer 11's eight questions, written below as `Q-S0043-1` to `Q-S0043-8` with their conservative readings. The owner's direction of 2026-11-04, quoted as data and recorded as one row of `docs/runs/decisions-log.md`: "When developer start the project they might having the SOW or BRD, PRD or Design figma URLs, how our AGK can help them to create Milestones, issues or specs, brief as it calls and define the scope and make sure it is moving as per the plan. We need clear realistic estimations for Milestone with AGK. So it will also adopt the phase of work and work similar to Agile ceremonies."

What it reuses, each name read on the default branch at 2e25012 on 2026-11-04: the one-sentence intake (SPEC-0012, `scripts/agk/intake.py`, whose `check` allows at most eight criteria and one new spec and ADR); `new_spec.py` (kit-only, writes a Draft spec, an ADR carrying a proposed requirement, or a brief file, and never edits `docs/requirements.md`); brief `Size:` and `Expected:` and the metrics fields `estimated_size`, `estimated_hours` and `actual_hours` (SPEC-0018, `metrics.py`), which the facts carry per pull request (`facts.py`); the facts' per pull request `flow` hours `taken_to_pull_request`, `to_first_verdict`, `verdict_to_cleared` and `cleared_to_merge` and its `stalled` field (SPEC-0034 rule 10, SPEC-0009); the charter milestones with a measurable `exit:` statement that `playbook.py check-start` checks (SPEC-0013 rules 4 and 5); the closed playbook format (SPEC-0038 rule 2, `playbook_format.py`); the design sign-off rows of `docs/design/signoffs.md` (SPEC-0037 rule 9); `session.py plan` (`scripts/agk/session_plan.py`, brief #247 build (a), ADR-0153, proposed as SPEC-0034 rule 15 by amendment 88; the spec's own text holds rules 1 to 14 and 17 to 27); `stalls.py` (read-only, `--json`); the brief shape and `check_brief.py` (SPEC-0034 rule 2); the decision inbox and the weekly product report (SPEC-0011, `product_report.py`, five sections and the facts as its one input); and the heavy-run queue's estimate (SPEC-0040 rule 7). Two specs are not on the default branch yet and are cited by brief number: the personal mode with its private state and its file forge (brief #536) and the data guard (brief #538); a name of theirs used below is marked `(verify)` until its build merges. The points the brief leaves open, and the points found by checking the brief against the code, are `Q-S0043-1` to `Q-S0043-19` below, each with the conservative reading that the rules apply until a person rules.

Negative cases are in the criteria: a source without its header, an item without a source location that exists, a milestone without a brief, a brief added to a baselined milestone without an approved scope change, an estimate below the calibration minimum and an input that cannot be read each fail, are refused or print `unknown` or `uncalibrated`, and are never guessed.

## Rules

### Sources (answer 1)

1. **The sources folder and its header.** `docs/sources/` holds the project's source documents as the person provides them, one file each, Markdown (`.md`) or plain text (`.txt`) only; a PDF, DOCX or other document is converted to text by the person's own tools before it is added, and no script of the kit converts or fetches one (`Q-S0043-1`). Each file starts with exactly these header lines, in this order: `Source: <document title>`, `Kind: <sow|brd|prd|design|charter|other>`, `Version: <the document's own version>`, `Date: <YYYY-MM-DD>`, then one blank line and the text. A location in a source is `<file>:<line>` (a line number of the file) or `<file>#<heading>` (the text of a Markdown heading of the file, exactly). `check_plan.py` fails a file under `docs/sources/` that is not `.md` or `.txt`, that lacks a header line, has them out of order, has a `Kind:` outside the list or a `Date:` that is not a real date, naming the rule and the file and never a value. A charter ADR of SPEC-0013 may be cited as a source location `docs/adr/<file>#Milestones` without a copy in `docs/sources/`.
2. **Design links.** A design link (for example the address of a design file) is one row of `docs/sources/design-links.md` (header `Kind: design`), a table with the columns `Name`, `Link` (an `https://` address), `Version` (the version or the date of the design file the person names) and `Frames` (the names of the frames the person names, comma separated). No check opens a link: `check_plan.py` checks only that each row has the four values and that `Link` starts with `https://`. A session reads a design only through the person's own design connector, in that session, and only the named frames (`Q-S0043-2`); what it read is written into one source file with the header of rule 1 (`Kind: design`, `Version:` the row's version), so that every trace cites a file line and never a link.
2a. **The prototype source** (amendment 163 item 2, with the owner's ruling on `Q-1073-2`). `python3 scripts/agk/design_import.py source --version i<n> --slug <slug>` writes once, as a new file only and never over an existing one, `docs/sources/<slug>-prototype-i<n>.md` with the header of rule 1: `Source: imported prototype i<n>`, `Kind: design`, `Version: i<n> <the manifest's digest>`, `Date: <YYYY-MM-DD from the clock in UTC>`, then one blank line. Then, for each row of the version's `map.md` that is not `out:`, in the map's order, one heading `## <screen>/<state>` and under it the page's visible text, read from its HTML as text only: all text outside `script`, `style` and `template` elements, in document order, with the names and placeholders of fields, one per line, each with its white space collapsed, empty ones left out, so no message of the prototype is lost. A row whose file is a picture page gets the one line `picture: <file>`. Nothing is run or opened, no network, no model (SPEC-0037 rule 15). The command refuses, with exit 1 naming the rule and the version and writing nothing, a version that is not on the branch and a version for which `design_import.imported_problems` reports a problem (the import check or the map check); it refuses an existing target file naming the file, and a missing or malformed `--slug` (a lower-case slug `[a-z0-9][a-z0-9-]*`, required, no default) with exit 2 naming `--slug` (`Q-1073-1`). The text is the person's to clean: rule 3's guard scans the whole file before any agent reads it, as for every source.
3. **The data guard first, and personal mode.** A source is read by an agent only after the data guard of brief #538 (SPEC-0042, #540) has passed it `(verify)`. The guard has no off switch (SPEC-0042 rule 1, #540: `[guard]` only adds rules), so the condition is whether it is installed, never a setting: `plan_intake.py` (every command) exits 2 with `data guard not installed: <path>` when `scripts/agk/guard.py` or `.claude/hooks/data_guard.py` is absent, naming the path and never a value. When it is installed, `plan_intake.py` runs `guard.scan_text` (SPEC-0042 rule 10, #540) on the whole text of each source before it reads any line of it, and a finding refuses that source with exit 1 and one line per finding naming the file, the kind and `line <l>, column <c>`, never the matched text; so a source holding a secret or customer personal data is cleaned by the person first. The builds of rule 27 that read sources declare `Depends-on` the builds of brief #538 that add `guard.py` and the read hook. Example sources in the kit, its tests and its guides are invented (`example.com`). In personal mode (brief #536) the folder `docs/sources/` and the folder `docs/plan/` live in the developer's private state, never in the product repository `(verify)`.

### The scope draft (answer 2)

4. **The skill writes proposals as data.** `/agk:plan-intake` (a plugin skill, `skills/plan-intake/SKILL.md`) reads the sources and writes one proposals file, JSON, `schema` 1, at a path the person names outside `docs/` (never committed; principle 5). It holds `scope` (`in`, `out`, `assumptions`, `constraints`, `open_questions`, each a list of items), `milestones` (each `id` `M1`, `M2`, ..., `title`, `exit`, `acceptance`, `target` a date or `null`), `requirements` (each `key`, `title`, `criteria` as Given, when, then text, and `milestone`), `areas` (the feature areas, each `name` and the `requirements` keys it covers), `briefs` (each `key`, `milestone`, `title`, `size` `S`, `M` or `L`, `expected` `<low>-<high> hours`, `advances` the requirement keys, `touches`, `depends_on` brief keys) and `conflicts` (each two locations and a plain description). Every item of `scope`, `milestones`, `requirements` and `briefs` has `sources`, a non-empty list of locations of rule 1. The skill never writes a requirement, a spec, a brief or a GitHub object itself.
5. **Validation.** `python3 scripts/agk/plan_intake.py validate --proposals FILE` exits 0 printing `ok proposals` or exits 1 with one line per problem naming the rule and the item's `key` or `id`, never its text. It refuses: an unknown or missing key; an item whose `sources` is empty; a location whose file is not under `docs/sources/` (or a charter of rule 1), whose line does not exist or whose heading is not in the file; a milestone whose `exit` fails the measurable test of SPEC-0013 rule 5 (the words `exit:` and a digit, `all`, `every`, `none` or `zero`; the `MEASURABLE` pattern of `playbook.py check-start`, imported, not copied); a brief whose `size` or `expected` fails SPEC-0018 rule 2; a brief whose `milestone`, `advances` or `depends_on` names nothing, or whose `depends_on` makes a cycle; and a milestone with no brief.
6. **Nothing invented, conflicts shown.** A point the sources do not settle is an item of `scope.open_questions` with the mark `(verify)` and its location set to where the sources fall silent, never a value made up (principle 7); `validate` refuses a `target` date, a size or an `expected` range that no location supports by printing it as an open question instead, with exit 1 (`Q-S0043-11`). Two sources that disagree (for example a statement of work and a product requirements document) are one item of `conflicts`; `render` prints every conflict first, under `Conflicts for the person`, and `validate` refuses a milestone, a requirement or a brief whose `sources` include both sides of a conflict that the person has not settled with a line `Settled: <location>` in the proposals. Nothing is resolved silently. For each screen that a heading of a `Kind: design` source names, the skill lists the states that `docs/design/inventory.md` gives that screen as `yes` and that no heading of the source covers (for example `error`, `empty`, `loading`, `no-permission`), as `plan_intake.py states` prints them, and each becomes one `scope.open_questions` item with the mark `(verify)` and the location of that screen's first heading in the source (amendment 163 item 5, `Q-1073-3`). A state the inventory marks `n/a: <reason>` is not asked again. Nothing is invented: the skill writes no requirement, criterion or brief for such a state until the person answers. `render` prints these items under `Open questions for the person`, after `Conflicts for the person`, and `validate` checks them as every open question: a non-empty `sources` list whose location resolves.
7. **Render, once, as drafts the person owns.** `plan_intake.py render --proposals FILE` writes, as new files only and refusing to overwrite: `docs/plan/scope.md` (the five lists of rule 4, each line ending with its locations), `docs/plan/milestones.md` (one `### M<n> <title>` block per milestone with `Exit:`, `Acceptance:`, `Target:` and `Source:` lines), one Markdown block per requirement in `docs/plan/requirements-proposed.md` (title, criteria, `Status: planned` and one `Source: <location>` line per location), one Draft spec skeleton per feature area made by the function of `new_spec.py spec`, and one brief body per brief in `docs/plan/briefs/M<n>/<key>.md` holding the lines of SPEC-0034 rule 2 (`Advances:`, `Touches:`, `Priority:`), `Size:` and `Expected:` (SPEC-0018 rule 1), `Milestone: M<n>` and `Source:` lines. After render these files are the person's: a later render refuses to overwrite them, and every later change is a person's edit or a scope change of rule 21. A rendered brief's `Advances:` names its requirement's `key` until that requirement's intake gives it a `REQ-n` number; the person or the session then replaces the key, and `publish` refuses a brief whose `Advances:` is not a requirement of `docs/requirements.md` (rule 25). `docs/requirements.md` is never edited by the script (it is protected): each feature area's requirements enter it through one intake pull request with its own ADR, as every requirement does (`Q-S0043-16`).
8. **The person confirms before anything is created.** The plan is confirmed by the person with a comment on the plan's pull request whose first line is `Approve: plan <full head ID>`, by an account in `spec_approvers` of `config/reviewers.yaml`, the same rules as a design sign-off (SPEC-0037 rule 9): a line by another account, or for another head, does not count, a session never posts it, and in solo mode it counts inside the person's `Confirmed:` comment, which the session prints and never posts (session rule 29) (`Q-S0043-13`). Until then nothing is created on GitHub or in the personal-mode forge, and `publish` (rule 25) refuses with exit 2 naming the missing confirmation.

### Traceability (answer 3)

9. **The trace is printed, never committed.** `python3 scripts/agk/check_plan.py --trace` prints the matrix from source location to requirement (its `Source:` lines), to spec rule (a spec whose `Requirements:` names the requirement, and the rule that cites it), to brief (its `Advances:`), to pull request (the facts' `Brief: #n` of a merged pull request, with `--facts FILE`) and to test (the `REQ-nnn ACn` markers of the tests), one row per source location, `none` where a link is missing. It is derived from committed files on every run, so it is printed and is not committed (principle 5); the brief's `docs/plan/trace.md` is the path the person may write it to locally (`Q-S0043-9`).
10. **The checks of the plan.** `check_plan.py` (a governance step, files only, no network) fails, naming the rule and the item and never its text: a requirement whose block in `docs/plan/requirements-proposed.md` or `docs/requirements.md` has no `Source:` line that resolves (rule 5); a line of `docs/plan/scope.md` under `In scope` whose location no requirement cites; a `## <screen>/<state>` heading of a `Kind: design` source that no requirement cites (amendment 163 item 4); a milestone of `docs/plan/milestones.md` that no brief file names in its `Milestone:` line; and the scope-change rule 22. A project with no `docs/plan/` passes with `ok plan (no plan)`, so every project without a plan sees no change.
11. **Coverage as counts.** `check_plan.py` ends with one line `ok plan: <a> of <b> in-scope source lines have a requirement, <c> of <d> requirements have a brief, <e> of <f> briefs have a merged pull request, <g> of <h> requirements have a test` (the last three counts only with `--facts FILE`, otherwise `not read`), each a count and never a percentage alone. In a source whose header says `Kind: design`, each `## <screen>/<state>` heading is one in-scope source location (`<file>#<screen>/<state>`, the location form of rule 1) and is counted in `<b>`, whether or not `docs/plan/scope.md` lists it; it counts in `<a>` when a requirement's `Source:` line cites it. So `<a> of <b>` proves that every mapped screen and state has a requirement (amendment 163 item 4).

### Estimation, realistic and calibrated (answer 4)

12. **The history window, the history and the minimum.** The window is the last `--weeks N` ISO weeks ending with the week of the facts' `today` (12 by default, a whole number from 4 to 52, refused otherwise with exit 2 naming `--weeks`; its first Monday is `window_start` of `facts.py`, imported, not copied). The facts hold only the pull requests of their own `--weeks` window (8 by default, SPEC-0009 rule 14, `facts.py --weeks`, and `product-report.yml` passes none), and they do not record that window, so the plan's facts are made with `facts.py --weeks N` for the same `N`, as the report's run does (rule 19), and the window is printed in the `inputs:` line (rule 16) for a person to check (`Q-S0043-19`). The history is the facts' merged pull requests whose `merged_at` is in the window, whose `estimated_size` is `S`, `M` or `L` and whose `actual_hours` is a number (SPEC-0018 rule 3), the most recent 30 of each size by `merged_at`. The throughput is the number of brief issues closed as completed per ISO week of the window, read from the facts (which list only open briefs today, `flow.briefs`; build (e) adds the ones closed in the facts' window, amendment 115 item 1), from the week of the first such close in the window to the week of `today`, weeks with none counting as 0. An estimate is calibrated when the history holds at least `[plan] calibration_min` items (10 by default, a positive whole number, `Q-S0043-3`) and at least 3 items of each size among the milestone's open briefs, and the throughput holds at least 4 weeks; otherwise it is `uncalibrated` (rule 14).
13. **The simulation.** `python3 scripts/agk/plan_estimate.py --facts FILE [--plan DIR] [--today D]` estimates each milestone of `docs/plan/milestones.md` in order. Hours: one generator `random.Random("hours:M<n>")` (the standard library's, seeded with that string), 10,000 trials, each the sum, over the milestone's open briefs sorted by issue number (by key before publish), of one `rng.choice(pool)`, where the pool of a size is its history sorted by `merged_at` then pull request number (all three sizes' pools joined in that order for a brief whose size is unknown). P50 and P85 are nearest-rank percentiles: the value at position `ceil(p / 100 * 10000)` (1-based) of the sorted trial sums, so positions 5000 and 8500, in hours rounded half-even to one decimal (`Q-S0043-4`). Finish dates: one generator `random.Random("weeks:M<n>")`, 10,000 trials, each drawing `rng.choice(weeks)` (the throughput's weekly counts in week order) one week at a time until the drawn closes reach the open briefs of this milestone and of every earlier one (milestones in order), the trial's result being the number `k` of weeks drawn, at most 520 (a trial that reaches 520 makes the dates `unknown`). P50 and P85 of `k` are taken by the same positions, and a count `k` becomes the date of the Friday of the `k`-th full ISO week after `--today`: the Monday after `--today` (`--today` itself is never counted) plus `7 * k - 3` days. A milestone with no open brief prints `done` for both dates. `--today` is a `YYYY-MM-DD` date, the facts' `today` by default (`Q-S0043-17`). The same facts, plan and `--today` give byte-identical output. No buffer is applied and no number is typed in: every figure comes from the facts.
14. **Uncalibrated, shown as such.** An uncalibrated milestone prints `uncalibrated` and the reason (`history <n> of <minimum>`, `size <S|M|L> <n> of 3` or `throughput <n> of 4 weeks`), the sum of the lows and the sum of the highs of its open briefs' declared `Expected:` ranges as `declared <low>-<high> hours`, and the finish dates `unknown`; it never prints a P50 or a P85 it cannot support and never a single number. A brief without a readable `Expected:` takes the owner's range for its size from `[plan] default_hours` (for example `S = "2-4"`), printed as `owner default`, and without that setting it is counted in `<n> briefs without an estimate` and adds nothing (`Q-S0043-10`). The playbooks hold no default per size and none is added: the playbook format is closed (SPEC-0038 rule 2).
15. **The waits are inside the lead time and shown apart.** `actual_hours` runs from the earliest commit to the merge (SPEC-0018 rule 3), so it already holds the waits for review and merge, the heavy-run queue and the person's approvals that fell inside the pull request; the estimator never adds them again (`Q-S0043-12`). It prints them as a breakdown of the history, measured and separate: the median `to_first_verdict`, `verdict_to_cleared` and `cleared_to_merge` hours of the history (the review and merge waits; the person's own approvals of an Approved spec or a solo confirmation fall inside `verdict_to_cleared` and are not shown apart, `Q-S0043-8`), and the heavy-run queue wait, which the facts do not carry today (`facts.py` and `kit/facts-schema.json` have no queue field, and SPEC-0040's queue keeps its job files in the lock's base folder outside every repository, SPEC-0040 rule 2), so it prints `unknown` until a later build adds it to the facts; no build of rule 27 adds it. A median the facts do not hold also prints `unknown`.
16. **Every estimate prints its inputs.** Each estimate is followed by one line `inputs: window <first Monday> to <today> (<N> ISO weeks), history S <n> M <n> L <n> (<first date> to <last date>), throughput <n> weeks median <x> a week, waits review <h> h merge <h> h queue <h|unknown>, trials 10000 seeds hours:M<n> weeks:M<n>`, so a person can check it by hand. The estimate is made again each time the command runs: the weekly report's run (rule 19) and the run that follows an approved scope change (rule 22).

### Tracking against the plan (answer 5)

17. **The status of each milestone.** `python3 scripts/agk/plan_status.py --facts FILE [--plan DIR] [--today D] [--json]` prints one block per milestone: `briefs <done> done, <open> open`; `hours <spent> spent of P50 <x> P85 <y>` (spent being the sum of `actual_hours` of the milestone's merged pull requests); the forecast finish `P50 <date> P85 <date>` (or `uncalibrated` as rule 14); the target date; the status; the trend; and the cause. A brief is the milestone's by its `Milestone:` line (rule 7) and is done when its issue is closed as completed. An input it cannot read prints `unknown`, never a guess or a zero.
18. **The status rule and the cause.** The status is decided in this order: `late` when `--today` is after the target date and a brief of the milestone is still open; else `unknown` when there is no target date or the forecast is `uncalibrated` or `unknown`; else `at risk` when the P85 finish date is after the target date; else `on track`. The trend is the same estimate made from the facts as they were at the start of the report's week (pull requests merged and briefs closed before it, scope as recorded before it), printed `P85 <n> days earlier`, `P85 <n> days later`, `same` or `unknown`. The cause is at most three plain phrases, in this order, each printed only when its count is above 0: `waiting on review <h> h this week` (the sum of `to_first_verdict` of the milestone's pull requests that waited in the week), `scope grew by <n> briefs` (approved scope changes of the week), `<n> briefs stalled (<kind>)` (the facts' `stalled`), `<n> of <m> estimates missed` (actual above the declared high, SPEC-0018 rule 6). With none, the cause is `none measured`.
19. **Into the weekly report and the inbox.** The report's five sections stay (SPEC-0011 rule 8): a milestone `at risk` or `late` is one line of `## At risk` (`Milestone M<n> "<title>" is <status>: P85 <date> after target <date>; <cause>`), and a scope change waiting for approval (rule 22) and a plan waiting for its confirmation (rule 8) are items of the decision inbox and of `## Needs you` (`Q-S0043-15`). The renderer still reads only one file (SPEC-0011 rule 2): when `docs/plan/milestones.md` exists, the existing `product-report` workflow, after `facts.py`, runs `facts.py --weeks 12` once more into a second file (the plan's facts, rule 12) and `plan_status.py --facts PLAN --weeks 12 --base IN --into OUT`, which writes a copy of the report's facts `IN` with one more top-level key `plan` (the `--json` output made from `PLAN`), and the report renders from `OUT` alone and the uploaded artifact is `OUT`. The key `plan` is optional: SPEC-0009 rule 3 fixes the top-level keys and `kit/facts-schema.json` sets `additionalProperties: false`, so amendment 115 item 1 adds `plan` to both. A project without `docs/plan/` runs neither step and gets no `plan` key; its `report.md` is byte-identical to today's, and its `report.json` is identical apart from `schema`, which rises from 3 to 4 for every report because SPEC-0011 rule 72 raises the number when a kind is added (amendment 115 item 2). Amendment 115 lists the changes to SPEC-0009 and SPEC-0011 this needs.

### Scope change control (answer 6)

20. **The baseline.** At the person's confirmation (rule 8), the session writes `docs/plan/baseline.json` in a commit that changes only that file: `schema` 1, the confirmed head, the date from `date -u`, the link of the `Approve: plan` comment, and per milestone its brief keys, its target date and its estimate as printed then (calibrated or not). The baseline is never rewritten: `check_plan.py` fails a change to an existing `baseline.json`, as `check_build_state.py` fails an edited build-state row (principle 4), and the report shows the baseline's and the current briefs and estimate side by side.
21. **A scope change is a record.** A change of scope after the baseline (a brief added or removed under a milestone, or a target date moved) is one block of `docs/plan/scope-changes.md`: `Scope change: SC-<n>` (the next free number), `What:`, `Why:`, `Source:` (a location of rule 1, or `person` with the date when the person asks with no document), `Effect:` (the P50 and P85 hours and days before and after, computed by `plan_estimate.py --with SC-<n>`), and `Status: proposed`.
22. **Approved before the briefs are added.** A scope change is approved by a comment whose first line is `Approve: scope SC-<n> <full head ID>` by an account in `spec_approvers` (`Q-S0043-7`), under the rules of rule 8; the session then appends `Approved: <date> <link>` to the block in a commit that changes only that file. `check_plan.py` fails a brief file under a baselined milestone that is not in the baseline and not named by an approved scope change, and a removed baseline brief with no approved scope change, naming the rule and the brief's key.

### Phases and ceremonies (answer 7)

23. **The iteration.** An iteration is a time box of `[plan] iteration_days` working days (Monday to Friday, 10 by default, a whole number from 1 to 30, `Q-S0043-5`), numbered from 1 from the baseline's date. An invalid value is refused with exit 2 naming the setting, never the value. The ceremonies are text that `python3 scripts/agk/plan_ceremony.py planning|daily|review|retro --facts FILE [--plan DIR] [--today D]` prints; AGK runs no meeting, posts nothing and files nothing (`Q-S0043-6`).
24. **The four outputs.**
    - **planning:** the open briefs proposed for the next iteration, in milestone order, then `Depends-on` order, then priority, up to the measured capacity (the P50 of briefs closed per iteration over the throughput of rule 12; `capacity unknown` while uncalibrated, and then no cut), with the forecast of rule 13, under the line `Proposed for the person to accept or change`;
    - **daily status:** at most ten lines: what finished since the previous working day, what is in progress, and what is blocked and why, the blocked lines read from a saved `stalls.py --json` output given with `--stalls FILE` and the facts' `stalled`, to paste or post by the person;
    - **review:** per milestone touched in the iteration, each exit criterion with its evidence links (the merged pull requests, the requirements done, the proof records) and, where `docs/design/signoffs.md` has a `design` row, that version and its link (SPEC-0037 rule 9); a criterion without evidence prints `no evidence yet`;
    - **retrospective:** measured facts only (the estimates within range by size, SPEC-0018 rule 6; the median waits of rule 15; the verdicts of kind `fix` per merged pull request as rework; the stalls by kind) and at most three proposed improvements, each as the text of a candidate brief printed for the person, never filed or applied.

### Where it writes and what does not change (answers 8 and 9)

## Residual

- 2026-11-04: the estimate assumes the future briefs of a size behave like the past ones; a project whose briefs change in kind (a new stack, a new team) is mis-estimated until its history catches up, and the range says nothing about that (due 2027-02-28).
- 2026-11-04: `actual_hours` starts at the first commit (SPEC-0018 rule 3), so the time from a brief's take to its first commit is in the throughput forecast but not in the hours; the hours understate the effort by that time (due 2027-02-28).
- 2026-11-04: the sources are converted to text by the person's tools; a table or a figure lost in conversion is lost to the plan, and no check can tell (due 2027-02-28).

## Open questions

Each is a point the brief leaves open (1 to 8, answer 11 of the brief) or a point found by checking the brief against the code (9 to 19); the reading after it is the most conservative one, and the rules above apply it until a person rules.

- Q-S0043-1: which source formats are accepted? Reading: Markdown and plain text only; PDF, DOCX and the rest are converted to text by the person's own tools before they are added, and no script of the kit converts or fetches one (rule 1).
- Q-S0043-2: may AGK fetch a design link? Reading: never in a check; only in a session, through the person's own design connector, and only the frames the person names in the row; what was read is written into a headed source file that the trace cites (rule 2).
- Q-S0043-3: what is the minimum history for a calibrated estimate? Reading: 10 merged pull requests with a size and actual hours (`[plan] calibration_min`), with at least 3 of each size the milestone's open briefs use and 4 weeks of throughput; below it the estimate is `uncalibrated` (rule 12).
- Q-S0043-4: P50 and P85, or another pair? Reading: P50 and P85, nearest-rank, from 10,000 seeded trials (rule 13).
- Q-S0043-5: the default iteration length? Reading: 10 working days, `[plan] iteration_days`, 1 to 30 (rule 23).
- Q-S0043-6: is a daily status posted automatically? Reading: no; it is printed for the person to paste or post, and AGK posts no ceremony output (rules 23 and 24).
- Q-S0043-7: does a scope change need the owner or any spec approver? Reading: any account in `spec_approvers` of `config/reviewers.yaml`, by `Approve: scope SC-<n> <head>`, never a session (rule 22).
- Q-S0043-8: do estimates count the person's own approval waits? Reading: yes, measured, because they fall inside `actual_hours` where they happen during a pull request; they are part of `verdict_to_cleared` and cannot be shown separately yet, since the facts record no approval time apart from the clearing verdict; the breakdown shows `verdict_to_cleared` as it is and claims no separate figure (rule 15).
- Q-S0043-9: the brief names `docs/plan/trace.md` as a committed file, but the matrix is derived from committed files on every run and principle 5 forbids committing generated files. Reading: `check_plan.py --trace` prints it, and nothing commits it (rule 9).
- Q-S0043-10: the brief has an uncalibrated estimate use "the playbook's default per size", but the playbook format (SPEC-0038 rule 2, `playbook_format.py`) is closed and holds no hours. Reading: an uncalibrated estimate uses the briefs' declared `Expected:` ranges (SPEC-0018), then the owner's optional `[plan] default_hours`, and otherwise counts the brief as without an estimate; no playbook key is added (rule 14).
- Q-S0043-11: may the skill propose a target date, a size or an expected range the sources do not state? Reading: no; each is an open question with `(verify)` until the person sets it, because an invented date is a guess (principle 7) (rule 6).

Reading: they are never added again, only shown as a breakdown, so the estimate does not count a wait twice (rule 15).
