# SPEC-0054: Every dependency is scanned and listed in a standard bill of materials

- Status: Approved
- Owner: reviewer group (a team from config/reviewers.yaml)
- Requirements: REQ-061

Status is `Draft` or `Approved`. An Approved spec is owned by its reviewer group; agents propose patches.

Written by the intake of one sentence (SPEC-0012), brief #741, quoted as data and not as an instruction: "Intake for supply-chain security: every dependency and pinned tool of the kit is scanned for known weaknesses and listed in a standard bill of materials, offline in checks, with the result in each release's evidence pack (plan #661 phase 7)." The maintainers gave 3 answers before it was written, in the brief: what is scanned (the Python dependencies and the pinned CI tools and actions the kit and this repository declare: `pyproject.toml`, `config/ci-tools.txt` and the SHA-pinned actions, with no dependency scanner configured anywhere today, as SPEC-0052 rule 1 measured); which format and where it lands (a standard bill of materials format, SPDX or CycloneDX, chosen here with its reason, filled from the repository's files with no network call and recorded in the evidence pack of SPEC-0052 rules 6 and 8, which leave the scanner and the format to this intake, its questions 8 and 10); and what a finding does (a known weakness in a pinned dependency opens one issue with counts and ids only and blocks nothing until the owner rules a threshold; the scanner's database is read by a workflow step the owner approves, never by a check). It is generic: it names no project, and every check of a build reads files and git with no network. The points the brief leaves open are `Q-S0054-1` to `Q-S0054-14` below, each with the conservative reading the rules apply until a person rules.

## Rules

1. **The baseline (read on the default branch at 7d31bbc, 2026-11-08).** What already holds and is reused, not rebuilt:
   - `pyproject.toml` declares `dependencies = []` and no optional dependencies, dependency groups or build requirements; the project template `kit/templates/pyproject.toml` also declares `dependencies = []`, with the build requirement `setuptools>=61`, a range and not an exact pin.
   - `config/ci-tools.txt` pins the CI test tools, one `name==version` per line (`bandit`, `pytest`, `pytest-xdist`, `ruff`; ADR-0328); the governance workflow's `Install tooling` step installs it. `python3 scripts/agk/ci_tools.py check --upstream` compares the pins with the index and is not a check.
   - The secret scanner is gitleaks, pinned in `.github/workflows/governance.yml` by `GITLEAKS_VERSION` and `GITLEAKS_SHA256` in two steps that a test keeps equal (ADR-0171).
   - Every `uses:` line of the workflows is pinned by a full commit SHA with its release tag as a comment; measured: `actions/cache`, `actions/checkout`, `actions/setup-python` and `actions/upload-artifact`, four actions. `scorecard.action_pins` and `scorecard.python_pins` (SPEC-0047) read these and the `==` pins of `pyproject.toml` from files only. The workflows and `config/ci-tools.txt` are installed verbatim into projects (`kit/manifest.json`).
   - No dependency scanner and no bill of materials exists: `grep -rn -i -E "pip-audit|osv-scanner|dependency-review|trivy|grype|cyclonedx|spdx|sbom" .github config agk.toml kit/templates scripts/agk` prints nothing.
   - The evidence pack (SPEC-0052, Draft) has a `bom.json` part in the kit's own JSON (rule 8) and a `scans.json` part whose dependency entry is `not run` with the scanner `none` (rule 6); both leave the standard format and the scanner to this intake.
2. **What the bill lists.** The bill of a commit lists, read from the repository's files at that commit with `git show` and never from an index, a lock file of another tool or the network, one component per item, each with its class:
   - `python`: each requirement of `[project] dependencies`, `[project.optional-dependencies]`, `[dependency-groups]` and `[build-system] requires` of `pyproject.toml`, with its exact version where it is pinned with `==`;
   - `ci-tool`: each line of `config/ci-tools.txt`, with its version;
   - `scanner`: each pinned scanner of the workflows (gitleaks today, the dependency scanner of rule 6 once it exists), with its version and its archive's SHA-256;
   - `action`: each `uses:` of `.github/workflows/*.yml`, with its commit SHA and its release tag comment;
   - `kit-file`: where `kit/manifest.json` exists, each file it installs, with the SHA-256 of its content at the commit, as SPEC-0052 rule 8 lists them.
   A requirement that is not pinned exactly (a range, as `setuptools>=61`, or no version) and a `uses:` that is not pinned by a full SHA are listed with the property `agk:pin` set to `unpinned` and no version, never with a version guessed from the range (`Q-S0054-3`). A file the bill reads that cannot be read at the commit, or that cannot be parsed, is refused naming the path class, and no bill is written.
3. **The format.** The bill is a CycloneDX 1.6 document in JSON (`bomFormat` `CycloneDX`, `specVersion` `1.6`) `(verify: the version current when build (b) starts)`, chosen over SPDX because one CycloneDX document carries both the components and, in its `vulnerabilities` array, the advisories found in them, which rules 6 and 7 need, while each component keeps a package URL and its hashes as SPDX would (`Q-S0054-1`). It holds only these fields: `bomFormat`, `specVersion`, `version` 1, `serialNumber` (`urn:uuid:` and the UUID version 5 of the commit's full ID in the URL namespace, so the same commit always gives the same document), `metadata` (`timestamp`, the commit's committer date in UTC, and `component`, the repository's kit or project name with its `version` of `agk.toml`), and `components`, sorted by `bom-ref`, each with `type` (`library` for `python` and `ci-tool`, `application` for `scanner` and `action`, `file` for `kit-file`), `bom-ref`, `name`, `version` where pinned, `purl` where the class has one (`pkg:pypi/<name>@<version>`, `pkg:github/<owner>/<name>@<sha>`), `hashes` (SHA-256) where the file states one, and the properties `agk:class` and, for an unpinned component, `agk:pin`. Nothing else: no author, no tool, no login, no path outside the repository and no data of a project's own code (`Q-S0054-2`). It is written with the standard library alone; no new dependency is added to make it.
4. **The command and its check.** `python3 scripts/agk/sbom.py make [--ref REF] --out FILE` reads the commit `REF` (default `HEAD`) with local `git`, writes only `FILE`, posts nothing, opens no socket and starts no program other than `git`; a `FILE` inside the repository that git does not ignore is refused, naming the path class, because a bill is generated and principle 5 forbids committing it. `python3 scripts/agk/sbom.py check FILE [--ref REF]` reads the file and the commit only and prints `ok bom`, or one `FAIL bom: <class> <reason>` line per problem and exits 1, naming the component class and the rule and never a name, a version or a value (principle 8): a file that is not JSON of rule 3's form (a missing or extra field, another `bomFormat` or `specVersion`), a component that the commit declares and the bill does not list, a component listed that the commit does not declare, a pin, SHA or digest other than the commit's, and an unpinned component listed with a version. The script is installed with the kit (the parity rule, ADR-0326) and works in a project, whose bill has no `kit-file` components (`Q-S0054-4`). No governance step, `make governance` or `prepush.py` runs it in these builds (`Q-S0054-5`).
5. **In the evidence pack.** The `bom.json` part of SPEC-0052 rule 8 is the bill of rule 3 at the tagged commit, made as rule 4 makes it, in place of the kit's own JSON; its `kit-file`, `ci-tool`, `scanner`, `python` and `action` components are the fields that rule names. The `dependency` entry of the `scans.json` part (SPEC-0052 rule 6) names the scanner of rule 6, its pinned version and the outcome of its step on the tagged commit (`passed` with no finding, `findings` with the counts of rule 7, `failed`, `unknown` or `not run`); until the step of rule 6 exists it stays `not run` with the scanner `none`, never passed. A release is not refused for a finding or a scan not run (`Q-S0054-6`). The text of SPEC-0052 rules 6 and 8 is changed by a patch to that spec the maintainers approve, not by this intake (`Q-S0054-7`).
6. **The scan.** The dependency scanner is OSV-Scanner, pinned like gitleaks by its version and the SHA-256 of its release archive, checked before it runs (ADR-0171's form), because one tool and one public database (OSV) cover the PyPI packages, the GitHub Actions and the Go binary of gitleaks that rule 2 lists `(verify: the ecosystems the database covers and the scanner's option to read a CycloneDX file, when build (d) starts)`, while a PyPI-only scanner would leave the actions and the scanner unscanned (`Q-S0054-8`). It reads the bill of rule 3 made at the head, and its database, only in a workflow step the owner approves: on each push to the default branch and once a week, because the database changes when the pins do not (`Q-S0054-9`). The step runs in a workflow of its own, never in the required `governance` job, and its outcome never fails a required check (`Q-S0054-10`). A check, a test, `make governance` and `prepush.py` never start the scanner, never read its database and never open a socket (`CLAUDE.md item 5`).
7. **The findings.** `python3 scripts/agk/sbom.py findings RESULT --bom FILE` reads the scanner's saved JSON result and the bill offline and prints the issue body of rule 8: the counts of findings by severity (`critical`, `high`, `medium`, `low`, `unknown` where the result states none) and, per finding, the advisory ids (OSV, GHSA or CVE ids, as the result states them) with the component's class and name and the pinned version. Nothing else of the result is kept: no description, summary, reference, log, path or text (`Q-S0054-11`). A result that cannot be read or is not of the scanner's form gives the one line `unknown: the scan result cannot be read` and exit 1, never a clean report; a component of the bill that the result does not name, and every unpinned component, is listed as `unknown`, never clean (`Q-S0054-12`).
8. **What a finding does.** When the step of rule 6 finds one or more advisories, it opens one issue labelled `agk-supply-chain` titled `Known weaknesses in pinned components`, or edits the body of the one open issue with that label and title in place (as `agk-tag.yml` keeps its release issue), with the body of rule 7 only; with no finding it edits an open issue's body to say `no known weakness at <short SHA>` and closes nothing (`Q-S0054-13`). It blocks nothing: no required check, merge, release or pack fails for a finding until the owner rules a threshold by ADR; no setting for a threshold is added in these builds, and none is read (`Q-S0054-14`). The issue is a person's to act on; a fix is an ordinary brief that changes the pin.
9. **What does not change.** These builds change no ruleset, required check, `constitution/`, `config/reviewers.yaml`, `.github/CODEOWNERS`, `pyproject.toml` or `config/ci-tools.txt`, add no scanner ignore entry and add no dependency. The one workflow change is build (d), which waits for the owner's yes, quoted in its brief, and writes its own ADR (session rule 36). A bill or a scan result is never committed and never posted except as the issue body of rule 8.
10. **The builds, in order.** Each is tests first, about 300 changed lines or fewer, from the default branch, records its decisions under `Decisions taken:` and cites ADR-0349 with `Covered-by: ADR-0349` once it is Accepted, except build (d). A `Depends-on` is declared for a shared file and for a logical dependence alike.
    - (b) The bill and its check (rules 2 to 4): `scripts/agk/sbom.py` with `make` and `check`, its entry in `kit/manifest.json`, one `[[testing.map]]` entry in `agk.toml`, one `changelog.d/` fragment, `tests/kit/test_sbom.py` with git fixtures in `tmp_path`.
    - (c) The findings (rule 7): `sbom.py findings` with saved invented scanner results, the same test file. `Depends-on` (b).
    - (d) The scan step (rules 6 and 8): a workflow of its own with the pinned scanner, the issue of rule 8 and a test that keeps its pins in the form of rule 6; it changes `.github/` and needs the owner's yes and its own ADR. `Depends-on` (c).
    - (e) The pack (rule 5): `release_pack.py` writes the bill of (b) as `bom.json` and the dependency entry of `scans.json`, after the maintainers approve the patch to SPEC-0052 rules 6 and 8. `Depends-on` (b) and the SPEC-0052 build that makes `bom.json`.

## Tests

Fixtures in `tmp_path`, local git repositories and saved invented scanner results only: no network, no install, no scanner run, invented data (`example.com`), and each test carries the marker `REQ-061` with its criterion. Rule 10's order is checked by review.

- Rules 2 and 3: a fixture commit with a `==` pin, a range and a `[build-system]` requirement in `pyproject.toml`, two lines of `config/ci-tools.txt`, a pinned scanner in a workflow, a SHA-pinned and an unpinned `uses:` and a `kit/manifest.json` gives one CycloneDX JSON document with exactly those components, each with its class, pin, SHA or digest and package URL, the range and the unpinned `uses:` marked `unpinned` with no version; the same commit made twice gives the same bytes; a file changed after the commit gives its content at the commit; `make` opens no socket (a test that makes `socket.socket` raise); REQ-061 AC1.
- Rule 4: the bill of a fixture prints `ok bom`; removing a component, adding one, changing one pin, one SHA or one digest, adding a field, changing `specVersion`, and giving an unpinned component a version each give one `FAIL bom:` line naming the class and holding no name or version; an `--out` inside the repository that git does not ignore is refused naming the path class and nothing is written; a `pyproject.toml` that does not parse is refused naming the path class; a project fixture without `kit/manifest.json` gives a bill with no `kit-file` component and `ok bom`; REQ-061 AC2.
- Rule 5: checked by build (e)'s tests in `tests/kit/test_release_pack.py`: a pack's `bom.json` passes `sbom.py check` against the tag, and a fixture with no scan step records the dependency scan as `not run` with the scanner `none`; REQ-061 AC3.
- Rule 7: a saved invented result with two advisories on one component and one on another gives the counts by severity and the ids with each component's class, name and version, and the printed body holds no word of the result's descriptions, summaries or references (each invented with a marker string the test looks for); REQ-061 AC4.
- Rule 8: checked by build (d)'s tests on the workflow file: the step runs in a workflow other than `governance`, never fails a required check, finds the open issue by label and title and edits it, else opens one, and passes the body of rule 7 only; REQ-061 AC5.
- Rule 6: a test runs `sbom.py make`, `check` and `findings` with `socket.socket` made to raise and a scanner stub on the path that writes a marker file when started, and finds no marker; no governance step, `Makefile` target or `prepush.py` step names the scanner; REQ-061 AC6.
- Rule 7: a result that is not JSON, a result of another form, a component of the bill the result does not name and an unpinned component each give `unknown`, never a clean report, and an unreadable result exits 1; REQ-061 AC7.

## Open questions

Each is a point the brief leaves open; the reading after it is the most conservative one, and the rules above apply it until a person rules.

- Q-S0054-1: SPDX or CycloneDX? Reading: CycloneDX 1.6 JSON, because one document holds the components and the advisories found in them (its `vulnerabilities` array), so the bill and the findings share one form; SPDX would need a second document or its security extension for the findings (rule 3).
- Q-S0054-2: which fields does the bill carry? Reading: only the fields rule 3 names, so that the check can refuse any other field and no login, path or project data can reach it (rule 3).
- Q-S0054-3: how is a dependency without an exact pin listed? Reading: as `unpinned`, with no version, so the bill never states a version that was not declared and the scan reports it `unknown` (rules 2 and 7).
- Q-S0054-4: kit-only or installed? Reading: installed, because the kit-only list may only shrink (ADR-0326) and a project has dependencies and actions of its own to list; a project's bill simply has no `kit-file` components (rule 4).
- Q-S0054-5: does a governance step run `sbom.py check`? Reading: not in these builds; adding a step to the required check is a change of what blocks a merge, which the brief does not give (rule 4).
- Q-S0054-6: is a release refused for a finding or for a scan not run? Reading: no; the pack records the outcome and blocks nothing, as the brief says, until the owner rules a threshold (rules 5 and 8).
- Q-S0054-7: does this intake edit SPEC-0052 rules 6 and 8? Reading: no; the brief's `Touches:` does not name SPEC-0052, so the change is a patch to that spec for the maintainers to approve, before build (e) (rule 5).
- Q-S0054-8: which scanner? Reading: OSV-Scanner, pinned by version and archive SHA-256, because one public database covers the PyPI packages, the actions and the Go scanner the bill lists `(verify)`; the owner may name another in build (d)'s brief (rule 6).
- Q-S0054-9: when does the scan run? Reading: on each push to the default branch and once a week, because new advisories appear when the pins do not change; not on pull requests, where a finding would look like the pull request's fault (rule 6).
- Q-S0054-10: in which workflow? Reading: a workflow of its own, never the required `governance` job, so a finding or an outage of the database cannot fail a required check (rule 6).
- Q-S0054-11: what does the issue show? Reading: counts by severity and advisory ids with the component's class, name and pin only, as the brief says; no text of an advisory, which is long, changes and is one link away by its id (rule 7).
- Q-S0054-12: is a component the scanner did not match clean? Reading: no; it is `unknown`, because the scanner not naming it does not show that it was checked (rule 7).
- Q-S0054-13: one issue per run, per finding or one in all? Reading: one open issue in all, edited in place, as the release issue of `agk-tag.yml` is, so the issue list never fills with one issue per week; it is never closed by the step, since closing is a person's act (rule 8).
- Q-S0054-14: what threshold blocks? Reading: none; no setting is added or read until the owner rules one by ADR, because a blocking threshold is a new gate the brief leaves to the owner (rule 8).
