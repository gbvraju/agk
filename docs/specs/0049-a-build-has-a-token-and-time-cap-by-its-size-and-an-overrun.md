# SPEC-0049: A build has a token and time cap by its size, and an overrun stops it

- Status: Draft
- Owner: reviewer group (a team from config/reviewers.yaml)
- Requirements: REQ-056

Status is `Draft` or `Approved`. An Approved spec is owned by its reviewer group; agents propose patches.

Written by the intake of one sentence (SPEC-0012), brief #671: "Every brief declares a token and a time cap by its size; a builder reports its usage at each milestone; the conductor's sweep marks a build over its cap as OVER and stops it; the overrun is a lesson row with its cause, and the caps are tuned from the weekly scorecard." The owner's direction, quoted as data from the brief (2026-11-06): strategy review item 1, "go ahead with your recommendation". It is a ruled exception to plan #542's requirement freeze, like REQ-052 to REQ-055. It is generic: it names no project, and every check of a build reads files, git and saved responses with no network. Everything it reuses is named below with what the default branch holds today (read at f6a7108 on 2026-11-06); where the brief's wording differs from the code, the rule follows the code and says so. The points the brief leaves open are `Q-S0049-1` to `Q-S0049-20` below, each with the conservative reading the rules apply until a person rules. Negative cases: a malformed cap table; a figure that was not reported (never read as 0 and never as over); a sweep that posts, stops or changes anything; a session that stops another; an over-cap pull request resumed or cleared before a person rules; a change of the caps without its evidence; and a cap read for review or merge work each fail, are refused or do not happen, naming the rule or the setting and never a value.

## Rules

### What exists and is reused

1. **Reused, never duplicated.** Each name below was read on the default branch; the builds call them and change none of their rules except where a rule here says so:
    - The size: every brief has one line `Size: S`, `Size: M` or `Size: L` (SPEC-0018 rule 1, checked by `scripts/agk/check_brief.py`). SPEC-0018's `Expected: <low>-<high> hours` is a pull request body line and is not read for a cap (`Q-S0049-3`).
    - The usage: every builder `Report:` line ends with `Usage: <n> tokens` or `Usage: not shown` (SPEC-0045 rule 8), read by `metrics.usage_of` (the pattern `REPORT_USAGE` in `scripts/agk/metrics.py`), which counts a missing figure as `not-reported`, never 0. The read-only sum by kind of SPEC-0045 build (d) is not on the default branch yet.
    - The milestones and the progress line: session rule 7 (the pushes) and session rule 8 (one `Progress: <head> done <n>/<m>; next: <step>` comment, edited in place).
    - The messages: `session.py tell --session ID --text ...` posts `Tell: <id> <message>` on the one open `agk-conductor` issue, and `session.py watch --pr N --session ID` ends on it with the line `tell <message>` (session rules 10 and 32).
    - The sweep: `conductor.py sweep` (ADR-0308, brief #643, merged as #644), GET only, posts nothing and writes no file; it prints one line `#<n> <head7> <state> <age>` per open pull request and marks `LATE` an unanswered `Question:` or `Report:`.
    - The stalled pull request: `session.py next` offers an open draft or builder pull request with no change for `stall_hours` (`offer_stalled`, SPEC-0033 rule 5) and `--take` takes it over.
    - The lesson: the conductor catch log `docs/runs/conductor-catches-N.md` (brief #604), one row per incident with the date, the kind, counts and timings, the cost, the cause and the guard; the conductor writes no project file, so it puts the row in the brief it files or in its report for a person (`.claude/agents/conductor.md`, "Operating lessons"). The guard ladder of brief #645 (#646, open) is not relied on.
    - The scorecard: SPEC-0047 (Draft, the intake #673, open). It has `ci_minutes_per_merge` and `lead_time_hours` and no token row (`Q-S0049-15`).
    - The rule budget: `config/rule-budget.txt` (ADR-0310), whose counts may only go down.

### The caps

2. **The cap table.** An optional `[caps]` table of `agk.toml` holds three keys, `S`, `M` and `L`, each an inline table with exactly two keys, `tokens` and `hours`, each a whole number above zero: `S = { tokens = <n>, hours = <h> }`. `config.py` reads it (build (b)). Without the table no build has a cap and the sweep marks nothing over, so a project that sets nothing sees no change (`Q-S0049-1`). A table that lacks one of the three sizes or one of the two keys, holds an unknown key, a value that is not a whole number above zero, or a size whose cap is below the cap of a smaller size (S above M, M above L) is refused naming the setting (`setting: caps.<key>`), never the value (principle 8). `agk.toml` is protected, so the table changes only with an ADR in the same pull request (rule 14). The kit ships no default values (`Q-S0049-2`).
3. **Which cap a build has.** The cap of a builder pull request is the cap of the size that the `Size:` line of the brief its `Brief: #n` line names gives, read from the brief issue's body with `check_brief.py`'s parse. A brief whose `Size:` line is missing or cannot be read gets the `L` cap and its line says `size unknown`; a guess never stops a build early (`Q-S0049-4`). A brief with several builds caps each build's pull request on its own with the brief's one size (`Q-S0049-5`).

### What a builder reports

4. **Usage at each milestone.** At each push of session rule 7, the builder's one progress line of session rule 8 ends with `; Usage: <n> tokens` when the runtime shows the figure, else `; Usage: not shown`, edited in place as today (build (c)). Every `Report:` line keeps the ending of SPEC-0045 rule 8, unchanged. Each figure is the tokens used since the builder's previous `Report:` on the same pull request (or since the take, for the first), so that the sum of `metrics.usage_of` counts each token once; a builder whose runtime shows only a session total subtracts the figure it reported last (`Q-S0049-6`). No check refuses a progress or report line: the comments are on GitHub and a check makes no network call (SPEC-0045 rule 8, CLAUDE.md item 5).
5. **The tokens used.** The tokens a build used are the sum of `metrics.usage_of` over its author's `Report:` lines plus the figure of its progress line when that line was edited after the newest `Report:`. When no figure was reported at all the tokens are `unknown`; `unknown` is never over a cap and never 0 (SPEC-0045 rule 8).
6. **The hours used.** The hours a build used count only the time the builder holds the turn, from saved comments and the pull request: from the `taken:` comment of the brief (session rule 18; for a later build, the one that names that build) to the first `Report: <head> ready for review` by the pull request's author; then from each `Verdict: fix list` or `Correction:` by a listed verdict author to the author's next `Report:`; the last open interval runs to the time of the sweep. The time from a `Question:` by the author to the next comment by a listed verdict author is the conductor's, not the builder's, and is not counted. Waiting for CI, a verdict, a merge or a person never counts. When the `taken:` comment cannot be read the hours are `unknown` and never over (`Q-S0049-7`). Hours are given with one decimal, rounded half up.

### The sweep and the stop

7. **The sweep marks, and only marks.** `conductor.py sweep` gains, after its pull request lines and before the default branch line, one line per cap a build is past: `OVER #<brief> <used>/<cap> tokens #<pr>` or `OVER #<brief> <used>/<cap> hours #<pr>`, where `#<brief>` is the brief its `Brief:` line names (build (b), through a read-only `scripts/agk/caps.py`, new). A build with an unknown figure has no `OVER` line for that unit and, when it has no figure at all, one line `UNKNOWN #<brief> tokens #<pr>`. The sweep still makes GET calls only, posts nothing, writes no file and stops, closes, labels or changes nothing (`Q-S0049-8`). The brief's `OVER <brief> <used>/<cap>` is read as this line, with the unit and the pull request added so that one line is enough to act on.
8. **Who stops a session.** The conductor, never the sweep and never another builder: on an `OVER` line the conductor sends `python3 scripts/agk/session.py tell --session <id> --text "stop: over cap <used>/<cap> <unit>"`, with `<id>` the session of the newest `taken:` or `taken over:` comment of the build; its guard already allows `session.py tell`. The brief says "by rule 18"; session rule 18's only ending line is `Assign: <id> none`, which ends a session waiting for an assignment, not a running build, so the stop is a `Tell:` of session rule 32, and build (c) adds to rule 32 the one sentence that lets a builder act on a `Tell: <id> stop: over cap ...` by a listed verdict author as rule 9 says (`Q-S0049-9`). A person may send the same line. No session stops, kills or messages another session by any other channel.
9. **What the builder does.** A builder that reads the stop line, from `watch` or from `session.py inbox`: commits a `checkpoint:` of its work; runs `session.py push-check` and `prepush.py` and pushes only if they pass (session rule 31), and otherwise pushes nothing and names its last pushed head; keeps the branch and the pull request (never closes, never deletes a branch, never force-pushes); leaves a draft a draft, and leaves a pull request it already marked ready as it is, because the REST routes have no way back to draft (`Q-S0049-10`); posts one comment `Report: <head> over cap <used>/<cap> <unit>; Usage: <n> tokens` (or `Usage: not shown`); posts no `released:`, so the take stays and `session.py next` gives the brief to no one else; starts no `watch`; and ends. The `Report:` is its last comment (session rule 17).
10. **Parked until a person rules.** A pull request whose newest `Report:` by its author is an `over cap` report, with no ruling after it, is parked: `session.py next` does not offer it as stalled (`offer_stalled`, build (c)), and the conductor gives it no clearing verdict. A person rules in one of three ways: closes the pull request; edits the brief's `Size:` line to a larger size, after which the build has that size's cap and may be offered again as stalled when it is no longer over; or, when the size is already `L`, splits the rest of the work into a new brief and closes or finishes this one by a smaller scope that a verdict clears (`Q-S0049-11`). A session never edits a `Size:` line to lift its own cap, and never rules on its own overrun.

### The lesson

11. **One lesson row per overrun.** Every `over cap` report is an incident of the conductor catch log: one row of kind `over-cap` with the date (from `date -u`), the brief, the pull request, the size, the used figure and the cap with their unit, one cause from the fixed list below, the cost (the used figure; `unknown` where it is unknown, never 0) and the guard. The row holds counts and numbers only, never a transcript, a log, a comment's text or a login. As for every catch-log row, the conductor writes no project file: it puts the row in its report for a person to add, or in the brief it files for the guard (`.claude/agents/conductor.md`). The catch log's test (`tests/kit_dev/test_conductor_catches.py`) gains the kind and the cause list (build (d)).
12. **The causes.** One of: `loop` (the same check failed on two or more heads of the pull request in a row, or the same file was changed in three or more commits with no green run between); `wander` (a file the pull request changes is outside its brief's `Touches:` globs); `estimate` (neither of those, and the work done fits the brief: the size was too small); `blocked` (more than half the counted hours lie between a tool error or a refused push the builder reported and its next push); `unknown` (the evidence cannot be read). `python3 scripts/agk/conductor.py over --pr N` (build (d), GET only) prints the counts each cause rests on, one line each, and the cause that the first matching rule gives in that order; the conductor may write a different cause only with the count that supports it (`Q-S0049-12`).

### How the caps change

13. **Tuned from evidence, never by feel.** A pull request that changes the `[caps]` table carries an ADR that names `agk.toml` (CLAUDE.md item 3) and one body line `Caps-evidence: scorecard <week> usage <S>/<M>/<L>`, where `<week>` names the weekly scorecard of SPEC-0047 it read (the audit issue and its week) and `<S>/<M>/<L>` are the measured token and hours figures (P50 and P85 per size) of the merged builds of the four weeks before it. `check_protected_changes.py` (build (e)), which already reads the pull request body that CI passes to it, fails a change of the `[caps]` table on the merge base with no `Caps-evidence:` line, naming the rule and never a value; a body line that does not have the shape fails the same way. Whether the figures are the right ones is the review's (`Q-S0049-13`).
14. **The first caps of this repository.** Build (e) sets this repository's `[caps]` table from the measured figures of rule 13: each size's cap is its P85 times 1.5, rounded up (tokens to the next 100,000, hours to the next whole hour), and states the inputs. When a size has fewer than five merged builds with a readable figure in the four weeks, build (e) sets no table and stops and asks; it never invents a number (`Q-S0049-14`).

### Scope and limits

15. **No cap on review or merge work.** A cap is read only for an open pull request whose body has a `Brief: #n` line and is built by a builder session. The conductor, the architect, a review agent, the shadow, `merge_cleared.py` and a person's work are never capped and never read the table. No cap changes a check, a test, a gate, a required run or what a build must read (principle 11); a build stopped over its cap has lowered nothing, and the next session that continues it meets the same gates.
16. **Refusals, network, data.** Every refusal names the rule or the setting and never a value (principle 8). Every check of this spec reads files, git and saved responses only; `conductor.py sweep`, `conductor.py over` and `caps.py` are read-only commands with GET calls, run by the conductor or a person, never inside a governance check or `prepush.py` (CLAUDE.md item 5). Tests use invented data (`example.com`) and saved responses; no pilot or customer data is read, quoted or used.
17. **The rule budget.** Builds (c) and (d) add text to `config/session-rules.md` and `.claude/agents/conductor.md`, whose counts in `config/rule-budget.txt` may only go down (ADR-0310): each keeps its file within its line by retiring or shortening text in the same pull request, or by making a rule a check, and lowers the counts it cuts; neither raises a count (`Q-S0049-16`).
18. **The builds, in order.** Each is tests first, about 300 changed lines or fewer, from the default branch, records its decisions under `Decisions taken:` and cites `Covered-by: ADR-0324` once ADR-0324 is Accepted (session rule 36). A build that finds it must change an Approved spec stops and asks.
    - (b) The table and the marks (rules 2, 3, 5 to 7): the `[caps]` reader and its refusals in `scripts/agk/config.py`; `scripts/agk/caps.py` (new, installed, read-only: the cap of a pull request, the tokens and the hours used); the `OVER` and `UNKNOWN` lines of `conductor.py sweep`; `tests/kit/` with saved responses and a `gh` stub; the `[[testing.map]]` entry in `agk.toml`; the line in `kit/manifest.json`; a changelog fragment. No dependence.
    - (c) The builder's side (rules 4, 8 to 10): the progress line's usage in session rule 8, the stop sentence in session rule 32, the steps of rule 9, in `config/session-rules.md` within its budget; `session.py`'s stalled offer skipping a parked pull request; `tests/kit/`. `Depends-on` (b).
    - (d) The conductor's side (rules 8, 10 to 12): the lines of `.claude/agents/conductor.md` (send the stop on an `OVER` line, no clearing verdict while parked, the lesson row) within its budget; `conductor.py over --pr N`; the guard's allowance for it in `.claude/hooks/conductor_guard.py`; the `over-cap` kind in `tests/kit_dev/test_conductor_catches.py`; `tests/kit/`. `Depends-on` (c).
    - (e) The caps by evidence (rules 13 and 14): the `Caps-evidence:` rule in `scripts/agk/check_protected_changes.py`, the token and hours figures per size beside SPEC-0045 build (d)'s sum by kind, this repository's `[caps]` table in `agk.toml`, `tests/kit/`. `Depends-on` (d), SPEC-0045 build (d) and SPEC-0047 build (b) (`Q-S0049-17`).

## Tests

Fixtures in `tmp_path`, saved GitHub responses and a `gh` stub only: no network, no install, no model, invented data (`example.com`), and each test carries the marker `REQ-056` with its criterion. Rule 18's order is checked by review.

- Rule 2: no `[caps]` table gives no cap and a sweep with no `OVER` line; a full table is read; a table missing `M`, missing `hours`, with an unknown key, a string, 0, a negative number, a fraction and `S` above `M` are each refused naming `caps.<key>` and never the value; REQ-056 AC1.
- Rule 4: the builder text of session rule 8 shows the `Usage:` ending of the progress line; saved progress and report comments with `Usage: 1200 tokens`, `Usage: not shown` and no usage give `not-reported`, never 0; `metrics.usage_of`'s output on the saved reports is byte for byte unchanged; REQ-056 AC2.
- Rules 3, 5 to 7: saved pull requests, briefs and comments give the tokens and hours used; a build past its token cap and one past its hours cap each print one `OVER` line with the unit and the pull request; hours waiting on a verdict, CI or a question are not counted; a brief with no `Size:` line is read at the `L` cap with `size unknown`; a build with no figure prints `UNKNOWN` and no `OVER`; the stub records GET calls only and a before and after snapshot shows no file written; REQ-056 AC3.
- Rules 8 to 10: the text of session rule 32 holds the stop sentence and the conductor's role file the `session.py tell` step; a saved `Tell: <id> stop: over cap ...` by a listed verdict author ends `watch` with `tell`, and the same line by another account does not count; `offer_stalled` on saved responses skips a parked pull request and offers it again after the brief's `Size:` is raised and the build is under the new cap; no command of the kit closes a pull request, deletes a branch or posts `released:` on a stop; REQ-056 AC4.
- Rules 11 and 12: `conductor.py over` on saved responses prints the counts for `loop`, `wander`, `estimate`, `blocked` and `unknown` cases and the first matching cause; the catch-log test accepts an `over-cap` row with counts and refuses one with a cause outside the list or a planted invented token; REQ-056 AC5.
- Rule 13: a fixture change of `[caps]` with a `Caps-evidence:` line passes `check_protected_changes.py`; without it, and with a malformed one, it fails naming the rule and never a value; a change that leaves `[caps]` alone needs no line; REQ-056 AC6.
- Rule 15: the conductor's, the architect's, the shadow's and the review agent's role files and `merge_cleared.py` name no cap and read no `[caps]` table; with a table set, the outputs of `check_pr_body.py`, `prepush.py --quick` and `session.py kind` on fixtures are byte for byte those without it; REQ-056 AC7.

## Open questions

Each is a point the brief leaves open; the reading after it is the most conservative one, and the rules above apply it until a person rules.

- Q-S0049-1: does a project without `[caps]` get a default cap? Reading: no; without the table nothing is capped and the sweep marks nothing, so no project's builds stop because of a kit default it never chose (rule 2).
- Q-S0049-2: which numbers are the caps? Reading: the kit ships none; this repository's are set by build (e) from its own measured figures, and a project sets its own by an ADR (rules 2 and 14).
- Q-S0049-3: the brief says "every brief declares a token and a time cap by its size". Reading: the brief declares only its `Size:` (SPEC-0018 rule 1, unchanged); the cap comes from the size by the table, so no brief template and no `check_brief.py` rule changes, and SPEC-0018's `Expected:` hours stay an estimate, never a cap (rules 1 and 3).
- Q-S0049-4: a brief whose `Size:` cannot be read. Reading: the `L` cap with `size unknown` on the line, so a guess never stops work early; `check_brief.py` already fails such a brief when it is filed (rule 3).
- Q-S0049-5: a brief with several builds. Reading: each build's pull request is capped on its own with the brief's one size; a brief does not carry a cap per build until a person adds one by a later decision (rule 3).
- Q-S0049-6: what does a `Usage:` figure measure? Reading: the tokens since the builder's previous `Report:` on the same pull request, so the existing sum counts each token once; this is how `metrics.usage_of` already sums (rule 4).
- Q-S0049-7: from when are hours counted? Reading: only while the builder holds the turn, from the `taken:` comment, excluding time waiting for CI, a verdict, an answer, a merge or a person; an unreadable `taken:` gives `unknown`, never an `OVER` (rule 6).
- Q-S0049-8: may the sweep stop a build itself? Reading: no; it stays GET only and marks, and the conductor acts (rules 7 and 8).
- Q-S0049-9: the brief says the conductor stops a session "by rule 18". Reading: session rule 18's `Assign: <id> none` ends only a session waiting for an assignment, so the stop is a `Tell:` of session rule 32, and build (c) adds the one sentence that lets a builder act on it; a `Tell:` stays information for everything else (rule 8).
- Q-S0049-10: "the branch is kept, draft". Reading: a draft stays a draft and a pull request already marked ready stays ready, since the REST routes cannot convert it back; in both, the `over cap` report parks it (rules 9 and 10).
- Q-S0049-11: how does an over-cap build go on? Reading: only by a person: a raised `Size:` line, a split into a new brief, or a close; a session never lifts its own cap, and a parked pull request is never offered as stalled (rule 10).
- Q-S0049-12: who chooses the cause? Reading: `conductor.py over` prints the counts and the first matching cause; the conductor may differ only with a count; the row holds counts only (rule 12).
- Q-S0049-13: "caps change only by a pull request that cites the scorecard's cost column". Reading: an ADR naming `agk.toml` and a `Caps-evidence:` line checked for presence and shape by `check_protected_changes.py`; the figures themselves are judged by review (rule 13).
- Q-S0049-14: what if a size has too few measured builds? Reading: fewer than five readable builds of a size in four weeks means no table is set and build (e) asks; no number is invented (rule 14).
- Q-S0049-15: SPEC-0047 (Draft, #673) has no token row; its cost numbers are `ci_minutes_per_merge` and `lead_time_hours`. Reading: the `Caps-evidence:` line cites the scorecard week for those and the token and hours figures per size from SPEC-0045's sums; adding a token row to SPEC-0047 is that spec's own decision, and this intake changes no file of #673 (rule 13).
- Q-S0049-16: the rule budget. Reading: builds (c) and (d) keep `config/session-rules.md` and `.claude/agents/conductor.md` within their counts by cutting text in the same pull request; a raised count would be a change of ADR-0310's decision and needs its own ADR (rule 17).
- Q-S0049-17: dependences. Reading: build (e) waits for SPEC-0045 build (d) (the sum by kind, not on the default branch) and SPEC-0047 build (b) (the scorecard reader), declared with `Depends-on` on the brief issue that names them; builds (b) to (d) depend on nothing outside this spec (rule 18).
- Q-S0049-18: may the builds cite `Covered-by: ADR-0324`? Reading: yes for every build of rule 18, since none changes `constitution/`, `config/reviewers.yaml`, a workflow, the ruleset or `.github/CODEOWNERS`; ADR-0324 names each class they change (session rule 36).
- Q-S0049-19: does a cap apply in personal mode or local mode? Reading: the cap reads GitHub comments, so in personal mode (a sidecar, SPEC-0041) the sweep is not run and nothing is capped; in local mode (`docs/guides/local-mode.md`) GitHub is still read and the caps apply as written (rule 15).
- Q-S0049-20: which numbers does this intake take? Reading: REQ-056, SPEC-0049 and ADR-0324 as the conductor reserved them (`session.py ids` printed ADR-0316 on 2026-11-06; the conductor's reservation is the number used); `intake.py check` is run with `--ids` holding these numbers.
