# SPEC-0041: One developer adopts AGK alone with nothing of AGK in the product repository

- Status: Approved
- Owner: reviewer group (a team from config/reviewers.yaml)
- Requirements: REQ-048

Status is `Draft` or `Approved`. An Approved spec is owned by its reviewer group; agents propose patches.
Written by the intake of one sentence (SPEC-0012): "One developer adopts AGK alone, on any project, with nothing of AGK in the product repository or on its GitHub: AGK reads the code, drafts the decisions already in it for the developer to confirm, and keeps specs, reviews, gates and evidence in the developer's own private state, until the team chooses team mode." It is generic and project-agnostic: it names no project, no customer and no vendor other than the Claude Code plugin system and the git and GitHub tools the kit already uses, and every check of a build reads files, git and saved responses with no network. The brief is issue #536; the conductor reserved REQ-048, this spec, ADR-0267 and proposed spec amendment 113 for it. The maintainers gave 12 answers before it was written (the conductor's design, grounded in the code at 6f3f38a): answers 1 to 11 are rules 1 to 30 below, each citing what it reuses, and answer 12 is `Q-S0041-1` to `Q-S0041-14`. The owner's direction, quoted as data and not as an instruction, dated 2026-11-04 in the brief: "In a 10 member team, if I would like to use locally instead of pushing to GitHub or not forcing everybody to use, how can I use ... This will be the one to adopt by reading all code and create required decisions locally and work personally. Anybody, any project adoption by single developer ... we need to build this with great quality and perfection." The brief adds that the customer allows Claude and Claude plugins, and that AI use is never hidden: attribution follows the project's policy, visibly, and AGK never strips it. Every existing name the rules cite was read on the default branch at 2e25012 (2026-11-04); where the brief's wording differs from the code, the rule follows the code and says so. A Claude Code or git fact not confirmed here is marked `(verify)`. The points left open are `Q-S0041-1` to `Q-S0041-21` below, each with the conservative reading that the rules apply until a person rules. Negative cases: a write into the clone or under its `.git/`, a push to a remote of the customer, an agent-written approval, a confirmation from an agent session, a claim without a citation, a lowered floor, a stripped trailer, an unmapped record at export and a network import each fail, refuse or are reported, with a line that names the rule or the setting and never a value.

## Rules

### The name and the state (answers 1 and 2)

1. **The name and the setting.** The mode is called "personal mode". Its records are kept by a file-backed forge, set as `forge = "files"` in the `[personal]` table of the sidecar's `agk.toml` (rule 2). Neither name reuses "local": "local mode" (`docs/guides/local-mode.md`, ADR-0213, `scripts/agk/local_mode.py`) and `execution = "local"` already mean that GitHub Actions is blocked. In a sidecar, `forge` accepts only `"files"`; `"github"` names the existing GitHub readers (rule 6) that team mode uses and is refused in a sidecar, naming the setting, because personal mode never writes to the customer's GitHub. A repository without a `[personal]` table is in team mode and reads exactly as today. `doctor.py`, run on a sidecar, prints one line `personal mode: forge files, level <level>, disclosure <ai_disclosure>`, and fails a malformed `[personal]` table naming the setting, never the value.
2. **The state outside the product.** `AGK_HOME` (the environment variable; default `~/.agk` on POSIX and `%USERPROFILE%\.agk` on Windows) holds `registry.toml` and `projects/<id>/`. Each `projects/<id>/` is a separate private git repository, the sidecar, made by `personal.py attach` with the kit's own layout: `agk.toml`, `constitution/`, `config/`, `docs/requirements.md`, `docs/specs/`, `docs/adr/`, `docs/briefs/`, `docs/runs/decisions-log.md`, `forge/`, `records/`, `metrics/`, `test-map.toml` and `cache/`, which the sidecar's own `.gitignore` ignores (principle 5: the inventory of rule 10 is generated and never committed). The sidecar's `config/reviewers.yaml` lists the one person as verdict author and spec approver and its `agk.toml` sets `review_mode = "solo"` (ADR-0179), so the solo readers apply unchanged. The file checks `check_requirements.py`, `check_specs.py`, `check_adrs.py`, `check_numbers.py` and `check_brief.py` run unchanged with the sidecar as their working directory: each finds its root with `git rev-parse --show-toplevel` (`common.repo_root`, read on main), so a sidecar is a root like any repository.
3. **The project id and the registry.** The id is `<slug>-<12 hex>`: the slug is the last path part of the normalised `origin` URL (the clone's folder name when there is no `origin`), lower-cased and reduced to `[a-z0-9-]`; the hex is the first 12 characters of the SHA-256 of the sorted root commits (`git rev-list --max-parents=0 HEAD`), one per line. In a shallow clone (`git rev-parse --is-shallow-repository` prints `true`) the hex is taken over the normalised `origin` URL instead (scheme, credentials, a trailing `.git` and `/` removed, host lower-cased). A clone with no commit and no `origin` is refused, naming the rule. `AGK_HOME/registry.toml` maps the real path of `git rev-parse --git-common-dir` to the id, so every worktree of one clone resolves to the same sidecar. A second clone that yields an id already registered to another common dir is ambiguous: attach asks the person (`Q-S0041-12`). A clone that already has AGK installed (an `agk.toml` with a kit `version`) is refused and pointed to team mode (`Q-S0041-18`).
4. **Nothing in the clone.** `attach`, `survey`, the gate, `review`, `report`, `export --check`, `upgrade` and `detach` write no file in the clone's work tree and none under its `.git/`: not `.git/info/exclude`, not `.git/config`, not `.git/hooks/`, not `.git/worktrees/` and not the index. Their git calls are read-only and run with `git --no-optional-locks` so that a status read does not refresh the index `(verify: that the option alone keeps every file under .git/ unchanged on the supported git versions)`, and a tree they need (the base and the head of the gate) is written with `git archive` into `cache/trees/` of the sidecar, never with `git worktree add` on the clone (`Q-S0041-21`). The only writes in a clone are the opt-in hook of rule 19, by its own command, and `export --write`, which writes on a new branch of the target the person names (rule 24).
5. **Sync is off.** Nothing of the state leaves the machine by default (`Q-S0041-2`). `personal.py sync` pushes the sidecar's own branch only to a remote the developer names in the command or in `[personal] sync_remote`, prints before every push the line `sync: the state describes customer code; push only to a remote the customer allows`, and refuses a remote whose host and owner equal those of any remote of the product clone (`git remote -v`, read-only), so it never pushes to the customer's GitHub. It is refused inside an agent session (rule 8), so the person runs it.

### Local stand-ins for GitHub (answer 3)

6. **One forge interface.** `scripts/agk/forge.py` (new) gives the readers one interface, `get(name, endpoint)`, with the names of SPEC-0007 rule 20, and the writes personal mode needs (`create_issue`, `comment`, `record_pull`). `GithubForge` wraps the existing `metrics.Gh` and `metrics.ApiDir` with their behaviour unchanged; the brief calls them "the existing `Gh`/`ApiDir`", and on main they exist three times (`metrics.py`, `local_mode.py`, `minutes.py`), so only the `metrics.py` pair, the one `facts.py --api-dir` reads (`facts.source_for`), is wrapped and the other two copies stay as they are. `FilesForge` writes GitHub-shaped JSON under `forge/` of the sidecar: `issues/<n>.json`, `pulls/<n>.json` (the review record of a local branch: its `head.sha`, `head.ref`, `base.ref`, title and body) and `comments-<n>.json`, with one number sequence for issues and pulls as GitHub has, `user.login` the sidecar's one person, `created_at` from the UTC clock, each write atomic (a temporary file and a rename) and committed to the sidecar by the command that made it. `FilesForge` makes no network call and runs no `gh`.
7. **The api view.** `personal.py api-view DIR` renders, from `forge/` and the product's git (read-only), the files that `metrics.ApiDir` reads (`pulls.json`, `comments-<n>.json`, `files-<n>.json`, `commits-<n>.json`, as SPEC-0007 rule 20 names them), into DIR outside the clone, so that `facts.py --api-dir DIR`, `metrics.py --api-dir DIR` and `check_final_clearance.py --comments DIR/comments-<n>.json` read personal state with no change to their code. On the same records saved from GitHub, the existing fixtures of `tests/kit/`, their output through the api view is byte for byte the output through the saved responses.
8. **An agent cannot approve, and the person confirms at a terminal.** A comment that `FilesForge` writes while `CLAUDECODE` is set in its environment (the variable `local_mode.SESSION_SETTING` already reads as the mark of an agent session, `(verify)` there and here) carries `performed_via_github_app: {"slug": "claude"}`. The sidecar's `agent_apps` setting is the kit's default (`agent_apps = ["claude"]`, `common.DEFAULT_CONFIG`), and a sidecar setting that removes `claude` from it is refused naming the setting, so the existing rule (`reviewers.via_agent`, ADR-0179 decision 3) refuses such a comment as an approval in `check_specs.py`, `check_final_clearance.py` and `metrics.py`. `personal.py confirm` is refused while `CLAUDECODE` is set, as `local_mode.py --write` is (session rule 30). A terminal confirmation is not a solo session confirmation and is not read as one: `reviewers.confirmed_comments` (read on main) needs a last line `confirmed by <login> in a session at <time>` (`reviewers.CONFIRMED_BY`) and a sha that is a pull request head, and neither holds for a record confirmed at a terminal, so that reader and its regular expressions stay unchanged and never read a terminal confirmation. Its shape, in order, one item per line: `Confirmed: <C>`, where `<C>` is the full 40-hex sha of the sidecar commit that holds the record as the person is shown it (the sidecar's `HEAD` when `confirm` starts, with a clean sidecar work tree, else refused naming the rule); `Verdict: cleared <C>` (always `cleared`: answering no writes nothing, so there is no `fix list` or `rejected` terminal confirmation); `Record: <REQ-nnn|SPEC-nnnn|ADR-nnnn>`; for a spec `Approve: SPEC-nnnn`, for an ADR `Accept: ADR-nnnn`, for a requirement `Confirm: REQ-nnn`, naming the same id; `Shown:` and exactly the three lines of rule 15; and last `confirmed by <login> at a terminal at <YYYY-MM-DDTHH:MM:SSZ>`, where the login is the sidecar's one person and the comment's `user.login`. A new reader, `reviewers.terminal_confirmations(comments, agent_apps, person)`, reads only that shape, only from the one listed person, never a comment marked with an app of `agent_apps`, and only where `Record:` and the next line name the same id; it adds, as the same author at the same time, `Approve: <C> SPEC-nnnn`, `Accept: <C> ADR-nnnn` or `Confirm: <C> REQ-nnn`. Each kind has one reader in the sidecar (each run with `--comments forge/comments-<n>.json`, the files-forge record of rule 15): a spec by `check_specs.py --comments`, which in a sidecar takes its items from `terminal_confirmations` instead of `confirmed_comments`, so the long `Approve: <sha> SPEC-<n>` line goes through the existing `approval_shas` and `unchanged_since` (the spec equals its text at `<C>` apart from its status line); an ADR by a new reading `check_adrs.py --comments FILE`, in a sidecar only, under which an ADR whose status line moves to `Accepted` needs an `Accept: <C> ADR-nnnn` line at a `<C>` where the ADR equals its text apart from its status line; and a requirement by a new reading `check_requirements.py --comments FILE`, in a sidecar only, under which a requirement with a `Source: observed in code` line (rule 14) that moves to `done` needs a `Confirm: <C> REQ-nnn` line at a `<C>` where its entry equals the current one apart from its status. A team-mode repository, and a solo-mode one, take neither new reading and read exactly as today. In the files forge the agent mark is written by the kit, not by GitHub, so it is a label and not proof (`Q-S0041-16`).
9. **What personal mode drops.** Personal mode has no router labels (`route.py`), no conductor, no `session.py watch`, `claim` or `review-queue`, no CODEOWNERS, no ruleset, no workflows, no `merge_cleared.py` and no scheduled report. `personal.py` offers none of them, and each of those scripts, run with a sidecar as its root, prints one line `personal mode: <command> is not used (setting: forge)` and exits 1 with no network call. Reports run on demand (rule 23).

### Adoption of existing code by one developer (answer 4)

10. **The survey reads, never runs.** `scripts/agk/survey.py` (new) is standard library only and deterministic: the same tree and the same ledger give a byte-identical `cache/inventory.json` (sorted keys, no clock; the date comes from `--today`). As SPEC-0002 rule 3 holds for adopt, it never imports, executes or runs product code or its tools: it reads tracked files only (`git ls-files`, read-only), as text by line patterns, never with a language's parser or interpreter, follows no symlink, skips binary files, and lists a file over 1 MB without reading it. The inventory holds: languages and lines (by file extension), the manifests found (for example `pyproject.toml`, `package.json`, `go.mod`, `pom.xml`, `Cargo.toml`, `*.csproj`) with their declared test commands copied as strings and never run, entry points declared by a manifest or found by name, CI files (for example `.github/workflows/*`, `.gitlab-ci.yml`, `Jenkinsfile`), the test files of rule 12, each file's rank (rule 11) and the read ledger.
11. **The budget, the rank, the ledger and the coverage.** The script measures every tracked text file (lines, import lines, test shape); the budget limits the files whose content the model reads for meaning in one pass of `/agk:personal-adopt`, the reading list. `survey_budget` in `[personal]` is a whole number from 1 to 1000, 40 by default (`Q-S0041-13`), and any other value is refused naming the setting. The rank of a file is its import fan-in (the tracked files whose import lines name it, by the language's import pattern) and then its churn (the commits that touched it, from `git log --format= --name-only`, read-only); the reading list takes files round-robin across the top-level folders, the highest rank first in each, until the budget is spent. The read ledger maps a path to the blob sha the model read; a later pass lists first the files whose blob changed and then those never read, and never lists a file whose blob equals its ledger entry. The inventory and `survey.py`'s last line state the coverage as `<read> of <total> files read`, where read counts files whose ledger blob is the current one; the coverage is always printed, also at 0.
12. **A test detector for many languages.** A new function of `survey.py` finds test files by language: Python (`test_*.py`, `*_test.py`), JavaScript and TypeScript (`*.test.*`, `*.spec.*`, `__tests__/`), Go (`*_test.go`), Java and Kotlin (`src/test/`, `*Test.java`, `*Tests.java`), C# (`*Tests.cs`, `*.Tests.csproj`), Ruby (`*_spec.rb`, `test/*_test.rb`), Rust (`tests/*.rs`) and PHP (`*Test.php`), each with its language and, where a manifest declares one, its framework as data. `adopt.detect_tests` (read on main: it returns the top-most directories that hold `*_test.py` or `test_*.py` files and the patterns that matched) is not changed and its output on the existing fixtures stays the same.
13. **Proposals carry citations that exist.** The skill `/agk:personal-adopt` has the model write its proposals as JSON (requirements, specs and ADRs, each statement with one or more citations `path:start-end@blob`). `scripts/agk/personal_adopt.py` (new) refuses every claim whose citation does not exist: the path is tracked, the blob is that path's blob at a commit of the product, and the line range lies inside that blob. It prints one line per refused claim naming the rule and the claim's position in the file, never its text, and renders nothing of a proposal whose every claim is refused.
14. **What is rendered.** Requirements are appended to the sidecar's `docs/requirements.md` as `planned`, each with a line `- Source: observed in code at <citations>` (`common.parse_requirements` ignores lines it does not know, read on main) (`Q-S0041-8`); specs are written `Draft` and ADRs `Proposed` with a line `- Kind: recorded` (`check_adrs.FIELDS` requires `Status`, `Date`, `Deciders`, `Related` and `Requirements` and ignores other lines, read on main). A point the citations do not show is marked `(verify)` in the rendered file (principle 7). Numbers come from `common.next_free_ids` on the sidecar. A requirement observed in code is never `done` until a test in the test map (rule 16) asserts it and the person confirms it.
15. **The person confirms each record.** Nothing rendered counts as decided until the person runs `personal.py confirm <REQ-nnn|SPEC-nnnn|ADR-nnnn>` from their own terminal: it is refused inside an agent session (rule 8) and when standard input is not a terminal, shows the three-line summary that the `Shown:` lines record, asks yes or no, and on yes: writes the files-forge pull record `forge/pulls/<n>.json` with `head.sha` `<C>` (rule 8) and the title `confirm <id>`, and the confirmation of rule 8 in `forge/comments-<n>.json`; moves a spec to `Approved` or an ADR to `Accepted` in the sidecar's work tree (a requirement's status does not move: rule 14 moves it later, and the confirmation is what rule 14 reads); runs the reader of rule 8 for the record's kind with `--base <C>` and `--comments forge/comments-<n>.json` on that work tree (`common.changed_files` diffs the merge base against the work tree, read on main); and only when the reader passes makes one sidecar commit, the child of `<C>`, holding the status line and the two forge files. When the reader fails, `confirm` restores the sidecar's work tree to `<C>`, commits nothing and exits 1 naming the reader. Only this terminal command sets a sidecar spec `Approved` or ADR `Accepted`, and only in the sidecar (SPEC-0005 rule 8 as amended by item 6 of amendment 113). The record says what it proves: that the yes was typed at a terminal with no agent session's mark, and nothing more (`Q-S0041-5`). With `[personal] sign = true` the commit is signed with the person's own git signing key; signing is optional and off by default.
16. **The baseline and the test map.** `personal.py baseline` prints the test command it would run (from `[personal] test_command`, else the one declared test command of rule 10, else it refuses naming the setting), runs it once only with `--approve`, which the skill passes only after the person says yes, on the head tree of rule 4, and records in `records/baseline.json` the head, the command, and each test already failing as a residual. Per-test results come from a JUnit XML report when the command's `{junit}` placeholder is set; without it the baseline records the whole run (`Q-S0041-19`). The test map is `test-map.toml` in the sidecar, mapping `REQ-n ACm` to one or more test ids (`path::name`); no marker and no file is ever written into the customer's tests.

### Governance levels and the floor (answer 5)

17. **Five levels.** `[personal] level` in the sidecar's `agk.toml` is one of: `light` (the default, `Q-S0041-7`: the floor, the inventory, the decisions log and field notes); `tests-first` (light, and proof red on the base then green on the head for each change, as `proof.py` judges it, SPEC-0010 rules 7 to 15); `spec` (tests-first, and a short spec or brief per change, confirmed by rule 15 before the change's first code commit); `review` (spec, and the review context of `review_context.py`, the reviewer agent, `check_review_report.py` and a confirmed verdict naming the head; advisory and experimental, because the reviewer agent caught 0 of 5 human findings in `docs/runs/shadow-review-4.md`, `Q-S0041-10`); `evidence` (review, and `prepush.py --record FILE` with `evidence.py check RECORD`, ADR-0208). Any other value is refused naming the setting.
18. **The floor, at every level.** Two steps run at every level and no setting removes them: the secret scan (gitleaks over the product branch's commits from the merge base to the head, with `--redact`, as `prepush.py` step 4 runs it) and the rule that no test that passed on the base fails on the head (per test with `{junit}`, else by the whole run, rule 16). Where `prepush.py` passes with `secret scan: not run` when gitleaks is not installed, the personal floor fails with `floor: secret scan not run (gitleaks not installed)` (`Q-S0041-15`). Without `{junit}` the no-regression step compares the whole run: a base whose run passes and a head whose run fails fails the floor, and a base whose run already fails makes the step `unknown`, which never passes, until the person sets `{junit}` (`Q-S0041-19`). The `[personal]` table accepts exactly these ten keys and no other: `forge` (`"files"`, rule 1), `level` (one of the five of rule 17), `ai_disclosure` (`"commit-trailer"`, `"pr-note"` or `"both"`, rule 22), `survey_budget` (a whole number from 1 to 1000, rule 11), `quote_lines` (a whole number from 0 to 20, rule 28), `sync_remote` (a non-empty string, rule 5), `test_command` (a non-empty string, rule 16), `sign` (a boolean, rule 15), `team_refs` (a boolean, rule 20) and `schema` (a whole number from 1, rule 27). An unknown key, a known key of the wrong type or out of its range, and a `test_command` that is empty or only spaces (which would skip the no-regression step) are refused naming the key, never the value; no key and no value removes, skips or weakens either floor step, so no setting lowers the floor (principle 11).
19. **Where the gate runs.** `/agk:personal push` runs the gate of the level on the head, writes `records/gates/<head>.json` (the schema of `prepush.py --record`), and on a pass prints the `git push` command for the developer to run; it never runs `git push` itself (rule 20). The optional pre-push hook is installed only by `personal.py hook install`, untracked in `.git/hooks/pre-push`, and is refused when `core.hooksPath` is set or a `pre-push` hook already exists; it calls the gate and fails closed with one line when the plugin path it recorded no longer exists. It is the one write under `.git/` (`Q-S0041-17`); the existing template `kit/templates/pre-push` (ADR-0186) runs `scripts/agk/prepush.py` from the product, which personal mode does not have, so it is not reused as is. `personal.py report` flags each local branch whose head equals its upstream (a pushed head, read from the remote-tracking ref without a fetch) and has no gate record, as `pushed without a gate: <branch>`.

### Output to the team (answer 6)

20. **The agent never pushes to the customer's remote.** In personal mode the agent never runs `git push` to a remote of the product, never opens a pull request and never posts to the customer's GitHub; the developer pushes ordinary branches by the team's own process. Commits carry no AGK file, no `REQ-nnn` marker and no `Advances:` line unless the developer sets `[personal] team_refs = true`; with it off, the gate prints a warning line naming the setting when a commit of the branch carries an `Advances:` line or a path of the sidecar layout.
21. **The pull request summary.** `personal.py pr-summary` prints, and never posts, an optional plain description of the change: the tests and their results from the gate record, the proof result where the level ran it, whether a review was done, and the disclosure line of rule 22. It names no REQ, SPEC or ADR id unless `team_refs = true`.
22. **AI use is disclosed, never hidden.** `[personal] ai_disclosure` is `"commit-trailer"`, `"pr-note"` or `"both"`, `"both"` by default (`Q-S0041-20`); there is no `none` and any other value is refused naming the setting (`Q-S0041-4`). With `commit-trailer` or `both`, the gate warns, naming the setting, when a commit of the branch made in an agent session lacks the trailer the project's policy sets; with `pr-note` or `both`, `pr-summary` ends with the disclosure line. No AGK command strips, rewrites or amends a trailer or a commit (no `commit --amend`, `rebase`, `filter-branch` or `notes` in any argument list). `personal.py status` and `pr-summary` print the disclosure in force.

### Metrics and the path to team mode (answer 7)

23. **Events and the report.** Each gate, proof, review and confirmation appends one JSON line to `metrics/events.jsonl` (the head, the step, the result, the UTC time). `personal.py report [--week YYYY-Www]` prints, on demand: defects caught before push (a gate or proof failure followed by a pass on a later head of the same branch, by step), review findings accepted, rework (commits after the first push of a branch, and changes reopened), and time per change (first commit to push), each against a baseline of the first seven days after attach, `unknown` where there are too few events, and the line `These numbers show correlation, not causation.` It reads files and git only.
24. **Export to team mode.** `personal.py export --target CLONE` is a dry run; `--write` writes, on a new branch of TARGET and never on its default branch: the files of the `adopt.py` plan (`adopt.build_plan`) when AGK is not installed there; the requirements, specs, ADRs and decisions-log rows, renumbered against TARGET's default branch with `common.next_free_ids` and the one-pass id mapping that `intake.py renumber` uses (`number_map` and `rewritten`; the command itself renumbers a branch's own additions against its merge base, so it is not called as is), with statuses reset to `Draft`, `Proposed` and `planned` and each carrying `confirmed by <person> in personal mode on <date>`; `gh issue create` commands printed, never run, for open briefs; a second new branch that proposes the test map as markers in the tests (principle 10); and `export-map.json`. It never pushes and never commits on the clone the person is working in unless it is TARGET.
25. **Export is lossless.** `personal.py export --check` fails unless every record of the sidecar (each requirement, spec, ADR, brief, decisions-log row, field note and test-map entry) appears in `export-map.json` as mapped to its new id or as withheld with a reason; private field notes are withheld by default (`Q-S0041-11`). The failure line names the count and the first unmapped id.

### Packaging (answer 8)

26. **A user-scope plugin.** Personal mode ships in the AGK plugin, installed at user scope from the marketplace the customer allows (`Q-S0041-1`) `(verify: the install command and scope flag)`. Every script runs from `${CLAUDE_PLUGIN_ROOT}` (as the skills of SPEC-0005 rule 5 already do); the sidecar stores the plugin version and never a script. The sidecar's `constitution/` and `config/` are pinned by that version and checked against `kit/hashes.json`, which holds `constitution/principles.md`, `config/core-rules.md`, `config/session-rules.md` and `config/review-checklist.md` for each release (read on main); `doctor.py` run on a sidecar reports each file that differs. A copy is changed only by a personal ADR of the sidecar, and `doctor.py` still reports the difference (`Q-S0041-14`).
27. **Upgrade and detach.** `personal.py upgrade` migrates the state's `schema` (a whole number in `[personal]`) one step at a time, one sidecar commit per step, and refuses a schema newer than the plugin's. `personal.py detach` first prints that `export` keeps the records, removes the registry entry, removes the hook only if its bytes still equal what `hook install` wrote, and with `--delete-state` deletes the sidecar only after the person types its id at a terminal (refused inside an agent session). A test proves that the product's `git status --porcelain` stays empty and that no file under `.git/` changes, by path, size and SHA-256, through `attach`, `survey`, the gate and `detach`.

### Security and privacy (answer 9)

28. **Nothing leaves the machine but what Claude Code sends.** Every new script is standard library only and imports no network library (`socket`, `http`, `urllib`, `ssl`, `ftplib`, `smtplib`), as the existing tests of three scripts check (`docs/guides/security.md`); nothing leaves the machine except what Claude Code itself sends under the customer's terms. On POSIX `AGK_HOME` is made `0700` and every file it writes `0600`; on Windows the folder inherits the profile's permissions `(verify)` and `doctor.py` says that it did not check them. State stores paths, line ranges, blob shas and summaries, never a code excerpt by default: `[personal] quote_lines` is a whole number from 0 to 20, `0` by default. gitleaks runs over the sidecar's commits at each gate, and a redaction check refuses a field note that matches a secret pattern before it is written. State holds no credential: no token, key or password is read into it or written by it.
