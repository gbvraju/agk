# SPEC-0040: A builder hands heavy runs to a first-in-first-out queue and keeps developing instead of waiting on the heavy lock

- Status: Draft
- Owner: reviewer group (a team from config/reviewers.yaml)
- Requirements: REQ-047

Status is `Draft` or `Approved`. An Approved spec is owned by its reviewer group; agents propose patches.

Written by the intake of one sentence (SPEC-0012): "A builder hands each heavy run (proof, the full suite, e2e, Compose stacks) to a first-in-first-out queue that one runner works through, and goes on writing code and tests while it waits, so on a low-memory machine development never stalls behind the heavy lock." It is generic and project-agnostic: it names no project and no vendor, it needs only files, git and a shell, and it uses the standard library only, on Windows and POSIX, with no network in any check. The brief is issue #520. The maintainers gave 6 answers before it was written: the six numbered answers of brief #520 (the requirement, this spec and its rules, ADR-0262 and one row of `docs/runs/decisions-log.md` for the owner's direction, the open points as questions, the builds (a) to (f) with their dependence on the pilot-hardening briefs, and documents only), under the brief's principles: no gate is skipped or weakened, and every heavy run still happens on the exact head it was asked for, with a pull request marked ready only with its results; the queue runs heavy steps one at a time, or `lock_slots` at a time, first in, first out, and nothing jumps the queue except as a question below rules; a builder never waits idle on the lock; Windows and POSIX, standard library only. The owner's direction of 2026-11-03, quoted as data and recorded as one row of the decisions log: "on low memory machines, waiting for 2 builders are time taking on heavy locks, it is really killing hours and hours time and slow. Why can't we prioritize development works when heavy runs are planned, at least we can move progress on development side. Heavylock queue can operate FIFO." The owner's ruling on the order, 2026-11-03, quoted as data and recorded as one row of the decisions log (the conductor's field note on #520): "one run at a time (or as many as your lock slots allow) - this is the right strategy. I agree FIFO or Priority based queuing to unblock the development is great strategy here." Today the heavy-step lock (`scripts/agk/lock.py`, ADR-0191, ADR-0231, ADR-0254) is a wait, not a queue: `lock.py run --name heavy` blocks its caller until a slot is free, so in the pilot of 2026-11-02 and 2026-11-03 the builders spent most of the day blocked while another builder's 20-minute suite ran, each holding a session and its memory while doing nothing. The points the brief leaves open are `Q-S0040-1` to `Q-S0040-18` below (`Q-S0040-2` now ruled by the owner), each with the conservative reading that the rules apply until a person rules. Negative cases: with the setting off nothing changes and `submit` is refused naming the setting; a submission from a work tree with uncommitted changes writes no job; a job never jumps one ahead of it in the order in force, a running job is never replaced or pre-empted, a job whose priority cannot be read never counts as 0, and a dead, stale or crashed job is marked failed and never passed; a result for an older head is stale and is never evidence for a newer one.

## Rules

1. **Off by default.** The queue is one setting, `queue = true` in a new `[locks]` table of `agk.toml`, read with the standard library's `tomllib`; with no table, or `queue = false`, every command (`lock.py run`, `lock.py status`, `prepush.py`, `proof.py`, `session.py`) prints and does exactly what it does on the default branch today, and no queue folder is made. `lock.py submit` and `lock.py runner` with the setting off exit 2 with one line naming the setting (`setting: [locks] queue`), never a value. Any other value of a `[locks]` key is refused the same way. The existing top-level lock settings (`lock_dir`, `lock_stale_minutes`, `lock_slots`, `lock_cleanup`) stay where they are and keep their meaning; the `[locks]` table holds only the queue's settings of this spec (`queue`, `queue_autostart`, `queue_idle_minutes`, `queue_order`, `queue_max_wait`) (`Q-S0040-5`). `queue_order` is `"fifo"` (the default) or `"priority"`, and `queue_max_wait` is a positive whole number of minutes, 120 by default (rule 5).
2. **The queue folder.** The queue of a lock NAME lives beside the lock, in the lock's own base folder (the user's temp folder, or `lock_dir`): `.agk-lock-NAME.queue/`, outside every repository, so nothing in it is ever committed. It holds `jobs/` (one JSON file per waiting or running job), `results/` (one JSON result and one output file per finished job), `seq` (the next sequence number) and `runner.json` (the live runner's process id, host, start time and the time it last read the queue). Every change to the queue is made under the lock's existing mutex (`.agk-lock-NAME.mutex`), and every file is written whole and then moved into place, so a reader never sees half a file (`Q-S0040-5`).
3. **`submit`.** `lock.py submit --name heavy --session S [--kind K] [--brief N] -- <cmd...>` refuses, with exit 2 and no job written, a work tree with uncommitted changes to tracked files, because the job runs on the committed head and an unrecorded change would be hidden. Otherwise it writes one job file: `schema` 1, the ticket, the sequence number, `session`, the repository (its top folder), the branch (or `detached`), the full `head` sha, the command as a list (no shell), the folder relative to the repository's top folder, the `kind` (`prepush`, `proof` or `other`, the last by default; it only groups past durations for the estimate of rule 7), the `brief` (the number given with `--brief`, or none) and its `priority` (rule 5), and the submitted time in UTC. The priority is the `Priority:` line (0 to 3) of that brief, read once at submission with one GitHub GET, the way `session.py` reads a brief; a job without `--brief`, or whose brief or `Priority:` line cannot be read, gets the priority `unknown`, which ranks after 3 and is never 0. No option sets the priority directly, so a builder cannot type its job ahead (`Q-S0040-17`). `prepush.py --queue` and `proof.py --queue` pass `--brief` from the `Brief: #n` line of the body file when there is one. The priority is recorded under either order and used only under `priority`. It prints one line `queued <ticket> position <n> of <m> (head <sha12>)` and returns at once; it never takes or waits on the heavy lock. A ticket is `NAME-<sequence, six digits>-<four random hex characters>`; the random part has no secret meaning and only keeps tickets apart after a queue folder is cleared.
4. **The runner.** `lock.py runner --name heavy` works the queue: it takes the waiting jobs by sequence number, runs each under the existing lock with the existing slot, ticket, stale and cleanup rules (ADR-0191, ADR-0231, ADR-0254), so a job holds a slot exactly as `lock.py run` does and passes `AGK_LOCK_SESSION` (the job's session), `AGK_LOCK_TOKEN` and `AGK_LOCK_NAME` down to its command, and writes its result beside the ticket: `schema` 1, the ticket, the head, the `outcome` (`passed` for exit 0, `failed (exit <n>)`, `failed (<reason>)` or `replaced by <ticket>`), the exit code, the `output_sha256` and `output_bytes` of the command's combined output, the output itself in `results/<ticket>.out`, `queued_seconds`, `run_seconds`, the start and end times in UTC, and the path of the record file when the command was `prepush.py --record FILE`. One runner works a queue at a time: a second `runner` for the same name exits 0 with one line naming the live one (`runner already running (pid <n>, host <name>)`). With `lock_slots` above 1 it runs up to that many jobs at once, each in its own slot, and a job starts only when every job ahead of it in the order in force (rule 5) has started (`Q-S0040-15`). Under either order, a job that is running is never stopped, paused or pre-empted, and the order never changes how many jobs run at once: one, or `lock_slots`.
5. **The order is a setting, and batching never lowers a gate.** The runner takes the next waiting job by the order that `queue_order` sets. With `"fifo"` (the default) the order is the sequence number and nothing else: no priority, no kind and no session changes it. With `"priority"` the order is the job's `priority` (0 first, `unknown` last), then the sequence number within the same priority; a job that has waited longer than `queue_max_wait` minutes since its submission is overdue, and every overdue job goes ahead of every job that is not, by sequence number among the overdue, so a newer job of a higher priority never starves an older one (`Q-S0040-18`). The red-default-branch brief that the router writes (`Priority: 0`) therefore goes first in `priority` mode and takes its turn in `fifo` mode; this is the owner's ruling, not an open point (`Q-S0040-2`). Under either order a running job is never stopped or pre-empted, and the order changes nothing but which waiting job starts next. Two submissions with the same repository, head, command and folder are one job: the second prints the first's ticket and adds nothing, while that job is waiting or running; a finished job is never reused, so a new submission after a result runs again (`Q-S0040-7`). A submission with the same repository, branch, session and command as a waiting job and a different head replaces that job in place: the new job takes the waiting job's sequence number and submitted time, so it keeps its position and its waiting time, and its priority is read again from its brief, and the replaced ticket gets the result `replaced by <ticket>`. A running job is never replaced, and a job of a detached head is never replaced (`Q-S0040-8`). Every heavy run still happens: a replaced job's head is no longer the branch's head, and a result for it would be stale under rule 10.
6. **The exact head.** The runner runs each job in a detached git worktree of the job's head, made in a temporary folder outside every repository (`git worktree add --detach`), at the job's folder inside it, and removes the worktree when the job ends, also when it fails; it never runs a job in the builder's work tree, which keeps moving while the job waits (`Q-S0040-6`). The command is run as listed, without a shell. A path argument that names a file outside the repository (the body file and the record file of `prepush.py`) is passed as it was submitted, and `--queue` of rule 9 submits such paths as absolute paths. The worktree of a job whose head no longer exists in the repository is not made: the job fails with `failed (head not found)`.
7. **`status` and the estimate.** `lock.py status --name heavy` prints, with the setting on, after the lock's existing lines, one line naming the order in force (`order: fifo` or `order: priority, max wait <m> min`), one line per running job (`running <ticket> <session> head <sha12> for <m> min`), one line per waiting job (`<position>. <ticket> <session> head <sha12> waiting <m> min, start in about <m> min` or `start unknown`, with `priority <p>` after the head and `overdue` after the waiting time under `priority`; the position is the place in the order in force), and `queue empty` when there is none; `status --ticket T` prints the one job's line, or its result (`result <ticket> <outcome> head <sha12> in <s>s, output <path>`), or `unknown ticket`. The estimate of a waiting job's start is computed from past durations only: for each job ahead of it in the order in force, the median `run_seconds` of the last ten finished results of the same `kind`, less the time already run for a running job (never below 0), summed and divided by the number of slots, rounded up to a minute; with fewer than three past results of a kind ahead of it, the start is `unknown` (`Q-S0040-4`). `status` changes no file and starts nothing.
8. **Who runs the runner.** The owner starts the runner once, like the conductor, with `python3 scripts/agk/lock.py runner --name heavy`, in the foreground of its own terminal. It stops by itself, with the line `runner idle for <m> min; stopped`, when the queue has been empty for `queue_idle_minutes` (10 by default, a positive whole number) (`Q-S0040-3`). The first `submit` starts a runner only when `queue_autostart = true` is set in `[locks]`, which the kit's templates list commented out and off; with it off, a `submit` that finds no live runner prints the extra line `no runner; start one with lock.py runner --name heavy` and still queues the job (`Q-S0040-1`). An autostarted runner is a background process of the same machine, started without a shell, that outlives the `submit` that started it; whether a runtime ends such a process when the session's turn ends is marked `(verify)` in the guide.
9. **`--queue` on the heavy runs.** `prepush.py --record FILE --queue [--body FILE]` and the proof run, `proof.py --queue [its options]`, submit themselves as one job of kind `prepush` or `proof` (the same command without `--queue`, with the paths of rule 6 made absolute) and return at once, printing the `queued` line of rule 3; they run no step of their own. `--queue` with the setting off exits 2 naming the setting. `--queue` without `--record` on `prepush.py` is refused with exit 2, because a queued run without a record leaves no evidence the conductor can check. The light steps that a builder runs before a push without the tests (`prepush.py --quick`) are unchanged and are not queued.
10. **Only the result for the exact head counts.** A result is evidence for a pull request only when its head equals the head that the builder pushes or marks ready. `lock.py status --ticket T --head <sha>` prints `stale (result for <sha12>, asked <sha12>)` and exits 1 when they differ, `failed` and exit 1 for a failed or replaced result, `waiting` or `running` and exit 3 while there is none, and the result line and exit 0 only for a passed result of that head. A passed result for head X lets the builder push exactly X at a milestone of session rule 7, with `git push origin <X>:<its branch>`, never a later head (`Q-S0040-10`). The `Evidence:` line of a queued `prepush.py --record` run is printed in the job's output and copied by the builder from there; `evidence.py check` reads the record as it does today.
11. **What a builder does while queued.** With the setting on, a builder submits each heavy run with `--queue` and goes on with the brief's remaining code, tests, documents and ADR, committing `checkpoint:` steps locally. Before it marks its pull request ready, it checks its ticket with `status --ticket T --head <its head>`; a head that moved since the submission needs a new submission, and it marks ready only on exit 0 for its final head. While a heavy run of its own is waiting, it never also runs the same heavy step under `lock.py run`. With the setting off, session rule 31 and the local-mode guide apply exactly as today. Build (d) adds this as one session rule, the next free number (`session.py ids`), and one sentence in session rules 30 and 31 that points to it; no other rule changes.
12. **A builder with nothing left to do ends and is resumed.** When only a queued heavy run is left, the builder pushes what its results allow, posts one `Report: <head> queued <ticket>; waiting on the heavy queue` on its pull request and ends its session (session rule 17: its last comment is a `Report:`). The resume uses the existing path for a stalled pull request (session rule 9): `session.py resume --pr N` prints, beside its `next:` step, the ticket of the last such `Report:` and its result, read from the local queue folder, or `waiting`; the next session started on that pull request, by the conductor or the owner, continues from it once the ticket has a result (`Q-S0040-11`).
13. **The plan puts development first.** `session.py plan`, with the setting on, counts a builder whose last comment on its open pull request is a `Report:` naming a ticket that has no result yet in the local queue as not building, so its slot is free. It offers that slot to a development brief only when `builder_memory_gb` is set and the machine's available memory divided by it allows one more builder (ADR-0223); with memory unknown or the setting unset it offers nothing more than today. The plan prints one line `heavy queue: <n> waiting, <m> running, next start in about <m> min` (or `unknown`). A builder that queued a run and is still working counts as building, as today (`Q-S0040-16`).
14. **Cleanup.** A job whose runner process no longer runs on this machine, whose command could not be started or ended by a signal, or whose job file is older than `lock_stale_minutes`, gets the result `failed (<reason>)`, never `passed`, when the next runner or `status` reads the queue under the mutex, and its worktree is removed; the lock's own stale clearing and `lock_cleanup` apply to its slot exactly as today (ADR-0231). A job file that cannot be read is moved to the results as `failed (unreadable job)`. A failed job is never run again by itself; the builder submits again. Results and output files older than seven days are removed by a runner when it starts (`Q-S0040-9`). A `runner.json` whose process no longer runs on this machine is replaced by the next runner with a line saying so.
15. **What does not change.** No gate is skipped, weakened or reordered: CI still runs every required check on every pushed head, a clearing verdict in local mode still needs the evidence of session rule 30, and `check_pr_body.py`, `evidence.py`, the required checks and the workflows do not change. `lock.py run` keeps working as today beside the queue: a direct run waits for a slot under the lock's ticket order, and the runner's jobs take their slots as one more run at the default priority (`Q-S0040-12`).
16. **The builds, in order.** After this intake, each of about 600 changed lines of code and tests or fewer, each from the default branch with its own ADR naming the protected classes it changes and citing ADR-0262 (`Q-S0040-14`), and one fragment under `changelog.d/` where it changes a file the installer writes. Brief #505 is closed as completed and its change is on the default branch, so no build declares it; each build that changes `lock.py`, `prepush.py` or `proof.py` declares `Depends-on: #508` while brief #508 is open (`Q-S0040-13`).

## Tests

Fixtures in `tmp_path` only: a temporary repository, a temporary lock and queue folder (`lock_dir`), fake commands written as small Python scripts that sleep, print and exit with a chosen code, and saved copies of GitHub comments; no network, invented data (`example.com`).

- Rule 1: with no `[locks]` table and with `queue = false`, `lock.py run`, `lock.py status`, `prepush.py --quick` and `proof.py --help` print exactly what the default branch prints, no queue folder is made, and `submit` and `runner` exit 2 naming the setting and never the value; an invalid `queue`, `queue_autostart`, `queue_idle_minutes`, `queue_order` or `queue_max_wait` is refused the same way; REQ-047 AC1.
- Rules 2 and 3: `submit` on a clean temporary repository writes one job file with every field, prints the `queued` line and returns before a held lock is released; on a tree with a changed tracked file it writes nothing and exits 2; two submissions racing under the mutex get two sequence numbers; with `--brief N` and a saved brief whose line is `Priority: 1` the job holds priority 1, and without `--brief`, with an unreadable brief, with no `Priority:` line and with a line outside 0 to 3 it holds `unknown`, never 0; REQ-047 AC2.
- Rules 4 to 6: three fake jobs run in submission order with one slot, never two at once, each in a detached worktree of its head while the builder's work tree is at another head; each result holds the exit code, the digest, the timings and the record path; with `lock_slots = 2`, the third job does not start before the second; with `queue_order` unset and with `"fifo"`, jobs of priorities 3, 0 and 2 run in submission order, exactly as with no priorities; REQ-047 AC3.
- Rule 5, the order: with `"priority"`, jobs of priorities 3, 2, 0 and `unknown` submitted in that order run 0, 2, 3, `unknown`, and two jobs of the same priority run in submission order; a job with an unreadable priority runs after every job of priority 3; with `queue_max_wait = 1` and a fake clock, a priority-3 job waiting longer than the limit runs before a newer priority-0 job, and two overdue jobs run by sequence number; a priority-0 job submitted while a priority-3 job runs waits until it ends, and the running job is never stopped, under both orders and with `lock_slots = 2`; REQ-047 AC9.
- Rule 5: a duplicate submission prints the first ticket and adds nothing; a later head on the same branch, session and command replaces the waiting job in its position and keeps its waiting time, and the old ticket reads `replaced by`; a running job and a detached-head job are not replaced; a finished job is not reused; REQ-047 AC4.
- Rule 14 and rule 8: a job whose runner process no longer runs, a command that cannot start, one killed by a signal and one older than `lock_stale_minutes` each get `failed (<reason>)` and never `passed`; `lock_cleanup` runs as for the lock; a second runner exits naming the live one; a runner stops after `queue_idle_minutes` with an empty queue; with `queue_autostart` unset, `submit` starts no process; REQ-047 AC5.
- Rule 7: `status` with two waiting, one running and five finished fake jobs prints the order in force, positions in that order, each job's priority under `"priority"` and none under `"fifo"`, running time and an estimated start equal to the median arithmetic of rule 7, and `unknown` with two past results; the queue folder's files are byte for byte the same before and after; REQ-047 AC6.
- Rules 9 and 10: `prepush.py --record FILE --queue` and `proof.py --queue` submit one job and return at once; `--queue` without `--record`, and with the setting off, exit 2; `status --ticket T --head` exits 0 only for a passed result of that head and reports `stale` for an older head; REQ-047 AC7.
- Rules 11 to 13: `session.py resume` on a saved pull request whose last comment is a `Report:` naming a ticket prints the ticket's result or `waiting`; `session.py plan` on saved comments and a fixture queue counts that builder as not building, offers one more development brief only when the fixture's free memory allows it, prints the queue line, and counts a builder that queued and still works as building; the session rules hold the new rule; REQ-047 AC8.

## Proof

REQ-047 AC1: *the queue is the owner's choice, and without it nothing changes.* Rule 1. REQ-047 AC2: *a builder hands a heavy run over and is free at once, and only committed work is queued.* Rules 2 and 3. REQ-047 AC3: *one runner works the queue first in, first out, under the existing lock, on the exact head.* Rules 4 and 6. REQ-047 AC4: *fewer heavy runs without a lower gate: duplicates are one job, and a newer head takes its place.* Rule 5. REQ-047 AC5: *a dead runner, a stale job or a crashed command never passes.* Rules 8 and 14. REQ-047 AC6: *anyone can see the queue and when a job will start.* Rule 7. REQ-047 AC7: *the heavy runs a builder makes can be queued, and only the result for the exact head is evidence.* Rules 9 and 10. REQ-047 AC8: *development goes first: a builder that only waits frees its slot and is resumed when its result arrives.* Rules 11 to 13. REQ-047 AC9: *the owner chooses the order, a running job is never stopped, and waiting is never starving.* Rules 4 and 5.

## Residual

- 2026-11-03: on a machine where several sessions share the queue, a job runs with the permissions of the runner's account, not of the session that submitted it; on one person's machine these are the same account, and a shared machine with several accounts is not covered (due 2026-12-31).
- 2026-11-03: the estimate of rule 7 is only as good as past durations of the same kind; a job whose suite grew since the last results starts later than estimated, and the estimate is never a promise (due 2026-12-31).
- 2026-11-03: whether a runtime ends a background runner started by `submit` when a session's turn ends (`queue_autostart`, rule 8) is not confirmed for every runtime; the guide marks it `(verify)`, and the owner-started runner is the default (due 2026-12-31).

## Open questions

Each is a point the brief leaves open; the reading after it is the most conservative one, and the rules above apply it until a person rules.

- Q-S0040-1: may the first `submit` start the runner? Reading: only when the owner sets `queue_autostart = true` in `[locks]`, off by default and commented out in the templates; with it off, `submit` queues the job and prints one line saying that no runner is running and how to start one, because a process started in the background by a session may be ended with that session's turn in some runtimes (rule 8).
- Q-S0040-2: may a priority-0 fix for a red default branch go to the head of the queue? Ruled by the owner on 2026-11-03 (the field note on #520, one row of the decisions log): the order is the setting `queue_order`; in `"priority"` mode the red-default-branch brief (priority 0) goes first, and in `"fifo"` mode, the default, it takes its turn; under either order a running job is never pre-empted; the lock's own `--priority` applies only to direct `lock.py run` callers, as today (rules 5 and 15).
- Q-S0040-3: how long does an idle runner stay? Reading: `queue_idle_minutes` of `[locks]`, 10 by default, a positive whole number; an empty queue for that long stops the runner with one line (rule 8).
- Q-S0040-4: how is the estimate computed? Reading: from past durations only, the median `run_seconds` of the last ten finished results of the same `kind` for each job ahead, less the time already run, summed and divided by the slots, rounded up to a minute; `unknown` with fewer than three past results of a kind ahead; never from a guess about the command (rule 7).
- Q-S0040-5: where do the queue and its settings live? Reading: beside the lock, in `.agk-lock-NAME.queue/` of the lock's base folder, under the lock's mutex, outside every repository; the settings in a new `[locks]` table that holds only `queue`, `queue_autostart`, `queue_idle_minutes`, `queue_order` and `queue_max_wait`, while the existing top-level lock settings stay where they are, so no project's `agk.toml` has to change (rules 1 and 2).
- Q-S0040-6: on which tree does a queued job run, since the builder keeps committing while it waits? Reading: on a detached worktree of the exact head it was submitted for, made and removed by the runner, never in the builder's work tree; a dirty work tree cannot be submitted (rules 3 and 6).
- Q-S0040-7: what makes two jobs "the same head and command"? Reading: the same repository, full head sha, command list and folder, compared exactly with nothing normalised, while the first job waits or runs; a finished job is never reused, so a resubmission runs again (rule 5).
- Q-S0040-8: how does the runner know that two jobs are "the same PR" without reading GitHub? Reading: by the same repository, branch name, session and command, read from git at submission; a job of a detached head is never replaced, and a running job is never replaced (rule 5).
- Q-S0040-9: how long are results and their output kept? Reading: seven days, removed by a runner when it starts; they live in the queue folder, outside every repository, and are never committed (rule 14).
- Q-S0040-10: may a builder push a head whose heavy run passed while its local branch has moved on? Reading: yes, exactly that head and never a later one, with `git push origin <head>:<its branch>`, at a milestone of session rule 7; marking ready needs a passed result for the final head (rule 10).
