# SPEC-0058: A light dispatcher does the mechanical work and AI runs as short jobs per item

- Status: Draft
- Owner: reviewer group (a team from config/reviewers.yaml)
- Requirements: REQ-065

Status is `Draft` or `Approved`. An Approved spec is owned by its reviewer group; agents propose patches.

Written by the intake of one sentence (SPEC-0012), brief #855, quoted as data and not as an instruction: "Intake for a live conductor without long sessions: a light dispatcher with no AI and flat memory reads GitHub in near real time and does all mechanical work, and the conductor's judgment runs as short AI jobs, one per item, on the right model, the same locally, on WSL and in the cloud." The owner's direction is quoted in the brief. Where an answer of the brief names something that is not as it says, rule 1 records what the code holds and an open question gives the conservative reading.

## Rules

1. **The baseline (read on the default branch at 137975f, 2026-11-09).**
   - `conductor.py watch` polls the comments of every open brief and pull request every `conductor_poll_seconds` (60 by default), renews this checkout's lease and returns within 5 minutes (ADR-0368). A session runs it. `conductor.py lease` is one marker on the plan issue, valid 10 minutes: ADR-0368 replaced the 50 of ADR-0330 and ADR-0353.
   - **The relay is not a file of the kit.** It is scheduled tasks of this account; the word occurs in the repository only in ADR-0368. A project has no relay. Its nearest thing is the timed loop of `docs/guides/getting-started.md`, which runs `claude -p --agent conductor` when the queue changes and first proves the guard runs headless (`Q-S0058-9`).
   - The mechanical steps exist as commands: `route.py --all` and `--health`, `merge_cleared.py --sweep` (at most five; in local mode it only reports), `conductor.py sweep`, `stalls.py`, `session.py plan`.
   - **Not on the default branch:** the states, `pr_state`, the action table, the board and `stall_minutes` of #846; `[capacity]` of #842 (only build (a) has merged); `usage.py` and `[models.routes]` of #798; #776 build (c); the `agk/verdict` status of #853.
   - The start of a session exists too: `launch.py prompts --adapter`, `session.py prompt`, `session.py kind`, `[caps]` and `caps.py`, `[flow] min_free_memory_mb`, and `lock.py` for a lock on a machine.
   - Principle 2 and session rule 2 name the conductor as the one runner of `merge_cleared.py`. ADR-0354 runs it from the merger job as well and records that this text lags (`Q-S0058-5`).
   - Measured on 2026-11-09: `gh api` prints a `304 Not Modified` and **exits 1**, so a conditional read cannot be judged by its exit code. `GET /repos/{owner}/{repo}/events` answers `X-Poll-Interval: 60`. `claude` 2.1.319 `--help` lists `-p`, `--agent`, `--model`, `--effort`, `--output-format` and `--max-budget-usd`, a limit in dollars, and has no token limit and no limit on turns.
2. **The program and its setting.** `python3 scripts/agk/dispatcher.py run|once|status` is a new installed script. It uses the standard library and the kit's own modules, runs no model and needs no package. It reads an optional `[dispatch]` table of `agk.toml`, on the default branch: `enabled` (default `false`), `poll_seconds` (default 60, `Q-S0058-3`), `merge` (default `false`, rule 6), `max_memory_mb` (default 200) and `[dispatch.limits]` (rule 10). With no table or `enabled = false`, no dispatcher step runs anywhere and nothing differs from today. An unknown key or a wrong value is refused naming the setting, never the value. A `poll_seconds` under 30 is refused.
3. **Flat memory.** The loop keeps only the conditional tag of each read of rule 4 (at most one each) and one record for each running job (at most the capacity), and no list that grows with time. Each pass that does work runs as a child process that exits, so what it read is returned to the system. All other state comes from GitHub each pass, and `once` after a restart behaves as a pass of a process that never stopped. The loop checks its own memory each pass and exits non-zero above `max_memory_mb`, so that the service restarts it; this holds where a service manager's own cap does not exist (rule 14).
4. **Reading GitHub.** A receiver of a GitHub App, where one exists, wakes a pass at once (build (e)). Otherwise each pass makes three conditional list reads with `If-None-Match`: the open pull requests, the repository's issue comments updated since the last pass, and the workflow runs. A `304` is read from the status line of the answer, never from the exit code (rule 1), and a read that fails counts as changed-unknown, never as unchanged. It does not poll the repository events list, whose delay GitHub does not bound for real-time use `(verify)` and which the three reads make unnecessary (`Q-S0058-3`).
   - All three unchanged: the pass ends with no other request.
   - Any changed: a pass over the pull requests that changed.
   - Every 5 minutes, changed or not: a pass over all, because a state ageing past its limit has no event.
   - It honours `Retry-After` and `X-Poll-Interval`. With `X-RateLimit-Remaining` under a fifth of its limit it does only the 5-minute pass and says so on the heartbeat, because it shares the account's limit with every session.
5. **The mechanical work of a pass, in order.** First the pause check of session rule 33: paused, it does nothing else. Then the state labels and board of #846, its stall detection and action table, the capacity of #842, and rule 6. It calls the functions those briefs ship and holds no copy of a rule. A step whose function is not on the default branch is skipped and says so, and never guesses. It writes only labels, its board comment, its lease, `Owner needed:` lines of #846 answer 8, the `Report:` of rule 10 for a job ended by a limit, the `Report:` of rule 11 for a job that ended with none, and starts of rule 9. It never posts a comment whose first line is `Verdict:`, `Approve:`, `Confirmed:`, `Final:`, `Correction:` or `Maintainer answer:`, never changes a workflow, the ruleset or a required check, never pushes and never reruns anything to get green.
6. **Merging.** With `[dispatch] merge = false`, the default, the dispatcher merges nothing and the merger job works as today (`Q-S0058-5`). With `true`, each due merge runs `merge_cleared.py` and nothing else, as a child process, one at a time, because the command runs governance and tests under the heavy lock for minutes and a pass must not wait for them. Its hold or refusal is listed as stuck with its reason, as #846 answer 8 says. A local login that the ruleset does not let merge is such a refusal, never a reason to try another route.
7. **The heartbeat.** One line of the board of #846: `Dispatcher: live, last pass <s> s ago, <n> jobs running, written <UTC time>`.
   - A comment cannot change when its writer is dead, so a line that says `live` proves nothing alone. The trailing time is added to the brief's form for that reason (`Q-S0058-10`). A reader treats a line whose written time is older than three times the larger of `poll_seconds` and 300 seconds as `stale`.
   - `route.py` on each router run, a relay run and `conductor.py sweep` each print or rewrite it as `Dispatcher: stale, last pass <UTC time>` by that reading, which is what "within one pass" can mean with the dispatcher itself gone.
   - The board comment is edited only when its text other than the seconds changed, or every 5 minutes. Each edit is an `issue_comment` event that starts no job, because no workflow filter matches its first line, and GitHub still lists a skipped run for each listening workflow; a build keeps it so.
   - Until #846's board lands (`Q-S0058-13`) the line stands alone in the comment.
8. **One dispatcher.** A lock on the machine (`lock.py`, name `dispatch-<repository>`, in `lock_dir`) keeps two starts on one machine apart. A lock cannot see another machine, and on some systems the temporary folder is per user, so the lock alone does not meet the brief's "two people never run two dispatchers" (`Q-S0058-6`). The GitHub lease of ADR-0330 does: the dispatcher takes it under the name `dispatch-<eight hexadecimal digits of a hash of the host name>`, so that no host name is posted, and renews it each pass, at most every 4 minutes. A login not in `verdict_authors` cannot hold the lease (ADR-0330), so it stands by and says so. A dispatcher that finds another valid holder stands by: it reads, writes nothing, starts no job and tries again each 5-minute pass. A live conductor session or relay holding the lease is such a holder, so the two never run beside each other.
9. **AI jobs.** A job is one of: a review of one head, one fix list, one build, one question. The dispatcher starts one only for one item that the state of rule 5 names, and for a key of kind, item and head that has no running job. A job ends when its item's `Report:`, `Verdict:` or `Question:` is posted. **No AI session runs a watch loop**, a lease or a `/loop` under the dispatcher: the next step of an item is a new job.
   - The prompt is built by `session.py prompt` and `launch.py` from kit text and numbers. No title, body or comment of GitHub goes in it; the job reads those itself as data (brief 247).
   - The tier is the kind's (SPEC-0045), through `[models.names]` or `[models.routes]` once #798 lands; a tier with no route uses a stronger one and says so, never a weaker one. A review runs on `strongest`, and every gate, guard, check and reading list is as for a session.
   - The number running never passes the capacity of rule 5 or `min_free_memory_mb`. A start that is refused or fails is listed as stuck with its reason, and is never silent.
10. **Limits per job.** Each job has a wall-clock limit and a token cap. The cap is SPEC-0049's by the brief's size where `[caps]` is set. `[dispatch.limits]` holds, per kind, `minutes` and `tokens`, and its defaults are chosen by the owner (`Q-S0058-4`): as read, a review 30 minutes, a fix list 60, a build 120 and a question 15, with no token cap beyond `[caps]`. The wall-clock limit is the dispatcher's own: it ends the job's process tree. A token cap cannot be passed to the tool (rule 1), so the dispatcher sums the usage the job streams and ends it at the cap `(verify: usage per message in the stream)` (`Q-S0058-7`). `--max-budget-usd` is not a token cap and is not used for one. A job ended by a limit posts, through the dispatcher, the `Report: <head> over cap <used>/<cap> <unit>` of session rule 32, leaves its checkpointed branch alone and parks as SPEC-0049 rule 10 holds.
11. **A job locally.** A `claude -p` process with its agent and its tier's model `(verify: the flags of the runtime used, rule 1 read one version)`, with no option that skips a permission or a guard. The headless guard proof of the getting-started guide is run first, and a machine that fails it starts no job. The job gets no token or secret that the dispatcher holds other than the person's own `gh` login, and a service file holds none (principle 9). Each job's pid, key and start are one file under `<git dir>/agk/jobs/`, so that a restarted dispatcher adopts or ends it and never starts a second. Its real tokens are the `Usage:` line of its `Report:`, from `usage.py` once #798 lands, and otherwise `Usage: not shown`, never 0. A job whose process ends with no `Report:` gets one from the dispatcher, so that no job ends silently (session rule 17). The login must be in `verdict_authors` for a review job, or review jobs do not start and the heartbeat says so.
12. **In the cloud.** No dispatcher runs unless a person or a small server hosts one (`Q-S0058-1`). GitHub events drive the router and merger as today, and nothing is added to them. Jobs start from one scheduled task per tier, each pulling its next item with `session.py next` and the work that #776's slots pull.
    - **The named gap: a GitHub event cannot start a cloud session.** So AI work in the cloud starts at the next scheduled firing, not at the event, and only the mechanical work of the router and merger is near real time.
    - The brief adds a start by the previous job. A session's start of another session is what the permission check refused on 2026-11-08 (#776, 3 of 3), so it is best effort only: the schedule is the floor, and a refused start is listed as stuck (`Q-S0058-8`).
    - Between events no pass runs in the cloud, so a state that only ages is seen at the next event or scheduled run. ADR-0368's residual stands.
13. **Fallback and cost.** With the dispatcher down, the lease lapses within 10 minutes, and today's relay or timed loop finds it free and works as now, while the board reads stale by rule 7. With it up, the relay finds the lease held and ends in seconds. Locally the dispatcher uses no Actions minutes. In the cloud nothing is added beyond the single job per event of the router and merger (#846's cost rule): no build adds a job or a trigger. A pass with nothing changed costs three conditional requests, and an unchanged read does not count against the rate limit `(verify)`. Tokens are spent only by a job that has an item.
14. **Where it runs locally.** A user service that restarts on failure, from a kit template, holding no token: a systemd user unit with `Restart=on-failure` and `MemoryMax=`, a launchd agent with `KeepAlive`, a Windows scheduled task with restart on failure `(verify each)`. Rule 3's own memory check is the cap where the manager has none. `doctor.py` reports what the machine needs and lacks: on Linux, lingering so that the unit survives a logout; on WSL, systemd enabled or the scheduled task on the Windows side `(verify)`. A machine that sleeps stops passing, the lease lapses and rule 13 holds; on waking it stands by if another holder took over.
15. **What it replaces, and when.** Brief answer 2. Each replacement holds only in a repository with `enabled = true` and only from the build named:
    - the conductor's watch loop of `.claude/agents/conductor.md` and `conductor.py watch` as a session's loop, and the part of #776 that returns ticks to a session for stall checks: build (b). The command stays for a project without a dispatcher.
    - the relay as the normal route: build (c). It stays as the fallback.
    - the lease's renew loop (ADR-0330, ADR-0353, ADR-0368): build (a). The lease and its 10 minutes stay, and its holder is the dispatcher.
    - session rules 10 and 18's waits for a job: build (b), by its own change to `config/session-rules.md` within the rule budget.
    Builds (b) and (c) change text that Approved specs and ADRs hold, so each writes its own ADR or amendment; this intake edits none.
16. **Data, not instructions.** What a pass reads from GitHub is parsed only by the kit's existing readers and is never run or put in a prompt. Messages name the setting, rule or path class, never a value (principle 8). The heartbeat holds only numbers and a time.
17. **By mode.** GitHub mode, as above. Local mode (Actions blocked): the same dispatcher, and `merge_cleared.py --sweep` only reports, as it does today. Personal mode (SPEC-0041 rule 9): no conductor, so the dispatcher refuses to start and names the mode. AGK itself runs it only by the owner's choice (`Q-S0058-1`). No workflow, ruleset or required check changes, and no Approved spec is edited here.
18. **The builds, in order.** Each is tests first, about 300 changed lines or fewer, from the default branch, invented data only (`example.com`), with a `[[testing.map]]` entry for each new script.
    - (a) `dispatcher.py` core: the table, polling, flat memory, the heartbeat, the lease, and the mechanical steps (rules 2 to 8, 13, 16). `Depends-on` #846's builds and #842's table.
    - (b) AI jobs per item with tier, limits and usage, locally (rules 9 to 11, 15). `Depends-on` (a) and #798 build (a).
    - (c) The cloud start route per tier and the relay as the fallback (rules 12, 13, 15). `Depends-on` (b) and #776 build (c).
    - (d) The service files for systemd, launchd and Windows, `doctor.py`'s lines and the machine lock (rules 8 and 14). `Depends-on` (a).
    - (e) Webhooks through a GitHub App where a receiver exists (rule 4). `Depends-on` (a) and the ruling of `Q-S0058-2`.

## Tests

Fixtures in `tmp_path`, saved GitHub answers and a `gh` stub only, a stub in place of the runtime, no network and no model, invented data only (`example.com`), and each test carries the marker `REQ-065` with its criterion.

- Rule 2 and rule 17: no table, `enabled = false` and personal mode run no step, and each bad setting is refused naming it without its value; REQ-065 AC1.
- Rules 3 and 4: a long run of unchanged passes keeps a flat `tracemalloc` figure and a fixed tag count, a stubbed `304` with exit 1 reads as unchanged, a failed read never does, an unchanged pass makes exactly three requests, and a low remaining limit gives only the 5-minute pass; REQ-065 AC2.
- Rule 5: saved states give the labels, stalls and actions from the kit's functions, a function that is absent is skipped and said, a paused repository gets nothing, and the writes never hold a forbidden first line; REQ-065 AC3.
- Rule 6: off merges nothing, on calls only `merge_cleared.py`, as a child that a slow stub does not make the pass wait for, and a held merge is listed as stuck; REQ-065 AC4.
- Rule 7: a heartbeat older than the limit reads stale by each named reader with no dispatcher running, an unchanged board is not edited inside 5 minutes, and the first line matches no workflow filter of the kit's workflows; REQ-065 AC5.
- Rule 8: a held lock stands by, a valid lease of another name stands by on another machine's fixture and writes nothing, and a lapsed lease is taken; REQ-065 AC6.
- Rules 9 to 11: one key starts one job, the prompt holds no text of a planted title or comment, a lower tier is never chosen, a job past its minutes or tokens is ended and reported, a job that ends with no `Report:` gets one, a restart adopts a running job, a missing figure is `not shown`, no argument skips a guard and the job's prompt names no watch or loop; REQ-065 AC7.
- Rules 12 and 13: with the dispatcher down the lease lapses and the fallback proceeds, a refused start is listed as stuck, and the diff of a build adds no job and no trigger to the workflow files; REQ-065 AC8.
- Rule 14: each service template (systemd, launchd, Windows) holds no token or secret-shaped value and sets restart on failure, the systemd template sets `MemoryMax=`, a template for a manager with no cap leaves it to rule 3's own check, and `doctor.py` on fixtures names what a machine lacks (lingering on Linux, systemd or the scheduled task on WSL) without printing a value; REQ-065 AC6.

## Proof

REQ-065 AC1: *a repository that does not choose it sees no change.* Rules 2 and 17. REQ-065 AC2: *the program stays small and quiet, and an unchanged read is known to be one.* Rules 3 and 4. REQ-065 AC3: *mechanical work is the kit's own and no judgment or approval is taken.* Rule 5. REQ-065 AC4: *there is one merge path and it never stalls a pass.* Rule 6. REQ-065 AC5: *a person can tell a dead dispatcher from a live one.* Rule 7. REQ-065 AC6: *two dispatchers never act at once, and the service that hosts one restarts, is capped and holds no token, and a machine is told what it lacks.* Rules 8 and 14. REQ-065 AC7: *a job is short, bounded, on its tier and leaves a true record.* Rules 9 to 11. REQ-065 AC8: *the fallback holds, a gap is named and nothing costs more.* Rules 12 and 13.

## Residual

- 2026-11-09: in the cloud, AI jobs start at the next scheduled firing, so judgment there is not near real time; only a hosted dispatcher or a future runtime route closes it (due 2027-03-31).
- 2026-11-09: a repository at rest in the cloud has no pass between events, and ADR-0368's residual stands (due 2027-03-31).
- 2026-11-09: taking the lease is a read and then a write, so two dispatchers starting in the same seconds can both take it; the one that next reads another name stands by, and the kit's job key limits the harm (due 2027-03-31).
- 2026-11-09: a machine that hosts the dispatcher is one point of failure; the fallback's first action is up to 10 minutes after it stops (due 2027-03-31).
- 2026-11-09: the token cap depends on usage that the runtime streams; a runtime that reports only at its end is held by the wall-clock limit alone (due 2027-03-31).
- 2026-11-09: a commit status does not change any of the three list reads, so a status-only event such as #853's is seen at the 5-minute pass (due 2027-03-31).

## Open questions

Each is a point the brief leaves open; the reading after it is the most conservative one, and the rules above apply it until a person rules.

- Q-S0058-1: where does the dispatcher run for this repository: a person's machine, a small server, or the cloud only? Reading: nowhere until the owner sets `enabled = true`, and the cloud route stays as today (rules 2, 12 and 17).
- Q-S0058-2: is a GitHub App wanted? Reading: no, polling only, and build (e) waits for this ruling, since an App and a public receiver add a secret and an exposed surface (rules 4 and 18).
- Q-S0058-3: what is the poll interval? Reading: 60 seconds, the conductor's today and the interval GitHub asks of its events list, with 30 as the floor (rules 2 and 4).
- Q-S0058-4: what are the job limits by kind? Reading: a review 30 minutes, a fix list 60, a build 120 and a question 15, and the token caps of `[caps]` only (rule 10).
- Q-S0058-5: may the dispatcher merge, when principle 2 names the conductor alone? Reading: off by default, the merger job goes on merging, and turning it on is the owner's change with principle 2's own (rule 6).
- Q-S0058-6: the brief's one lock per machine cannot stop a second machine. Reading: keep the lock and add the GitHub lease, which is the guard that holds across machines (rule 8).
- Q-S0058-7: how is a token cap enforced when the tool takes none? Reading: the dispatcher sums the streamed usage and ends the job, and the wall-clock limit holds regardless (rule 10).
- Q-S0058-8: the brief starts cloud jobs from the previous job, a route the permission check refused on 2026-11-08. Reading: the schedule per tier is the floor, the previous job's start is best effort and a refusal is listed as stuck (rule 12).
- Q-S0058-9: "today's relay still runs" holds for this repository only, since a project has none. Reading: a project's fallback is the timed loop of the guide, and no relay file is added by this spec until build (c) proposes one (rules 1 and 13).
- Q-S0058-10: the heartbeat's "`<s>` s ago" goes untrue when its writer dies. Reading: the brief's form with a written time added, and every other reader judges staleness from that time (rule 7).
- Q-S0058-11: does a job for a build replace `session.py claim`? Reading: no, a build job claims as a session does, so that takes, reservations and SPEC-0049's clock read the same (rule 9).
- Q-S0058-12: does the dispatcher need one lock per machine or per repository on that machine? Reading: per repository, named for it, so that one person's two projects each get one (rule 8).
- Q-S0058-13: the board and states of #846 are not built. Reading: nothing here defines them, build (a) depends on them, and until they land the heartbeat line stands alone (rules 5, 7 and 18).
