# SPEC-0071: The kit runs from the plugin and a product repository keeps only its project

- Status: Draft
- Owner: reviewer group (a team from config/reviewers.yaml)
- Requirements: REQ-078

Status is `Draft` or `Approved`. An Approved spec is owned by its reviewer group; agents propose patches.

Written by the intake of one sentence (SPEC-0012), brief #1420 under plan #661, quoted as data and not as an instruction: "Intake for a clean product repository: the whole kit runs from the AGK plugin on the machine, the repository keeps only the project's own records, and one command removes AGK at the end of an engagement, with the workforce's speed, quality and cost unchanged." The maintainers gave 6 answers before it was written: the six numbered answers of brief #1420, whose evidence and the owner's direction (quoted there as data, 2026-11-16 17:35 and 18:08 IST) this spec does not repeat. It builds on personal mode (SPEC-0041), on the uninstall of brief #348 (ADR-0203), on the licence notices of brief #1419 (open) and on local mode (`docs/guides/local-mode.md`); it edits none of their text. Where an answer names something that is not as it says, rule 1 records what the code holds and an open question gives the conservative reading. Negative cases: a session that runs a kit file from the product repository in a clean project, a session that starts with no plugin or with another plugin version, a migration in CI mode or in personal mode, a migration that deletes a kit file the project changed, a migration that leaves a file naming a removed path, an uninstall that deletes the project's specs and decisions by default, an uninstall or a migration that rewrites history or force-pushes, a doctor message that quotes a value, a steward that writes kit code into the product, a customer project migrated before the rehearsal's figures are written, and a change to a workflow, the ruleset or a required check.

## Rules

1. **The baseline (read on the default branch at 01b619e, 2026-11-16).**
   - **What an installed project holds.** `kit/manifest.json` lists 146 `verbatim` files: 93 under `scripts/agk/`, 8 under `.github/workflows/`, the 10 playbooks under `config/playbooks/`, 6 agents under `.claude/agents/`, 5 hooks under `.claude/hooks/`, `.claude/settings.json`, `CLAUDE.md`, `Makefile`, `agk.mk`, `.gitignore`, `config/ci-tools.txt`, `config/core-rules.md`, `config/session-rules.md`, `config/review-checklist.md`, `config/stack-signals.toml`, `constitution/principles.md`, four issue templates and the pull request template under `.github/`, three runbooks, two guides and four `TEMPLATE.md` files. `tests/kit` is the manifest's separate `kit_tests` entry, not one of the 146 (the brief counts it among them); `templates`, `rendered`, `adopt`, `extendable` and `experimental` list the rest.
   - **How the kit is called today.** The kit-only scripts (`upgrade.py`, `uninstall.py`, `intake.py` and others) already run from the plugin as `python3 "${CLAUDE_PLUGIN_ROOT}/scripts/agk/<script>"` with the project as their target, in the skills and in `docs/guides/getting-started.md`, `planning.md` and `reference.md`. The installed scripts are called as `python3 scripts/agk/<script>` from the project: by the session prompts (`kit/templates/runtime/builder.txt`, `conductor.txt`, `launcher.txt`), the agents (`.claude/agents/`), the hooks of `.claude/settings.json` (`python3 "$CLAUDE_PROJECT_DIR"/.claude/hooks/<hook>.py`), the guards' allowed command forms, `Makefile` and `agk.mk` (`make lint`, `make governance`), `prepush.py` and the workflows.
   - **What exists to reuse.** `uninstall.py` (brief #348, ADR-0203) deletes the kit files whose bytes equal a released copy listed in `kit/hashes.json`, lists every kit file the project changed and keeps it, keeps the project's own work (requirements, ADRs, specs, briefs, the vision, design documents, `docs/runs/`, the tests other than `tests/kit/`), writes one uncommitted branch with `--write` and prints, never does, the GitHub side; `/agk:uninstall` runs it. `upgrade.py` and `/agk:upgrade` prepare an upgrade as one pull request. `agk.toml` already holds `version`, the kit version the project runs, equal today to the plugin's `version` in `.claude-plugin/plugin.json` (0.64.5); there is no `[kit]` table and no `plugin_version`. `execution` in `agk.toml` is `hosted` (the default), `hybrid`, `pool` or `local` (`scripts/agk/execution.py`).
   - **What does not exist.** No `/agk:setup` skill (the brief names one; the skills are `init`, `adopt`, `start`, `upgrade`, `uninstall`, `doctor`, `wsl` and others, and SPEC-0061's `/agk:builder` is not built), no `LICENSE-AGK` and no `[licence]` table with `valid_until` (both are brief #1419's, open), and no doctor warning about kit files in a product repository.
   - **The kit's own repository** (`gbvraju/agk`) is the plugin's source and governs itself with the installed layout; this spec changes nothing in it but the builds' own files (rule 13).
2. **The split: the kit lives in the plugin, the repository keeps the project.** In a clean project (`[kit] layout = "plugin"` in `agk.toml`, written only by the migration of rule 8):
   - **In the plugin, read from `${CLAUDE_PLUGIN_ROOT}` `(verify: the variable is set for every session, hook and headless job the plugin serves, one version read)`:** every kit script, hook, agent, skill, playbook, runbook, guide and template, the governance rules (`constitution/principles.md`, `config/core-rules.md`, `config/session-rules.md`, `config/review-checklist.md`), `config/ci-tools.txt`, the gate that `make lint` and `make governance` run today, and the kit's tests (`tests/kit/`, run against the project's root).
   - **In the repository:** the project's own records (`agk.toml`, `docs/requirements.md`, `docs/specs/`, `docs/adr/`, `docs/build-state.md`, `docs/runs/`, the briefs, the vision and the design documents), the project's own code and tests, a short project `CLAUDE.md` that names the plugin, its pinned version and the project's own rules (at most 30 lines, written from a template of the plugin), `LICENSE-AGK` (brief #1419), and the files that git and GitHub read only from the repository: `.gitignore` and the issue and pull request templates under `.github/` (`Q-S0071-5`). The GitHub plan, issues, labels and pull requests are unchanged.
   - **One entry point.** The plugin carries one resolver: an installed script of the kit, run as `python3 "${CLAUDE_PLUGIN_ROOT}/scripts/agk/<script>"` in a clean project and as `python3 scripts/agk/<script>` in an installed one, takes the project's root from the working directory's git top level and never writes into the plugin's folder. Prompts, agents, hooks, guards and skills name the script once through the resolver of build (a), so that one text serves both layouts.
3. **The same workforce.** In a clean project the conductor, the builders, the steward, the autopilot supervisor (SPEC-0064), claims, reviews, the merge guard and `merge_cleared.py` work exactly as in local mode; only where the code is read from changes. A rule of `config/session-rules.md` that names `python3 scripts/agk/<script>` names the resolver's form after build (a), by that build's ADR.
4. **Hooks, agents and permissions from the plugin.** The hooks run as plugin hooks, the agents as plugin agents and the permission rules name the plugin's paths, each `(verify)` and settled by a recorded run before build (b) changes anything:
   - `(verify: plugin hooks fire for every session, interactive and headless, including a builder's worktree)`;
   - `(verify: how a plugin agent is named for --agent, such as agk:conductor)`;
   - `(verify: how --allowedTools and a permission rule name a plugin path, and whether a plugin may carry permission rules)`.
   A behaviour that a run cannot confirm is a question on build (b)'s pull request, never a guess; when the plugin cannot carry a rule, a short project `.claude/settings.json` that holds only the permission rules (no hook code and no script) is written by the migration and named in rule 2's list (`Q-S0071-6`). The guards (`architect_guard.py`, `conductor_guard.py`, `data_guard.py`, `steward_guard.py`, `stop_check.py`) allow the resolver's command forms in both layouts and nothing more.
5. **Workflows.** A clean project runs none: it requires `execution = "local"`, where GitHub Actions do no work and governance runs through `prepush.py` on the machine (`docs/guides/local-mode.md`). In CI mode (`execution` of `hosted`, `hybrid` or `pool`) the governance check needs the code where CI runs, so CI mode keeps today's install until a separate design (a private reusable workflow or a self-hosted runner) is approved by its own brief; this spec records that limit and solves nothing of it (`Q-S0071-2`).
6. **One version on every machine.** `[kit] plugin_version` in `agk.toml` pins the plugin version (`Q-S0071-7`). Every session, hook and kit script run in a clean project reads it at start and compares it with the running plugin's `version` in `.claude-plugin/plugin.json`; on a mismatch, older or newer, or with no plugin, it is refused with one line naming the setting (`plugin_version`) and never a value, exit 1, and does no work. The plugin is installed at user scope, so every worktree of the machine has it `(verify: user-scope install and the worktree)`; an offline machine with the pinned version works, and an upgrade waits for the network. In team mode two people with different versions are both held to the pin, and the older one is refused. A teammate with no plugin is told the one install command `(verify: the plugin install command for a private source)`; no skill can install the plugin it belongs to (`Q-S0071-4`). Raising the pin is a release pull request (SPEC-0028 rule 4).
7. **Protected on the machine.**
   - The plugin is installed from the owner's private source with the user's own login, never copied into the product.
   - `doctor.py` warns `kit-in-repository` when a file of the kit manifest (rule 1), other than those rule 2 keeps, appears in a clean project, naming the path class, never the file's content.
   - The steward (SPEC-0059) never pastes kit code into an issue, a pull request, a comment or a file of the product; its prompt says so, and its guard refuses a write of a file whose path the manifest lists into the product.
   - The licence grant: when brief #1419's `[licence]` table is present, a session warns at start after `valid_until` and never stops work (`Q-S0071-3`).
   This limits exposure and does not make it impossible: an administrator of the machine can still copy the plugin folder, and what is already in the product's history and in its clones stays there until rule 9's clean-up. Protection rests on the licence and the written grant (brief #1419).
8. **The migration.** `/agk:upgrade --clean-repo` (`upgrade.py --clean-repo`, kit-only) prepares one branch and one pull request, as `/agk:upgrade` does today, that:
   - refuses, naming the setting, unless `execution = "local"` (rule 5), and refuses in personal mode (`forge = "files"`, SPEC-0041), which already keeps the kit out of the product;
   - removes the manifest's kit files whose bytes equal a released copy (`uninstall.py`'s match), writes the short `CLAUDE.md`, `[kit] layout = "plugin"` and `[kit] plugin_version`, and keeps rule 2's files;
   - lists every kit file the project changed and keeps it: the person decides, removes it by hand in the same pull request or keeps it as the project's own, and the pull request body names each (`Q-S0071-8`);
   - proves that no remaining tracked file names a removed path (a scan of every tracked text file for each removed path, the paths of `${CLAUDE_PLUGIN_ROOT}` excepted), and fails naming the path class when one does;
   - is rolled back by reverting that one pull request. It raises no `version` and carries the ADR of the protected classes it changes, written as `upgrade.py --write-adr` writes one today.
9. **The end of an engagement.** `/agk:uninstall` (`uninstall.py`, extended, `Q-S0071-9`) in a clean project prepares one pull request that removes the project's AGK records the owner and the customer agreed to remove, and `LICENSE-AGK`; by default it keeps the project's specs and decisions, which describe the customer's product (`Q-S0071-1`). It then prints, and never runs, a history clean-up of the kit's paths (`git filter-repo` with a path list, `(verify: the git filter-repo options for a path list)`), whose list names every kit path that ever existed in the project's history (every path of every release row of `kit/hashes.json` that `git log --all` finds), with a checklist: the customer's written agreement, every clone made again, branch protections paused and restored by the repository's administrator. The kit never force-pushes, never rewrites history and never changes a GitHub setting; those are the repository owner's acts.
10. **Edge cases**, each with its rule and a test:
    - a machine without the plugin, or with another version: refused at start, naming the setting (rule 6);
    - a builder worktree: the plugin is at user scope, so every worktree has it (rule 6);
    - an offline machine: the installed plugin works, and an upgrade waits (rule 6);
    - two people with different plugin versions in team mode: the pin refuses the older one (rule 6);
    - a project that changed a kit file: the migration lists it and keeps it (rule 8);
    - a teammate who never installed the plugin: the refusal names the one install command (rule 6);
    - personal mode: unchanged, and the migration refuses there (rule 8).
11. **Speed, quality and cost proven before any customer move.** On a sample local-mode project of invented data (`example.com`), the same five briefs run with the conductor and two builders, once installed and once clean. Lead time per brief, tokens per merged pull request (`metrics.py --cost`), first-review pass rate and failed checks of the clean run must each be no worse than the installed run's within 10%; each figure, both runs and the run dates are written to this spec's proof by build (g). No customer project is migrated before they are written and the maintainers accept them: until the proof holds the four figures, `upgrade.py --clean-repo` refuses, naming the proof, unless it is run with `--rehearsal` on the sample project.
12. **The builds, in order.** Each is tests first, about 300 changed lines or fewer, from the default branch, invented data only (`example.com`), a `[[testing.map]]` entry for each new script, and no workflow change.
    - (a) Scripts and prompts resolve the kit from the plugin (rules 2 and 3): the resolver, the session prompts and the agents' and skills' command forms, with its own ADR for `kit/`, `config/` (session rules that name a script) and `.claude/agents/`.
    - (b) Hooks, agents and permission rules from the plugin (rule 4), each `(verify)` of rule 4 settled first by a recorded run, with its own ADR for `.claude/` and `.claude-plugin/`. `Depends-on` (a).
    - (c) The version pin and the start check (rule 6), with its own ADR for the `[kit]` table of `agk.toml`. `Depends-on` (a).
    - (d) `/agk:upgrade --clean-repo` and its no-dangling-path proof (rule 8). `Depends-on` (b) and (c).
    - (e) `/agk:uninstall` in a clean project and the printed history clean-up with its checklist (rule 9). `Depends-on` (d).
    - (f) The doctor's `kit-in-repository` warning, the steward's rule and the grant warning (rule 7), with its own ADR for the steward's role file. `Depends-on` (c).
    - (g) The rehearsal of rule 11, with its figures written to the proof. `Depends-on` (d) and (f).
13. **Measured goals.**
    - A clean sample project holds no file of the kit manifest except `LICENSE-AGK` and rule 2's named files.
    - The five-brief rehearsal is within 10% of the installed run on each of the four figures of rule 11.
    - A version mismatch, older or newer, is refused, naming the setting.
    - `/agk:uninstall` leaves no kit file, and its printed clean-up names every kit path that ever existed in the project's history.
    - Personal mode is unchanged, CI mode keeps today's install, the kit's own repository keeps its layout, and no workflow, ruleset or required check changes.

## Tests

Saved git trees of invented sample projects, a stub plugin root with its own `.claude-plugin/plugin.json`, a `gh` stub and a stub runtime only; no network; invented data only (`example.com`, sessions such as `cb-example-1`); each test carries the marker `REQ-078` with its criterion.

- Rules 2 to 4: in a stub clean project every prompt, agent, hook, guard and skill command form resolves to a file under the stub plugin root and none to the project, the gate runs from the plugin against the project, and the sample project holds no manifest file but rule 2's named files; REQ-078 AC1.
- Rule 6 and rule 10: no plugin, an older and a newer plugin version are each refused with one line naming `plugin_version` and no value and exit 1 before any work, the pinned version runs with the network stub off, and a second worktree of the sample reads the same plugin; REQ-078 AC2.
- Rule 8: the migration of an installed sample removes the released kit files, writes the short `CLAUDE.md` and the `[kit]` table, lists and keeps a changed kit file, fails naming the path class when a remaining file names a removed path, is undone by reverting its one commit, and refuses with `execution = "hosted"` and with `forge = "files"`, each naming the setting; REQ-078 AC3.
- Rule 9: the uninstall of a clean sample removes the agreed records and `LICENSE-AGK`, keeps the specs and decisions by default, prints a clean-up whose path list equals every kit path that the sample's history holds, with its checklist, and runs no `git filter-repo`, no `git push --force` and no GitHub write; REQ-078 AC4.
- Rule 7: the doctor warns `kit-in-repository` for a manifest file planted in a clean sample, naming the path class and never the content, warns after `valid_until` and stops nothing, and the steward's guard refuses a write of a manifest path into the product; REQ-078 AC5.
- Rule 11: the rehearsal record holds both runs' four figures for the same five briefs, the check of the record fails when a figure is missing or worse than the installed one by more than 10%, and `upgrade.py --clean-repo` without `--rehearsal` refuses, naming the proof, while the proof lacks a figure; REQ-078 AC6.
- Rules 1, 5 and 13: a personal-mode sidecar is unchanged by every build, a CI-mode sample keeps its installed files, the kit's own repository keeps its layout, and no test writes a workflow, the ruleset or a required check; REQ-078 AC7.

## Open questions

Each is a point the brief leaves open, or a name it cites that the code holds otherwise; the reading after it is the most conservative one, and the rules above apply it. `Q-S0071-1` to `Q-S0071-9` are ruled as read by the maintainer's answer on #1422 (comment 6917216479). One file each under `docs/runs/decisions/`, and the rules above hold their readings. No question is open.

- `Q-S0071-1`: do the project's specs and decisions stay at uninstall? Reading: yes, they describe the customer's product; the uninstall removes only the records the owner and the customer agreed to remove (brief answer 6; rule 9).
- `Q-S0071-2`: can CI mode run clean? Reading: not in this spec; CI mode keeps today's install and the migration refuses there (brief answer 6; rule 5).
- `Q-S0071-3`: may the plugin check the grant's `valid_until` at start? Reading: it warns and never stops work, and only once brief #1419's `[licence]` table exists (brief answer 6; rule 7).
- `Q-S0071-4`: the brief names `/agk:setup` to install the plugin for a teammate; no such skill exists, and a plugin's skill cannot run where the plugin is not installed. Reading: the start check's refusal names the one install command, no `setup` skill is added, and SPEC-0061's join command, when built, runs the same check (rule 6).
- `Q-S0071-5`: the brief's goal allows no manifest file but `LICENSE-AGK`, but `.gitignore` and the issue and pull request templates are manifest files that git and GitHub read only from the repository and that hold no kit code. Reading: they stay, named in rule 2 and in the goal of rule 13, since removing `.gitignore` risks committing generated files (principle 5).
- `Q-S0071-6`: if a plugin cannot carry permission rules, is a short project `.claude/settings.json` with only those rules allowed? Reading: yes, written by the migration, holding no hook code and no script, named in rule 2's list once build (b)'s run shows it is needed (rule 4).
- `Q-S0071-7`: `agk.toml` already holds `version`, equal today to the plugin's version. Reading: the brief's `[kit] plugin_version` is added as it says, and build (c) checks that it equals `version` in a clean project rather than replacing `version` (rule 6).
- `Q-S0071-8`: the brief says the migration "asks before removing" a changed kit file, but the migration is a script that prepares a branch. Reading: it lists and keeps every changed file, never deletes one, and the pull request body names each for the person to decide (rule 8).
- `Q-S0071-9`: the brief names `/agk:uninstall` as new; it exists (brief #348, ADR-0203). Reading: build (e) extends `uninstall.py` for a clean project and changes none of its decisions for an installed one (rule 9).
