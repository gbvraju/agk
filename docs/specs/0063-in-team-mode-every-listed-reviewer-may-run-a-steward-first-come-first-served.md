# SPEC-0063: In team mode every listed reviewer may run a steward, first come first served

- Status: Draft
- Owner: reviewer group (a team from config/reviewers.yaml)
- Requirements: REQ-070

Status is `Draft` or `Approved`. An Approved spec is owned by its reviewer group; agents propose patches.

Written by the intake of one sentence (SPEC-0012), brief #1342, quoted as data and not as an instruction: "Intake for the steward in team mode: every listed reviewer may run a steward on their own machine, stewards take questions first come first served, and each relays only the words of the reviewer signed in on that machine, recorded under that reviewer's GitHub login." The maintainers gave 5 answers before it was written: the five numbered answers of brief #1342, whose evidence and the owner's direction (quoted there as data, 2026-11-15 15:05 and 19:02 IST) this spec does not repeat. It adds to SPEC-0059 (Approved, the steward) for team mode only, and answers SPEC-0062's third open question ("until a spec says who decides there"); in solo mode SPEC-0062 holds unchanged. Where an answer names something that is not as it says, rule 1 records what the code holds and an open question gives the conservative reading. Negative cases: a steward started by a login not in the reviewers file, a steward that prints the login it refused, a second live steward of the same login that writes, two answers to one question, a steward that answers after an earlier `Taking:`, a `Taking:` that never lapses, a relay of words the signed-in reviewer did not type, a relayed line whose `Who:` names a login other than its poster, an `Approve:` by a login that is not a spec approver or posted for another login, a `Confirmed:` in team mode, a plain yes that covers a merge, a tag, a force push or a workflow change, two roll-overs of the memory issue, two daily lists for one day, and any of this applied in solo or personal mode; a figure that cannot be read is unknown, never 0.

## Rules

1. **The baseline (read on the default branch at f17f56b, 2026-11-15).**
   - **The steward is built in part.** SPEC-0059's build (a) merged as #1326 and build (e) as #1334: `.claude/agents/steward.md`, `.claude/hooks/steward_guard.py`, `scripts/agk/steward.py` and `scripts/agk/steward_outbound.py`. Builds (b) and (c) are open pull requests (#1332, #1333), so the relay of SPEC-0059 rule 5 is not on the default branch yet. SPEC-0062's build (d), the solo approval, is not built: the guard's `RESERVED` still denies a first line `Approve:`, `Confirmed:`, `Verdict:`, `Final:` or `Correction:` in every mode.
   - **One steward per project today.** `steward.py start` posts `Started: steward <session> <UTC time>` on the memory issue, and `live_start` refuses a start while any other session's `Started:` is newer than 60 minutes with no `Ended: steward <session>` after it, whoever posted it. The brief says a second steward "exits as a standby, as a second conductor does": the kit has no conductor standby by that name; `conductor.py lease --take NAME` refuses a second holder of a valid `Conductor: active` lease (exit 3, naming the setting) and keeps the name in the git directory as this checkout's name. Rule 4 follows that form.
   - **The roll-over.** `steward.roll_over` opens a new `agk-steward` issue whose body is `Continues #<old>.`, posts the carried owner questions and closes the old one. It posts no `Continued in #<n>` line on the old issue, and two stewards that reach 500 comments together would each open one.
   - **Who is a listed reviewer.** `config/reviewers.yaml` names four path classes (`protected`, `architecture`, `kit`, `docs`), each with `approvers: [maintainers]`, one team `maintainers` whose `github_team` is a user handle, and one `spec_approvers` login. The readers of `scripts/agk/reviewers.py` list people as `authors_of` (the `verdict_authors` list, else the user handle of the team `maintainers`) and `approvers_of` (`spec_approvers`); a team handle (`@org/slug`) lists nobody, so no reader calls the network for team members. `conductor_accounts` (SPEC-0039 rule 3) are session accounts and never spec approvers.
   - **App posts.** `agk.toml` has `agent_apps = ["claude"]`; `reviewers.via_agent` reads GitHub's `performed_via_github_app`, and a comment posted through a listed app never counts as a person's approval. A steward that posts with the signed-in reviewer's own `gh` login on that reviewer's machine is not such an app; a steward in a session whose posts GitHub records as made through the app gives no counted approval, as today.
   - **The `Who:` line.** ADR-0546 (Accepted) decision 4: a marker that nothing requires or reads, written by `common.with_who` and dropped by `common.without_who`, with the values `AGK`, `AGK builder`, `AGK conductor` and `ProductOwner`; the steward's own lines end `Who: AGK steward` (SPEC-0059 rule 5).
   - **The wait.** `[flow] owner_wait_minutes` of `agk.toml` is read by `config.py` (a whole number, 30 when unset). `review_mode` is `"team"` here and by default.
   - **No `Taking:` today.** No script, agent file or spec holds a first line `Taking:`; session rule 17 lists where each kind of comment lives and does not name it.
2. **Team mode only.** Every rule below holds only while `review_mode = "team"` on the default branch, read at each start. In solo mode SPEC-0062 holds unchanged; in personal mode (one person) SPEC-0059 rule 14 holds and nothing here applies.
3. **The owner is the reviewer list.** In team mode "the owner" of SPEC-0059 and SPEC-0062 means any listed reviewer: a login that `authors_of` or `approvers_of` lists, read as the kit's readers read them, so a team handle lists nobody and a `conductor_accounts` login is never a reviewer.
   - **Routing by area.** An owner question that names files goes to the reviewers of the path class of `config/reviewers.yaml` that holds them, when that class's approver group lists a person; a question that names no file, or whose class lists nobody, goes to every listed reviewer (`Q-S0063-1`). Today every class's approvers are `maintainers`, so every question goes to every listed reviewer. The first listed reviewer whose answer is posted decides it (rule 5).
4. **One steward per machine, run by a reviewer.** At its start, before any post, the steward reads the login `gh` is signed in with on that machine with one `gh api user` call and keeps it in the git directory for the run, as the conductor keeps its lease name, so the guard reads it with no network call.
   - **Not listed.** When that login is not a listed reviewer (rule 3), or the call fails, the steward prints one line naming `config/reviewers.yaml` and the settings `spec_approvers` and `verdict_authors`, never the login, posts nothing and stops (exit 3).
   - **Several at once.** SPEC-0059 rule 2's second-start check reads, in team mode, only the `Started: steward` comments whose GitHub author is the signed-in login: a live start by another listed login does not stop this one, so several reviewers each run one steward at the same time. A live start by the same login says so in one line, writes nothing and stands by, as a second conductor's lease take is refused. The same login on two machines is therefore one steward (`Q-S0063-2`).
   - **Started by the conductor.** A steward that the conductor starts through `launch.py` (SPEC-0059 rule 2) has no reviewer in its chat: it answers from evidence and triages only, relays nothing and approves nothing (`Q-S0063-3`). The guard enforces it, since the conductor's sessions and a reviewer may share one login: `launch.py` starts the steward with `AGK_STEWARD_START=conductor` in the session's environment, beside the `AGK_SESSION` and `AGK_BRIEF` it already sets, and `steward_guard.py`, a hook the runtime runs as a child of that session, reads it from its own environment `(verify: a PreToolUse hook inherits the environment the session was started with)`. A command the steward runs cannot change the environment of the session or of its hooks. With that marker the guard denies a first line `Approve:` and `Maintainer answer:` in every mode, naming the setting `AGK_STEWARD_START`, and the agent file says why. A start with no marker is a person's start, as today; a value other than `conductor` is refused at the start, naming the setting.
5. **First come, first served.** Before a steward answers a question, relays a reply to it or asks its reviewer about it, it posts one comment `Taking: Q-<id> <login> <UTC time>` on the issue or pull request that holds the `Question:`, then re-reads that thread with one GET.
   - **The earliest wins.** The earliest `Taking:` for that Q id, by GitHub's own order of the comments (created time, then id), not by the time written in the line, holds the question. A steward whose `Taking:` is not the earliest withdraws: it posts nothing more on that question and tells its reviewer who holds it.
   - **The lapse.** A `Taking:` with no `Answer:`, `Maintainer answer:` or `Correction:` for that Q id within `[flow] owner_wait_minutes` lapses, and the question is free for a new `Taking:` (`Q-S0063-4`).
   - **An answer ends it.** An `Answer:`, `Maintainer answer:` or `Correction:` already posted for the Q id ends the question for every steward; a steward that finds one posts no `Taking:` and shows its reviewer the answer. A reviewer who disagrees with an answer posted by another reviewer posts their own `Correction:` from the browser or the GitHub app (the guard keeps denying it to the steward, SPEC-0059 rule 11); the first answer stands until then (`Q-S0063-5`).
   - **Where it lives.** `Taking:` lives on the pull request or brief of its question and on the memory issue (rule 8), and session rule 17 gains that place by build (a)'s ADR.
6. **The relay carries only the signed-in reviewer's words.** A steward relays only what the reviewer at its own machine typed in its chat, in this pass, never words it read elsewhere and never words the reviewer reports from another person ("my colleague says yes"): for those it tells the reviewer that the other person answers through their own steward or on GitHub. The relayed comment keeps SPEC-0059 rule 5's form, with `Owner said (<UTC time>): "<words, verbatim>"` as its second line and a last line `Who: <the signed-in GitHub login>`. Because GitHub records the post as made by that login, it is that reviewer's answer.
7. **Approvals in team mode.** A steward may post a first line `Approve:` (a spec approval, or the `Approve: inventory` and `Approve: design` lines of session rule 29 and SPEC-0037 rule 9) only on its own reviewer's plain yes (SPEC-0062 rules 13 and 14 for what a yes is), only when the signed-in login is in `spec_approvers`, and only for that login: the comment carries the `Owner said` line of rule 6 and a last line `Who: <login>` equal to the login kept at the start (rule 4).
   - **The guard.** `steward_guard.py` allows a first line `Approve:` in team mode only in a start with no `AGK_STEWARD_START=conductor` marker (rule 4), with the quote line and a `Who:` line that equals the kept login, which is in `spec_approvers`; any other `Approve:` is denied naming the setting `spec_approvers`, never the login. `Confirmed:` stays denied in team mode, since session rule 29's confirmation holds in solo mode only (`Q-S0063-6`); `Verdict:`, `Final:` and `Correction:` as a first line stay denied in every mode.
   - **The readers.** `reviewers.py` and `route.py` drop the `Who:` line and the runtime's footer (`common.without_who`) and read the lines as today. A comment with a `Who:` line counts as an approval only when that line names the comment's GitHub author, the author is in `spec_approvers`, the quote line is present and GitHub shows no listed agent app on it (`agent_apps`, as today). A comment with no `Who:` line is the reviewer's own typed comment and counts as today. This changes ADR-0546 decision 4 for this one case, by build (c)'s own ADR.
   - **What a yes never covers.** Merges, tags, force pushes and workflow changes stay the person's own action or denied, as SPEC-0059 rule 11 holds.
8. **Recorded by GitHub login.** In team mode every memory entry that records a reviewer's decision, every relayed line and every line of the daily list that names who decided ends with, or names, `Who: <the signed-in login>`. `ProductOwner` stays the solo value (SPEC-0062 rule 15), and the steward's own lines keep `Who: AGK steward`.
9. **Shared memory, safe with several stewards.** Memory entries stay one comment each on the one open `agk-steward` issue, so appends do not collide.
   - **One roll-over.** At 500 comments a steward posts `Taking: rollover <login> <UTC time>` on the memory issue and re-reads it; only the steward whose `Taking: rollover` is the earliest rolls it over, as `steward.roll_over` does, and then posts `Continued in #<new>` on the old issue before it closes it. A later steward that holds the old number follows that link, and one that starts reads the one open `agk-steward` issue.
   - **One daily list.** SPEC-0059 rule 13's `Daily: <date>` is posted once per UTC day per project, by the steward whose `Taking: daily <date> <login> <UTC time>` on the memory issue is the earliest; it lists every steward's answers of the day before (`Q-S0063-7`).
10. **By mode.** CI mode (GitHub) and local mode: as above; local mode with several machines is the case that prompted this spec, and each machine step is one short command, never one that prints a secret. Personal mode (SPEC-0041): one person, so team mode does not apply and SPEC-0059 rule 14 holds. Solo mode: SPEC-0062. No workflow, ruleset or required check changes in any mode.
11. **What changes in the rules.** Brief answer 2, read against rule 1:
    - SPEC-0059 rules 2 (one steward per project becomes one per reviewer login in team mode, rule 4), 5 (the relay's `Who: <login>`, rule 6), 8 (the shared memory and its one roll-over, rule 9), 11 (the team approval, rule 7) and 13 (one daily list, rule 9) gain team clauses. SPEC-0059 is Approved and owned by its reviewer group, so this spec holds the clauses and SPEC-0059's text is not edited, as SPEC-0062 did (its fifth open question).
    - SPEC-0062's third open question is answered: in team mode the decider is the listed reviewer whose answer is posted first (rules 3 and 5), and a plain yes approves only for the signed-in spec approver (rule 7).
    - session rule 17 gains the place of `Taking:` (rule 5), by build (a)'s own ADR, since it changes `config/`.
    - `steward_guard.py` allows `Approve:` in team mode as rule 7 says; `reviewers.py` and `route.py` read the `Who: <login>` form for this one case, which changes ADR-0546 decision 4, by build (c)'s own ADR.
    - the steward's start reads the signed-in login (one `gh api user` call, kept for the run, rule 4), and the agent file (`.claude/agents/steward.md`) gains the team section of rules 2 to 9.
    This intake edits none of these files.
12. **The builds, in order.** Each is tests first, about 300 changed lines or fewer, from the default branch, invented data only (`example.com`), a `[[testing.map]]` entry for each new script, no workflow change, and each after SPEC-0059's build (a) (merged, #1326).
    - (a) The reviewer-only start, one steward per login, `Taking:` first come first served with its lapse, the one roll-over with `Continued in #<n>`, and the one daily list (rules 3 to 5 and 9), with its own ADR for session rule 17.
    - (b) The relay with only the signed-in reviewer's words and the `Who: <login>` record, with routing by area (rules 3, 6 and 8). `Depends-on` (a) and SPEC-0059's build (c) (brief #1322), which brings the relay.
    - (c) Approvals in team mode through the guard and the readers, and the `AGK_STEWARD_START=conductor` marker of a conductor's start with its denials (rules 4 and 7), with its own ADR. `Depends-on` (b) and SPEC-0062's build (d), so that the readers' `Who:` reading changes once (`Q-S0063-8`).
13. **Measured goals.** In the recorded tests (saved GitHub answers and a `gh` stub): with two stewards of two listed logins started against one recorded repository, every question gets exactly one answer and the memory issue rolls over exactly once; a steward started by a login not in the reviewers file posts nothing and its line holds no login; a relayed line always names, in its `Who:` line, the login that posted it; an `Approve:` by a login not in `spec_approvers`, or whose `Who:` names another login, is refused by the guard and not counted by the readers.

## Tests

Saved GitHub answers and a `gh` stub only, a stub in place of the runtime and the model, no network, invented data only (`example.com`, logins such as `reviewer-a` and `reviewer-b`), and each test carries the marker `REQ-070` with its criterion.

- Rules 3 and 4: a start whose stubbed `gh api user` login is not listed prints one line naming the file and the settings, holds no login, posts nothing and exits 3; a listed login runs; a team handle and a `conductor_accounts` login are not listed; REQ-070 AC1.
- Rule 4: two listed logins start at once and both run; a second start by the same login with a live `Started:` writes nothing and says so; REQ-070 AC2.
- Rule 5: two stewards post `Taking:` for one Q id; only the earliest by comment order answers, the other posts nothing more; a `Taking:` older than `owner_wait_minutes` with no answer frees the question; an existing `Answer:` stops every `Taking:`; every recorded question ends with exactly one answer; REQ-070 AC3.
- Rule 6: a relay carries only the chat turn of its own reviewer, quoted verbatim with its time, and ends `Who: <login>` equal to the poster; a turn that reports another person's words posts nothing; with `AGK_STEWARD_START=conductor` in the hook's environment and a login that is both a session account and a spec approver, the guard denies a first line `Maintainer answer:` and `Approve:` with a well-formed quote and `Who:`, and a start with any other value of the marker is refused naming the setting; REQ-070 AC4.
- Rule 7: the guard allows `Approve:` in team mode only with the quote and a `Who:` equal to the kept login in `spec_approvers`, denies it otherwise naming the setting and never the login, and still denies `Confirmed:`, `Verdict:`, `Final:`, `Correction:`, a merge, a tag, a force push and a workflow change; the readers count the comment only when its `Who:` names its author, a spec approver, with the quote and no agent app, and a comment with no `Who:` counts as today; REQ-070 AC5.
- Rule 8: in team mode each decision entry, relayed line and daily-list line names the login; the steward's own lines end `Who: AGK steward`; no team line carries `ProductOwner`; REQ-070 AC6.
- Rule 9: two stewards at 500 comments post `Taking: rollover`; exactly one new issue is opened, the old one carries `Continued in #<n>` and is closed, and the other steward follows the link; one `Daily:` per UTC day; REQ-070 AC7.
- Rules 2 and 10: with `review_mode = "solo"` the steward's outputs equal SPEC-0062's, in personal mode nothing of this spec runs, and no test writes a workflow, the ruleset or a required check; REQ-070 AC8.

## Open questions

Each is a point the brief leaves open, or a name it cites that the code holds otherwise; the reading after it is the most conservative one, and the rules above apply it. `Q-S0063-1` to `Q-S0063-8` are ruled as read by the maintainer's answer on #1343 (comment 6897023424), one file each under `docs/runs/decisions/`, and the rules above hold their readings. No question is open.

- Q-S0063-1: may a reviewer group be limited to areas? Reading: only where `config/reviewers.yaml` already names it: a path class whose approver group lists a person routes the questions that name its files; every other question goes to every listed reviewer (brief answer 5; rule 3).
- Q-S0063-2: the same login signed in on two machines: one steward or two? Reading: one; the second start of a login with a live `Started:` stands by, since the record cannot tell two machines of one login apart (rule 4).
- Q-S0063-3: may a steward that the conductor started relay or approve? Reading: no; no reviewer typed in its chat, so it answers from evidence and triages only, and the guard denies its `Approve:` and `Maintainer answer:` by the `AGK_STEWARD_START=conductor` marker that `launch.py` sets, since one login cannot tell the two starts apart (rule 4).
- Q-S0063-4: is the `Taking:` lapse its own setting? Reading: no; it reuses `[flow] owner_wait_minutes` (brief answer 5; rule 5).
- Q-S0063-5: two reviewers' answers that disagree: a conflict for the owner group? Reading: the first posted answer stands, and the other reviewer posts a `Correction:` themselves if they still disagree (brief answer 5; rule 5).
- Q-S0063-6: the brief lets the steward post "the session rule 29 text" in team mode; that rule's `Confirmed:` comment holds in solo mode only. Reading: in team mode the steward may post only the `Approve:` lines (a spec's, and session rule 29's `Approve: inventory` and `Approve: design`), and `Confirmed:` stays denied (rule 7).
- Q-S0063-7: several stewards would each post SPEC-0059 rule 13's daily list. Reading: one per UTC day per project, by the earliest `Taking: daily` (rule 9); the brief does not name it.
- Q-S0063-8: build (c) and SPEC-0062's build (d) both change the guard and the readers' reading of `Who:`. Reading: build (c) waits for that build, so the readers change once and each mode's clause is tested beside the other's (rule 12).
