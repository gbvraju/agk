# Changelog

The changes to the kit of this repository, newest first. In flow mode a build pull request adds one line under `## Unreleased`; a release pull request moves the lines under the new version (SPEC-0028). The history before 0.54.0 is in the git log and in `docs/runs/`.

## Unreleased

## 0.57.1 (2026-10-26)

- #262 governance: an edited description no longer cures a red full run that skipped a step it does not repeat (lint, tests, the secret scan): the edited run fails with "the last full run did not reach <steps>; push a commit or re-run it"; and every step after `PR body file` now runs unless the run is cancelled, so a failed description hides no later check (brief #261, ADR-0159)

## 0.57.0 (2026-10-26)

- #248 requirements: `retired` joins the requirement statuses and its `REQ-nnn` markers fail `check_requirements` (naming the requirement and the files); the weekly drift audit lists the test files that carry no marker as D8 (never blocking), and `traceability.py` ends with the retired requirements and the untagged test files (SPEC-0004 rule 24, SPEC-0010 rule 26, brief #244 build a)
- #249 session: `session.py plan [--json]` prints which builder sessions to start (waves by `Touches:` overlap, capacity with claims that have no pull request, `[flow] reviews_in_flight`, the measured merge-rate backpressure with `[flow] merge_hours`), the safe merge set, ready pull requests far behind (`[flow] stale_commits`) and stale briefs, which `plan` and `next` skip (SPEC-0034 rule 15, brief #247 build a)
- #250 launch: `/agk:launch` (a skill) runs `session.py plan`, asks the person to confirm and starts one session per planned slot through an adapter (one-time scheduled tasks in Claude's cloud, else one ready-to-paste prompt for each session), `launch.py prompts` prints the prompts or calls the team's own command once for each session; the rule that no session starts another gains the exception of a confirmed plan (SPEC-0034 rules 6 and 16, brief #247 build b)
- #253 plan: `session.py plan` and `/agk:launch` name the next free build of a brief with a `Builds:` line (not merged, no live take, no open pull request; a build waits for the one before it unless marked `independent:`), `launch.py` prompts `session.py claim --build <x>`, and a brief without builds is planned as before (SPEC-0034 rules 15 and 16, brief #251)
- #255 session: `watch --assign` also takes the newest `Assign:` for the session posted between its previous `Request:` and its current one and not yet taken, so the conductor may assign before the `Request:` and never posts a line twice (brief #252)
- #256 reviewers: the installed `config/reviewers.yaml` (init and adopt) lists `spec_approvers` with the placeholder next to `maintainers`, `reviewers.py --check` fails while it lists only the placeholder (naming the setting), the doctor's placeholder finding names both settings and step 4 of both guides says to replace both, so a person's first `Approve: SPEC-<n>` counts (SPEC-0032 rule 5, brief #254)
- #260 governance: the step `Secret scan` runs the pinned gitleaks 8.30.1 binary for linux x64, its SHA-256 verified in the workflow, over the commits of the change, instead of `gitleaks/gitleaks-action`, so the scan needs no licence key and no secret on an organisation repository (brief #258, ADR-0158)

## 0.56.0 (2026-10-26)

- #218 the shadow reviewer role file (SPEC-0035 rule 1) with a shadow mode of the conductor guard, and the Shadow and Marks shapes in the session rules (REQ-042 build a)
- #220 CI runs only where it can change a result: `proof` skips an edited description and a status-only final commit (`status_only.py`), `governance` runs only the body steps on an edited description, both cancel a superseded run, and the router starts a job only for a comment that can change a state (brief #216)
- #221 release: the workflow `agk-tag.yml` (this repository's own) checks every pushed tag `v*` (changelog section, no fragment left, one version everywhere, the hashes table), fails the job and opens one plain issue `The tag <tag> is not a release` (label `agk-release`) when the commit is not a release; tag only the merge commit of a release pull request (brief #212, SPEC-0028)
- #222 shadow_rate.py prints the conductor's catch rate from the Shadow and Marks comments of the merged pull requests (SPEC-0035 rules 3, 4 and 8, REQ-042 build b)
- #224 session: `session.py ids` also prints the next free session-rule number and takes `--exclude-pr N`, `intake.py check` takes `--ids FILE` for the numbers of a session and allows rows added to the decisions log, and rule 15 lists a session rule number moved to the next free one (SPEC-0034 rule 4, brief #176 build (e))
- #225 a person approves a spec with one short line, `Approve: SPEC-<n>`, with no commit id: the text approved is the spec as of the comment (the server-side time of the pull request's workflow runs gives the push), and the approval stops counting if a later commit changes the spec apart from its status line; an approving GitHub review counts at its own commit; the conductor's `Approval:` line shows the line to paste (REQ-039, build (g) of SPEC-0032, ADR-0132)
- #226 every pull request body that is not a draft needs one Summary line of 1 to 120 characters, the pull request template asks for it, and a project that upgrades must add the line to its pull request bodies (an open pull request needs only a description edit), and the conductor and the session rules say so (SPEC-0036 rules 1 and 6, REQ-043 build a)
- #227 router: `route.py` writes `pipeline.json` after every routing run (what waits for a person: ready, approve, counts), `kit/pipeline-schema.json` defines schema 1, and `agk-route.yml` uploads it as the artifact `agk-pipeline` for 7 days (SPEC-0036 rules 2 to 5 and 7, brief #213 build (b))
- #228 the weekly report gains the shadow review's catch rate and counts next to the conductor's verdicts, report schema 7: the item `week-totals` carries `shadow` (the counts of the week and in total with the rate, `not-running`, or `unknown`); `facts.json` carries the optional section `shadow` (REQ-042 build (c), SPEC-0035 rule 5)
- #230 the router judges the checks of a head by the latest run of each check name and the latest status of each context, so a cancelled or replaced run never makes a green pull request look red (SPEC-0032 rules 2 and 7, REQ-039, brief 229)
- #232 an edited pull request description cures a full governance run that failed only in the steps that read the body, without a new push (brief 216 build b)
- #233 router: `required_checks` in `agk.toml` (default `["proof", "governance"]`) names the checks the router judges for a pull request and the default branch; an unlisted failing check never labels a pull request red (SPEC-0032 rules 2 and 7, brief #231)
- #235 governance skips its lint, tests and installs on a status-only final commit whose base has not moved, by the same decision as proof (brief 216 build c)
- #239 the Summary check of a pull request body says whether the line is missing, repeated (how many), empty or too long (how many characters against the limit) (SPEC-0036 rule 1, brief 237)
- #240 kit: the root `pyproject.toml` the kit installs now installs as nothing (`[build-system]` and `[tool.setuptools] packages = []`), so a host that runs `pip install .` at the root no longer fails the deploy, and `agk upgrade` appends the two tables to an init install that lacks them (brief #236)
- #241 a verdict whose Final line the router cannot read is answered by one Correction needed reply, and the conductor guard refuses it before it is posted (SPEC-0021 rules 1 and 2, REQ-039, brief 238)
- #243 approvals: `agent_apps` in `agk.toml` (default `["claude"]`): a comment posted through a listed GitHub App never counts as a person's approval, and while the list is not empty a review does not count either; the router answers each once with `Correction needed:` (SPEC-0032 rule 5, brief #242)

- #188 the checks of a pull request compare it with the first parent of the merge ref GitHub checked out, set by one step of the governance and proof workflows, not with the event's older base sha, so a pull request is never failed for files another one merged (brief #180, ADR-0111)
- #192 a builder commits `checkpoint:` steps and opens a draft pull request, the body and final-clearance checks ignore a draft until it is ready (`--draft`), and the workflow runs on `ready_for_review` (SPEC-0033 rules 1 to 3, REQ-040)
- #193 router: `agk-route.yml` and `route.py` set one `agk:` label on every pull request from GitHub events (state, review, fix, approve, ready), and write nothing else (SPEC-0032 rules 1, 2 and 8, REQ-039)
- #195 `session.py resume --pr N` prints where a pull request stands, and `session.py next` offers and takes over a pull request that has waited on its builder for `stall_hours` before any new brief (SPEC-0033 rules 4 and 5, REQ-040)
- #197 session: `watch --pr` ends on a change of the router's `agk:` label, `queue --role` lists a role's pull requests so a restarted session resumes from GitHub, and the session rules say how `watch` is started so its end wakes the session (SPEC-0032 rules 3 and 4, REQ-039)
- #198 the facts carry the usage figure of a pull request from its `Report:` comments and the cost lines of the weekly report sum it, `not reported` when there is none (`report.json` schema 5), and the guide says what happens when the credits run out (SPEC-0033 rules 7 and 8, REQ-040)
- #199 check_brief.py also requires the `Advances:` and `Touches:` lines of a brief (and an optional `Priority:`), `--root DIR` fails a requirement that does not exist; check_pr_body.py requires `Closes #n` when a row sets `REQ-nnn done`, and `Brief: #n` when the governance workflow's new `Open briefs` step finds an `agk-brief` issue; doctor reports a missing `agk-brief` label (SPEC-0034 rules 2 and 9, REQ-041)
- #200 the router opens, updates and closes the one brief `The default branch is red` from the checks of the default branch, and `session.py next` hands out only that brief while it is open (SPEC-0032 rule 7, REQ-039)
- #201 session: `next` takes no brief at `max_builders` open builder pull requests (`full n/m`), skips a brief whose `Touches:` overlap open work, orders by `Priority:`, reserves numbers in its take and frees a take after `claim_hours` or `released:`; new `ids`, `demand` and `push-check` (SPEC-0034 rules 1, 3 to 6 and 7b, REQ-041)
- #202 a person approves every spec: `spec_approvers` in `config/reviewers.yaml`, `check_final_clearance.py` reads `Approve: <sha> SPEC-<n>` from comments and reviews, the conductor ends an intake verdict with an `Approval:` line, and the router sets `agk:approve` on it (SPEC-0032 rules 2, 5 and 6, REQ-039); without `spec_approvers` in `config/reviewers.yaml`, a covered fix list that sets a spec `Approved` now fails `final-clearance`, so add your user handles there
- #203 the session rules gain push-check before every push, the shared-mechanical files, mechanical conflicts only, the Question and Report shapes and the hand-off of a finished builder (per-build claims, claim, after, watch --assign, [flow] assign); the conductor reads and answers them; the guide shows the launcher contract with two examples (SPEC-0034 rules 6, 7c and 11, REQ-041)
- #205 governance: a pull request that sets a spec to Approved, by a `Final:` line or an ordinary commit, needs an `Approve: <sha> SPEC-<n>` line by a listed person for the text of the spec at its head (SPEC-0032 rule 5, REQ-039)
- #206 a cause is measured and a correction travels the same channel: `check_brief.py` fails a `Priority: 0` brief without a `Measured:` line, `session.py watch` ends on a `Correction:` comment of a listed author on the pull request or on its brief, and the session rules and the conductor role file say how (SPEC-0032 rules 9 and 10, REQ-039)

- #215 release: a valid release pull request needs no ADR for the protected files it changes, and the hashes table ends the row of a version at its release commit, so an upgrade from 0.54.0 installs the files added since (brief #212)
